## 它的功能

`to-questionnaire` 會將您無法自行定稿的決策轉化為一份**問卷** — 即一份 Markdown 文件，您可以將其交給掌握您所缺失內容的那個人，供他們進行非同步填寫，或者供您們二人在會議中一起處理。

它會盤問您關於**發送對象**，而不是主題本身。就主題而言對您進行訪談在此處毫無意義：不知道主題正是您撰寫給其他人的原因。因此它詢問您總是可以回答的兩件事 — 這要發給誰，以及您需要從他們那裡獲得什麼 — 並將文件中的每個問題都指向這兩者之間的**缺口**。

## 何時使用它

您可透過輸入 `/to-questionnaire` 來呼叫此功能 — [Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不會主動使用它。

當決策因存在於另一個人的腦海中的知識而被阻塞時，請使用它：客戶、領域專家、掌握商業規則的高管、您不與之坐在一起的團隊中的同事。您需要哪種 Skill 取決於答案實際在哪裡：

| 答案存在於… | 使用工具 |
| --- | --- |
| 您自己的腦海中，未經磨練 | [grill-me](https://aihero.dev/skills-grill-me) |
| 程式碼庫 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 其他人的腦海中 | `to-questionnaire` |
| 尚未在任何人的腦海中 — 問題需要可以反應的對象 | [prototype](https://aihero.dev/skills-prototype) |

常見的情況是停滯的 [盤問](https://www.aihero.dev/ai-coding-dictionary/grilling) 階段作業：呈現的一些內容不是由您來回答的。在同一個對話中執行 `/to-questionnaire` 以將這些問題移至離線，然後將答案帶回來並繼續。

## 發送對象，而非主題

訪談是兩次交流，然後停止。

- **這要發給誰？** 他們的角色、專業知識、他們與您的關係。這穩定了語氣以及文件必須攜帶的背景資訊量 — 外部客戶需要引導，團隊成員則不需要。
- **您需要收回什麼？** 您無法單獨解決的具體決策或事實。這成為衡量完成檔案的清單：您命名的每個項目都會收到一個針對它的問題。

在此之後的一切都是草擬。檔案落腳於當前目錄中的 `to-questionnaire-<slug>.md`。沒有設定、沒有工作區，也沒有需要設定的內容。

## 文件

它被構想為一份**探索問卷** — 您缺乏背景資訊，收件者掌握背景資訊 — 且該構想驅動了它的形狀：

- 一行說明適用於其上的決策的目的行，以及一個針對從未存在於您腦海中的收件者的簡短背景資訊區段。
- 問題按**最重要優先**排列，並分組在主題標題下，因為非同步意味著您可能只能獲得一次傳遞。
- 每個問題一個想法，絕不複合，下面有一個答案存根，且僅在問題可能被誤讀的地方放一行*為什麼這很重要*。
- 明確許可回答「我不知道」— 標記出的不確定性是有用的；讀起來像事實的自信猜測則無用。
- 結尾的包羅萬象問題：有什麼我們沒問但應該知道的事嗎？

它刻意不具備的兩件事。它不是**分歧的** — 問題是一個扁平的、分組的列表，而不是如果您回答了 A 就跳過 D 區段的樹結構。且它不是**多收件者的** — 一次執行為一個人產生一份文件。

## 常見問題

**它會讀取我的盤問階段作業並從中擷取問題嗎？**
不會作為其自身的步驟。Skill 沒有攝取階段：它詢問發送對象，然後草擬。使其在盤問階段作業後起作用的原因是您在**同一個對話**中執行它，因此 [階段作業](https://www.aihero.dev/ai-coding-dictionary/session) 已經在 [內容](https://www.aihero.dev/ai-coding-dictionary/context) 中，且草擬可以利用它。在新的階段作業中啟動它，它對盤問一無所知 — 當您回答「您需要收回什麼？」時，您將自己重新提供主題。

**缺失的答案並非全部與同一個人同在。它可以按收件者拆分它們嗎？**
不能。第一步詢問*收件者*（單數），且整個文件的語氣和背景資訊都是針對他們進行調整的。如果三個人掌握答案的三個部分，請執行三次，每人一次。在單一文件中按學科或角色引導路線是人們提出的要求；它不是已發布的功能。

**問題是否相互依賴 — 它是否會根據先前的答案跳過區段？**
不會。探索了依賴問題設計，但未發布。輸出是一個靜態文件：主題分組、最重要優先、每個問題都是即時的。對它的反對意見是公平的 — 一個 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 在真實答案之前規劃超過兩個或三個問題會規劃得很差，且分歧文件必須在每個答案之前規劃所有問題。

**如果收件者也不知道該怎麼辦？**
文件告訴他們直接說明。「我不知道」和部分答案被明確要求，且標記出的不確定性比猜測更有價值，因為一旦模糊答案和自信錯誤的答案回到您的內容中，它們看起來是一模一樣的。

**它會將其發送到任何地方嗎 — Slack、Issue 追蹤器、電子郵件？**
不會。它在當前目錄中寫入一個 Markdown 檔案，並告訴您路徑。交付是您的工作：將其貼入 [工單](https://www.aihero.dev/ai-coding-dictionary/ticket)、放在 Slack 討論串中、附在電子郵件中，或者在共享螢幕上開啟它並即時進行處理。人們已經手動連接了這四種方式。

**這不就是批次模式下的 `/grill-me` 嗎？**
不是，且這種區別值得保持。`grill-me` 已經以**輪數**提問 — 一次詢問整個前沿，然後從您的答案重新計算 — 因此「一次給我所有問題」的需求在那裡得到了滿足。`to-questionnaire` 關乎不同的軸線：不是問題如何交付，而是答案存在於誰的腦海中。自己更快地回答它們是 `grill-me`；從其他人那裏獲取它們是這個。

**難道我不能直接向 Agent 要求這個而不需要 Skill 嗎？**
可以，且在它存在之前很多人就是這麼做的 — `OPEN_QUESTIONS.md` 檔案、發送給客戶的試算表、每個未回答問題一個「需要更多資訊」的工單。Skill 為您換取了兩件事：訪談絕不會偏離到主題上，且文件以非技術收件者實際上可以填寫的形式產出。如果您已經有適用的房屋格式，誠實的答案是您不需要這個。

## 運作良好的指標

- 它詢問收件者以及您需要收回什麼，然後停止提問。關於主題本身的問題是 Skill 脫軌了。
- 您命名為「我需要收回什麼」的每個項目都可以追溯到檔案中的一個問題。
- 問題讀起來針對*收件者*所知道的事物，而不是逐字複製您自己的開放問題。
- 您可以將檔案交給不在對話中的人，他們會知道為什麼收到它以及何時回覆。
- 傳回的答案是新一輪盤問的可用輸入，而不是一套全新的問題。

## 適用位置

`to-questionnaire` 是一個隨時可使用的獨立工具。它位於您自己知識的邊界處，在該處下一步是另一個人而不是另一個 Skill — 最常見的是在流程中途，當規劃在非由您決定的事物上停滯時。

它的鄰居是 [grill-me](https://aihero.dev/skills-grill-me)，兩者在答案存在之處分道揚鑣：盤問挖掘您，問卷挖掘其他人。傳回的內容是原材料 — 將其餵入另一輪盤問，或者如果工作正朝著建構前進，則餵入 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。當您不確定哪個 Skill 適合該時刻時，[ask-matt](https://aihero.dev/skills-ask-matt) 會為您引導路線。
