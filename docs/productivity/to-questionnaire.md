## 功能說明

`to-questionnaire` 會將你無法自行解決的決策轉變為一份**問卷**：一個 Markdown 文件，由你提交給掌握你所缺資訊的那個人，供他們非同步填寫，或供你們兩人在會議中逐項討論。

它會針對**發送對象與需求**對你進行盤問，而絕不會針對主題本身。在這裡針對主題對你進行訪談是毫無意義的：不了解該主題正是你需要寫信向別人請教的原因。因此它只詢問你始終能回答的兩件事（這份問卷要發給誰，以及你需要從他們那裡獲得什麼反饋），並將文件中的每個問題精準對準兩者之間的**落差**。

## 何時使用它

你可以透過輸入 `/to-questionnaire` 來呼叫它；[Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不會主動使用它。

當一項決策因缺乏另一人腦中的知識而受阻時使用它：客戶、領域專家、掌握商業規則的高階主管、不在同一個團隊辦公的同事。你需要哪種技能取決於答案實際在何處：

| 答案位於… | 應使用的工具 |
| --- | --- |
| 你自己的腦海中，尚未梳理清晰 | [grill-me](https://aihero.dev/skills-grill-me) |
| 程式碼庫中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 其他人的腦海中 | `to-questionnaire` |
| 尚未存在於任何人的腦海中，該問題需要實物以供感受反應 | [prototype](https://aihero.dev/skills-prototype) |

常見的情境是 [盤問](https://www.aihero.dev/ai-coding-dictionary/grilling) 工作階段陷入停滯：浮現出的某些問題並非你能回答的。在同一個對話中執行 `/to-questionnaire` 以將這些問題轉移到離線處理，然後帶回答案並繼續進行。

## 關注發送需求，而非主題本身

訪談只有兩次互動問答，隨後便告結束。

- **要發送給誰？** 他們的角色、專業知識、與你的關係。這決定了語氣以及文件需要承載多少上下文：外部客戶需要背景引導，團隊成員則不需要。
- **你需要取回什麼？** 你無法獨自解決的具體決策或事實。這會成為衡量最終文件的檢查清單：你列出的每一項都會有一個針對它的問題。

在此之後的一切就是起草。檔案會儲存為目前目錄下的 `to-questionnaire-<slug>.md`。不需要設定、不需要工作區，也沒有任何需要配置的項目。

## 問卷文件結構

它被設定為**探索型問卷**（你缺乏上下文，收件人掌握上下文），這種架構決定了它的形式：

- 一行目的說明，指出取決於此的決策，以及一段簡短的上下文，供從未涉足你思考過程的收件人參考。
- 問題依**最重要者優先**排序並歸類在主題標題下，因為非同步意味著你可能只有一次提問機會。
- 每個問題僅包含單一概念，絕不複合提問，下方附有回答預留欄位，且僅在問題容易被誤讀處附上一行「為何這很重要」。
- 明確允許回答「我不知道」：標記出的不確定性是有用的；讀起來像事實的自信猜測則有害無益。
- 結尾的全面補充提問：是否有任何我們沒有問到、但我們應該知道的事？

刻意排除的兩點：它不是**分支型問卷**：問題是平面的分組清單，而不是回答了 A 就跳過 D 區段的樹狀結構。它也不是**多收件人型**：單次執行只會為單一人員產出一份文件。

## 常見問題

**它會讀取我的盤問工作階段並從中擷取問題嗎？**
不會作為獨立步驟執行。此技能沒有資料擷取階段：它詢問發送需求，然後起草。在盤問工作階段後它之所以能發揮作用，是因為你在**同一個對話**中執行它，因此該[工作階段](https://www.aihero.dev/ai-coding-dictionary/session)已經存在於[上下文](https://www.aihero.dev/ai-coding-dictionary/context)中，起草時可以直接借鑑。若在全新工作階段中啟動它，它對先前的盤問將一無所知；當你回答「你需要取回什麼？」時，你將必須自行重新提供該主題。

**缺失的答案並非全在同一個人身上。它可以按收件人拆分嗎？**
不能。第一步要求輸入*單一*收件人，整份文件的語氣與上下文都是為該對象量身打造的。如果三個人各自掌握答案的一部分，請執行三次，每個人一次。在單一文件中依專業領域或角色分派問題是許多人提出的需求，但並非目前發布的功能。

**問題之間是否具備依賴關係：它會根據先前的回答跳過某些區段嗎？**
不會。依賴型問題的設計曾被探討過但未發布。產出是一份靜態文件：主題分組、最重要者優先、每個問題皆為有效提問。反對該設計的理由非常中肯：在獲得真實回答之前，[模型](https://www.aihero.dev/ai-coding-dictionary/model)若預先規劃超過兩三個問題，其規劃品質會很差，而分支型文件必須在每個回答之前預先規劃好全部問題。

**如果收件人也不知道怎麼辦？**
文件會指示他們直接說明。「我不知道」和部分回答都是被明確鼓勵的，且標記出的不確定性比猜測更有價值，因為模糊的答案與自信但錯誤的答案一旦回到你的上下文中，看起來毫無二致。

**它會將其傳送到任何地方嗎（Slack、issue 追蹤器、電子郵件）？**
不會。它會在目前目錄下寫入一個 Markdown 檔案並告訴你路徑。發送由你負責：貼到[工單](https://www.aihero.dev/ai-coding-dictionary/ticket)中、丟入 Slack 對話串、附加到電子郵件，或在共享螢幕上開啟並即時逐項討論。人們手動實作過這四種方式。

**這難道不只是批次模式的 `/grill-me` 嗎？**
不是，這種區別值得牢記。`grill-me` 已經以**輪次**提問：一次提出整個邊界，然後根據你的回答重新計算，因此「一次給我所有問題」的需求在那裡已經得到滿足。`to-questionnaire` 涉及的是另一個維度：不是問題如何交付，而是答案存在於誰的腦海中。更快自行回答是 `grill-me`；從其他人那裡獲取答案則是此工具。

**難道我不能直接要求 Agent 提供這個功能，而不用透過技能嗎？**
可以，而且在它存在之前很多人就是這麼做的：`OPEN_QUESTIONS.md` 檔案、寄給客戶的試算表、每個未回答問題建立一張「需要更多資訊」工單。該技能為你換來兩件事：訪談絕不會偏離到主題細節上，而且產出的文件格式是非技術收件人真正能填寫的。如果你已經有行之有效的內部既定格式，坦白的回答是你不需要這個。

## 運作良好的跡象

- 它詢問收件人以及你需要取回的內容，然後停止提問。提出關於主題本身的問題代表該技能脫軌失控。
- 你指明為「我需要取回的內容」之每一項，都能追溯到檔案中的某個問題。
- 問題讀起來是針對*收件人*所知道的內容，而不是逐字抄錄你自己懸而未決的疑問。
- 你可以將檔案交給未參與對話的人，他們會明白為什麼會收到該檔案以及何時需要回覆。
- 收回的答案可作為新一輪盤問的可用輸入，而不是引出全新的一組問題。

## 適用定位

`to-questionnaire` 是一個隨時可用的獨立工具。它位於你自己知識的邊界上，在此處下一步行動是向另一個人請教而非使用另一個技能，最常出現在流程中途，當規劃因為非你能決定的事項而停滯不前時。

它的鄰近夥伴是 [grill-me](https://aihero.dev/skills-grill-me)，兩者的分工在於答案所在之處：盤問挖掘的是你，問卷挖掘的是別人。收回的內容是原始材料：將其輸入到另一輪盤問中，或者若工作準備進入建構階段，則輸入到 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。當你不確定當下適合哪種技能時，[ask-matt](https://aihero.dev/skills-ask-matt) 會為你引導。
