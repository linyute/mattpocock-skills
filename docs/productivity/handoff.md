## 它的功能

`handoff` 會將您當前所在的對話壓縮為一份**交接文件** — 即寫入作業系統的暫存目錄而不是工作區的單一 Markdown 檔案，全新的 [Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 可以讀取該檔案以接手工作。

它所換取的是**可攜性**，而不是壓縮。這使得該 Skill 比聽起來更狹窄。只有當工作必須*移動*時您才需要一個檔案 — 移動到全新的 [框架](https://www.aihero.dev/ai-coding-dictionary/harness)、全新的目錄、同事，或者您想分叉出的旁支任務。如果沒有任何東西在移動，您不需要交接：留在 [階段作業](https://www.aihero.dev/ai-coding-dictionary/session) 中、`/clear`、[子 Agent](https://www.aihero.dev/ai-coding-dictionary/subagent) 和 `/compact` 涵蓋了普通的階段結束情況，且 `/compact` 比此 Skill 更常涵蓋該情況。

## 何時使用它

您可透過輸入 `/handoff` 來呼叫此功能 — Agent 不會主動使用它。傳遞一條關於下一個階段作業目的的附註，文件就會為其編撰。

四種情況是完整的觸發條件：

| 情況 | 為何需要檔案 |
| --- | --- |
| 切換框架 — Claude → Codex | 新框架無法看到舊的 [內容](https://www.aihero.dev/ai-coding-dictionary/context) |
| 移動到不同的目錄或儲存庫 | 原型目錄是常見的情況 |
| 將工作傳送給同事 | 他們需要可以閱讀的內容 |
| 分叉階段中途發現的旁支任務 | 您繼續工作；第二個 Agent 接手分叉 |

對於任何其他情況 — 相同的框架、相同的目錄、您已完成 [盤問](https://www.aihero.dev/ai-coding-dictionary/grilling) 並轉向實作 — `/compact` 是正確的選擇。[ask-matt](https://aihero.dev/skills-ask-matt) 承載了階段邊界處所有五個選項的有序樹結構。

## 分叉是人們忽略的用法

該 Skill 的描述讀起來像階段作業的恢復：撰寫摘要、在此結束、在彼處恢復。按這種方式閱讀，它看起來像是一個更糟的 `/compact`，因此被匆匆略過。分叉情況才是值得了解的情況。您**留在您的階段作業中**，並將累積內容的副本交給平行工作的第二個 Agent。

這正是繞道使用 [prototype](https://aihero.dev/skills-prototype) 的用途。您沉浸在設計對話中，遇到了一個只有執行程式碼才能定稿的問題，且您不想將建構的討論串花在查明答案上。交接給原型階段作業，取得答案，將答案交接回來，並從原始討論串中引用它。兩次跨越，一次即時對話，無需重新解釋任何內容。

階段邊界處五個選項中的三個保留了不同的內容：`/compact` 保留您的意圖，`/clear` 不保留任何內容，`/handoff` 保留工作移動的能力。

## 什麼隨之移動，什麼不隨之移動

該文件攜帶即時討論串 — 正在進行什麼、原因以及接下來是什麼 — 加上一個命名下一個 Agent 應該使用什麼的**建議技能**區段。Secrets 在寫入前會進行遮蔽。

它刻意不攜帶任何已經寫下的內容。規格、計畫、ADR、Issue、Commit 和 Diff 都透過路徑或 URL 引用，絕不複製。這保持了檔案微小，並將定稿的細節保留在一個地方，而不是兩個隨時間偏離的地方。

## 常見問題

**Handoff 還是 compact？**
除非有東西在移動，否則選擇 `/compact`。留在同一個任務上是 compact，而不是 handoff — 在大多數日子裡，階段邊界樹結構落腳於相同的框架、相同的目錄且您需要保持在迴圈中。`/handoff` 的優勢不在於它的總結能力更好；而在於其結果是一個您可以攜帶到 `/compact` 無法到達之處的檔案。

**那麼 compact、clear 和 handoff 之間的實際區別是什麼？**
保留三種不同的內容。`/compact` 壓縮此內容並讓您在全新的視窗中繼續進行 — 意圖存活下來。`/clear` 清空視窗並從零開始 — 當您身後的一切都是可拋棄的時這是正確的，且如果不是可拋棄的則是單向的。`/handoff` 撰寫一個可攜式的檔案 — 工作在移動到其他地方後存活下來。請注意，這三者都將 **[原始來源](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（對話發生的過程）轉變為 **[二次來源](https://www.aihero.dev/ai-coding-dictionary/secondary-source)**（對話的摘要）。繼續進行是唯一不改變來源性質的操作，這就是為什麼它是第一個排除的操作。

**我的 handoff 檔案去哪裡了？**
暫存目錄，這是該 Skill 被回報最多的摩擦：路徑很長，每個作業系統都不同，且在 Windows 上 Agent 有時會嘗試幾次才能找到正確的路徑。在您繼續之前要求傳回路徑並保留它。暫存是刻意的：handoff 是一個過渡文件，而不是您維護的產物。它也不是一個持久的文件 — 請參閱下一個問題。

**我的 handoff 在階段作業之間消失了。**
某些環境會在階段作業之間清空暫存（Codex 是回報的情況），且 `/private/tmp` 會在重啟時消失。如果下一個階段作業不會在一小時內開始，或者是在不同的框架下開始，請在寫入後立即自己將檔案複製到持久的地方。這也適用於文件*指向*的任何內容：引用暫存中其他檔案的派發是下一個 Agent 無法跟隨的派發。

**我該如何實際將其交給下一個 Agent？**
開啟全新的階段作業並指向該路徑：讀取此檔案，然後繼續。請指向檔案而不是將摘要貼入 Shell 命令中 — 包含反引號或 `$(...)` 的摘要在插值到 `claude "<summary>"` 時會被損壞，且通常的失敗是默默截斷而不是報錯，因此新 Agent 會帶著默默不完整的簡報開始。

**這與 `/branch`、`--fork-session` 或內建的 `/handoff` 相同嗎？**
類似，但不完全相同，且 `/branch` 這裡不是已發布的 Skill — `/handoff` 是規範名稱。分叉繼承了內容的精確副本；此 Skill 在檔案中產生針對指定下一個任務的*定向*壓縮。在分叉可行的地方 — 相同的機器、相同的框架、相同的目錄 — 分叉工作量更少。一旦目的地是分叉無法到達的地方，檔案就會勝出。

**什麼時候內容應該屬於 `CLAUDE.md`？**
詢問它下個月是否仍然為真。`CLAUDE.md` 是關於專案的常設背景資訊，無論是否有關都會載入到每個階段作業中。Handoff 是關於正在進行的一項工作，並在該工作落地後失效。不斷重新解釋的事實是 `CLAUDE.md` 的問題；半完成的任務是 handoff。

**它捕捉了什麼，但沒有捕捉為什麼。**
一個公平且重複的批評。有兩件事有所幫助。傳遞引數 — 告訴它下一個階段作業的目的 — 這樣適用於*該目的*的推理就會被保留而不是被抹平。並且注意階段作業從未實際驗證過的自信主張：「X 未建構」、「Y 已完成」。下一個 Agent 將該文件視為契約且不會重新檢查，因此寫成事實的信念會成為後續一切的錯誤前提。在交接之前閱讀該文件，並降級您僅是假設的任何內容。

**為什麼它是一個 Skill 而不是斜線命令？**
兩者都可以；它們適合不同的情況。作為一個 Skill，它透過與這裡的其他內容相同的安裝路徑發布與更新，這使得它可以共享 — Agent 不會自己觸發它的約束是由其 Frontmatter 設定的，而不是由機制設定的。

## 運作良好的指標

- 文件是對話的一小部分，且規格、Issue 和 Diff 作為路徑與 URL 出現在其中，而不是作為複製的文字。
- 您可以在不開啟原始階段作業的情況下冷靜地閱讀它，並知道接下來要做什麼。
- 全新的 Agent 開始工作，而不是要求您重新解釋設定。
- 在分叉情況下，當您回來時，您的原始階段作業仍然原封不動地擺在那裡。
- 建議技能區段命名了您自己會使用的 Skill。
- 其中沒有任何內容是密鑰、權杖或密碼。

## 適用位置

`handoff` 是一個**隨時可使用的獨立工具**，位於階段作業之間的縫隙中，而不是在建構鏈內部 — 但它很狹窄，且誠實的地圖是您在階段邊界處使用它的頻率將低於其他四個選項。它最近的鄰居是 [prototype](https://aihero.dev/skills-prototype)，因為原型生活在其自己的目錄中，且往返的過程精確地是此 Skill 適用於的跨越。當您處於邊界且不確定是否繼續、清除、交接、委派或壓縮時，[ask-matt](https://aihero.dev/skills-ask-matt) 承載了對這五者進行排序的樹結構 — 並為您引導整個集合中的其餘內容。
