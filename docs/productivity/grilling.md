## 功能說明

`grilling` 是一個訪談循環，在任何人對計畫、決策或想法採取行動之前對其進行壓力測試。它將主題描繪成**設計樹**：每個決策都會分支出依附於它的後續決策，並逐一分支對你進行訪談，直到沒有留下任何默默預設的假設。

它不會一次只問一個問題，也不會一次問完所有問題。每個**輪次**都會詢問整個**邊界**：每個先決條件皆已確定的決策，別無其他。如果一個問題依賴於另一個問題，這兩個問題絕不會出現在同一個輪次中；取決於尚未定案之答案的問題會留到後續輪次。你的回答敲定了決策，邊界向外推進，下一輪則詢問因此而解鎖的問題。十三個問題通常大約在三個輪次內完成，而不是分成十三輪。

## 何時使用它

輸入 `/grilling`，或者當任務適合時，[Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 會自行呼叫它。它是盤問家族中唯一由模型呼叫的[技能](https://www.aihero.dev/ai-coding-dictionary/skill)，這也是為什麼你很少需要手動輸入它：通常是你*確實*輸入的某個技能正在為你執行它。

直接輸入 `/grilling` 只會為你提供純粹的訪談，別無其他。如果你需要更多功能：

| 你目前的情況 | 應使用的工具 |
| --- | --- |
| 你不在工作目錄中操作 | [grill-me](https://aihero.dev/skills-grill-me)：同一個[工作階段](https://www.aihero.dev/ai-coding-dictionary/session)，採用 Agent 絕不會自行觸發的名稱 |
| 你在工作目錄中操作 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)：同一個工作階段，且會在進行過程中寫入 `GLOSSARY.md` 與 ADR |
| 工作量過於龐大無法在單一工作階段中容納 | [wayfinder](https://aihero.dev/skills-wayfinder)：它繪製地圖並在決策工單內執行盤問 |
| 無法透過交談解決的問題：外觀或感覺應該如何 | [prototype](https://aihero.dev/skills-prototype)：建構拋棄式版本，然後再回來 |
| 你自己的技能需要訪談機制 | 從該技能呼叫 `/grilling`，而不是另外寫一個訪談機制 |

## 輪次、邊界與決策者

三個概念支撐了整個技能。

**設計樹**是主題的模型：也就是掛載著後續決策的決策群體。**邊界**是先決條件已全數敲定的決策集合：也就是目前真正能被合乎邏輯地提出的問題。**輪次**則是單一邊界，完整提出並獲得完整回答。

在一個輪次中，每個問題都以固定格式呈現：在 `❓` 後方標記編號與標題，接著是內文，然後在 `➡️` 行上單獨給出 Agent 的建議答案。這使得一整個輪次可以透過編號來回答（「1 好、2 第二個選項、3 不好，原因如下」），而不需要引用原始問題。這個格式有一個已知的不便之處：建議有時會反駁該問題本身的措辭，因此同意建議意味著對問題回答「否」。當這種情況發生時，針對建議做出回答並說明這點。

設計的另一半是事實與決策的劃分。事實是技能本身的工作：當邊界問題需要[環境](https://www.aihero.dev/ai-coding-dictionary/environment)可以解決的資訊時，它會分派 [Sub-Agent](https://www.aihero.dev/ai-coding-dictionary/subagent) 前去調查，而不是向你詢問。它不會為此完全阻塞；只有執行中探查的下游問題需要等待。決策是你的責任，它必須等待你的決定。執行 `grilling` 的 Agent 若自行回答決策問題，那就是破壞了該技能，而非彈性詮釋。當邊界變空時工作階段結束，且在確認你們達成共識之前，它不會對你們商定的內容採取行動。

坦白說其限制在於：邊界取決於 Agent 的判斷，而非由演算法精確計算出來的圖形。它可能會在同一輪提出兩個問題，事後才發現其中一個答案本應改變另一個問題。對此除了提醒它之外沒有其他防護措施，而提醒它會在下一輪重新開啟受影響的分支。

## 常見問題

**我可以改回一次只問一個問題嗎？**
可以，而且很大一部分使用者正是這樣做的。將此內容新增至你的全域 `CLAUDE.md`：

```
When grilling, ask one question at a time.
```

預設以輪次為單位的方式確實存在爭議。閱讀較慢、使用第二語言工作，或將循序格式視為專注鷹架的實踐者皆表示，一次一個問題的節奏對他們更好，因此退出選項是正式支援的，而不僅僅是勉強包容。

**`/batch-grill-me` 去哪裡了？**
併入了這個技能。基於輪次的提問方式曾短暫作為獨立技能推出，隨後移入 `grilling` 本身，因此基於該原語建構的所有內容（`grill-me`、`grill-with-docs`、`triage`、`wayfinder`）都同時獲得了該功能。沒有 `batch-grill-me` 可以安裝，也沒有單獨的循序技能；上面那行 `CLAUDE.md` 就是切換回一次一問的方式。

**一次提出一整輪問題，必然會遺漏我較早答案本應引出的問題吧？**
這是對輪次設計最常見的反對意見，而邊界正是對此的解答：一個輪次只包含彼此互不依賴的問題，因此同一輪中的任何回答都不會使該輪的另一個問題失效。回答依然會重新塑造下游的所有內容：下一輪是重新計算的，而不是預先寫好的。你所失去的少於「一次提出所有問題」所暗示的程度，但也並非完全沒有代價：請參見上述邊界的限制。

**它問完了問題並開始進行建構。**
確認關卡的存在正是為了解決這個問題：當邊界清空時技能並未結束，只有當你確認已達成共識時技能才算完成。較弱和較快的[模型](https://www.aihero.dev/ai-coding-dictionary/model)仍然會打破這一點；這在低推論深度或非前沿模型上最常被回報，這些模型會將「訪談直到達成共識」壓縮成兩三個問題和大綱。如果你的模型這樣做，可靠的解決方法是在你自己的 `AGENTS.md` 或 `CLAUDE.md` 中加入一行，告訴 Agent 未經許可不要進行實作。

**它自行回答了自己的問題而不是詢問我。**
這是執行過程中的錯誤，不是預期的行為，這也是為什麼在此技能的文本中將事實與決策分開的原因。當另一個技能在「解決此工單」的架構下執行 `grilling` 時最常出現這種情況，因為周圍的任務被解讀為可以繼續推進的許可。同樣的限制也是為什麼沒有非同步模式的原因：有人曾要求一個能讀取 GitHub issue 並發布一份合併決策備忘錄的變體，但那是不同的技能，因為沒有人回答的盤問工作階段產出的是 Agent 的意見，而不是你的意見。

**我可以限制問題數量的上限嗎？**
不能，且限制上限刻意被排除在範疇之外。有些計畫需要三個問題，有些則需要五十個；固定的上限要麼會截斷困難的情境，要麼在簡單的情境下顯得武斷。使用自然語言引導是預期的控制方式：告訴它收尾，或停止並接受目前的計畫現況。如果工作階段執行時間非常長，原因通常是範圍過大；拆解工作並對各個部分進行盤問。

**我單獨安裝了 `grill-me`，但沒有任何反應。**
`grill-me` 是一個單行技能，其整個主體就是「執行 `/grilling` 工作階段」，因此它也需要安裝這個技能。`grill-with-docs` 也是如此，它還額外需要 [domain-modeling](https://aihero.dev/skills-domain-modeling)。安裝整套工具可以避免這個問題；選擇性安裝意味著你也必須同時安裝這些原語。

**`grill-with-docs` 執行了，但它從未載入 `grilling`。**
這是跨[測試載具](https://www.aihero.dev/ai-coding-dictionary/harness)與模型皆有回報且尚未修復的真實缺陷：提及另一個技能的技能並不能可靠地觸發該技能的載入，而 `grill-with-docs` 提及了兩個。其跡象是工作階段一次提出所有問題且沒有附帶任何建議：這代表模型是在臨時拼湊訪談，而不是執行這個訪談。直接詢問 Agent 是否已載入 `grilling` 與 `domain-modeling` 通常可以恢復正常。

## 運作良好的跡象

- 輪次以編號清單呈現，每個問題的建議都位於單獨的 `➡️` 行上，且你可以按編號回答整個輪次。
- 同一輪次中沒有任何問題需要先回答該輪中的另一個問題。
- 後續輪次提出的問題是第一輪不可能提出的內容。
- 它會主動查證事實（讀取檔案、分派 Sub-Agent），而不是向你詢問它本來就能查明的事情。
- 背景執行的研究不會使輪次停滯；只有依賴於該研究的問題才需要等待。
- 它在最後停下來並要求你確認達成共識，而不是直接開始工作。
- 問題數量維持在高水準，而輪次數量保持在低水平。

## 適用定位

`grilling` 是一個**原語**，而不是排定的步驟：它是訪談技術的單一事實來源，保留在同一個地方，讓每個需要訪談的技能都能直接取用，而不是重新發明一套。[grill-me](https://aihero.dev/skills-grill-me) 與 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 是其兩個由使用者呼叫的入口，而 `grill-with-docs` 是主建構鏈開始的地方，位於 [to-spec](https://aihero.dev/skills-to-spec) 之前。[wayfinder](https://aihero.dev/skills-wayfinder) 執行它以解決決策工單，[triage](https://aihero.dev/skills-triage) 執行它以將模糊的報告盤問成可操作的報告，而 [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 則在選出要深入探討的候選項後走訪該樹狀結構。當你不確定哪一個進入點合適時，[ask-matt](https://aihero.dev/skills-ask-matt) 會為你引導。
