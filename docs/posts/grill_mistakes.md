# 人們使用我的 /grill-* 技能時常犯的 9 個錯誤

我的 Grill Me 與 Grill with Docs 技能推出已經有一段時間了，世界各地的人都把它們當作代理程式（agent）中 plan mode 的替代方案。不過，我偶爾會聽到有人說「Codex 一口氣問了我 200 個問題」，就像這個 issue 所描述的，聽到時我總有點替他們捏把冷汗。

這些技能的設計理念，是不斷地追問你，持續向你提問，直到雙方對某件事情達成共識。這代表整個過程仰賴回答問題的人的功力。也就是說，使用 Grill Me 技能的你，必須擅長規劃：你要懂得掌握範圍（scope），也要能判斷哪些問題需要多高的擬真度（fidelity）才能回答。

這正是我製作這支影片的原因。我希望讓你真正精通這些技能的用法。這些技能本身其實並不長，它們的設計目的是輔助你這位工程師，而不是取代你。

我整理了一份清單，列出人們使用這些技能時常犯的九個錯誤。但在那之前，我們先透過幾個視角來理解這些失敗模式，因為如果沒有用正確的方式理解它們，就無法加以改善。

## 視角一：問題的擬真度

進入烤問（grilling）工作階段時，我們真正想做的是回答問題。對於即將要建構的東西，我們多半有些尚未釐清的地方。而這些問題在回答時所需的擬真度各不相同，這個說法借用自 Ryan Singer 的經典著作《Shape Up》。

- **高擬真度問題**：需要非常貼近、非常細緻、高擬真度的畫面才能理解的問題。例如：這個 UI 元件用起來的感覺如何？應該把所有表單欄位拆成多個頁面，還是做成一份填寫到底的超大表單？要真正理解這類問題，唯一的辦法就是高擬真度的原型，或是乾脆把整個東西做出來。
- **低擬真度問題**：不需要高擬真度的原型或畫面就能回答的問題。例如：這個路由應該放在哪個 URL 上？這類問題只需要直接作答即可。

### 錯誤一：在烤問工作階段中試圖回答高擬真度問題

我在 Grill Me 技能上看到的第一個失敗模式，就是試圖在烤問工作階段中回答高擬真度問題。換句話說，有些問題是「可烤問的」（grillable），也就是能在烤問工作階段中回答；有些則是「不可烤問的」（ungrillable），無法在烤問工作階段中回答。

那麼，遇到不可烤問的問題時該怎麼辦？當問題關乎「手感」，必須實際看到更高擬真度的東西才能回答時，我通常會進行**原型交接（prototyping handoff）**：

1. 在第一個工作階段中進行烤問，直到遇到一個不可烤問的問題，也就是必須以更高擬真度來檢視的問題。
2. 使用 handoff 技能（連結附在下方），交接到一個原型製作工作階段，專心針對該問題做原型，以更高的擬真度檢視它。
3. 將從中學到的結論再交接回原本的烤問工作階段，繼續處理那些可烤問的問題。

我的許多工作階段都是這樣進行的：先用 Grill with Docs 烤問，交接到原型工作階段，再交接回原本的 Grill with Docs 工作階段。我就是這樣回答那些高擬真度問題的。

## 視角二：範圍

接下來要理解的概念是範圍，也就是你所烤問的東西有多大。如果範圍太大，會遇到兩個問題。

### 錯誤二：烤問的範圍太大

**第一，高擬真度問題會藏在其中。** 範圍過大時，裡面很可能暗藏一些高擬真度問題，不真正看到完整成品就很難回答。在已知可行、且做得扎實的基礎上繼續往下建構，永遠比無止境地規劃遙遠的未來容易。許多人替自己排好好幾天的工作任務，結果成果很糟，原因就在於他們沒有建立在一個彼此認同的基礎上。換句話說，他們試圖把計畫推得太遠，卻沒有踩在穩固的地基上。

**第二，這也有實務上的限制。** 烤問的東西太大，你就會撞上模型的「笨蛋區」（dumb zone）。你或許一開始的上下文視窗（context window）幾乎是空的，但隨著問答不斷進行，問題連一半都還沒回答完，就已經進入笨蛋區了。這時你可能得交接、壓縮（compact）或做些麻煩的處理。如果一開始就選擇較小的範圍，這一切都能避免，你也就能在「聰明區」（smart zone）內舒適地烤問。

對於不知道這個概念的人說明一下：我估計大多數最先進的模型，其笨蛋區大約從 120k tokens 開始。因此你必須密切留意上下文視窗，確保不要超過這個界線，否則模型的注意力關係會變得吃緊，開始做出比較愚蠢的決策。

這意味著，如果你一開始面對的是像這樣很大的範圍，很可能已經超出代理程式能處理的程度，這時比較好的做法是**事先請代理程式把這個範圍拆解成較小的範圍**，再逐一針對各個小範圍進行烤問並回答所有問題。

## 視角三：被動或主動

接下來要檢視的視角是：在與代理程式互動，尤其是在烤問工作階段中，你是被動的還是主動的。

### 錯誤三：太被動

我看到許多冗長的烤問工作階段，擔心當事人對代理程式太過被動。我在烤問時總是相當主動，總是試圖主導對話。請記住，這是一場**對話**，不是一場面試。代理程式雖然負責提問，但釐清方向、掌握範圍、讓事情不偏離軌道，仍是你的責任。

如果你太被動，代理程式就很容易在訪談中做出蠢事：問你 540 個問題、讓範圍爆炸、問一些擬真度太低的細枝末節。你必須主動出手掌控。

### 錯誤四：太主動

然而，也有可能過於主動：明明需要實際做出東西才能看到實際運作的樣子，卻還在針對擬真度太低的內容不停烤問。

所以這裡藏著兩種失敗模式：太被動（過度坐享其成），以及太固執（太晚開始動手寫程式碼）。使用這些技能時，請思考自己落在這條軸線上的哪個位置：是太被動，還是其實有點太強勢、太積極。

## 視角四：烤問的產出價值

### 錯誤五：不重視烤問過程中所建立的成果

另一個失敗模式是，人們沒有重視自己在烤問工作階段中所建立的東西。你在回答這些問題的過程中，上下文視窗裡累積了許多非常有價值的內容：你給出的答案、你做出的設計決策。這一小塊藍色的上下文視窗價值非凡。

通常你的目標是：如果剩餘的預算足夠，就能立刻開始實作。也就是先規劃一小段時間，然後說「好，直接實作吧」。不需要交接，上下文視窗還有足夠的空間，可以根據我已經做出的設計決策直接實作。

不過，如果你已經到了必須結束這個工作階段、需要交接的地步，那大概就是該寫 PRD 的時候了。我的 to-prd 技能是建立交接文件的好方法，這類文件更偏向工程用途，無論是跨多個工作階段還是單一工作階段都很實用。

但我看過一個瘋狂的錯誤：有人先清除上下文，建立一個全新的上下文視窗，然後才在裡面執行 to-prd。這對我來說簡直不可思議，你在做什麼？你好不容易建立了這個了不起的工作階段，裡面有大約 100,000 tokens 的優質設計決策，卻要把它丟掉？

烤問工作階段中的每一項決策都非常寶貴，應該被記錄在某處，轉化為程式碼，或寫進之後可以參考的交接文件。千萬不要把烤問工作階段中的內容隨手丟棄。我想這大概是技能問題，人們需要對上下文管理有更多的認識，例如在清除、壓縮、交接之間該如何決策。這個錯誤真的讓我很震驚。

請務必保留你在烤問工作階段中做出的決策，並為它們建立某種交接成品。

## 視角五：模型的選擇

### 錯誤六：用太弱的模型來烤問

另一個常見的錯誤，是使用太弱的模型來烤問。判斷哪些問題是低擬真度、哪些是高擬真度，以及找出該問哪些正確的問題來促使你做出更強的設計，這些都需要一個好模型。

想想模型的知識來自哪裡，大致有兩個來源：

- **上下文知識（contextual knowledge）**：你明確放進它上下文中的內容，可能來自讀取檔案、使用者的提示詞，或是呼叫工具進行研究後帶回的工具結果。
- **參數知識（parametric knowledge）**：模型在訓練過程中學到、理解的內容。這一類可靠度低得多，但這裡恰恰要仰賴它。

我們仰賴的是模型對系統與應用程式的先天理解，讓它提出我們還沒想到的好點子。因為如果我們已經想到了，早就把它們當作上下文知識傳進去了。我們是靠它的先天理解，來提供出人意料的建議與奇特的想法。

既然要仰賴參數知識，你就需要參數量大的模型，而這通常是大型前沿模型的特點。不僅如此，它們的訓練也是頂級的，整體能力就是比較小的模型更強。由於烤問如此依賴參數知識，使用太弱的模型是我最常看到的失敗模式之一。

大多數人不知道的是，**實作階段其實可以使用比較弱的模型**，因為你傳遞的資訊大多是上下文知識。到了實作階段，你通常已經有一份詳細的實作計畫，也會傳入程式碼庫中的相關檔案讓它參考模仿，其中很少需要參數知識，主要都是上下文知識。

## 視角六：平行處理

### 錯誤七：沒有平行烤問多個工作階段

最後這個非常簡單，但很多人都沒有這樣做：你應該**同時平行烤問多個工作階段**。

我通常是這樣運作的：我在其中一個工作階段烤問，輸入一些東西（通常是用語音口述）回答它的問題，然後切換到另一個工作階段，那邊到這時通常已經處理完了，我回答它的問題，再回到原本的工作階段，就這樣來回切換。

有人說這是在做上下文切換，但其實就像同時管理兩個不同的 Slack 討論串，真的沒那麼難。當然，你需要做大量高層次的決策，但這是我發現唯一能提高產出量、在更短時間內完成更多規劃的方法。

我通常最多同時進行兩個工作階段；除非其中一個正在執行耗時很長的任務（例如做研究），那麼在精神飽滿、想挑戰一下的時候，我會試試三個，但大多數時候兩個就是我的極限。不論如何，我的產出量因此翻倍，感覺相當不錯。如果你有足夠的心智餘裕，絕對應該這麼做。

我也認為烤問是一項可以越練越好的能力，隨著你越來越熟練，就能增加更多產出量與平行度。

## 總結

讓我們整理一下學到的內容：

- 烤問的核心是**問題**。問題分為低擬真度與高擬真度兩種。低擬真度問題只要一問一答就能解決，也就是可烤問的問題；高擬真度問題則是不可烤問的。
- 遇到不可烤問的問題時，你可能需要進入原型模式：透過 handoff 交接到原型製作工作階段，專門釐清該問題（或是該問題連同其他一批問題），然後再回到原本的烤問工作階段繼續。
- 找出正確的**工作範圍**至關重要。如果一次烤問太多，你會耗盡上下文視窗、消耗自己的體力，最後卻沒有任何成果。
- 如果在烤問工作階段中**太被動**，你就只會坐在那裡，任由電腦不斷用越來越多的問題轟炸你；但如果**太主動**，你可能會針對低擬真度的問題無止境地烤問，而你真正需要的其實是動手寫程式碼。
- 你需要一個**聰明的模型**，才能仰賴它的參數資訊，給你更好的建議與更好的問題。
- 最後，我建議**同時烤問兩個工作階段**。一旦你掌握了這些基本功，也清楚每個工作階段在做什麼，就能順暢地在它們之間切換。如果你的大腦比我更有彈性，甚至可以增加到四個。
