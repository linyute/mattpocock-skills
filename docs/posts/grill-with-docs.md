# 我不再用 /grill-me 來寫程式了，我改用這個

幾個月前，我寫下了幾句話，大約四句，結果成了我寫過影響力最大的四句話。我把這四句話打包成 Grill Me 技能（skill），讓 LLM 不斷地訪問你，直到雙方達成共識：它會沿著設計樹的每一條分支往下走，逐一解決各項決策之間的相依關係。

我知道這個技能很有影響力，因為我每天都會收到大約五則訊息，說他們試過之後非常喜愛：

- 「這個技能簡直是改變遊戲規則的神器。」
- 「你最喜歡哪些技能？Grill Me 很棒。我正在做一個專案……」
- 「Grill Me 技能會追問我含糊不清的地方，太棒了。」
- 「Grill Me 技能超強。」
- 「一開始我覺得問題太多會拖慢進度，但用了一陣子後，我覺得它可能反而省時間。你只要把所有脈絡都收集齊全，之後就能一次到位。」
- 「你試過叫做 Grill Me 的那個技能了嗎？」

聽完這些讚美，你大概會想：那你應該繼續用這個技能就好了吧？聽起來相當不錯。但事實上，我已經打造出一個更好的版本。我從來不滿足於躺在功勞簿上，總覺得流程中的每個環節都還有改進空間。現在，Grill Me 已經被一個新技能取代了。

## Grill Me 哪裡不夠好

讓我開啟一個工作階段，來說明 Grill Me 的問題出在哪裡。我先貼上事先準備好的提示詞，內容是一個新功能的點子（我是用語音輸入的，所以細節就不贅述了）。

簡單來說，我想在資料庫中新增一個實體（entity），也就是我的應用程式要處理的新實體。目前這個應用程式處理的是課程（course）、課堂（lesson）、影片（video）、章節（section）等等。我想加入「提案」（pitch）這個概念。

這源自 Mr. Beast 風格的一條準則：在真正決定影片內容之前，應該先思考影片的「包裝」。在這個設定裡，提案指的就是影片的包裝，包括標題、描述，以及我要如何向觀眾呈現這支影片。我會建立一大批提案，從中挑出最好的，再把它們製作成影片。

注意到了嗎？我在與代理程式（agent）溝通時，真正關注的是語言，也就是「提案」到底是什麼。我得向你說明這一點，你才跟得上；同樣地，代理程式也需要從我這裡取得這些資訊。

此外，提示詞裡還有一些代理程式還不知道的行話。例如我提到「獨立影片」（standalone video）。獨立影片是什麼意思？噢，當然，就是沒有連結到任何課堂或課程的影片。我當然知道，這是使用這整套設定時的專門術語，但代理程式還不知道，它對這個詞毫無概念。所以在拷問（grilling）的過程中，它必須問我什麼是獨立影片，或是試著從程式碼中推敲出來。

隨著我越來越常使用 Grill Me，我開始注意到幾種情況：

- 代理程式講話變得非常冗長，我得提醒它：「不對，這個東西已經有專有名詞了。」
- 但很多時候其實根本沒有對應的名詞，或是我自己的思考方式就很冗長，而代理程式並沒有對此提出質疑。
- 又或者，我們明明得出了很棒的共用語言，卻沒有被記錄在任何地方。

於是我開始對 Grill Me 感到不滿足，因為拼圖少了一塊：我們雖然能有效地溝通程式碼，但每次都得重新解釋程式碼庫與領域（也就是我們要解決的問題）中所有不那麼顯而易見的事，才能開始做任何有生產力的事。

## 通用語言（Ubiquitous Language）

我開始思考：能給 AI 多一點助力的最薄一層文件，會是什麼？於是我做出了「通用語言」技能。

通用語言是源自領域驅動設計（Domain-Driven Design，DDD）的概念，出自 Eric Evans 那本大家都愛提的藍皮書。它的核心是：你要建立一份文件，記錄程式碼庫、開發人員與領域專家所共同使用的語言。所謂領域專家，就是了解你在建構什麼、但不一定清楚你如何建構的人。這三個群體都應該使用同一套共用語言，因為這樣一來，領域專家可以說「應用程式的這個部分有問題」，開發人員明白他在說什麼，而程式碼也反映了同樣的語言。

所以，我的做法是：在拷問過程中，一旦發現某些用語需要釐清，就呼叫通用語言技能，一邊進行一邊建立一份 ubiquitous language.md。

## 合併成 Grill With Docs

這樣我同時使用 Grill Me 與通用語言兩個技能，然後我意識到：「如果把兩者合併成一個新技能，不是更好嗎？」

這個新技能就是 **Grill With Docs**。它最上方的文字和 Grill Me 完全相同，但多了幾個額外的部分。

### context.md

第一個新增的能力，是尋找 context.md 檔案。這個檔案會記錄該情境（context）內所有的共用語言。

「context」這個詞的意義被過度使用，所以我有點不太自在，但還能接受。它其實就是 DDD 中的「限界上下文」（bounded context）：應用程式中使用同一套共用語言的某個部分。如果你有一個龐大的 monorepo，可以在此建立一份情境地圖（context map），底下包含許多不同的情境，這就是將此做法延展到超大型儲存庫的方式。不過，如果你只有一個相當大的儲存庫，整個應用程式與領域專家說的都是同一種語言，那麼只要使用單一的 context.md 即可。

這個技能被指示去尋找既有的文件，把其中的共用語言帶進來。在工作階段進行中，它還有一些額外的行為：

- 根據既有的詞彙表（glossary）檢驗用語的使用方式
- 釐清含糊的用語
- 討論具體的情境
- 與程式碼交叉比對
- 隨著進行即時更新

這些做法能幫助你在使用 Grill With Docs 時，真正把語言磨得更精確。而且這些投入會隨著時間產生回報。我向一些人徵求過意見，收到了一些很棒的回饋。其中一位整天都在使用它，一開始它要他定義很多術語，有些術語很難達成共識，有些則是他肯定會忘記的。但四、五個工作階段之後，他開始注意到 Claude 在拷問階段就能掌握脈絡，「神奇地與我在話說出口之前腦中的想法對齊了」。

這就是你能得到的好處。藉由記錄那些不顯而易見的事、並就共用語言取得共識，你真的可以與 AI 達到一種神奇的默契，讓你只需要用少得多的字詞，就能傳達你的意思。

舉例來說，這是我自己儲存庫中的文件。裡面有一段簡短的說明，介紹這個儲存庫是什麼；接著是課程與課程儲存庫，以及其中所有的實體，包括課程版本（因為我有多個版本）。如果我們找前面談到的那個「獨立影片」，它就在這裡。現在我們對「獨立影片」的意思有了明確的規格。

Grill With Docs 技能知道要去尋找這份文件，但我同時也在本機的 claude.md 裡加入了一個情境指標（不是放在全域那份 claude.md）。內容就是這段領域文件說明：單一情境的配置，context.md 位於儲存庫根目錄，並附上一小段額外的文件，說明相關資訊的位置。

### 架構決策紀錄（ADR）

Grill With Docs 還有最後一個功能。釐清模糊的用語能解決某些問題，但有些問題它解決不了。所以我想要一個額外的層級，用來說明那些無法記錄在 context.md 中、不那麼顯而易見的決策。為此，我選用了架構決策紀錄（Architectural Decision Record，ADR）。

ADR 其實就是放在儲存庫中的簡單 Markdown 檔案，用來記錄所有不顯而易見的決策。只有在符合以下條件時，才值得建立 ADR：

- **決策難以回頭**：如果只是「我們改用這個函式庫而不是那個函式庫」，兩者差不多可以互換，之後隨時都能換掉，就不需要。
- **沒有脈絡就會令人意外**：儲存庫中有很多決策在缺少脈絡時令人費解，尤其是比較複雜的決策。
- **是真正權衡取捨的結果**：換句話說，這個決策在未來會帶來後果。

我在其中定義了一個 ADR 格式，LLM 在建立這些 ADR 時會依循此格式。

## 實際示範

了解所有組成之後，讓我們回到前面，把 grill me 換成 grill with docs，實際開始一場拷問。

它做的第一件事是說：「哦，context.md 內容很豐富。獨立影片已經被定義為 lesson ID 等於 null 的影片。」接著它說，在繼續之前，想先點出與詞彙表之間的一個張力。這就是 Grill With Docs 常見的表現：在真正討論實作細節之前，它會先聚焦在語言上。

**第一個問題：提案與獨立影片的基數（cardinality）。** 它詢問的是：一個提案是否對應多支獨立影片，還是一個提案恰好對應一支獨立影片？我覺得採納它的建議是合理的，也就是採用一對多的關係。所以我回答：「正確。」

**第二個問題：術語衝突。** 接著它發現「獨立影片」這個詞出現了衝突：獨立影片可能是完全獨立的，也可能與提案有關聯。所以它基本上是在問：我們要把「獨立影片」維持為「任何沒有課堂的影片（無論有無提案）」，還是重新定義為專指「沒有提案、也沒有課堂的影片」？

我們如何回答這個問題，會影響後續的一切，包括獨立影片在 UI 中是否擁有自己的區塊，或是獨立影片與有提案的影片是否混在一起。因為我們在這裡定義的語言，也是使用者在頁面上瀏覽時會看到的語言。

我同意它的看法。其實一開始我原本以為會為「已提案的影片」另外設一個區塊，但現在我同意，把「提案」當作獨立影片本身的 metadata 是合理的。順帶一提，我用來語音輸入的是 Whisper Flow，用起來還行，不確定是否會推薦，不過還可以。

**第三個問題：狀態語意。** 它接著說需要定義一些狀態語意：每個提案可以是閒置（idle）、已排程（scheduled）或已發布（shipped）。我想允許自由轉換狀態。我並不在意是否自動化，之後隨時可以再加上自動化，例如按下「傳送到 YouTube」時自動進入新狀態。但現在我自己手動切換就可以了。

**第四個問題：提案可以沒有影片嗎？** 當然可以。重點在於，我們是在產生提案，也就是影片的點子，這就是 Mr. Beast 的做法：先把包裝準備好。而這段關係與語言，也會延伸到刪除連鎖（deletion cascade）這類具體的細節。所以我決定採用「刪除時限制」（on delete restrict），主要是因為我喜歡限制性的刪除，而且實際上我通常是封存而不是刪除。

接下來就進入更多實作細節了。為了不讓你看我把整場拷問都走完而感到無聊，我直接說：「可以把目前的成果先存進 context.md 嗎？如果還有沒釐清的地方，在你調整之前先拷問我。」看看它會怎麼做。

好的，它對 context.md 做了一系列更新，特別是新增了許多與提案相關的資訊：提案（實體本身）、提案狀態（提案可處於的狀態）。「已提案的獨立影片」（pitched standalone video）這個詞有點彆扭，我可能想再就此拷問它一下。還有「未附屬的獨立影片」（unattached standalone video），這也有點……基本上它變成了「獨立的獨立影片」。

請記住，我對這些用語看起來可能有點吹毛求疵，你可能覺得這是在爭論無關緊要的細節（bike-shedding）。但這會影響所產生的每一部分程式碼：所有的變數名稱、所有的檔案名稱，都會以這些 context.md 文件為基礎。因此，把這件事做對，對於與 AI 保持對齊至關重要。

當然，我們也不想無止境地吹毛求疵。所以我現在就喊停，說「夠好了，就這樣上線吧」，之後隨時都可以修改，並重構成新的用語。

## 這套做法帶來的好處

讓我們快速談談好處：經歷這套儀式之後，你實際得到了什麼？

1. **回覆更簡潔。** 因為有共用語言，AI 可以用更少的 token 與你對話，不需要冗長地重複或重新描述每件事。它只會說：「好的，獨立影片有變動。我們需要修改提案以及提案的顯示方式。」
2. **思考過程也更精簡。** 這種簡潔同樣反映在它自己的思考軌跡中。畢竟 AI 是用語言在自我思考，所以它能更貼近你的意圖，並且用更少的 token 進行思考。這是我觀察到的現象，感覺相當不錯。
3. **程式碼更容易瀏覽。** 因為規劃文件，以及你與 AI 交談的方式，都與程式碼的樣貌一致，所以它可以直接說：「好，我需要找出所有與提案相關的資訊，我來搜尋一下。」

這當然合理，因為這些全都是領域驅動設計本身所描述的好處。同樣的技巧對人類有效，結果發現對 AI 也有效。

## Grill Me 還有用嗎？

你可能在想：Grill Me 是不是死了？是我把它殺掉了嗎？它的創作者是不是從背後捅了它一刀？

絕對不是。我認為 Grill Me 是一個非常非常棒的技能，只是**當你有程式碼庫時，Grill With Docs 更好**。在我的技能集中，我已經把 Grill Me 移到「生產力」（productivity）分類，用於一般用途，也就是沒有程式碼庫的使用情境。

我聽過一個最令人驚豔的故事：有人在為母親撰寫悼詞，他用 Grill Me 讓 AI 針對他的母親向他提問，挖掘出許許多多美好的回憶。可見 Grill Me 在工程之外也有不可思議的用途。

此外，即使專案處於非常早期的階段，我仍然會建議使用 Grill With Docs，因為你能從共用語言中獲得很多好處，而專案初期往往正是需要建立共用語言的時候。

所以，規則很簡單：

- **有程式碼庫時，使用 Grill With Docs。**
- **沒有程式碼庫時，使用 Grill Me。**

## 持續更新與結語

我會非常頻繁地更新這些技能，也常常對技能本身、甚至是在不更動技能的前提下如何用得更好，有新的想法。所以我透過「給真正工程師的 AI 技能」電子報讓大家掌握最新資訊。這是我原本那份不錯的電子報之外的附加內容，只提供一些額外的技能更新，也許在更新發生時每週一則。我真的很討厭垃圾郵件，所以不會濫發給你。這個小頁面能幫助你掌握所有技能的變更紀錄，並提供一些不錯的額外內容，讓你學會如何更有效地使用這些技能。
