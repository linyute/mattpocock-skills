## Handoff：把工作交給下一個代理

Skills 儲存庫最近又大幅成長，短短幾天就突破了七萬顆星。當然，我也持續投入開發，所以本週的變更紀錄還有不少內容可看。最重要的消息是，我新增了兩項技能。第一項是 Handoff，我曾在 Twitter 上介紹過它，大家反應非常熱烈。這次不如直接讀讀技能內容，因為這次光看技能本身，就很能說明它的用途。

它的描述是：把目前的對話濃縮成一份交接文件，讓另一個代理接手。撰寫一份摘要目前對話的交接文件，讓新的代理可以繼續工作。將文件儲存到由暫存檔路徑產生器提供的路徑，並在寫入前先讀取該檔案。

這裡的做法是，在暫存目錄中建立一份不打算長期保留的暫存文件，只用來在兩個代理之間交接。要求先讀取檔案再寫入，是因為 Claude 若在寫入前沒有先讀取檔案，就會報錯。這只是 Claude Code 那種有點繁瑣的操作引導。

技能也會要求建議下一個工作階段可以使用哪些技能（如果有的話）。這是交接文件很重要的一部分：它不只要交接上下文視窗中的內容，也要交接當下的互動氛圍與意圖。比如說，如果你正在進行一場深度詰問，接著把工作交給另一個代理，交接文件就會建議它繼續這場詰問。

另一項關鍵要求是：不要重複其他成果中已經記錄的內容，改以檔案路徑或 URL 引用它們。如果使用者有提供參數，就把它們視為下一個工作階段的焦點描述，並據此調整交接文件。

我為什麼要做這項技能？因為我發現自己一直在手動完成這件事。假設我們正在深度詰問，遇到一個只有透過實際操作程式碼才能回答的問題。當然可以直接在詰問過程中做原型之類的工作，但我一直覺得這樣很彆扭。比方說，假設目前的工作階段已經用了六萬個 token，那我只剩下四萬個 token 可以做原型、提供回饋並反覆修改，接著就會開始擔心上下文視窗不夠用。

我真正想要的是開啟另一個上下文視窗，把深度詰問的所有背景帶過去，然後只專注處理原型。這正是 Handoff 發揮作用的地方。使用方式很簡單：你只要對 Claude Code 說：「把我交接給另一個代理。」它就會產生交接文件。接著把文件路徑交給新的代理，在另一個終端機開啟工作即可。完成後，甚至可以把原型結果交還給前一份工作，只要說：「這是我們從原型中學到的內容，現在回去繼續深度詰問。」

這裡主要有兩種模式。第一種是「發出去就不管」（fire and forget）：例如你正在進行另一場深度詰問，突然需要處理某件事；或者實作時發現一個錯誤，就請代理交接出去，讓新的代理去修正它。

另一種是我稱作「DIY 子代理」的模式，也就是剛才描述的情境：你正在深度詰問或規劃，發現需要修改程式碼，就切換到另一個代理的上下文視窗處理，完成後再交接回原本的工作。這有點像是你自己掌控的子代理，而且它不像一般子代理那樣受限。它有自己的完整上下文視窗，也能自行啟動子代理。大概就是這個概念；需要時，它當然也可以再交接給其他代理。

Handoff 是一項非常酷、非常實用的技能，顯然適合工程工作，但老實說，在工程以外也有用處。因此你會在這裡看到它被歸類在生產力類別。

## Prototype：先用原型釐清設計

接下來是另一項讓我非常興奮的技能，位於工程類別：Prototype。原型製作在 AI 工程中特別重要，因為你可以把原型當成研究、技術探勘（spike），或是在承諾採用某項設計之前釐清設計決策的方法。這些原型的設計目的就是用完即丟。

提到原型，大家通常馬上想到 UI，對吧？它確實非常適合 UI，可以用來決定介面應該長什麼樣子、給人什麼感覺，或在頁面上該如何運作。不過，原型在許多其他情境也很有幫助。舉例來說，商業邏輯中任何會隨時間改變的狀態邏輯，例如資料庫裡的某個實體需要依據使用者操作改變，就可以透過邏輯原型來釐清。

這種做法的概念是建立一個小型、可互動的終端機應用程式，讓它依序推進狀態機，測試那些只靠紙上推演很難理解的情況。這非常實用：你可以說「我大概知道它應該怎麼運作，幫我做個原型」，代理就會建立原型；你可以提供意見，讓它更新原型，最後再交接給另一個代理，根據原型實際建構功能。

當你遇到某些未知問題，而且只有看著程式碼實際運作才能找到答案時，就適合使用這項技能。即使你覺得自己大概知道答案、但又不完全確定，也可以直接說：「我們先做個原型吧。」

UI 原型的功能很有意思：它會產生數個差異極大的 UI 版本，而且會直接在你預定放置 UI 的專案根目錄中建立原型。頁面底部會出現一個浮動按鈕，你可以按左右鍵切換不同版本。選定一個版本後，就能沿著設計分支繼續探索，例如：「我喜歡這個版本的這個部分，也想採用另一個版本的那個部分。把 A 和 B 的一些元素合併成新版本，其他版本就捨棄。」

這非常適合在背景代理（AFK agent）開始實作之前，先確認 UI 應該長什麼樣子。這類代理也許由 Sun Castle 提供支援。大家常問我：「要怎麼讓背景代理更擅長做前端？」答案就是原型。你真的需要讓真人和代理一起工作，針對成果提供回饋。UI 非常仰賴品味，也很受應用程式既有風格影響；而 AI 往往看不見自己實際建構出來的畫面。因此需要有人運用自己的品味，參與並引導這個過程。

這就是 Prototype。它真的很好用，希望大家會喜歡。

## 修正 Grill with Docs 與標籤流程

接著快速聊聊這次修正的幾個問題，其中有一項很有意思。我把大家常用的 Grill with Docs 技能包在幾個 XML 標籤裡，原始內容裡可以看到這些標籤。

我發現 Grill with Docs 有時太急著開始實作。我猜問題在於，模型可能把下方的補充資訊看得比上方的主要指示更重要。對我來說，提示詞有點像音量大小：不同提示或提示詞的不同部分，可能會互相競爭，影響最終輸出的程度各有不同。

所以我用 XML 標籤把內容分開，明確指出上方這段是技能實際要執行的工作，下方則是補充資訊。這能讓大型語言模型知道，下方內容不是正式指示。Anthropic 的模型通常很適用這種方式，他們的文件中也有提到。這樣一來，`supporting info` 裡的內容就會稍微降低優先級。這項調整效果很好，至少從使用者回饋來看是如此。我沒有針對這個案例執行評估，也許應該做；不過自從加入 XML 標籤後，大家就不再回報這個問題了。

另一項修正是：我在 `/to-prd` 和 `/to-issues` 中加入指示，套用 `ready for agent triage` 標籤，不需要額外分流。之前的指示是加上 `needs triage` 標籤，我覺得不太合理。透過 `/to-prd` 和 `/to-issues` 建立的內容，本來就還沒準備好交給代理執行；看看 `/to-issues` 的設計意圖就知道了。

有人問過，是否應該把 `/to-prd` 產生的內容標記為可交由代理執行，因為代理也許會自行實作。針對這種情況，你只要明確告訴代理：「不要實作 PRD，只實作真正的 issues。」總之，這就是這一版加入的修正。

## 進行中的寫作技能：從片段到文章

最後，我想展示幾項目前還在開發中的內容。大致上有兩組技能。第一組是寫作技能，我正在嘗試拆解 AI 寫作的要領，並把它做成可重複使用的流程。我今天早上才剛開始用，一邊調整、一邊試玩，目前覺得很有趣。

這套流程的想法是先寫「片段」（fragments）。片段是一些之後可能會整理成完整作品的文字素材。作者常常會多年來持續寫下長篇日記，觀察各種事物、思考個人生活與外在世界，也記錄朋友等等；這些片段最後可能幾乎原封不動地出現在故事裡。

這套做法認為，AI 可以幫上忙，因為它能透過提問引導你寫出更好的片段。我通常會直接口述想法，然後讓它整理成一份片段文件。

接著，你可以從這些片段中尋找可能的故事走向，並透過撰寫「節拍」（beats）一步步鋪陳。節拍就是故事可能發展過程中的一個個節點。想像你要寫故事、文章，或像我一樣寫電子報，面對許多可能的發展方向，需要選出一條路徑；撰寫節拍就能幫助你做到這件事。它會根據片段提供三個下一步方向供你選擇，再按照你的選擇寫出相應節拍。

最後是「文章架構」（writing shape），這是一個回頭檢視的流程：確認文字聽起來不會太像 AI 生成、結構安排恰當，並進行最後一輪修訂。這就是整套流程的構想，我很期待看看它最後會發展成什麼樣子。這些技能短期內大概還不會準備好，我還需要投入不少時間開發；不過大家現在就可以自由試用。

## 進行中的 Code Review 與文件網站

另一項我想談的進行中工作，是許多人期待已久的 review 技能，也就是 code review 技能。我一直拖著沒做，因為要寫一項通用的 code review 技能確實很難。不過，我想出兩個可能的切入面向：檢查變更是否符合程式碼庫的標準，以及是否符合規格。

第一個面向是儲存庫既有的程式碼標準：這份差異（diff）是否遵循專案的程式碼規範？第二個面向是規格：這份差異是否忠實實作原始 issue 或 PRD？我發現，如果只看標準，就會漏掉規格方面的問題；如果只看規格，又會漏掉標準方面的問題。因此，我的構想是讓 review 技能平行啟動兩個子代理，分別檢查這兩個面向。

標準面向比較棘手，因為每個人的程式碼標準都不一樣，也各有需求。我想我可能還得另外做一項技能，從你的儲存庫中擷取程式碼標準，讓 review 技能有更好的依據。這部分還有不少工作要做，希望大家會感興趣。

最後，我們也正在製作一個文件網站，裡面會有每項技能的個別影片，還有一份電子報。這會成為我的主要電子報；你可以選擇不接收技能相關內容，但如果你很喜歡這些技能更新、想追蹤我做的所有事情，這裡就是訂閱的地方。

非常感謝大家一路關注，也謝謝你們提供這麼好的技能回饋，這讓我有動力繼續投入。我很喜歡看到大家終於透過這些技能掌握 AI，也會依自己的用途調整技能。謝謝收看，我們下次見。
