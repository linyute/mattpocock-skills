幾週前，我發現自己在使用代理（agent）時，習慣做一件我覺得非常聰明的事，但又覺得它太過簡單，似乎不值得特地做成一個技能。

先說明一下，我總是在思考技能（skill）這件事：如何把我的直覺和寫程式的實務做法，封裝成可重複使用的技能。也因此，我的技能儲存庫在錄製本影片時已經有將近 100,000 顆星。

我開始構思的這個技能，就是 handoff（交接）技能。它的構想是：把目前工作階段的上下文視窗（context window）壓縮成一份 Markdown 檔案，交給另一個工作階段繼續處理。幾週前，我把它發布了。它位於 skills 底下的 productivity 資料夾，也就是這裡的 handoff。這是一個非常、非常簡單的技能，內容大意是：撰寫一份交接文件，摘要目前的對話內容，讓全新的代理可以接續這項工作；並將文件儲存到使用者作業系統的暫存目錄，而不是目前的工作區。

我把它放進技能資料夾，當作一項實驗，想看看自己會用到什麼程度。結果發現我用得非常頻繁。

在這支影片中，我會深入介紹這個技能：我為什麼這樣設計、它的用途是什麼、它與某些執行框架（harness）內建的工具（例如 compact）有何不同，以及如何善用它，讓你的 grilling（拷問式提問）工作階段發揮最大效益。

如果你喜歡我分享的這類內容，那你一定會喜歡我開設的課程：**AI coding for real engineers**（寫給真正工程師的 AI 寫程式課）。這是一個為期兩週的梯次制課程，適合想用 AI 程式開發工具交付高品質程式碼，而不是粗製濫造內容的人。課程將於 6 月 1 日開始，目前正在舉辦優惠活動，歡迎點擊下方連結了解詳情。

## 為什麼需要 handoff？它和 compact 有何不同

首先，我們來說明我為什麼做這個技能，以及它與壓縮（compaction）有什麼差別。你可能已經聽過壓縮這個概念。

### 上下文視窗的「聰明區」與「笨蛋區」

在這樣的程式開發工作階段中，隨著我們與代理對話、代理呼叫工具、編輯檔案，上下文視窗會被越填越滿，裡面的 token 越來越多。

以我使用的執行框架 Claude Code 為例，它的上下文視窗相當大，有 100 萬個 token。但上下文視窗其實存在「聰明區」（smart zone）與「笨蛋區」（dumb zone）。

在上下文視窗的前段，代理的表現會好得多，因為注意力（attention）關係還沒有那麼吃緊：token 少，需要計算的 token 間注意力關係就少，代理的注意力就不會太分散。換句話說，內容越少，它越能專注。

這表示隨著對話不斷進行，代理的回應會越來越笨，一路下探到 80 萬個 token。不過我個人從沒用到那種程度，因為大約在 12 萬個 token 時，我就已經覺得自己進入笨蛋區了。

也就是說，儘管 Anthropic 宣傳這些模型有龐大的上下文視窗，但要處理真正需要智慧的任務，你實際上只有大約 12 萬個 token 可用。因此，你必須有效率地編列預算，並隨時留意自己的上下文視窗用量。

### 壓縮（compact）的運作方式

那麼問題來了：當你快要踏入笨蛋區時該怎麼辦？要如何挽救對話？要如何在跨越笨蛋區之後，仍然維持聰明的狀態繼續對話？

答案就是 compact。compact 會將像這樣的長對話做成摘要，讓你從接近笨蛋區的位置，一口氣回到聰明區。

視你使用的執行框架以及是否啟用而定，有時還有所謂的自動壓縮緩衝區（auto compact buffer）。也就是當你接近上下文視窗的尾端，比方說已經深陷笨蛋區時，自動壓縮緩衝區會啟動，自動把你的對話摘要到一個新的工作階段中。

這份摘要通常包含：被參考過的檔案清單、你在對話中說過的內容，以及對話的整體語氣。它會像一小塊濃縮精華，放在新工作階段的開頭；隨著新工作階段累積上下文，你會不斷參考舊的工作階段。

這代表當你一再壓縮、再壓縮，最後會得到由先前各次對話層層堆疊而成的「沉積層」。這樣做效率上或許不夠理想，但如果你要進行某些需要在同一個問題上反覆鑽研的工作階段，這仍然是不錯的做法。

例如在除錯時它其實非常有用：你可以把已經嘗試過的各種方案壓縮起來，繼續嘗試其他做法，碰壁之後再壓縮一次，基本上就是儲存目前的狀態。這是一種長時間執行工作階段的方式，但本質上仍然只有一個工作階段。

所以我仍然覺得 compact 是非常實用的工具，適合用來維持長時間的單一工作階段。

## handoff 要解決的問題：把工作交給另一個工作階段

不過，我漸漸發現自己想用 compact 做其他事情：我想把內容壓縮到「另一個」工作階段。

舉例來說，假設我正在某個工作階段中，過程中注意到一個小小的重構機會。這件事完全超出目前工作階段的範圍，但我知道遲早得處理它。那麼我有哪些選擇？

- **延長目前的工作階段**：但這會讓上下文變得被稀釋，一半在處理這件事、一半在處理那件事，肯定會進入笨蛋區，我大概也就無法完成最初的目標。
- **直接 compact**：但這樣會破壞我在目前工作階段中累積的所有進度。

我真正想要的，是說：「好，我要在另一個工作階段完成這件事，同時讓目前的工作階段保持純粹。」換句話說，我想要的是只擷取與這項額外修復相關的那一小部分上下文，交給另一個工作階段，讓兩個工作階段各自獨立執行。

於是有一段時間，我會這樣對代理說：「把我目前工作階段中的內容拿出來，我想修正這個特定的錯誤，幫我寫一份 handoff.md 文件，好讓我直接把它交給另一個代理。」後來我發現自己實在太常這樣做了，便決定：「好，我需要為此做一個技能。」

### 範例：在 grilling 工作階段中交接任務

我最常在 grilling 的過程中使用 handoff。這裡是我為了規劃 Sandcastle（我的某種軟體工廠）未來功能所進行的一場 grilling 工作階段。

你可以看到我正在回答一些問題，而且才進行到第 2 題，所以這場並不長。我在這裡說：「我認為未來我們可能會想把迭代次數和完成訊號移到一個獨立的 API。事實上，我們把這個任務交接給另一個代理吧。」

你可以看到，我在下達 handoff 時，會說明交接的原因，以及文件中究竟該包含什麼內容。這麼做有兩個效果。

第一，它會讓我目前的 grilling 工作階段更加聚焦。代理會回應：既然有這個限制，第 2 題就不用再討論了。也就是說，因為我已表明這部分超出範圍、之後再另行處理，這對我目前的 grilling 工作階段是有幫助的。

第二，它會建立一份 Markdown 檔案，內容包含下一個工作階段的焦點：建立一個 GitHub issue，並最終設計出將迭代次數與完成訊號拆分為獨立 API 的方案。之後我只要把這份檔案交給另一個代理，請它建立 issue 即可。很簡單。

## 進階模式：在 grilling 中交接給 prototype

另一個我非常推薦的模式，是在 grilling 的過程中，把任務交接出去做原型（prototype）。

當你在 grilling 時（也就是代理透過我的 grill me 或 grill with docs 等技能向你提問），你通常會發現需要回答的問題分成兩類：一類是「已知的未知」，也就是代理能夠問你的問題；另一類則是你必須在程式碼中親眼看到，或必須做出原型才能判斷的內容。這在 UI 原型，或是你還不確定該怎麼處理的複雜邏輯上尤其明顯。

### 實際案例

在這場 grilling 工作階段中，我們進行到第 13 題，代理也給出了最終的結論。接著你可以看到我說：「把困難的部分交接出去做原型，包括視窗之間的通訊，以及 tldraw SDK 的整合」，那是我當時正在開發的東西。它建立了交接文件，之後我便在該分支上實作原型。

在原型的工作階段中，這最終變成一場龐大的工作階段，高達 16.9 萬個 token，遠遠超出 grilling 工作階段所能容納的量。我在其中做出了這個 UI 的原型，以及我想看到的互動方式。

接著我說：「好，我們把這個交接回原本衍生出它的 grilling 工作階段。把原型帶來的所有心得，凡是沒有直接記錄在原型本身，或是不那麼顯而易見的內容，都寫成一份交接文件，讓我交還給規劃者。」

### 自製的子代理（sub-agent）

這其實是我常用的一種模式：你在最初的工作階段中做了一些工作，把它交接給另一個工作階段；那個工作階段再建立另一份交接文件，傳回原本的工作階段。這幾乎就像是自己動手做了一個子代理：你可以為某項特定任務使用一個專屬的上下文視窗，把該任務的所有心得壓縮起來，再傳回給上層（父工作階段）。

之後，我就能完成 grilling 工作階段，並產出完整的 PRD 與 issue，而且其中包含了原型。所以，對於想從 AFK（不需人員在旁盯著）的代理身上取得成果，並善用原型來說，這是一種極為豐富的模式，非常酷。

### 以 Markdown 文件跨代理協作

還有一點值得一提：直接使用 Markdown 文件，而不是仰賴代理的原生功能，好處在於第一個工作階段可以是 Claude Code，但你可以把這份文件交給另一個代理，例如 Codex 或 Copilot CLI，隨你使用什麼。因此，如果你想進行任何對抗式審查（adversarial review），或讓不同的程式開發代理之間互動，這是一個非常簡單的方法。

## 技能的設計原則

我們也來讀一讀這個技能的最後幾個部分，好讓你了解每個設計背後的理由。

### 加入「建議技能」區段

技能中的設定是：在文件裡加入一個「建議技能」（suggested skill）區段，列出代理應該呼叫的技能。我會加入這一點，是因為我常用技能來定義某個工作階段的風格。有了建議技能區段，你只要把交接文件貼進新的工作階段，它就會自動呼叫所需的技能，例如 grill with docs、diagnose 或 prototype 等，接著就可以開始工作了。你不需要再去思考下一個工作階段該使用哪些技能，非常方便。

### 不要重複已記錄在其他產出物中的內容

我經常發現這些交接文件變得非常龐大，而且只是在重複其他 Markdown 檔案，或 GitHub issue 之類資源中已經存在的內容。因此，這項原則基本上是說：請使用指標（連結）來指向這些內容，而不要把文件中的一切重複抄寫一遍。

### 將交接檔案存放在作業系統的暫存目錄

我也非常堅信，應該把這些交接檔案儲存到使用者作業系統的暫存目錄。換句話說，這些交接檔案是用完即丟的，不該長久留存、在你程式碼庫的文件中逐漸腐朽。

### 遮蔽敏感資訊

交接文件必須遮蔽任何敏感資訊，例如 API 金鑰、密碼或個人識別資訊（PII）。這點基本上是必要的，你不會希望這些資訊散落在隨處可見的 Markdown 檔案裡。

### 依使用者提供的引數量身調整文件

最後，如果使用者傳入了引數（也就是下一個工作階段的用途），就把它視為對下一個工作階段焦點的描述，並據此調整文件內容。我認為這對 handoff 來說至關重要，因為要寫出一份像樣的文件，代理必須知道下一個代理工作階段將專注於什麼。

每次使用 handoff 時，我總是會描述目的，也就是我們為什麼要交接，因為我實在想不出，不這樣做要如何寫出一份好的交接文件。當然，語音輸入讓這件事變得非常輕鬆，我只要一口氣說完，就可以開始了。
