## 為什麼需要 triage 技能

大多數以技能（skill）為基礎的工作流程，對單打獨鬥的開發者來說很好用，但一進入團隊協作就顯得不足。在團隊中、在維護別人的專案，或是替別人實現想法時，你經常得對他人提出的點子進行分流（triage）：判斷這些點子好不好、值不值得開發、是不是錯誤回報、是否需要先重現問題，諸如此類。只要長期開發過具一定規模的專案，對這些情境一定不陌生。

因此我建立了一個技能來處理這件事，名稱就叫 triage，而且我在自己維護的每一個開源儲存庫上都會執行它。它很適合用來處理 GitHub issue，也可以接上 Jira 或任何待辦清單（backlog），把清單內容充實起來，轉化為代理（agent）可以接手的可執行任務；或是直接駁回，又或是進行各種其他處理。

## 編碼在標籤中的狀態機

驅動這一切的核心，是一個編碼在標籤（label）裡的狀態機。目前有兩種類別角色：bug（錯誤）與 enhancement（功能增強），這是任何做過 triage 的人都熟悉的分類。此外還有五種狀態角色。這些角色未來也可能調整，我之後大概會再擴充，但就目前而言，這套設計對我來說運作良好。

## 五種狀態角色

這五種狀態角色，各自對應一張工單（ticket）可能處於的狀態：

- **needs triage（待分流）**：需要維護者查看。維護者完成處理之前，工單都停留在這個狀態。
- **needs info（待補充資訊）**：正在等待回報者提供更多資訊。
- **ready for agent（可交給代理）**：規格已完整定義，可以交給 AFK（不需人在旁邊）的代理，讓它直接衝刺完成任務。
- **ready for human（可交給人類）**：需要由人類現在來查看並實際實作。
- **won't fix（不修正）**：這項工單不會被採取行動。

這是一個狀態機，因為每一張經過分流的 issue，都應該恰好帶有一個類別角色與一個狀態角色。換句話說，同一張工單不可能同時是「ready for human」又是「needs triage」。這就是老派又可靠的狀態機；任何追蹤過我的人都知道，我非常喜歡狀態機。

## 使用方式

triage 的使用方式很彈性：

- 可以針對特定的 issue 進行分流。
- 可以對整份待辦清單進行分流，例如請它「列出現在需要我關注的所有項目」。
- 可以直接下指令，例如「好，把這一張移到 ready for agent」。

順帶一提，ready for agent 是個很棒的設計，因為要把工單移到這個狀態，就必須替將要接手的代理撰寫一份簡報（brief）。技能裡內建了一份代理簡報範本（agent brief template），讓你可以把這張工單寫得相當完整。

## 實戰示範：分流 Sandcastle 的 issue

你大概在想：「基本概念我懂了，那就實際操作給我看吧。」剛好，Sandcastle 裡有一批 issue 等著分流，所以我就用自己的儲存庫來示範這個技能。

可以看到裡面已經有不少項目：有些是 ready for agent，而且已經做成 PR；有些是 needs triage，我需要再看一次；有些完全沒有標籤；還有一些被標為 won't fix。

我會在自己的儲存庫中開啟一個新的 Claude 工作階段，輸入 triage，然後說：「把所有未關閉的 issue 給我」，或者更精確地說，只要我還沒分流過的那些。送出之後看看會發生什麼事。它會先探索儲存庫，並偵測到我使用的是 GitHub issue，你看，它動起來了。

好，它發現有九個尚未分流的未關閉 issue。我請它逐一處理，替每個 issue 加上基本標籤，做完初步分流，這樣我就不用做太多決定。

### 代理如何判斷什麼值得處理？

你可能會好奇：代理怎麼知道哪些項目可以處理、哪些是好的候選？答案是，我在儲存庫最上層放了一個 `.out-of-scope` 目錄，裡面收錄了幾項我已經用這個技能分流過的內容。凡是我決定「這個我們不做」的功能，都會被標記為日後的範圍外（out of scope）項目。舉例來說，Sandcastle 不提供以程式方式組合 Dockerfile 或管理基底映像檔的抽象層。

這本質上就像架構決策紀錄（ADR），只不過專門記錄我們不打算實作的功能。這表示代理在檢視 issue，尤其是功能增強類的 issue 時，會參考我建立的這些範圍外文件，然後判斷：「這是我們不會承諾實作的增強項目，可以直接關閉。」

好，它已經標完一批了：全部分成 bug 或 enhancement，並且都標為 needs triage。

## 從 bug 開始：診斷並修復

我們先從 bug 開始往下處理，我想這類項目比較容易理解。我請它從 477 號開始，送出看看結果。

它回報了建議：這是一個 bug，並建議把它移到 ready for agent。這張工單裡已有相當完整的分流筆記，指出確切的根本原因，並附上重現用的堆疊追蹤（stack trace）等等。不過，我希望它能自己重現一次問題。它對回報者提供的內容有點太輕信了。

所以我想改用我的另一個技能，請它「自己診斷這個問題」，讓它完整走過重現 bug 並嘗試修復的流程。而且我們可以直接在同一個工作階段中進行。

### 留意上下文用量

當然，無論用 LLM 做什麼，我都會留意上下文（context）的用量，也就是左下角顯示的數字。我替這個工作階段抓了 100K 的預算，目前用了 46.5K，我覺得還可以。要診斷並修復這個問題，上下文綽綽有餘。而且我有預感這只是個小錯誤，這件事一直在我心裡盤算著。

triage 的好處是，所有項目都已經標上正確的標籤。在之後的分流工作階段中，我只要回到 issue 列表，說一聲「好，我們現在來處理這個 issue」就行了。

### 代理管理的本質是佇列管理

有趣的是，AI 與 AFK 代理的管理，很大程度上其實就是佇列管理。我們現在做的正是這件事：修剪一個佇列，並在建立工單的人類與負責實作的 AI 之間，扮演轉譯層。

Sandcastle 是我的 AFK 代理軟體工廠。它的規劃提示詞（plan prompt）會尋找 ready for agent 標籤，而且只會處理被明確標示為 ready for agent 的項目。

### 診斷結果與修復

好，看來它找到問題了，診斷確認。問題在於有幾個變數含有字面上的 task ID，而這種語法如果使用者沒有傳入值，就會導致錯誤。因此它的做法是把這些 task ID 換成另一種 ID 的樣式；至於那種不使用雙大括號的佔位符，就不會造成錯誤，所以沒有問題。

我們也看到它加入了回饋迴圈（feedback loop）的概念：用單元測試搭出一個簡單的迴圈，並斷言產生出來的 prompt.md 中不含任何未解析的 task ID。這看起來很棒，而且它沒有多問就直接往前衝，這個情況下沒有問題。

可以看到，diagnose 技能使用的設定與我的 TDD 技能很類似：先建立迴歸測試、先建立回饋迴圈，再在這個回饋迴圈中進行修復。它已經建立了完整的測試套件和型別檢查，看起來可以開工了。

這也是 triage 的另一個好處：一旦把 issue 拉進來、理解並診斷之後，如果你願意，可以當場就修好它。

### 雙工作階段並行

我常做的一件事，是同時開兩個工作階段：一個在這裡分流 issue，另一個在左邊，我可能會直接在 main 上修復問題。

好，它跳出了一個指令請求。我先回答 yes，然後切換成自動模式（auto mode）。看起來不錯，它加入了變更集（change set），也加入了修復。我會請它把變更推送到 main，並關閉原本的 issue。

我也可以請它建立 PR，由 PR 引用原始 issue，這樣一來，當我合併 PR 時就會自動關閉該 issue。這是我平常偏好的做法，不過這次就直接推到 main 吧。其實我事先做了一些檢驗，已經知道修復方式了，而這就是修復內容。算是給你們看一點電影魔法吧。

## 總結

以上就是 triage 技能。它本質上是讓你與 AI 協力合作，把雜亂的人類點子轉化為代理可以接手處理的實際任務，而且是專為 AFK 代理設計的。要讓代理順利運作，你需要一份可以讓它隨時間陸續領取的任務待辦清單。替每一項任務加上明確的標籤，代理就不會在那些還沒準備好的糟糕任務上亂闖。

而 ready for agent 這個訊號特別棒，因為你可以看著自己的待辦清單逐漸被一個個小標記填滿，而你知道這些項目都會被實作出來。非常酷。

### 與既有技能的搭配

它也能和我現有的技能搭配得很好。舉例來說，我們可以在這裡建立 PRD。像這一份是關於以 work tree 鎖定機制來避免代理並行存取的 PRD，我已把它標為 ready for agent，所以代理會看到它並接手。工單也可以這樣處理：這張就是依據 PRD 拆出來的工單，它的父項就是我們剛才看到的那份 PRD，同樣標為 ready for agent，所以接手的 AI 也會看到它。
