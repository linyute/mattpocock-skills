## 全新文件網站

各位好，Skills 系列又來了，這次帶來更多技能更新。這是 1.2.0 版，為我原本就廣受歡迎的工程技能組合帶來一大堆改進。Skills 這個儲存庫目前是 GitHub 有史以來星數排名第 24 高的儲存庫，星數來到 20.4 萬顆。既然已經成長為一個成熟的專案，我們就需要一份像樣的文件，於是我們把它做出來了：網址是 aihero.dev/skills，我和團隊一起打造了這個非常棒的網站。

瀏覽這個網站最好的方式，是先進入主頁面 /skills，看看裡面的分類方式。舉例來說，你可以看到這裡的主要流程：從 grill with docs 開始，接著進入 spec，然後是 ticket、implement，最後是 code review。左側面板則提供每一項技能的完整參考清單與說明。我以前的正職工作其實就是撰寫文件，所以能重拾這件事讓我蠻開心的。網站上甚至還有一份常見問題清單，這些問題其實是從我平常維護的個人 wiki 整理出來的，裡面收錄了大家最常問我的問題。

這些技能也串接到我一直在整理的 AI 寫程式詞典。舉例來說，這裡這個小小的 ticket 連結，就是連到我對「ticket」這個詞彙的定義。所以這份文件不只能幫助你更深入了解我的技能，也能用來學習 AI 寫程式的知識，讓你對整個運作方式有更深層的理解。

## 正式上架 Claude Code 外掛市集

第二個重大改變，是我們現在正式成為 Claude Code 官方外掛市集的一部分。這代表你可以打開 Claude Code，輸入「plugin」之類的指令，搜尋 Matt Pocock 或是 Matt Pocock skills，就能直接從那裡安裝。這樣一來，你就會得到一份唯讀的套件包，不需要任何額外步驟，而且日後我對這些技能所做的任何更新，都會自動同步到你那邊。

## 正式支援 Codex

對 Claude Code 使用者來說這聽起來很不錯，但如果你是 Codex 的使用者呢？這次更新對你有什麼幫助？其實，我現在替每一項技能都附上了 openai.yaml 檔案，這代表它們應該能夠開箱即用，直接相容於像 Codex UI 這類介面。這也意味著 allow implicit invocation false 這項設定，現在也能延伸套用到 Codex 上。

在此之前，我們的技能分成「由模型觸發」與「由使用者觸發」兩種。「由使用者觸發」技能的好處，從主要的 skill.md 檔案裡就能看到：這類技能在你實際呼叫之前，不會出現在代理的上下文視窗中。這個機制在 Claude Code、在 Pi，還有其他幾套執行環境裡都能運作，但在 Codex 裡卻行不通——老實說，我一開始並沒有意識到這點。所以現在我們替每一項技能都附上這個同層檔案（sidecar），讓 allow implicit invocation false 這項設定生效，這樣一來就能在 Codex 上開箱即用了。

## 新技能：Wait, What?

接下來我想推出的技能，是為了解決一個問題：Opus，尤其是 Opus 5，最近講話開始變得很離譜。我也不太清楚原因，可能只是新模型的某種特性吧。但不知為何，每次我跟 Opus 互動，它講的內容都讓我完全摸不著頭緒。它變得異常囉唆，用了一堆很奇怪的 LLM 慣用語，讓我讀起來非常非常吃力，我相信很多人都有同樣的感受。

老實說，當時擺在眼前的選項不外乎是接受現狀、重新改寫驗收標準（AC），或是把摘要資訊隨著匯出一起保存下來，這樣下次重新發布且內容沒有變動時，就能直接跳過重新讀取、進入標記階段，而不必重新挑選一次。這句話到底在說什麼？確實是有實際意義的，這也是為什麼你能感覺到它的重要性。

（以上這段故意寫得又長又難懂，正是在示範 Opus 最近講話的那種感覺。）

我試過各種方法想解決這個問題，像是切換不同的 output style，或是在我的 agent.md 裡加東西，但後來我發現，我真正需要的其實只是一個技能，讓我能夠直接說：「等等，你剛剛是在說什麼？」於是，這個技能就叫做 Wait What。

這是一個非常非常簡單的技能，只做兩件事。第一，它會告訴代理：「使用 ASD STE 100 簡化技術英文（Simplified Technical English）這個標準」，說穿了，這其實只是引導代理使用非常簡單的語言，用清楚、直述的句子來表達。第二，它也會要求代理回頭對齊 context.md 裡的通用語言（ubiquitous language）。

真正能治好囉唆毛病的方法，並不是叫它用「簡單的語言」——雖然我們多少也這麼做了一點——而是叫它用「你的語言」，也就是你在 Grill with Docs 這個技能裡已經建立起來的那套語彙。每當代理生出一堆莫名其妙的東西，而你完全看不懂它在講什麼的時候，就可以使用這個技能。你只要說一句「等等，什麼？」，它就會回覆一個清楚得多的版本給你。

## Grill me 重大更新：分輪提問

接下來要說的改變相當重大，這是我目前最受歡迎的技能——Grill me 的更新。以前，Grill me 每次只會問你一個問題：你會先拿到一個問題，回答之後，再拿到下一個問題，再回答，依此類推，每一輪只問一題。

但這樣的設計有一個很糟糕的失敗模式：當你進行到一場 grilling（深度詰問）的尾聲、大部分困難的部分都已經討論完畢時，剩下的往往都是一堆簡單的問題，卻依然一題一輪地問下去，你只能一直回答「對，這樣可以。」「對，這個也可以。」這種體驗非常令人沮喪，而且感覺慢得要命。所以，有好一段時間，我都想找方法加快這個流程。

對我來說最合理的做法，就是讓每一輪可以同時問多個問題。這樣一來，如果有一大堆簡單的問題，你就可以直接「對、對、對、對、對」一口氣回答完。但問題來了：如果第三題的答案，其實取決於第一題的答案，那該怎麼辦？

在舊版設計裡，這從來不是問題，因為你本來就是一題一題依序回答，如果某一題依賴前面的問題，那前面的問題這時早就已經回答過了。但在新的設計裡，這看起來似乎會更混亂，因為你可能會在錯誤的時間點回答某個問題，或是回答到一個其實需要先回答別的問題才能成立的問題，又或者回答了一個其實不該出現的問題。這樣要怎麼運作才合理？

其實，只要換個角度想，這些問題彼此之間的關係比較像是一張圖（graph）。可能在一開始會有一個關鍵問題，必須先回答，才能打開後面一整串其他的問題，而這些問題可能又會再引出更多問題。因此，現在的 Grill me 會沿著這張問題圖走，每一輪只問「目前可以回答」的問題，並以「輪」為單位來提問。於是，你會先拿到第一輪的問題，這一輪可能只有一個關鍵問題。接著，你再進入下一輪，這一輪會開放出更多新的問題——整個設計的精神，就是盡可能快速地把你推向問題的最前緣。

實際畫面大概是這樣：你可以看到我目前在第一輪，畫面上列出 Q1，後面還附上一個小小的建議回答。我決定在這裡加上一點 emoji——我知道，我知道，你可能不喜歡這樣，但我自己很愛，這樣畫面才多一點色彩。這讓我可以很輕鬆地用眼睛掃過整個畫面：好，這是 Q1，接著是建議的回答；Q2，也看得到建議的回答。因為我是用語音輸入，所以我可以一口氣講完：好，Q1，我同意。Q2，我同意。Q3，這邊需要改一下。Q4，這邊也要改。再往下看，你會看到第二輪的問題出現了，格式完全一樣。所以整個流程就是：我們回答完第一輪的問題，接著拿到下一輪的問題，就這樣不斷把問題的前緣往前推進。

## Writing for Agents 技能更新

下一個重大改變，是我把原本的 Writing Great Skills 技能做了修改，因為我發現自己其實把它用在「技能」以外的地方。只要是代理會讀取、用來讓代理表現更好、讓文件更精簡、讓輸出更可預期的任何內容，我都會拿這個技能來處理。

所以，現在這個技能改名為 Writing for Agents，你可以用它來修改 agents.md 或 Claude.md，當然也包括建立或編輯技能本身。這個技能裡還額外附上了一份參考檔案，裡面補充了一些和技能機制相關的內容。也就是說，你可以用它來寫技能，更重要的是，你也可以用它把你的 agents.md 內容抽取出來，拆分成一個個技能，藉此避免那種把所有東西都一股腦塞進前置內容（front loading）的糟糕做法。

整體來說，每當我需要撰寫任何代理設定、又希望它讀起來順暢、也希望代理能依照它好好執行的時候，我發現自己越來越常用到這個技能，Writing for Agents 就是正確的選擇。而且，它本身也支援由模型自動觸發，描述寫得相當清楚明確，所以只要在修改 agents.md 的時候，它就應該會自動被引用進來，這點我非常喜歡。

## 新技能：Wizard

接下來是一個全新的技能，是我私藏了一陣子的東西，叫做 Wizard。最近我剛好需要建置一批基礎設施，還得走過一堆 AWS 的設定流程，老實說，我很討厭這個過程。我心想，應該有辦法讓代理在這裡幫上忙吧。

於是，我做出了這個 Wizard 技能，它會產生一個互動式的 bash 精靈（wizard），引導人類一步步完成那些「只有人類本人才能做」的步驟。換句話說，我原本大可以讓代理直接進入 AWS、用 computer use 之類的方式幫我把東西建置好，但那種做法讓我感覺不太舒服。我希望能夠掌控整個流程，但同時也希望整件事盡可能簡單。

實際上它長這樣：我記得這次是用在搬遷到一個遠端主機（remote box）的設定流程上。你只要啟動它，它就會問你：「準備好要開始了嗎？」你回答「好，開始吧」，接著它就會直接把我帶到我需要去的那個頁面——對了，這個過程中它自己就會打開對應的網頁，我完全不需要動手。它會帶我去登入、帶我去改需要調整的設定。接著我就能把 API 金鑰貼上去——記得，這是一支確定性（deterministic）的腳本，整個過程完全沒有代理介入，也不會把任何東西送到 Anthropic 那邊。所以，我把金鑰貼進去，它就會把資料存進該存的檔案裡，甚至在需要的時候，也會直接把它存進 GitHub secrets。它會這樣一步步帶著我走過各個不同的階段，搭配一個很不錯的小型介面，直到我們完成所需要的所有設定為止。

我發現，這讓原本痛苦萬分的服務建置流程，變得出奇地令人愉快，因為我太清楚以前這件事要花多久時間了。所以，Wizard 現在已經成為我技能組合裡不可或缺的一部分。我其實已經開發了好幾個月，一直處於「進行中」的狀態，直到現在我才覺得：「好了，是時候讓大家看看它了。」

## 新技能：To Questionnaire

下一個，大概是我做過最無聊的技能名稱了，但我發現自己真的非常需要它，而且也意識到它的用途遠不只我原本設想的那樣。它叫做 To Questionnaire，用途是把一場 grilling（深度詰問）過程中做出的各項決策抽取出來，整理成一份文件，讓你可以帶著它和別人一起走一遍。

當時我正在做一場 wayfinder 會談，想在我家後院蓋一間花園辦公室，結果我發現，雖然是代理在對我進行詰問，但我真正需要討論的對象其實是我太太——畢竟，這個空間她顯然也會一起使用，所以我們應該要一起設計才對。於是，我讓代理把原本要在詰問過程中問我的那些內容，整理成一份 markdown 文件。接著我把這份文件放進 Google 文件，傳給我太太，我們一起一項一項討論過一遍，最後再把答案帶回去給代理。

這其實是一個我希望有朝一日能夠刪掉的技能，因為它某種程度上只是一個「補丁」，用來彌補目前代理在協作上還不夠順暢這個事實。我注意到有些團隊的做法相當不錯：他們把代理放進 Slack，平常的討論都在那邊進行，需要時再把代理標記（tag）進來。這樣一來，大家就能一起協作、一起回答問題，尤其是和利害關係人（stakeholder）討論時特別有用，然後代理也能直接加入進來，說：「好，我會照這個方向去實作。」

但現實是，很多人目前還沒有走到那種協作方式。很多人並不是「AI 原生」的工作型態，甚至可能連 Slack 或 Microsoft Teams 都沒有在用。所以，能夠把內容整理成一份文件，直接拿出來交給別人，讓對方可以在 Google 文件之類的平台上留言、提出意見，其實非常實用。
