最近我發表了不少關於 Claude Code 該怎麼用的內容，大多是從「理念」的角度切入。許多人認為這是一場全新的典範轉移，但事實上，我們過去 20 年來累積的那些做法，搭配 Claude Code 依然非常有效。當你把它當成團隊中可以放手委派工作的夥伴時，才能發揮最大的效益。換句話說，你要專注在架構上、確保擁有良好的回饋迴圈，也就是這 20 年來我們一直在做的事，例如不要在一開始就規劃過頭。

許多留言都在說：「給我們看點實際的，讓我們看你實際操作。」所以，這支影片就是為此而生。我不知道這支影片會有多長，也不確定到底會涵蓋哪些內容。我只打算直接在我工作用的儲存庫裡，用 Claude Code 做一些實際的工作，並一邊講解給你聽。我會展示我用到的所有技能（skills）與我的流程，盡可能完整地呈現這些工具在實務上是如何使用的。

如果你喜歡這些內容，我在幾週後會開設一門「給真正工程師的 Claude Code」群組課程（cohort），本週享有 4 折優惠。這門課要麼教你做真正的工程所需的技能，要麼提供轉換課程，讓你把既有的技能應用到這個新時代。如果聽起來不錯，連結就放在下方。

## 專案背景

首先，讓我們了解我所在的專案，以及它目前處於生命週期的哪個階段。

這是我的「課程影片管理器」（course video manager），大約有 1,200 個提交（commit），我已經關閉了約 637 個 issue。它是我處理所有內容創作工作的主要入口：我在這裡製作影片、整理課程、發布影片、編輯縮圖、撰寫文章。它真的是我完成工作所需的一站式服務，非常好用。

在技術上，它是一個 React Router 應用程式，使用 TypeScript 與 Node，資料庫 ORM 採用 Drizzle，資料庫是 Postgres，並大量使用 Vitest 進行測試。我並不部署它，只在本機執行：建構之後，用 start 指令啟動即可。

對我來說，製作這支影片有點令人混亂，因為我現在正在用「課程影片管理器」處理我正在錄製的這支影片。你可以看到，這裡就是我，以及從我正在錄製的影片中偵測出來的片段，上一個片段也在這裡。這確實有點繞，你懂我的意思吧？

主要檢視畫面如下：左側是課程，接著是課程裡的課堂（lesson）與章節（section）。我要展示的內容，就在這邊的「免費影片」之中。

## 功能構想

### 幽靈課堂與真實課堂

應用程式中有「幽靈課堂」（ghost lesson）與「真實課堂」（real lesson）的概念，你可以在篩選器上看到。幽靈課堂在磁碟上並不存在，我必須在課堂上按右鍵，選擇「在磁碟上建立」，才會真正在磁碟上的儲存庫中建立這個課堂。

這部分的邏輯相當複雜，因為我也可以把課堂轉回幽靈課堂，此時必須刪除檔案系統上的所有檔案，再把它轉回幽靈。這個設計的用意是讓我能在同一個 UI 中規劃並建立課程，用起來非常順手。

但我想新增一些強化功能：

- **直接建立真實課堂**：建立課堂時，不應該只能建立幽靈課堂，我應該可以直接新增真實課堂。
- **直接刪除真實課堂**：刪除真實課堂時，應該可以直接刪除，而不是得先把它轉成幽靈。

這個部分的程式碼測試得很完善，所以應該是相對簡單的建構。

### 幽靈課程

另一件我想做的事，是在上方新增課程時，能夠建立「幽靈課程」，也就是尚未存在於檔案系統上的課程。目前每個課程都必須在檔案系統中有對應的項目。

### 從模糊的想法開始

以上就是我的想法，需求非常鬆散。這或許就是大多數開發者日常工作的開頭：你需要對應用程式做一些小調整，依據的是一些模糊的想法。這些想法可能是你自己想出來的，也可能來自其他地方。而第一件要做的事，就是實際檢驗並強化這些想法。

## 第一步：用「Grill Me」釐清需求

我們先在 VS Code 中開啟專案，然後對 Claude 說「Grill me」（來拷問我吧）。我會使用語音輸入工具把想法口述進去：

> 我們處理幽靈課堂與真實課堂的方式，在某些地方有點繁瑣。我們必須先建立幽靈課堂，才能建立真實課堂，這很煩人。而且刪除真實課堂時，也無法直接刪除，必須先把它變成幽靈課堂。

說到這裡，我開始思考：「在這個工作階段中，我是否也要順便處理另一件事，也就是幽靈課程的概念？」我的決策空間是：這會不會排擠掉 Grill Me 的討論，還是兩者其實可以相當順暢地銜接？

因為這次 Grill Me 的目的，是從中產出一份文件，之後用它來進行後續的建構。所以我的決定是：我要建立一份同時涵蓋這兩件事的 PRD（產品需求文件），還是它們是各自獨立的關注點，需要拆成不同的 PRD？我決定這些東西其實屬於同一類。不過說實話，這個決定有點隨意。

我接著口述：

> 我也想擴充課程功能，讓我可以在沒有檔案路徑的情況下建立課程。這會是一種幽靈課程，也就是我尚未決定是否要實際建構的規劃中課程。

### 一定要說明「為什麼」

說到這裡，我發現第二段我還沒解釋「為什麼」。我解釋了我要這個功能做什麼，卻沒說明我為什麼需要這個功能。進入這類工作階段時，向 LLM 說明「為什麼」非常重要。因為如果 LLM 只知道「做什麼」，它雖然明白你想建構什麼，但如果不知道「為什麼」，它就無法提出替代方案。於是我補充：

> 我想要這個功能，是為了能自由地規劃課程，而不必先決定檔案系統上的確切結構。初始化新的儲存庫有點麻煩，我有時比較喜歡在「空白空間」中建構東西，而不必先確定實際的形狀。幽靈課程在限制上會稍有不同。幽靈課程可能必須……不對，我想幽靈課程也可以有真實課堂。只是一旦裡面有了真實課堂，它就會變成真實課程，這時就必須把它放進檔案系統。或者我不知道，我不確定這個流程該怎麼走，也許我們可以一起想想。

請注意，這段口述有多粗糙。這只是一個極度草率的構想，我就這樣一股腦丟給 LLM，讓它去做所有的工作。

如果你還沒看過我的 Grill Me 技能，我會把連結放在下方，它收錄在我的「前五大技能」文章中，你可以看看它做了什麼。它真的很酷。

### 補充：什麼是 Explore？

接著，它會進入「探索」（explore）階段，我趁機去倒杯水。順帶一提，如果你不知道 explore 是什麼：它基本上是呼叫一個子代理程式（sub-agent），也就是向另一個代理程式傳遞一則訊息，請它去探索這個程式碼庫。該代理程式會在自己的內容視窗（context window）中進行探索，然後將探索內容整理成摘要，交還給上層的代理程式。

因此，explore 階段可以發揮很大的效益：探索代理程式可以「砰砰砰砰砰」地讀取大量檔案，而上層代理程式只會收到摘要，所以非常節省 token。不過我先去倒水了。

### Grill Me 開始提問

好，Grill Me 回來了，它說：「讓我挑戰你對目前痛點的描述。」

它指出，查看程式碼後發現，`course write service` 中的刪除課堂功能，已經能直接處理幽靈課堂與真實課堂：如果是真實課堂，它會刪除目錄並重新編號；如果是幽靈課堂，則只會移除資料庫中的資料列。所以，你其實可以不先轉成幽靈就直接刪除真實課堂。它問：UI 中是否有什麼東西強制採用「先轉成幽靈再刪除」的流程？

沒錯，確實有：UI 上沒有立即刪除課堂的選項。而我所謂「刪除真實課堂」，指的是同時刪除資料庫中的項目，並清除磁碟上的實體內容。

## 通用語言（Ubiquitous Language）

趁著它處理的時候，我來介紹一件我最近才開始做、而且非常酷的事。我最近在讀《領域驅動設計》（Domain-Driven Design）這本書，書中談到，維護一份描述系統的所有術語的「詞彙表」是多麼重要。這種「通用語言」可以用來彌合開發者與領域專家（也就是你實際為其開發的對象）之間的鴻溝。

我很喜歡這個概念，因為這正是 LLM 與我之間所需要的：我是領域專家，LLM 是開發者，我們需要某種共用的語言，才能精確地交談。舉例來說，我們有「幽靈課堂」這個概念：存在於資料庫中，但尚未存在於檔案系統上的課堂。因此，每當 LLM 在搜尋與幽靈課堂相關的內容時，就會讀到這份通用語言檔案。

### 用 `/btw` 快速提問

它回來了，說：「是的，UI 目前只對真實課堂提供『轉成幽靈』的選項，而沒有直接完全刪除的選項。這是個很直接的 UI 缺口。」好，這很有用。

讓我們快速談談它所用的 service，以及這在我的程式碼庫中實際代表什麼。我想試試新的「順帶一提」（by the way）功能。當你只想問個簡單的問題，又不希望它進入對話歷史紀錄時，這非常好用。我問：

> 描述一下 course write service 的概況，描述它的形狀與能力。

我之所以問這個並展示給你看，是因為我對這個儲存庫的設計方式相當自豪。當然，裡面肯定有需要再檢視的地方，但我認為這個 service 的做法相當不錯。

回覆是：course write service 是變更課程資料的主要商業邏輯層，也就是系統的「寫入端」。它協調資料庫、檔案系統，以及路徑編號與重新編號的邏輯。它有一個非常清楚的介面，例如：你可以新增幽靈課堂、將幽靈實體化（materialize，即把幽靈課堂轉成真實課堂）、再把它轉回幽靈、刪除課堂等等。所以這是一大塊功能。

這個 course write service 的測試都集中在同一個地方。咦，原本在 `course-write-service.test.ts`，現在不在了，它們在這裡，`course-write-e2e.test.ts`。這些測試會建立測試資料庫、設定暫時的 Git 儲存庫，並測試兩者之間的所有同步行為。

這個儲存庫使用 Effect，而 Effect 讓你能在系統中非常輕鬆地建立這類容易測試的單元。其他語言將這點視為一等公民，但 Effect 以非常優雅的方式把這項能力「外掛」到 TypeScript 之上。我曾在這個頻道製作過一支關於 Effect 的影片（就只有一支），總之我依然非常喜愛它，幾乎所有事情都用它來做，至少我建構的每個後端都是用 Effect。

至於這個龐大的 service，它就放在 DB function service 中：它是一個檔案，裡面基本上有一堆方法，例如 materialize ghost、add ghost section、add ghost lesson、delete lesson 等等。我們談到這個 service 時，指的就是這些。

接著，我只要按空白鍵、Enter 或 Esc，就能離開這個「順帶一提」的畫面，回到原本的對話。

### 持續被追問

回到對話，它問了一個很好的問題：「你實際想要的流程是什麼？你是想要一個建立課堂的動作，直接在磁碟上建立目錄，完全跳過中間那一步嗎？還是說，真正的痛點在於『先建立幽靈、再實體化』這兩步驟的流程，在你已經確定想要真實課堂時，顯得是不必要的繁文縟節？」

對，沒錯，兩步驟的流程確實不必要。它回應：「好，所以你想要一個單一的建立課堂動作，在你已經確定它是真實課堂時，一次同時建立資料庫實體與磁碟上的目錄。」沒錯。

接著，它轉到更大的主題：幽靈課程。它說：「你說了一件有趣的事，但立刻又猶豫了：幽靈課程可以有真實課堂，一旦有了，它們就會變成真實課程，你就必須把它放進檔案系統。讓我把這拆開來看。第一個問題：幽靈課程沒有檔案路徑，所以沒有 Git 儲存庫。其中的章節與課堂必然都是幽靈，因為沒有辦法把它們放到磁碟上。當你說幽靈課程可以有真實課堂時，在沒有檔案系統的情況下，『真實』是什麼意思？」

這裡它所做的，是把我含糊的措辭具體化，迫使我說得更明確。這個問題我很容易回答：我不想要某種介於兩者之間的狀態，比幽靈「更充實一點」的狀態（這說法真棒）。顯然答案是選項 A：在幽靈課程中新增真實課堂，就是觸發「必須指定檔案路徑並將課程實體化」的契機。

### UI 流程的取捨

這時我已經在從 UI 的角度思考：什麼是最容易、或者說對使用者而言最明顯、最乾淨的 UI？有兩種做法：

1. 在幽靈課程中建立真實課堂時，直接說「不行，你得先選一個磁碟上的位置，然後再點擊離開」。
2. 建立一個整合的流程：「你要把它寫入磁碟了。第一次在幽靈課程中這麼做時，你需要選擇它要存放的位置。」

我傾向第二種，因為在 UI 上要做到並不複雜，而且我認為流程會比較順暢。所以我就這樣告訴它：我們選 A，並且我覺得合理的做法是：當你按下「轉換」或「在檔案系統中顯示」之類的按鈕，無論那個按鈕叫什麼，只要你將它實體化……

請注意，這裡就是通用語言派上用場的地方。我剛才說得有點含糊，但我想表達的是：當你把幽靈課堂實體化時，應該跳出一個強制你同時將課程也實體化的彈出視窗。看看這種說法乾淨多少，因為我與 LLM 對「實體化」這個詞已有共識。

### 課程版本

接著，應用程式中有「版本」的概念，也就是課程版本。這對我很重要，因為我有一個團隊負責把課程套用到 CMS，所以我有課程與變更紀錄（change log）。例如在我的 Claude Code 群組課程中就有好幾個版本。我越接近開課，就越常在修 bug 或抽換影片。最新的版本永遠是草稿版本，我可以發布該草稿版本並附上提交訊息，它就會進入變更紀錄。這裡就是發布新版本的 UI，以及變更紀錄的預覽。

我很確定我們依賴的結構描述（schema）需要讓幽靈課程仍然有版本，因為章節與課堂等內容需要版本才能存放。但是，發布幽靈版本毫無意義，所以我們應該隱藏選單中允許發布的 UI 與動作。好，就這樣送出。

從我的影片編輯器可以看到，我們已經進行了大約 15 分鐘，請注意我們花了多少時間在充實這些想法上。我們在這裡做得越多，之後實際引導 LLM 時需要做的就越少。

### 檔案指派的時機

它接著追問：「讓我針對檔案指派的時機再深入一點。當你因為要實體化其中的課堂而實體化幽靈課程時，你需要給它一個檔案路徑。這個儲存庫可能已經存在，也可能還不存在。當你為幽靈課程指派檔案路徑時，應用程式應該幫你建立儲存庫嗎？」

不，它不應該處理儲存庫的建立，它只是指向一個已存在的目錄。這個問題很容易回答。

這是一個非常聰明的好問題。它整理出你的需求：真實課堂的直接刪除、真實課堂的直接建立、幽靈課程，以及在幽靈課程中實體化課堂。接著它問：「直接建立也適用於幽靈課程內部嗎？」這真是太聰明了，這問題問得真好。我可以想像我以前的老闆 Willow Reagan 會問這種問題，我從他那裡學到了很多主任開發者的本領。他有種驚人的能力，能夠坐在會議室裡連續好幾個小時不斷提出聰明的問題。而 AI 在這裡做的正是這件事：在流程中的正確時機，提出非常聰明的問題。

它問：如果你在幽靈課程內按下建立課堂，應該立即觸發「指派檔案路徑」的彈出視窗並在磁碟上建立嗎？這裡同樣存在取捨。與其在自己腦中思考（看起來並不怎麼好看），不如和 LLM 一起把它推演出來。我問：「你能給我這兩種做法的取捨嗎？」

它回答：

- **選項 A**：在幽靈課程中建立課堂，一律只建立幽靈課堂。這讓幽靈課程維持純粹的規劃空間。「指派檔案路徑」的時刻，只會在你明確選擇實體化時發生，那是一個明確、刻意的動作。缺點是：如果你已經決定這個課程是真實的，只是要新增課堂，你又回到了你想解決的兩步驟麻煩。
- **選項 B**：在幽靈課程中建立課堂，會觸發實體化串聯（materialization cascade）。

它認為，依據你所陳述的目標，選項 A 是顯而易見的選擇：你描述的兩步驟麻煩，具體而言是針對檔案系統已存在、而你想要真實課堂的真實課程。

我大致同意。如果我們要一致的 UI，就會希望無論課程處於哪個階段（真實或幽靈），都能同時建立真實課堂與幽靈課堂。這意味著前端的工作會少一些，因為我們不需要有條件地顯示東西。這樣合理，選項 A 聽起來不錯。我認為它大多在這種情況下才合理：有兩個按鈕，一個建立真實課堂，一個建立幽靈課堂。

### 與 AI 輪流主導

我接著問：「你能帶我稍微看看 UI，以及這會是什麼樣子嗎？」請注意，我現在稍微在主導對話。這也沒關係，這種方式的好處在於夠靈活：有時我主導，有時 AI 主導。

它先去檢查目前建立課堂的 UI。這是這個技能的一部分：與其對所有事情都向我提問，如果有些問題能透過查看程式碼來回答，它就應該先看程式碼。我真希望 explore 能更快一點。Explore 是每個工作階段都需要的東西，有時一個工作階段還要好幾次，我真希望它能更快。

好，目前 UI 的運作方式是這樣：在章節標題上按右鍵可以新增課堂；在既有課堂上按右鍵，可以選擇在前面或後面新增課堂，同樣只會建立幽靈。在真實課程中，右鍵點擊章節會看到「新增幽靈課堂」與「新增課堂」。在幽靈課程中，右鍵點擊章節只會看到「新增幽靈課堂」。所以問題來了：在幽靈課程中，你是否想要有「建立真實課堂」的按鈕？

說實話，我也不知道。我想像這個 UI 會變得相當擁擠，因為會有多個按鈕：例如「在這個之前新增課堂」，然後還要選擇是幽靈還是真實？天啊，這其實相當棘手。我在想，我是否真的該做個原型，才能看看它長什麼樣子？因為有很多種方式可以調整並做到好用。你可以做成「新增課堂」之後開啟彈出視窗，讓你選擇它是幽靈課堂還是真實課堂。

我想我大概會先用其中一種方式建出來，之後再給回饋。所以我回答：是的，在幽靈課程中也要有「建立真實課堂」按鈕。我其實可以停止整個 Grill 流程，進入原型製作模式，做三種或五種不同版本，看看 UI 長什麼樣子，但我現在比較想直接進入實作。

### 收斂細節

它接著確認：在幽靈課程中建立真實課堂，會觸發完整的串聯：彈出視窗詢問檔案路徑、課程變成真實、章節實體化、課堂在磁碟上建立，全部在同一個流程中完成。沒錯。這個彈出視窗做了很多事，是的，它需要取得課堂標題與課程檔案路徑，就這樣，只需要課堂標題與課程檔案路徑。我感覺得到我們快要結束這場拷問了。啊，也許還沒。

它接著問到章節的行為：幽靈課程中的章節。章節的狀態基本上是從課堂推導出來的：如果章節內有任何真實課堂，那它就是磁碟上的真實章節。章節基本上就是磁碟上的一個目錄，你可以重新命名它（連同重新命名目錄），也可以往裡面新增東西，大概就是這樣。章節邏輯應遵循我們目前已有的規則，章節本身沒有什麼新東西。例如，當我們在幽靈課程中的某個章節內建立真實課堂時，就會一路向上串聯：它成為真實章節、真實課堂，以及真實課程。

接著它談到資料庫結構描述：目前 courses 資料表中，檔案路徑是必填的文字欄位。對於幽靈課程，這需要改成可為 null。這是我預想的唯一結構描述變更。好，我就回答「是」。

### 棘手的邊界情況

接著它拋出一個棘手的邊界情況：假設有一個有檔案路徑的真實課程，裡面有一些真實課堂與一些幽靈課堂。如果你刪除所有真實課堂，或將它們全部轉成幽靈，這個真實課程會變成幽靈課程嗎？這又是一個典型的 Willow Reagan 式問題，非常棒。

答案是：不會。真實課程不會變成幽靈課程。一旦課程有了檔案路徑，它就永遠是真實的，因為磁碟上的東西不會憑空消失。我之前就在想這件事，所以很高興它問了，因為現在這個答案已經寫進內容脈絡中了。

它又問另一個邊界情況：你有一個幽靈課程，實體化了一個課堂、指派了檔案路徑，一切都變成真實，這時課程有檔案路徑但沒有真實課堂。我覺得我們剛剛才回答過了，對吧？這個問題有點怪，我不認為 Willow Reagan 會問這種問題。

然後它轉到刪除面：你想要在 UI 中對真實課堂提供直接刪除動作。目前真實課堂的右鍵選單顯示「轉成幽靈」但沒有刪除。這是 UI 的事。真實課堂應該兩個選項都有嗎：轉成幽靈與刪除？我想我們兩者都需要。

### 確認完整範疇

它說：「好，我們快到了。我想我已涵蓋主要的分支。讓我列出我所理解的完整範疇，請告訴我是否有遺漏。」

1. 課程的檔案路徑改為可為 null。
2. 幽靈課程建立：全新的課程建立流程，只詢問名稱，不需要檔案路徑。（正確）
3. 幽靈課程 UI：隱藏發布與匯出動作。（正確）
4. 「建立真實課堂」按鈕在真實課程與幽靈課程中都可使用。在真實課程中，會立即在磁碟上建立；在幽靈課程中，則會觸發彈出視窗，先詢問檔案路徑，再串聯實體化。（看起來不錯）
5. 「建立幽靈課堂」維持現狀，隨處可用。
6. 真實課堂的刪除動作：一個步驟內同時從磁碟與資料庫清除。（是的）
7. 幽靈課堂的刪除動作：已存在，維持不變。
8. 「轉成幽靈」保留給那些想繼續規劃但要從磁碟移除的真實課堂。（完全正確）

就這樣，這八個要點，我們花了整整 22 分鐘的影片才得出來。這對我來說非常熟悉，這就是我經常與 AI 合作的方式：我會在行事曆上預留半小時，把我想要的功能確切地想清楚，之後的一切幾乎都「上軌道」了。困難的部分已經完成，也就是「人在迴圈中」（human in the loop）的部分。

## 更新通用語言文件

接下來，我會做一件這幾天一直在嘗試的事：讓它更新我的通用語言文件，使其與我們這裡討論出的任何想法保持同步。例如，我們現在有了新的術語，像是「幽靈課程」這個新概念。我們來看看它決定怎麼修改。其實我直接接受，之後再檢視。

好，我們可以看到它更新了對「幽靈實體」的理解，包含幽靈課堂、幽靈章節與幽靈課程。動詞「實體化」（materialize）現在也正確地收錄了：將幽靈實體轉換為真實實體，並建立其磁碟上的表示。我也喜歡它列出了「應避免的別名」，例如 create on disk（在磁碟上建立）與 realize（實現），非常棒。它甚至有「實體化串聯」的概念：在幽靈課程內實體化課堂時的連鎖反應，即指派檔案路徑給課程、實體化章節，然後實體化課堂。

我真的超愛這一點，因為之後我可以說：「實體化串聯裡面有個 bug。」而它就會確切知道我在說什麼。接著我提交（commit）這個通用語言文件的更新。看吧，有時候我確實會自己提交程式碼。

### 處理過時的概念

好，它回到了拷問。它現在基本上重述了那八個要點，並問到：現有的「plan」（規劃）實體是一個獨立、未連結的規劃工具。對，我以前確實有個獨立的規劃區，但後來我用幽靈的概念，把它整合進我真正的課程功能中。通用語言文件裡這邊往下還有 plan、plan section 與 plan lesson，但這基本上已被棄用，我之後會移除。所以我們可以說：「plans 已棄用，幽靈課程才是新的做法。」

事實上，我想我可以說我滿意了。

## 第二步：撰寫 PRD

接著我會呼叫下一個技能：「write a PRD」（撰寫 PRD）。想想我們剛剛與 LLM 的那場對話，它是極佳的素材，可以把它轉成一份更精簡的摘要文件，涵蓋我們想建構的一切。

### 為什麼問答格式如此有效

我真的很愛「問與答」的格式，因為它把問題與答案放在一起。我知道這聽起來是很基本的說法，但注意力機制的運作方式，是讓彼此靠近的內容，對 LLM 而言往往會成為注意力的「熱點」，就像對人類一樣。這意味著，這是一份讓它能深入查閱的非常豐富的文件。

它現在又做了一次 explore 階段。我們應該快速檢查一下下方的內容視窗：目前只用了約 4 萬個 token，考慮到我們與 LLM 花了這麼長的時間，這相當令人驚艷。

### 為什麼不用 AskUserQuestion 工具

很多人問我，為什麼我的 Grill Me 技能不使用「ask user question」工具，也就是我們並沒有使用 Claude 內建的提問機制。原因是：首先，我不太喜歡那個 UI；其次，如果你可以選擇呼叫工具或不呼叫工具，不呼叫工具永遠比較節省 token，因為每次呼叫工具，你都必須把它包在 JSON 裡，並做各種處理。

### 先勾勒模組，再寫 PRD

好的，我們看到它在寫 PRD 之前，先勾勒出主要的模組。我以前在這個頻道談過，我認為「模組」有多重要，也就是在不需要深入查看內部的情況下，理解程式碼庫中的各個模組。像我們之前看過的 course write service，就是一個大型、可測試的模組，我在設計它與它的介面時非常謹慎。我認為這點太重要了，所以我把它內建在我的 write a PRD 技能中：它會勾勒出模組並呈現給你。我不一定需要查看這些模組內部，我只想知道它們有什麼變化。

例如，我在這裡看到一個有點可疑的地方：它想在 course write service 上建立一個新方法「materialize course and lesson」（實體化課程與課堂），內部重用既有的「實體化幽靈」與章節實體化邏輯。我在想，它能不能改用既有的 materialize ghost，再傳入一個額外參數？但我認為那樣在 API 設計上會有點不妥。所以我想它可能是對的，應該有個新方法。請注意，我思考的是介面，而不是實作。實作我並不太在意，但我想確保它是可測試的，並且儲存庫的其他部分與未來的任何 AI 代理程式都能理解它在做什麼。

再次請注意，有了通用語言之後，這些函式有多容易命名。

接下來是各模組：

1. **幽靈課程結構描述與資料庫操作**：看起來沒問題。
2. **實體化串聯 service**：看起來沒問題，只是 course write service 上的一個新方法。
3. **兩個新的 API 路由**：合理，因為我們要做直接建立真實課堂與直接刪除真實課堂。我也可以把它們放進其他 API 路由，但由於這只是內部工具，我並不在乎 API 對外長什麼樣子，所以我不在意有多少路由或它們長什麼樣，那只是實作細節。
4. **幽靈課程 UI**：側邊欄新增「新增幽靈課程」選項，沒問題。
5. **實體化模型**：右鍵選單中的兩個課堂建立按鈕，以及刪除動作。
6. **棄用 plans**：嗯，我確實想在某個時間點棄用 plans，但我不想現在就做，當然也不該是這份 PRD 的一部分。

### 要為哪些模組寫測試

它接著問了第二個問題：你想為哪些模組撰寫測試？我說，我想在既有測試框架已存在的地方撰寫測試。所以 course write service 當然要，而直接刪除的部分，我想也是 course write service 的一部分，對吧？

接著很好笑：它說 course write service 沒有現成的測試框架，儲存庫中的測試大多是針對純函式與 reducer。這是胡說。所以我要學 Rafiki（《獅子王》裡的角色）那樣說：「再找仔細一點。」然後，找到了，一整套依關注點分類的測試都在那裡。

### 以 GitHub Issue 發布 PRD

好，它滿意了，已經取得所需的一切。接著它會撰寫 PRD，並以 GitHub issue 的形式提交。這是我處理 PRD 的方式，也是我處理所有 issue 的方式：我把它們放在 GitHub 上，因為當我們用 AFK 代理程式（AFK agent，即「人不在鍵盤前」的代理程式）實際實作時，AFK 代理程式會拉下所有 GitHub issue，選擇其中一個來處理，然後只處理那一個。

那麼問題來了：我會審閱這份 PRD 嗎？不會。LLM 非常擅長摘要，所以我知道這份 PRD 大概會是這場對話的一份相當好的摘要。因此我選擇相信它，直接接受，然後說：「PRD to issues」（將 PRD 轉成 issues）。

## 第三步：將 PRD 拆分為 Issue

現在是時候把 PRD 拆成一個個獨立的 issue 了。這樣做的好處是：PRD 因為剛寫完，已經在它的內容脈絡中，所以我們可以直接從那裡拆解 issue。這些 issue 之間有阻擋關係（blocking relationship）：這個不被任何東西阻擋，那個被第 1 號阻擋，另一個也不被任何東西阻擋，很好。

### 切片大小的拿捏

我們來看看有多少個。六個感覺差不多。我的意思是，這些 issue 會被 Ralph 迴圈（Ralph loop）撿起來，依序逐一處理這些任務。所以我想挑選不太大也不太小的任務：如果太小，我們就得為了像第 2 號「在幽靈課程中隱藏發布與匯出 UI」這種微小任務，付出啟動整個代理程式的成本，這種任務可以和其他任務合併。

至於「幽靈課程建立」，大小似乎還不錯，因為它涉及 UI、結構描述與 API。至於兩個課堂建立按鈕（建立幽靈課堂與建立真實課堂），看起來非常小，我覺得它拆得有點太細了，但實體化串聯可能要獨立成一項。所以我想我們把 2 和 3 合併，應該就會滿意了。我們在底部輸入：「merge two and three together」（合併 2 和 3）。

好，現在有四個切片：課程建立、UI 相關、直接刪除動作，以及實體化串聯。很好，我們來建立這些 issue。

我會審閱這些 issue 嗎？絕對不會。我已經事先審閱過了，它只是把 PRD 中的內容展開，再放進 issue 裡，不會有問題。

### Issue 長什麼樣子

我只展示其中一個，讓你看看它們的樣子：它會連結到上層的 PRD、明確說明要建構什麼、給出一些驗收條件（acceptance criteria）、說明被什麼阻擋，並列出上層 PRD 中對應的使用者故事（user stories）。如果說上層 PRD 是目的地，那麼這些 issue 就是通往目的地的旅程。

另外請注意，PRD 本身有一堆使用者故事、一些實作決策，以及測試決策。這一切基本上都來自我組合出來的技能，我發現它們已足以讓 LLM 保持在軌道上。我特別喜歡加入測試決策，因為這會讓它更有可能遵循 TDD（測試驅動開發），並在過程中建立一些回饋迴圈，這很棒。

## 第四步：讓 AFK 代理程式實作

好了，我們已經把一切都準備好了，讓 AFK 代理程式有最大的機會產出好的成果。

### Sandcastle 與 Ralph 迴圈

過去 24 小時，我一直在調整我的設定，並建了一個小型函式庫，讓它運作得比以前更好。暫定名稱叫做 **Sandcastle**。這裡有一個 Dockerfile，它會啟動一個 Docker 容器，把工作目錄掛載到這個容器中。Claude 會在容器內執行，在容器中所做的任何提交，之後都會被擷取成修補檔（patch），再套用回我的本機儲存庫。

我發現這個設定極為靈活。我有一個 Dockerfile 與一份提示詞，就能一次又一次地執行 Ralph 迴圈，傳入一批 issue，以及最近 X 個提交。你可以到儲存庫查看這個檔案的最新版本。

我要執行的指令，我想是 `pnpm ralph`。這會啟動我的 AFK 代理程式，最大迭代次數為 100。它應該會在 GitHub issue 用完時停止，因為它每為一個 issue 建立提交，就會關閉該 issue。但此時，我基本上就可以離開了：你可以看到它正在終端機裡做事，說它正在查看 issue，例如「直接刪除的動作給 Ralph」等等。而我可以去喝杯茶、泡杯咖啡，或吃午餐。更有可能的是，我會再開另一個終端機，進入另一場拷問工作階段。

### 日班與夜班

對於那些說這個方法看起來非常慢的人，你需要明白：它之所以慢，是因為你要從人腦中提取想法。而當這件事在進行時，你有 AFK 代理程式在背景實作你先前拷問工作階段的成果。這就是它具有革命性的原因：一旦我們完成了想法的思考，我們的工作基本上就結束了，直到我們實際對產出進行 QA（品質保證）為止。

我在 Twitter 上的朋友 Jaman 稱之為「日班與夜班」：我做日班，思考想法、與 LLM 拷問、把它們變成 PRD，再把 PRD 變成 issue；然後 LLM 接夜班，Claude 去實際以 AFK 方式實作這些東西。

所以我要休息一下，也許去散個步，等它完成後再回來看看。

我們可以看到，代理程式在五次迭代後發出了完成訊號。也就是說，我們在儲存庫中基本上執行了五次全新的 Claude Code 代理程式，它應該為我們產出了六個提交。其中一個可能是我還沒推送的提交。我們可以看到完整的提交歷史，它留下了非常詳細的提交訊息。

## 第五步：QA 與回饋迴圈

### 產生 QA 計畫

此時，我需要回頭檢視這些提交。我雖然很想看程式碼，但我想先審視實作成果。我會開啟新的 Claude 工作階段，而我還沒為此想出一個技能，所以我就隨興地輸入：

> 取最近五個提交，為我建立一份 QA 計畫。把這份 QA 計畫存成 GitHub issue。QA 計畫應該提供逐步指南，教我如何測試新實作的每一個部分。

我一直在考慮把這個加進我的技能裡，因為我認為幾乎每個面向使用者的變更都適用。在它處理的同時，我會重新建構並在本機重新執行應用程式，讓我們能確實看到實際情況。

好，它為我們建立了 QA 計畫，太棒了。不過我必須說，沒有什麼比看著別人做 QA 更無聊的了。所以我會自己走完整個流程，若有任何問題再回來向你報告。

### 回饋按鈕：我的 QA 方式

第一個問題出現得非常早：按下「新增課程」彈出視窗時，我看到裡面有兩個分頁。我其實很討厭這樣。我只想要：每次新增課程，一律建立幽靈課程，而且我不喜歡「幽靈課程」這個術語出現在 UI 中。

所以我先退出，我有一個小小的「回饋」按鈕，只要我把自己移開就能看到。我可以透過這個回饋按鈕詳細描述我的回饋，它就會為我建立一個 GitHub issue，之後就能被 Ralph 迴圈撿起來處理。我說：

> 當我開啟新增課程彈出視窗時，我希望唯一的選項就是新增幽靈課程。而且我不希望「幽靈課程」出現在 UI 中。它看起來應該就是在建立課程，然後在背後建立幽靈課程。

送出之後，到 GitHub issue 頁面，我們可以看到新增了一個 issue：「隱藏新增課程彈出視窗中的幽靈課程選項，並靜默建立幽靈課程」。這裡我用了 Haiku 來產生標題，接著是它送出時所在的路由，然後是我在回饋按鈕中所說的內容。這就是我做 QA 的方式。這些資訊足以讓 Ralph 把事情做得很好。

所以我一邊進行，一邊啟動我的 Ralph 迴圈。我回到 QA 計畫，在上面加一則留言：「Ralph 迴圈不該處理這一個，這是一項只能由人工參與的任務。」其實，我直接把第一個重新命名為 AFK 就好。我在我的提示詞中寫了一條規則：如果它帶有「human in the loop」之類的標籤，或看起來是給人類處理的，就不要去處理。所以我們回到這裡，再次執行 `pnpm ralph`，它就會在我 QA 其他東西的同時處理這個 issue。我回去做一點 QA，待會見。

### 持續發現問題

好，新的狀況：當我建立一個幽靈課程，例如取名「new fun course」，按下「建立幽靈課程」時，似乎什麼也沒發生。但實際上你可以在左上角看到，首先，我們看到一個奇怪的、被壓縮過的 React 錯誤，我會把它複製下來，稍後貼到回饋表單。課程確實有建立，但我們沒有被導向該課程，彈出視窗也沒有關閉。

所以我們把這點加回回饋：「當我建立幽靈課程時，它沒有把我導向新頁面，並顯示這個錯誤。此外，按鈕上沒有載入狀態，從使用者的角度看很令人困惑。」我們再次送出。

先前為了修復前一個 bug 而啟動的代理程式其實已經完成了，所以我再次啟動它，並繼續進行 QA。這次我不會中斷它，只會繼續走完這些 issue，並讓 Ralph 在背景嘗試修復它們。

### 有些設計得看到實物才知道

好，這一個我覺得值得展示。當我在幽靈課程中新增幽靈章節，並在這裡按右鍵時，「建立幽靈課堂」與「建立真實課堂」的選項讓我覺得不太對。我覺得進入「建立幽靈課堂」時，我只想要一個「新增課堂」之類的東西。我們這裡本來就有彈出視窗，我們應該做的是加一個核取方塊，寫著「同時在檔案系統上建立」。

這是我們在這個功能的早期討論中遇到的問題：在真正看到實物之前，我始終無法判斷該往哪個方向走。事情有時就是這樣。我們本可以多一個設計階段，或多一個原型階段，但我其實不介意直接跳進程式碼，在那裡修正。所以我會為這點加上回饋，但就不讓你聽我的口述了。

### 六個 issue，Ralph 在背景處理

好，我已經走完整個 QA 計畫，在這 8 分鐘內建立了六個 issue（或說七個）。我們可以看到，在我進行 QA 的同時，Ralph 一直在背景運作並修復這些 issue。其中大多數是 bug，但有些是我們沒想到的功能。例如，刪除真實課堂時，我們想加上確認彈出視窗，以免不小心點到就直接刪除了。

當然也有一些致命的 bug。例如，如果它不是 Git 儲存庫，就會進入非常奇怪的狀態。是的，如果課程儲存庫不是 Git 儲存庫，且其中任何相關操作失敗，我們就應該回滾（walk back）在其中建立的目錄，因為目錄、檔案系統與資料庫會因此不同步。這又是我們一開始 Grill Me 階段沒有想到的事，所以現在只能在 QA 中發現。

正是這類事情，讓我認為「規格轉程式碼」（specs to code）的做法永遠行不通：因為當你身處其中、處於 QA 迴圈、一步步朝目標迭代時，你一定會發現這類很難事先規劃到的奇怪邊界情況。好，抱怨結束。

重點是，我現在多做了一道 QA 步驟。Ralph 接下來會逐一處理這些 issue。我大概可以關閉這份 QA 計畫了，如果我想重做，也許會重新開啟它，但由於行為已經稍有改變，所以我先關閉它，把它從代理程式的內容脈絡中移除，以免它把這份計畫當作「應建構內容」的真實依據。總之，我先去做別的事，等 Ralph 回來再看看結果。

### Ralph 完成工作

好，我們回來了，現在是第八次迭代，幾乎完成了。看起來是最後一個 issue，也就是在刪除真實課堂時，加入含檔案詳細資料的確認彈出視窗。我們可以看到，在整個功能建構過程中，已經累積了 14 個提交，而這些 issue 也幾乎都關閉了。你可以看到我上次開啟這個是 30 分鐘前，這大概就是它執行的時間。

我想加入的一件事，是把這些 Ralph 迴圈平行化，讓一個代理程式團隊同時處理。不過老實說，有這些空檔其實很不錯，因為這表示我能對某件事進行深度專注（例如讓它對我拷問另一個主題），之後再回到程式碼進行一次大規模 QA，再送出去，你懂的。

這些 Ralph 迴圈成功的關鍵之一，是確保每次提交都會執行測試與型別檢查。我們可以看到，大多數迴圈中它也都有新增測試，例如更新 reducer 測試以涵蓋新的動作。現在它正在提交並關閉 issue，所以應該快好了。好，完成了。

### 最後驗證

我會重新執行建構，再做一點 QA。我就不為你展示額外的 QA 步驟了，但簡單來說，從這一刻起，我會回到這裡繼續 QA、找出更多 bug，並在某個時間點宣告完成，然後停止這項工作。

這種彈性的待辦清單（backlog）做法有個很棒的地方：任何時候我都能排入一批 bug 修復，它就會進去修復它們。

我們來確認一件事：新增課堂現在不再顯示「幽靈課堂」與「真實課堂」了，而是有一個小核取方塊寫著「在檔案系統上建立」。如果我輸入 foobar 並勾選「在檔案系統上建立」，它就會新增課堂，完成後我們應該就能看到。這個有點慢，對吧？我很好奇為什麼這麼慢，尤其這一切都在本機執行。現在它應該完成了，並把 foobar 建立成第二個課堂。這樣就完成了。依我的估算（不完全準確），影片到這裡大約是第 42 分鐘。
