# 使用 /grill-me 與 /grill-with-docs 時，人們常犯的 9 個錯誤

`/grill-with-docs` 技能已成為代理程式工作流程中取代規劃模式的熱門選擇。然而，許多人在有效運用它時遇到困難。這個技能的運作方式，是不斷地向你提問，直到雙方達成共識，但**這需要你自己具備良好的規劃能力**。

這些技能並非要取代工程師，而是要輔助你。本指南的目標，是透過了解最常見的九種失敗模式，幫助你熟練掌握它們。

## 理解問題：低擬真度 vs 高擬真度

進入拷問（grilling）環節時，你的目標是回答有關你即將建構之事物的問題。但並非所有問題都生而平等。

![不同擬真度問題的示意圖](https://res.cloudinary.com/total-typescript/image/upload/v1779715889/ai-hero-images/qkcmn8yccs0rrbu5og3k.png)

| 問題類型          | 定義                                                   | 範例                               | 可拷問？ |
| ----------------- | ------------------------------------------------------ | ---------------------------------- | -------- |
| **低擬真度**      | 不需要詳細原型或圖像就能回答的問題                     | 「這個路由應該放在哪個 URL 上？」  | ✓ 可以   |
| **高擬真度**      | 需要放大細節的圖像或原型才能回答的問題                 | 「我們在使用這個 UI 時應該有什麼感覺？」 | ✗ 不行   |

表單欄位的版面配置就是高擬真度問題的好例子。你應該將表單欄位拆分到多個頁面，還是使用一個超大的表單？你真的需要看到原型，或是把整個東西建構出來，才能妥善回答。

### 處理無法拷問的問題

第一個主要的失敗模式，就是在拷問環節中試圖回答高擬真度問題。

當你遇到無法拷問的問題，也就是需要更高擬真度才能理解的問題時，請使用**交接（handoff）**模式：

1. 在第一個工作階段（藍色工作階段）中，持續拷問低擬真度問題
2. 當你遇到高擬真度問題時，交接到原型製作工作階段
3. 在那個獨立的工作階段中建構或製作原型，以便更清楚地理解該問題
4. 再交接回原本的拷問工作階段，繼續處理可拷問的問題

這個模式看起來像是：**拷問 → 原型 → 再次拷問**。它讓你能夠回答高擬真度問題，同時不打斷拷問的節奏。

![顯示拷問與原型製作工作階段之間交接模式的圖表](https://res.cloudinary.com/total-typescript/image/upload/v1779715889/ai-hero-images/dkks1wlw7mkpjr0slii2.png)

## 選擇正確的範圍

範圍，也就是你所拷問事物的規模，絕對至關重要。

如果你的範圍太大，會出現兩個問題：

**問題 1：隱藏的高擬真度問題**
在已知可行的基礎上繼續建構，永遠比無止盡地規劃未來來得容易。當人們試圖為 AI 排定好幾天的工作任務時，往往成果不佳，因為他們並不是建立在自己所理解的穩固基礎之上。

**問題 2：上下文視窗限制**
你可能一開始上下文視窗幾乎是空的，但隨著不斷拷問下去，你會碰到模型的「笨蛋區」，對大多數最先進的模型來說大約是 120k 個 token。一旦超過這個門檻，模型的注意力關聯就會變得吃緊，並開始做出較差的決策。

![顯示上下文視窗逐漸填滿並進入笨蛋區的圖示](https://res.cloudinary.com/total-typescript/image/upload/v1779715890/ai-hero-images/yxo684qm8iwlvyx18ip1.png)

### 拆解大範圍

與其對單一龐大的範圍進行拷問，不如一開始就請代理程式將它拆解：

1. 從一個大範圍開始
2. 讓代理程式將它拆成較小、可拷問的區塊
3. 針對每個較小的範圍分別進行拷問
4. 在這些獨立的工作階段中回答所有問題

這能讓你穩穩處於「聰明區」，並避免在工作階段中途撞上上下文視窗的牆。

![將大範圍拆解為較小、易於管理的範圍](https://res.cloudinary.com/total-typescript/image/upload/v1779715891/ai-hero-images/efw0w7wzr3xzzh6taokc.png)

## 主動，而非被動

許多冗長的拷問工作階段之所以失敗，是因為人們對代理程式太過被動。請記住：**這是對話，不是面試**。

代理程式負責提問，但_你_需要：

- 弄清楚你要往哪裡去
- 理解範圍
- 讓事情維持在正軌上
- 主動引導對話

如果你太被動，代理程式會用 540 個問題轟炸你，並提出一堆擬真度太低的要求，讓範圍爆炸。

但這其中需要取得平衡。太過主動則意味著在你其實該寫程式碼的時候，仍無止盡地拷問低擬真度的細節。如果你只是不停地規劃再規劃，而沒有動手建構，就是過度拷問了。

**找到中間地帶**：積極參與並引導工作階段，同時知道何時該停止規劃、開始實作。

![顯示與代理程式之間被動與主動互動程度的光譜](https://res.cloudinary.com/total-typescript/image/upload/v1779715891/ai-hero-images/yrglde19tasebulnsabm.png)

## 保存你的設計決策

這是一個至關重要卻常被忽略的失敗模式。當你進行拷問時，你會產生一份極有價值的產物：**一個充滿設計決策的上下文視窗**。

當你完成拷問時，你已經針對系統應如何運作做出了數百個 token 份量的選擇。這是純粹的黃金。

你的選項：

- **如果你還有上下文額度**：直接在同一個工作階段中實作，不需要交接
- **如果上下文快用完了**：使用 `/to-prd` 技能建立 PRD（產品需求文件），作為交接產物

**不要**為了撰寫 PRD 而清除上下文並重新開始。那等於是把你所有的設計成果都丟掉。拷問工作階段中的每一項決策都有價值，應該要不是化為程式碼，就是記錄在交接產物中。

![警告在建立 PRD 之前不要清除上下文的圖示](https://res.cloudinary.com/total-typescript/image/upload/v1779715892/ai-hero-images/zja4advhqmfkig5eorns.png)

## 使用聰明的模型進行拷問

使用「笨」模型來拷問是常見的錯誤。以下說明為何這很重要：

當你進行拷問時，你依賴兩種知識來源：

| 知識類型       | 來源                                     | 可靠度                 | 何時重要   |
| -------------- | ---------------------------------------- | ---------------------- | ---------- |
| **上下文式**   | 你傳入的檔案、提示詞、工具結果           | 非常可靠               | 實作階段   |
| **參數式**     | 模型的訓練資料與參數                     | 較不可靠，但富有創意   | 拷問階段   |

在拷問期間，你依賴的是模型的**參數式知識**，也就是它對系統與應用程式的內在理解，用來提出你可能沒想過的事情。如果你早就想到了，你就會把它們當作上下文傳入。

**笨模型無法給你好點子。**你需要一個擁有大量參數的模型，通常是大型的前沿模型，才能獲得有創意的建議與發人深省的問題。

不過，在實作時你可以使用較小的模型，因為那裡大部分的資訊都是上下文式的（你的詳細計畫、程式碼庫等等）。

![顯示上下文式與參數式知識來源的圖表](https://res.cloudinary.com/total-typescript/image/upload/v1779715892/ai-hero-images/qwbrfqpigkqevehpb3mn.png)

## 平行執行多個拷問工作階段

最後是一個簡單卻強大的技巧：**同時平行拷問多個工作階段**。

運作方式如下：

1. 你在工作階段 A 中進行拷問
2. 代理程式問了你一個問題
3. 你回答它
4. 趁代理程式思考時，切換到工作階段 B
5. 在那裡回答問題
6. 工作階段 A 準備好了，切換回去
7. 重複以上步驟

這就像同時處理兩個 Slack 討論串。你其實不會大幅地切換上下文，只是在管理各自獨立的對話。

**好處：**

- 你的產出量加倍
- 你能在更短的時間內完成更多規劃
- 你能讓多項設計決策同時推進

大多數人最多輕鬆應付兩個工作階段。如果其中一個工作階段正在執行像研究這類耗時較長的任務，你或許可以處理三個。隨著你越來越擅長拷問，就可以增加平行的數量。

![在兩個平行拷問工作階段之間來回切換的示意圖](https://res.cloudinary.com/total-typescript/image/upload/v1779715893/ai-hero-images/zvlogainpdjwt6bjv9cy.png)

## 重點摘要

- **拷問的核心是問題。**低擬真度的問題可以拷問；高擬真度的問題則需要製作原型
- **範圍很重要。**選擇較小的範圍，以免耗盡你的上下文視窗
- **保持主動。**引導對話，同時知道何時該停止規劃、開始撰寫程式碼
- **保存價值。**你在拷問中做出的每一項決策都應該記錄在某個地方
- **使用聰明的模型。**你需要參數式知識來獲得有創意的建議
- **平行執行。**一旦了解每個工作階段在做什麼，就能有效率地在它們之間切換

你越了解這些失敗模式，就越能有效地運用拷問工作階段，在撰寫程式碼之前先完成設計。
