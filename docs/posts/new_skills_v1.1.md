## 重新命名兩項技能

各位好！隔了一陣子，我終於帶來新影片。最近我一直在忙著製作 skills 儲存庫的 v1.1，裡頭新增和調整的內容多得驚人。深度詰問（grilling）有了全新的做法，可能值得另外拍一支影片，不過這次我會盡量在這裡講完。既有技能也有不少改動，其中包括兩個主要流程技能的重新命名。內容實在太多，沒辦法在開場全部介紹，大家就接著看下去吧。

現在 PR 已經準備好要合併了，那就直接合併吧！就這樣，v1.1 正式準備就緒。先從最可能讓大家困惑、甚至想問「為什麼要這樣改？」的兩項變更說起。這次重新命名有很明確的理由：兩項技能都換了名字。原本的 `/to-prd` 現在改為 `/to-spec`，而上一層的 `/to-issues` 則改為 `/to-tickets`。

這件事困擾我很久了。`/to-prd` 產出的其實不是 PRD，而是規格（spec）。產品需求文件（PRD）描述的通常是產品本身更多面向；我們過去卻讓不一定屬於 PRD 的內容也混進去。所以我一直想把它改名為 `/to-spec`，因為我們產出的就是規格。規格是更廣泛的概念，涵蓋我們打算打造的事物：可以是技術性的、非技術性的，也可以兩者兼具。

至於 `/to-issues`，這個名稱總讓我覺得偏向使用 issue 一詞的 GitHub 和 Linear；但我們真正想要的是 tickets。先有一份 spec，再由它拆出 tickets，列出實際落實並完成 spec 所要走過的步驟。這件事困擾我好一陣子，如今終於不再讓我煩心，反而讓我很開心。

這次改名有個麻煩之處：你可能得先刪除舊技能，再重新安裝。skills 安裝程式應該不會自動辨識改名，也不會把 `/to-prd` 更新成 `/to-spec`。最穩妥的做法是執行 `npx skills add mattpocock/skills`，重新挑選想安裝的技能。安裝後也建議檢查一下 skills 資料夾，確認沒有留下不該繼續使用的舊版本，並確保自己有意識地選好了要安裝的技能。

## 修正 Grill me 與 Grill with Docs

接下來，我修正了大家在 Grill me 和 Grill with Docs 遇到的幾個問題。這兩項技能都依賴一份中央的 grilling 參考資料，用來教大型語言模型如何向使用者進行深度詰問。我把「一次問多個問題會讓人不知所措」這項指示寫得更明確。即使原本已經要求一次只問一題，模型偶爾還是會一次丟出多個問題；因此我也補上了原因，說明為什麼不要這麼做。

此外，我們在流程結尾加入確認關卡：在我確認雙方已達成共識之前，不要開始執行計畫。不同模型的使用者回報，有時 grilling 才剛結束，代理就直接開始實作，因此多了這道確認程序。

最後，有些情況下代理會自己詰問自己，這真的很奇怪。我自己沒遇過，但我只能看到這些技能少部分的實際使用情形。這個問題尤其常出現在 Fable。為了改善它，我在指示中區分了「事實」和「決策」：事實是代理探索程式碼庫後自行找到的資訊；決策則是需要由使用者做出的選擇。過去的措辭有時讓代理只顧探索程式碼庫，接著反過來詰問自己。只改了幾句話、調整了幾個地方，整體行為就一致得多了，關於這些奇怪問題的抱怨也少了很多。

## 從規劃到完整開發流程

接著要介紹幾項新技能。它們把原本偏重規劃、卻沒有一路帶你進入實作的流程，擴展成一套完整的軟體開發生命週期。很多人問我：「這些技能的主要使用流程是什麼？」流程大致如下。

首先，不要使用 plan mode，而是讓代理透過 grilling 詢問你。過程中會用到幾份文件，逐步建立詞彙表，幫助代理更了解你的需求；也會建立架構決策紀錄（ADR），記下那些不言自明、容易被忽略的重要決策。Grill with Docs 整理出的內容接著會形成 spec，說明我們要前往的目標。然後，把 spec 拆成個別 tickets，讓工作可以分散到多個代理工作階段。這就是 `/to-tickets` 的用途。

接下來，用 `/implement` 技能逐一完成 tickets。這項技能非常簡單，核心指示是：實作使用者在 spec 或 tickets 中描述的工作；在事先約定的接縫（seam）上，盡可能採用 TDD；定期執行型別檢查和單一測試檔；最後再執行一次完整測試套件。完成後，使用 code review 檢查成果，然後將工作提交到目前的分支。

我差點沒把它做成一項技能，因為內容真的很簡單，大部分只是仰賴代理原有的能力，以及執行環境對代理行為的引導。但大家一直問我流程是什麼，所以我決定做一項簡單明確的 `/implement` 技能。流程的每個階段都呼叫相應技能：拿到 `/to-tickets` 產生的 tickets 後，在不同的程式設計工作階段逐一實作；而 `/implement` 本身也會接著呼叫 code review。

## Code Review：標準與規格

Code review 技能在 v1 時還屬於進行中的技能，現在已經正式納入；v2 也做了一些更新。它會從兩個面向檢視程式碼，並為每個面向各啟動一個子代理。

第一個面向是「標準」：程式碼是否符合儲存庫所記載的程式碼標準？例如，若儲存庫中有 `coding-standards.md`，子代理就會讀取並據此檢查。我通常認為，程式碼標準應該放在 `agents.md` 之外的獨立文件中；而 code review 正是運用這些標準的好時機。

第二個面向是「規格」：程式碼是否忠實實作了原始 issue、PR 或 spec 的要求？兩個子代理會平行執行，逐項檢查各自負責的面向。

這次技能很棒的一項新內容，來自我重新閱讀 Martin Fowler 的《Refactoring》。他在書中列出許多可用來辨識不良程式碼的「異味」（code smells）。這本書歷史悠久、引用廣泛，這些概念早已深植於代理的知識中。你只要點出幾種異味，例如難以理解的命名、重複程式碼、Feature Envy、資料泥團（Data Clumps）、基本型別偏執（Primitive Obsession）、重複的 switch、發散式變更（Divergent Change）、投機性泛化（Speculative Generality）或訊息鏈（Message Chains），代理通常就能理解。

我發現，只要簡短描述這些異味，代理便會沿用這些詞彙回報，例如：「我找到幾段訊息鏈，需要移除」或「這裡有個中間人，需要修正。」我試用了幾週，效果好得出乎意料，確實能提升程式碼品質，而且只要在技能裡加上大約十行指示，成本很低。

## Wayfinder：把大型規劃拆成可走的路線

接下來要談我最期待的一項新技能：Wayfinder。它徹底改變了我們啟動並逐步完善 spec 的方式，也就是進入 spec 之前的準備階段。在某些情況下，它可以取代 Grill with Docs。我會再為 Wayfinder 拍一支完整影片；先簡單說，如果你正考慮使用 Grill with Docs，我很希望你改以 Wayfinder 作為預設選項。

Wayfinder 適合用在這種情境：你有一大堆事情想規劃，規模卻大到無法在單一代理工作階段中完成。也就是說，工作可能超出代理能有效處理的範圍，甚至超出上下文視窗；你得先把它拆成多個部分，才能看清楚要走向哪裡。

一個模糊的想法浮現了：它太大，無法在一個代理工作階段內處理，而且前方仍迷霧重重。從現在到目的地的路線還看不清楚。Wayfinder 會在儲存庫的 issue 追蹤系統中，建立一張大家共用的路線圖，再逐一處理圖上的 tickets，直到路徑明朗為止。

這些路線圖會儲存在 GitHub issues 裡。舉例來說，我在 Sandcastle 儲存庫建立了一張地圖，規劃是否要把 AI SDK 納入為相依套件。這是個幅度很大的變更。當時還沒有任何決策定案，需要做的決策則分別記在子 issues 中；這些子 issue 之間設有阻擋關係。因此，有些決策必須等到一開始的關鍵決策完成後才能進行。

每一項決策都會控制在一個代理工作階段可以處理的範圍內，並標示任務類型。例如，Research 類型代表代理可以在背景自行進行研究，再帶回結果；有些工作則屬於 grilling，需要透過對談釐清。這些類型都會列在 ticket 類型中，除了 Research 和 Grilling，還有 Prototype。

我最近一直提倡在寫 spec 之前多做原型。原型的目的，是先做出成本低、粗略但具體的成果，讓大家能針對它討論，藉此提高討論的明確度。成果可以是大綱、粗略的技術雛形，或是透過 Prototype 技能建立的 UI 邏輯程式碼，也可以把原型連結作為附件。如果「應該長什麼樣子」或「行為應該如何運作」是關鍵問題，就適合採用 Prototype。幾乎所有會碰到前端程式碼的工作都需要這一步，因此我非常推薦前端相關工作使用 Wayfinder。

最後一種是一般任務，例如需要設定的組態、開通存取權限，或把資料整理成指定格式。這些可能是繁瑣但必要的工作，不需要透過 grilling 做決策，也不一定能交由 AI 自動完成。

所有 tickets 關閉後，蒐集到的資訊會回存到地圖中，原始 tickets 則是記錄內容的第一手來源。接著，你就能像平常一樣把地圖轉成 spec。

使用 Grill with Docs 時，我常會焦慮地管理工作階段、擔心怎麼交接，以及是否會超出代理能有效工作的範圍。Wayfinder 幫我把這些事都管理好了：我只要結束目前的工作階段，再開啟下一張 Wayfinder ticket。所有內容都保存在 GitHub，方便團隊協作與分享。地圖完成後，接著使用 `/to-spec` 就可以了。

## Research、Prototype 與 TDD

為了支援 Wayfinder，我們新增了一項精簡實用的 Research 技能。當你需要進行研究時，可以直接呼叫它；它也會引導模型用我偏好的方式研究。技能會啟動背景代理進行調查，讓你在代理閱讀資料時仍能繼續工作。它會針對問題查找第一手來源，把研究結果寫成簡單的 Markdown 檔案，並依照儲存庫既有慣例，放到存放這類筆記的位置。需要研究時，只要呼叫 Research 技能即可。

接下來是 Prototype。之前我稍微展示過它，但好像還沒為它拍過完整影片。現在 Prototype 也支援模型呼叫，因此 Wayfinder 可以自行使用它。這項技能會讓你選擇要做「邏輯原型」或「UI 原型」，兩者的處理方式很不一樣。

最後一項變更，是許多人期待已久的 TDD 技能調整。過去它會建議一套操作步驟，有時不太順手：它可能先和你確認要寫哪些測試，接著再一步一步帶著你做，這不符合許多人對 TDD 的期待。理想上，你應該能把 TDD 技能交給背景代理，讓它直接按照 TDD 工作。

因此，現在的 TDD 技能只提供參考資料。它不再規定特定流程，而是說明測試的撰寫順序，也就是先紅再綠，一次處理一個小範圍；重構則不再納入這個循環。換句話說，不再是 Red-Green-Refactor 循環，而是 Red-Green。我認為把重構放到 code review 階段處理更有效率，實作時也不會同時背負太多工作。

## 結語：Wayfinder 與 AI 寫程式速成課程

以上就是這次技能更新的內容。這次改動不少；如果擔心漏掉更新，我建議先移除現有技能，再執行 `npx skills update`，重新安裝需要的技能。如果你已經自行修改過技能，也可以讓代理參考我的儲存庫，尤其是 release notes，幫你取回其中值得採用的新內容。

我想，大家最會記得這次把 `/to-spec` 和 `/to-tickets` 改了名字。這多少會帶來一點摩擦，但我認為這是好的摩擦，因為新名稱更準確地說明了它們的用途。我也希望這次更新能讓你開始愛上 Wayfinder。我現在幾乎什麼事都用它規劃，甚至包括非程式設計的工作。我也正在用 Wayfinder 規劃下一門課，效果非常好。既然提到了，不如就和大家介紹一下。

這門課叫做「AI 寫程式速成課程」（AI Coding Crash Course），和我平常開設的梯次課程不同：價格會便宜許多，而且採自學進度，任何時候都可以購買。你一樣能透過 Discord 獲得協助，但課程不會像一般梯次課程那樣有名額或時間限制。無論你是不是開發者，這都會是很適合入門 AI 寫程式的課程。對資深工程師來說，它會是一門轉型課程；對剛接觸開發的人來說，則能幫助你運用這些新工具，真正開始有效率地工作。

目前我還沒公布價格，也會先開放大家登記意願。等影片拍攝完成後，課程就會上線，我想大概會在八月左右。各位，謝謝收看。能和大家分享這些技能更新一直很愉快，也很高興看到使用人數持續成長。很多人都說我不該展示星數，不過目前已經有大約 16 萬顆星，skills.sh 上也有 700 萬次下載，實在很不可思議。謝謝大家喜歡這些技能，希望它們能幫助你更有效率地交付更多成果。我們很快再見。
