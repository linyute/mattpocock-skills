經過漫長的開發期後，Skill 儲存庫的 1.1 版本終於準備好合併了。此版本包含驚人數量的變更，包括全新的審問方式、對現有 Skill 的諸多更新，以及兩個主要流程 Skill 的重新命名。

我們不再嘗試在此概述所有內容，而是直接深入探討各項變更。

## 如何遷移

由於此版本包含 Skill 的重新命名與合併，您需要更新安裝。Skill 安裝程式不會自動擷取這些變更。

執行此指令以獲取所有新 Skill：

```bash
npx skills add mattpocock/skills
```

這讓您可以自由挑選所需的 Skill。完成後，請檢查您的 skills 資料夾，確保沒有殘留的舊 Skill。

新的公開文件頁面位於：

- `docs/engineering/to-spec.md`
- `docs/engineering/to-tickets.md`

## 主要重新命名：`/to-spec` 與 `/to-tickets`

最可能令人困擾——但理由非常充分——的兩項變更是 Skill 的重新命名。這些問題困擾我很久，因為原先的命名無法準確反映我們實際建構的內容。

### 從 `/to-prd` 到 `/to-spec`

`/to-prd` Skill 已重新命名為 `/to-spec`。這裡的關鍵洞察是，我們所建立的實際上並非 PRD（產品需求文件）。PRD 描述的是關於實際產品本身的內容，而我們卻允許非產品的內容滲透進來。我們真正建構的是規格——這是一個更廣泛的術語，可以是技術性、非技術性，或兩者的結合。

「Spec」現在是整個 Skill 套件中唯一的貫穿術語。您可能仍將此文件稱為 PRD，但「spec」是我們未來使用的統一口徑。

### 從 `/to-plan` 與 `/to-issues` 到 `/to-tickets`

兩個 Skill 已合併為一個：`/to-plan` 與 `/to-issues` 現已統一為 `/to-tickets`。舊名稱讓人感覺偏向 GitHub 和 Linear，它們使用「issue」作為術語。但實際上，我們處理的概念更為通用：您有一份規格，而在該規格之下您有 ticket——也就是您實際執行該規格並建立它所經歷的歷程。

`/to-tickets` 將計畫、規格或對話拆解為一組 **Ticket**——曳光彈式的垂直切片，每個切片都宣告其**阻礙相依關係**。根據您的追蹤工具設定，這個單一產物有兩種運作方式：

- **本機檔案** (`tickets.md`) – 相依關係以文字形式撰寫，您以手動方式由上至下逐一處理
- **真實追蹤工具** – 相依關係成為原生阻礙連結，因此任何阻礙已完成的 Ticket 都位於前沿，多個 Agent 可以平行處理

經過多年希望名稱能準確無誤後，這種命名上的清晰帶來了莫大的欣慰。

## 審問 Skill 的改進

下一組變更修復了人們在 `/grill-me` 與 `/grill-with-docs` 中遇到的 Bug。兩者都依賴一個核心參考審問 Skill，該 Skill 向 LLM 展示如何有效地審問一個人。

### 三大關鍵修復

**1. 更清晰的提問指引**

原先的指引提到「一次提出多個問題會令人困惑」。即使有了這項指示，模型偶爾仍會忽略它並同時提出多個問題。因此我更明確地說明了*為什麼*我們不希望一次提出多個問題。

**2. 實作前的確認關卡**

在最後加入了確認步驟：「在我確認我們已達成共識之前，請勿執行該計畫。」許多人回報審問階段會直接結束，隨後模型就直接跳入實作。這個關卡防止了這種情況。

**3. 防止自我審問**

在某些奇特的情況下，模型會自己審問自己——探索程式碼庫並在沒有人類輸入的情況下進行審問。這在 Fable 中特別常發生。為了修復此問題，我添加了前置引導詞以區分兩種類型的資訊：

| 類型          | 定義                                       | 範例                                    |
| ------------- | ------------------------------------------ | --------------------------------------- |
| **事實**      | 你透過探索程式碼庫所發現的事物             | 程式碼模式、現有實作                    |
| **決策**      | 使用者需要決定的事項                       | 架構選擇、功能範圍                      |

只增加了兩句話並重新排列了少數內容，就讓這個 Skill 變得更加一致。這些微調大幅減少了人們所回報的異常問題。

## 完整的軟體開發生命週期流程

我新增了幾個新 Skill，將審問流程從主要作為規劃的練習轉變為合適的軟體開發生命週期。許多人問我：「我應該在這些 Skill 中使用的主要流程是什麼？」就在這裡：

![Diagram showing the complete development workflow](https://res.cloudinary.com/total-typescript/image/upload/v1783519442/ai-hero-images/dswt0zd86eyaztzabvci.png)

### 流程：從審問到部署

**1. 從審問開始**

與其直接使用計畫模式，不如讓 Agent 就你的目標深入審問你。這會使用兩份支援文件：

- 詞彙表：協助 Agent 更好地了解你的領域
- 架構決策記錄 (ADR)：用來擷取非顯而易見的內容

**2. 產生規格**

審問的輸出會進入規格中，這定義了你的目的地——你透過這個功能或專案要前往的方向。

**3. 拆解為 Ticket**

接著你使用 `/to-tickets` 將該規格轉化為個別的 Ticket。這會將開發工作分散到多個 Agent 階段中，每個階段專注於一個 Ticket。

**4. 實作每個 Ticket**

使用 `/implement` Skill 實作每個 Ticket，其內容令人耳目一新般簡單：

```
實作使用者在規格或 Ticket 中所描述的工作。
在預先約定的接合處盡可能使用 TDD。
定期執行型別檢查。
定期執行單一測試檔案。
最後進行一次完整的測試掃描。
```

`/implement` Skill 主要仰賴 Agent 的先驗知識以及你的 `agents.md` 檔案所教導它的內容。我差點沒有為此建立 Skill，因為它太簡單了，但人們一直問「流程是什麼？」所以現在你有了一個明確的終點：一旦你有了 Ticket，只需在單獨的編程階段中實作每一個即可。

**5. 程式碼審查**

實作完成後，`/implement` Skill 會呼叫 `/code-review` 在提交前審查工作成果。

### 包含重構異味的程式碼審查

程式碼審查 Skill 會在兩個維度上審查程式碼，每個維度使用一個子 Agent：

| 維度          | 目的                             | 詳細資訊                                                           |
| ------------- | -------------------------------- | ------------------------------------------------------------------ |
| **標準**      | 符合編程標準                     | 讀取儲存庫中的 `codingstandards.md` 或類似檔案                     |
| **規格**      | 針對需求的正確性                 | 程式碼是否忠實實作了原始規格或 Ticket？                            |

兩者皆作為平行子 Agent 執行，逐一檢視程式碼的每個部分。

這裡呈現了這個 Skill 酷炫且新穎之處：我最近再次閱讀了 Martin Fowler 的《重構》，並意識到 Agent 已經在它的訓練中深刻了解程式碼異味。你只需要喚起這個概念即可。以下是一些範例：

- 神秘名稱
- 重複程式碼
- 依戀情節
- 資料泥團
- 基本型別偏執
- 重複的 switch
- 發散式變更
- 誇誇其談未來性
- 訊息鏈
- 中間人

當你描述這些時，Agent 會抓住這些術語並說：「是的，我發現了訊息鏈。我需要移除它們。我發現了中間人情況。我需要修復它。」

我測試了幾個星期，它在提高程式碼品質方面非常有用。最棒的部分呢？加入它的成本非常低——大約只需要 10 行指引。

## 推出適用於大型計畫的 Wayfinder

現在介紹我真正感到興奮的 Skill：一種啟動與塑形規格的全新方法。它被稱為 `/wayfinder`，旨在於許多情況下取代 `/grill-with-docs`。

![GitHub issue showing a Wayfinder map with blocking relationships](https://res.cloudinary.com/total-typescript/image/upload/v1783519443/ai-hero-images/hrjyn3a1hjruevbd1kyp.png)

### 何時使用 Wayfinder

`/wayfinder` 適用於你有太多需要規劃的內容，以至於單一 Agent 階段無法容納的情況。你不是會超出 Agent 的聰明區間，就是會達到其上下文視窗限制。你需要將其拆分為多個部分來弄清楚你要去哪裡。

概念如下：

> 一個尚未成熟的構想出現了，對單一 Agent 階段而言過於龐大且籠罩在迷霧中。從這裡到目的地的路徑目前尚不可見。此 Skill 在儲存庫的 Issue 追蹤工具上將路徑繪製為共享地圖，然後一次處理一個 Ticket，直到路線清晰為止。

### Wayfinder 的運作方式

Wayfinder 會建立一份儲存為 GitHub Issue 的地圖，其中的決策範圍設定為一個 Agent 階段的大小。每個決策都透過阻礙相依關係進行連結，因此在先決條件解決之前無法做出相依的決策。

以下是來自 Sandcastle 儲存庫的範例，用於調查是否引入 AI SDK 作為相依套件：

**Ticket 類型：**

- **研究** – 供 Agent 研究並回報結果的離線任務
- **審問** – 用於做出決策的審問階段
- **原型** – 用於提高討論保真度的快速原型
- **任務** – 設定、佈署或其他不需要審問的工作

### 為什麼建立原型很重要

我一直倡導在產出規格之前進行更多原型設計。其構想是透過製作一個廉價、粗糙、具體的產物來做出回應，以提高討論的保真度——例如大綱、初步構想、虛設常式或使用者介面邏輯程式碼。

**在以下情況使用原型設計：**

- 「它應該長什麼樣子？」是關鍵問題
- 「它的行為應該如何？」是關鍵問題

這對於幾乎所有涉及前端程式碼的工作都是必不可少的。我絕對建議對任何前端工作使用 `/wayfinder`。

### Wayfinder 完成後

一旦所有 Ticket 都已關閉，所有這些資訊都會儲存到地圖上，並以原始 Ticket 作為主要來源。接著你可以採用這份地圖，並以常規方式將其轉化為規格。

Wayfinder 的優點在於，你不必使用 `/grill-with-docs` 來管理工作階段焦慮——擔心交接與聰明區間——一切都為你管理好了。你只需關閉一個階段並開啟下一個 Wayfinder Ticket。它完全儲存在 GitHub 中，因此具有協同性且可在整個團隊中共享。

## 支援 Skill：Research 與 Prototype

為了支援 Wayfinder 工作流程，新增了兩個新 Skill。

### `/research` Skill

`/research` Skill 體積小但很實用：

- 啟動背景 Agent 進行研究，讓你在它閱讀時繼續工作
- 針對原始來源調查問題
- 將發現寫入簡單的 Markdown 檔案
- 將其儲存在儲存庫原先保留此類筆記的位置，以符合現有慣例

每當你需要進行研究階段而不中斷流程時，都可以隨時使用它。

### `/prototype` Skill

`/prototype` Skill 現在由模型呼叫，以便 Wayfinder 可以自行呼叫它。它讓你在兩種類型之間進行選擇：

| 類型                | 目的                             | 使用情境                        |
| ------------------- | -------------------------------- | ------------------------------- |
| **邏輯原型**        | 測試行為與邏輯                   | 後端 API、商業邏輯              |
| **UI 原型**         | 測試外觀與互動                   | 前端元件、使用者流程            |

它們的反應截然不同，並能幫助你在確認規格之前探索設計空間。

## TDD Skill 更新

最後的變更解決了人們一直要求的項目：將 `/tdd` Skill 傳遞給離線 Agent 並讓它順利運作的能力。

### 先前的方法

舊的 `/tdd` Skill 會推薦一組步驟並要求你確認每一步。這很彆扭，因為它不符合大多數人實際使用 TDD 的方式——他們希望 Agent 能夠自主工作。

### 新方法

`/tdd` Skill 現在僅作為參考資料。它不指定特定步驟，只指定基本順序：

```
1. 紅燈 - 撰寫失敗的測試
2. 綠燈 - 讓測試通過
3. 重構 - 改進程式碼（已移出循環外）
```

關鍵變更：重構不再是 TDD 循環的一部分。它現在在程式碼審查階段處理，這保持了實作的專注與乾淨。透過這種方式，你不會讓實作階段負擔過重的重構考量。

## 值得關注的項目

- **`/to-spec` 取代 `/to-prd`** – 更新任何流程或文件
- **`/to-tickets` 取代 `/to-plan` 與 `/to-issues`** – 這些現已統一
- **新工作流程** – 考慮採用新流程：審問 → 規格 → Ticket → 實作 → 程式碼審查
- **Wayfinder 無所不在** – 針對較大型的規劃任務，嘗試使用 `/wayfinder` 代替 `/grill-with-docs`
