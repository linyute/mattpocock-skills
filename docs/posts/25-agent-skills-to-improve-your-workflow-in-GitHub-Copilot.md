## 引言

我非常高興能來到這裡。而不知怎地，我手上擁有了世界上最受歡迎或第二受歡迎的 skills 套件庫。我現在從陽光明媚的牛津郡向大家致意，我將向各位介紹這個 skills 套件庫，並且或許還會看看幾個即將進入此 skills 套件庫的新功能，以及各位如何在 GitHub Copilot 中應用這些功能。

首先，讓我展示這個套件庫給各位看。我們已經達到大約 25.9 萬顆星，這對我來說相當瘋狂。我從未真正想過我們會走到這一步。

## 主流程：從 grill-with-docs 開始

而我們首先要開始的地方是這裡的主流程。這些 skills 的核心概念，就是你真的能交付任何規模的你想做的工作。而我們幾乎總是開始的地方，就是這個 **grill-with-docs** skill。

對於以前沒使用過我的 skills 的人來說，這本質上是一種讓自己與代理對齊的方式。這意味著，過去你常常會叫來代理，然後檢視他們所做的工作，而他們卻往往沒有產出你想要他們產出的東西。因此，在代理進行任何工作之前，進行某種**會前盤問（pre-session grilling）**，我發現這絕對是至關重要的。

這就是在 GitHub Copilot 中的運作樣貌。如果我們切換到這裡的終端機，我今天早上一直在我的套件庫上進行一些實際的工作。我的套件庫是一個課程影片管理器，我在這裡處理我所有的影片剪輯。我管理我所有的課程影片。讓我們來看看那實際上是什麼樣子。

首先，我所做的是，我使用 GitHub issues 來協調整個我想對套件庫本身所做的變更。這意味著將這些事項保持在套件庫之外，我能獲得更多價值，將它們輸入到自動化迴圈中、直接傳遞給代理，有時甚至僅透過標籤來觸發它們。但這有點超出今天的討論範圍。

不過這在 GitHub Copilot 中看起來的樣子是，它意味著我可以直接進入 issues。我可以在這裡按 W 打開一個工作樹（worktree），而我最終進入了這個工作樹之中。所以在這個小範例中，如果我按下 enter 進入，實際發生的情況是，我就直接說：`grill with docs issue 1612`。而這個 issue 是我實際上需要修復的問題。它基本上是在此隨附的課程影片管理器 CLI 中新增一些功能。

首先發生的事情是，它會前往子代理中進行探索，非常棒。一旦它完成了探索，一旦它理解了想要盤問我什麼問題，接著它就開始提問。而這裡的這些問題是**支援階層選取器**。這裡的問題在於，我有個實體想要去取得，稱為 beat，而該 beat 是附加在影片上的，但它希望能够不僅搜尋影片，還能搜尋具有多部影片的單元課程（lessons），以及在其下具有多個單元課程的章節（sections）。所以它問說，好的，這兩個選取器是否互斥？

我打算使用語音輸入工具來完整回答這些問題，因為我事前稍微做了一些準備，所以我知道自己在做什麼：

- 是的，我認為我們應該使用**全部三種**支援的階層選取器。
- 我認為使用**確定性的階層順序**是合理的。
- 然後針對企劃為空的影片，我認為我們**直接排除它們**即可。我不認為我們需要在那裡加入任何類型的額外訊號。

現在這些資訊已經送進去，我只要在這裡按下 Enter，它現在就會向我提出下一輪的問題。換句話說，grill with docs 在做的事情，就是拓展這些問題的前沿邊界，而我們達成共識的速度不是越來越慢，而是越來越快、越來越快。所以它又去啟動了另一個探索代理，而且在啟動該探索代理的同時，它還會向我提出更多問題。

> 這種程度的對齊基本上代表你和代理正在共同達成共識與理解。你們正在一起釐清接下來要走向何方。而這在許多情境下特別實用，例如當你面對大量未知的未知（unknown unknowns），還不太清楚該往哪裡走時。所以我真心非常喜歡這個。

## 從盤問到 Pull Request

但接下來會發生什麼事呢？在完成了一次盤問流程之後，你要做什麼？那麼，讓我們來看看接下來發生了什麼事。

所以在我這裡的真實版本中，我所做的，這是一段相當長的對話歷史。我們進行了我們的盤問會話。它問了使用者一連串的問題，又問了使用者更多的問題，然後它就啟動更多問題，然後它就啟動並且實際實現了它。所以 grill-with-docs 所做的，就是採納它先前向你提出的那一組問題，然後嘗試與你達成共同的理解。接著我們最終獲得的是一個非常漂亮的小 Pull Request。

所以如果我點進去該 PR 本身，我實際上在 PR 中玩了一個小把戲，我對此感到相當自豪，而且這其實不是我的把戲，而是別人的創意。所以如果我們來看一下，剛才那個 PR 在哪裡？就是新增這個：`add bulk section and lesson beat lists`。

現在，這個 PR 的內容描述對你來說可能看起來相當賞心悅目。我們所擁有的，是我們有這個相當棒的 diff，精確顯示了 CLI 到底變更了哪些內容。你只有這個非常小巧的保留既有緊湊格式、排除封存的 beats、lessons 等等。而且我們還有個很漂亮的 Mermaid 圖表，我們可以在這裡將它展開。因此我們看到 sections，好的，sections 包含單元課程，具有小數排序，單元課程包含影片，而且我們可以透過單元課程存取這些影片，然後影片則包含具有小數排序的 beats。各位知道，這是一個真實的應用程式。這裡包含相對複雜的內容。而我們可以深入鑽研這張 Mermaid 圖表和這份 diff，並能理解得透徹許多。

## 用 show-me 打造易讀的 PR

而在這裡發揮作用的、讓這一切看起來如此美好的，並不是我的 skill。事實上，我要向 HumanLayer Skills 的 Dexter Horthy 致敬，他寫了一個很棒的名為 **show-me** 的 skill。它協助使用者透過簡潔的圖表、程式碼形狀、草圖以及聚焦的 HTML 產出物，以視覺化方式理解當前主題。

我是說，光是看這些東西。這基本上是一套非常、非常棒的工具，用來理解程式碼是如何變更的：

- **虛擬碼（pseudocode）**：如果你對某個相對複雜的演算法有變更，我們可以用虛擬碼來呈現它。
- **呼叫樹（call tree）**：我們可以將執行階段控制流程呈現為這裡的呼叫樹。
- **UI 結構圖**：在前端元件（frontend components）方面棒極了，因為它精確展示了各個元件所在的位置。它能夠某種程度展示出跨越不同元件以及不同檔案的變更內容。
- **Mermaid 圖表**：GitHub 本身就能自然原生支援。
- **檔案職責劃分**：以及所有那些內容。

而我真正喜歡的是 **diff**。也就是使用 diff 呈現元件變更、呈現檔案版面結構變更、呈現呼叫樹以及呼叫堆疊（call stack）的變更。而這個 skill 所做的，就是它會非常鼓勵代理朝著使用這類 diff 檢視表的方向推進，而不是在文字中寫上一大堆內容。因此這個 PR 最棒的地方在於，它閱讀起來非常簡短。這裡包含的字數少於一百字。一旦你深入理解了 Mermaid 圖表，你再深入理解這份 diff，感覺非常棒。

因此作為該 skill 的一部分，或者該工作階段（session）的一部分，就在先前的紀錄中，在該階段的某個時間點，我說：好，使用 show-me 來建立該 PR。

## 程式碼審查：實作流程的一部分

現在，接下來會發生什麼事？有一件我非常有興趣的事是：當然，你拿到了這個 PR，但我們要如何確保在人類接觸到這個 PR 之前，確保這個 PR 具有足夠高的品質，讓我們能真正保證使用者的時間不會被浪費，對吧？

因為我非常討厭——而且這是當我與不同團隊合作並試圖讓他們的流程變得更好時，一次又一次反覆出現的問題。就像有這麼多的團隊都在反映說：好，PR 現在成了瓶頸所在。我們到底該如何消化眼下所看到的大量 PR？當然，我們可以改善 DX（開發者體驗），對吧？我們可以改善這個檢視表，以利確保審查起來盡可能容易，但我們也必須確保程式碼本身具有足夠高的品質。

因此，針對這點，我建議使用我的**程式碼審查（code review）** skill。因此在實作之後，我建議執行這個程式碼審查 skill，它就在這裡的某段歷史紀錄中。而這個程式碼審查 skill，它所做的是——還有我們之前看到的 show-me——程式碼審查所做的，是它首先釐清你要對比的基準是什麼、變更了哪些內容，而它在這裡使用 `origin main` 作為基準點。接著它會搜尋任何你留在套件庫裡的編碼標準（coding standards）。你可以看到 GitHub Copilot 正在這裡搜尋編碼標準。它正在讀取 `CLAUDE.md` 檔案，現在它會做兩件事。

**第一，檢查編碼標準。** 它會繁衍出一個子代理來檢查這些編碼標準。所以它在檢查實際實作出來的程式碼，是否符合你所寫下的「我們需要用這種方式處理、我們需要用 X 方式處理」的規範。而我在套件庫中保留了一份編碼標準清單，當出問題時我就會將其附加進去。我們稍後會再討論這一點。

**第二，規格檢查（spec check）。** 因此它會對照我實際指定的內容進行檢查，使用這個對話歷史紀錄，以確保被建構出來的東西確實是我們所想要的東西。而這意味著，因為我們是在子代理中執行這些工作，這些都是乾淨的上下文視窗。這代表代理會拋棄很多既有的成見，我們在對話中獲得了一條全新的軌跡，而且它常常能夠浮現出你先前從未考慮過的事情。

所以看起來我們的規格檢查返回時沒有任何問題發現。這很棒。而在標準方面，有一項判定稱為「在 DB beat 服務操作中存在重複的 beat 學習目標關聯設定」。好的，很有意思。如果我們進入 GitHub Copilot，我們可以看到這被建立為這裡的一個提交（commit）。也就是「去除重複的 beat 關聯查詢」，讓我們在這裡進行審查。我們可以看到，好的，它所做的是，先前我們在兩次呼叫之間有著稍微重複的設定，而它將其轉變成一個類似 `as const` 的物件，以解決這個問題。這很棒。這是一個很棒的小變更。

而所有這些事情，程式碼審查都發生在使用者親自去審查之前。我認為在 AI 程式碼審查方面，有一種普遍的看法認為程式碼審查隨後應該交給人類，去釐清接下來應該變更什麼，或是我們是否真的應該實作這些東西。換句話說，多數程式碼審查 skills 的產出就是評論（comments）。但我認為程式碼審查算是實作流程的一部分。所以它有點類似傳統的**紅燈-綠燈-重構（red green refactor）**：

- 實作者代理負責執行紅燈與綠燈，就像單純讓功能運作起來一樣。
- 然後重構工作則由這些與我一起協作的審查代理來完成。

這意味著我們最終獲得一個審查起來相當令人愉悅的 PR。

而且實際上往下檢視這裡的程式碼，我可以看到，好的，有些東西讓我稍微感到有點壓力。這與這裡的指令或任何這些東西無關。我剛才稍微看了一下，然後我意識到，噢，好吧，這個——這是在哪裡？這裡的 RPC 層，我隱約覺得這裡不是非常具有型別安全（type safe）。稍微看了一下程式碼內部，我意識到，是的，那實際上相當糟糕。我真的很不喜歡那樣。所以我意識到我想要——我不想阻擋這個 PR，但作為這個 PR 合併的一部分，或者可能放在堆疊（stack）中，我想檢視那項工作，檢視這段程式碼，並或許思考一下改善它的架構。

## improve-codebase-architecture：架構審查

為此，我們有一個非常棒、非常棒的 skill，位於維護（upkeep）類別中，名為 **improve-codebase-architecture**。這個 skill 所做的，就是檢視你的套件庫，而且你可以稍微引導它關注你希望它檢視的內容。而它所做的，就是根據它認為你應該變更的事項，提供一份報告給你。而這份報告可能具有難以置信的價值。

所以如果我們來看一下我們所產出的報告——所產生的，我想其實是這一個，對於突然切換到亮色模式感到抱歉。讓我來查看實際的會話，它位於 improve-codebase-architecture planning 之中。當時我所做的是，我這樣呼叫它：

> 我希望你檢視一下最近的 PR，看看你是否能改進任何與 RPC 相關的事項，也許讓東西更具型別安全。我不太確定該區域周圍的架構。我希望你檢視一下並提供一些建議。

這段程式碼是我自己並沒有真正親自撰寫的內容。我一直有點放任 AI 自由發揮。我相信各位對那種感覺有很深刻的體會。

而這裡的 improve-codebase-architecture，它所產出的是一張非常漂亮的簡短圖表。它說的第一件事是，好的，這些是它在下方列出的建議。檢查每一個遠端呼叫。很有意思，因此它標示出了它在此處檢視的精確行號。而且它說明了問題所在：

> 遠端介面卡模組在接縫處過於淺層。每個介面卡只檢查自己擁有的呼叫。它不會回報遺失的呼叫。最後的型別轉換告訴 TypeScript 介面卡具備每一個領域呼叫。

現在，它在這裡所使用的語言相當生硬晦澀。而針對這種生硬晦澀的語言，我實際上還有另一個我非常喜歡的 skill。事實上，有兩個 skills。有一個是我的 skill，但實際上我要向別人的 skill 致敬，稱為 **poteto skill**。而這裡的 [poteto](https://cursor.com/marketplace/cursor/pstack) 是一位極其出色的 skill 作者。而這是你絕對必須納入你的函式庫中的一個 skill，也就是說，它基本上會接收 AI 產出的文字並去除其廢話（unslop）。因此它會將其轉化為真正優美。我也許不太確定是否優美，但它能剔除你的成果中所有的 AI 痕跡。這意味著像這樣可怕的、類似垃圾的內容：這句「遠端介面卡模組在接縫處過於淺層」，你實際上可以讓它用更淺顯平實的語言來撰寫。因此如果你對 [unslop skill](https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md) 感興趣，我強烈推薦它。

不過，我確實理解它的意思。而且我確實喜歡這個想法，好的，我們可以單純精簡它，讓它在這裡變得更簡單一點。在最底部這裡還有一點也是我所喜歡的。也是我很欣賞的部分。因此這算是一種從許多淺層模組中衍生出來的深層模組。

## 大型工作：從規格到工單，再到實作

所以我所做的是，我決定：好的，讓我們實際實作它吧。現在，實作這麼複雜的東西看起來會是什麼樣子？因為上一個範例，我剛好知道我們嘗試要做的相對範圍有多大。我們嘗試要達成的目標。我知道我們只要在單一會話中就能搞定它。單純在單次會話中。我們不需要跨多個會話來進行。換句話說，我們剛才只做了 grill-with-docs，接著我們實作了它，然後在底部使用了程式碼審查。

但對於可能跨越多個會話、或者在規模上可能失控的事情，那我建議採取不同的方法：

1. 你可以先做 **grill-with-docs**。而且在我們的例子中，我們算是已經獲得相當可行的成果了。
2. 我們可以執行 **improve-codebase-architecture**，然後將其轉化為一份**規格（spec）**。

現在，規格的重點在於，如果我們看一下我們在此處的 GitHub issues，我們可以在這裡檢視我所建立的這個規格，也就是，我想它是在這裡。我認為就在這裡。`讓 cvm RPC 呼叫對應與轉發具備型別安全`。我最終所做的，就是我將那張非常漂亮的圖表、這份原本打算要完成的規格，轉化為一份正式的規格，在其中我們具備使用者故事、我們在這裡有解決方案與問題，以及一連串的實作決策，並大致詳述出我對這項工作確切想要的要求。

接著我們在它下方呼叫另一個 skill，來建立對應於讓規格化為現實的實際**工單（tickets）**。因此這份規格本質上是目的地，而這些工單則是前進的旅程。而我所做的是，所有這些都是在單一會話內完成的，也就是在規劃會話中。你可以看到它在最底部發布了兩張獨立的工單。就在最底部。而我一直使用的是 **to-tickets** 這個功能。

然後在另一個單獨的會話中，我進行了實作。而對於以前使用過我的 skills 的人來說，這項實作會相當新穎，也就是我使用了一個名為 **implement spec** 的 skill，而且我就直接把該規格傳送給它。所以它首先做的是，它前往梳理出該工單的依賴關係，然後開啟了一個草稿 PR。接著事實證明這兩張工單彼此是相互獨立的。因此它們可以各自獨立地被處理。

所以它所做的是，它在各自獨立的工作樹與分支上處理它們。所以我們在這裡實現了**平行化**。我們能夠繁衍出多個子代理，將它們分配到不同的工作樹上。GitHub Copilot 替我處理了這所有的一切。接著它將它們 rebase 在一起並合併進草稿 PR，一切運作正常，合併介面卡工單，大功告成。然後它在最後進行了程式碼審查。

所以這個 skill 做得非常出色的一點是——我們稍後實際上可以花點時間檢視這個 skill——就是它會執行一個探索代理，平行執行所有能夠平行的項目，然後在最後對其進行程式碼審查，並修復它所發現的所有問題。所以一旦我們進展到那裡，接著我們就能去看程式碼審查的執行，並看到它修復審查發現的項目，我們最終獲得了一個相當棒的 PR，我們實際上可以直接堆疊在另一個 PR 之上。

因此這裡是原始的 PR——噢不，在這裡，不，這才是正式的 PR。它關閉了所有我們所建立的工單，關閉了規格，關閉了每張個別的工單，然後我們得到了一個好成果，我們實際上可以將其合併在其之上，以便讓我們未來的操作具備型別安全。

> 這就是整個流程：如果你希望你的程式碼隨著時間推移能運作得更好、並清理掉一些廢話雜質，你最終就會擁有這些優秀的架構審查，讓你可以持續在此基礎上推進。

## retro：回顧你的會話

但如果你希望真正採取這種方法，採取這種去蕪存菁的方法，並將其應用於你自己的代理、應用於你的代理環境，那時你該怎麼做？

那麼，我有個全新的 skill，而這個新 skill 稱為 **retro**。Retro：取得最近的四次回話，並對它們進行回顧（retro）。而 retro 源自於 retrospective（回顧）這個詞，也就是在一項工作的結尾，你回顧審視自己所做的事情，並看看有哪些可以改進的地方。

代理在這方面相當擅長，因為許多代理都可以存取自己的會話歷史紀錄，許多代理都有權限存取自己的會話歷史紀錄，GitHub Copilot 也是如此。所以它會讀取最近的會話，讀取實作會話、架構會話，尋找所有的會話產出物以及會話檢查點（checkpoints）。接著它會提出一連串的想法建議。

因此我們可以看到 implement spec 執行時直接從作用中的功能分支建立 PR，而不是從預期的基礎分支。因此代理在那裡產生了一點混淆。所以它指出，你可能需要稍微修改一下這個 skill，收緊實作規格的整合分支步驟，在建立任何內容之前先解析目標基礎分支。然後它還檢視了**工具經濟性（tool economy）**。它檢視我們所呼叫的工具是否具備足夠的 Token 效益。同時我們也在此處檢視導覽步驟。

因此這個 retro 是讓我感到非常興奮的事情。這是我將會繼續投入開發的功能。而它建立在這些 skills 的主流程之上，在該流程中：

1. 你進行**盤問**（grill-with-docs）；
2. 接著你要麼去建立**規格與工單**，以利在多個不同會話、多個子代理中處理它；
3. 然後你去**實作**它；
4. 接著對其進行**程式碼審查**；
5. 然後你進行 **retro 回顧**，在其中尋找下次可以做得更好的機會。
