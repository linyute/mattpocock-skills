## 前言

在使用 AI 撰寫程式碼時，有一件事讓我抓狂，我也已經為此疾呼了好一陣子：許多人認為「我必須先替 AI 寫好規格」。也就是要先擬好計畫（Plan 模式）、採用規格驅動開發（spec-driven development），把所有心力投入在一份極度詳盡的規格上，期望 AI 產出的結果能與規格完全吻合；只要事先把一切都講清楚，就能完美命中目標。

然而，在這股衝動之下，大家忘了一件事：**你其實可以直接寫程式碼**。在朝著規格邁進的同時，你完全可以一邊撰寫程式碼。原型（prototype）與探索性實驗（spike）自敏捷（Agile）時代以來就一直存在，說起來現在仍是敏捷的時代，敏捷依然非常盛行、影響深遠。但人們卻不再做原型了。

因此，我在自己的技能（skills）儲存庫中，試著扭轉這個現象，並提供了一個 `prototype` 技能。

**原型，就是用來回答問題的拋棄式程式碼。**

大家都說「程式碼很廉價」。這句話有一部分是對的，但我也有一部分很討厭這個說法。真正變得廉價的，是產出程式碼的成本，它已經大幅下降。因此，製作原型、做快速的拋棄式探索，從未如此便宜，也從未如此有效。

在這支影片中，我會介紹這個 prototype 技能，談談何時該使用它、它能用來做什麼，以及它如何融入我全新的 Wayfinder 技能。

## 先談「擬真度」：高擬真與低擬真

要說明這個概念，得先從擬真度（fidelity）說起。

每當你在設計某樣東西時，腦中都會浮現一些需要解決的問題：

- **基本問題**：例如你正在建構的東西的基本框架。以彈出視窗（modal）為例，開啟時應該有「取消」與「確認」兩個按鈕。這類單純的問題不需要高擬真度，光靠討論就能解決。
- **較細緻的問題**：假設這個彈出視窗在某些情況下需要顯示一些資料，那麼你可能就得提高一點擬真度。要怎麼呈現這些資料？在規劃規格時，往往很難確切知道畫面該長什麼樣子、在特定情境下該有什麼行為。要確保這些想法都已在「半可運作的程式碼」中實際驗證過，就需要更高的擬真度。

有些問題，真的只能透過原型來回答。而且由於製作原型的成本比以往任何時候都低，我傾向讓更多的討論以較高的擬真度進行。

### 我的工作方式

基本的東西，我會直接用討論解決：代理程式（agent）會問我一些問題，通常是透過一場 grilling（拷問式提問）討論，然後我說「好，聽起來不錯」。但一旦遇到任何讓我覺得「我真的需要看到它實際運作、親身感受它、看著它跑起來」的地方，我就會要求做一個原型。

### 原型在 Wayfinder 中的角色

原型是我全新的 Wayfinder 技能的一環。Wayfinder 是一個能讓你規劃大量工作的技能（之後會有專門介紹 Wayfinder 的影片）。它的做法是：處理一大塊工作，並將其拆分成不同的規劃階段（planning sessions），每個階段都有自己的票券（ticket）。

在文件中應該有一段「票券類型」（ticket types）的說明，清楚列出有哪些不同的票券類型。這裡我們要看的是兩種：

- **grilling 類型**：使用 grilling 技能。這是預設情況，也就是你與代理程式聊天，釐清所建構項目的基本範圍。
- **prototype 類型**：當你需要提高討論的擬真度時使用，也就是做出一個廉價、粗略但具體的成品（artifact）讓你可以據以回應，例如大綱，或是透過 prototype 技能對 UI、邏輯、程式碼做的粗略嘗試，並將原型作為資產（asset）連結起來。當「它該長什麼樣子」或「它該有什麼行為」是關鍵問題時就適用。

無論你有沒有使用 Wayfinder，這都為你提供了一套非常明確的判斷標準，告訴你什麼時候該動手做原型。

## 實際示範：為圖表應用程式加入搜尋功能

我想你一定迫不及待想看實際操作，那我們就來看看成果。

我一直在用 Wayfinder 擴充我的圖表繪製應用程式，它是以 TLDraw 為基礎建構的。我想要有一個能搜尋舊圖表的方法，但這裡的資料模型相當複雜：有圖表（diagrams），還有圖表隨時間變化的快照（snapshots）。我想建立一個搜尋列，卻不確定它該長什麼樣子、有什麼行為。

於是我執行了 prototype，它在畫面底部做出了一個小小的切換器（picker）。切換器裡有三個不同的選項：A、B 與 C。每個選項都編碼了幾項設計決策，讓我可以針對它們做出回饋並反覆調整。

### 檢視三個選項

**選項 A**：我剛產生出來，還沒仔細看過。我可以搜尋圖表，看看會出現什麼。這個選項是「原地重排的分組列」（reflow in place grouped rows），它會依圖表名稱將快照分組。我很喜歡搜尋框放在上方的位置，但這種分組方式讓我覺得不對勁。

**選項 B**：我們再搜尋一次，這次在 model 裡搜尋。現在左側有分組，可以用來向下篩選，這相當不錯。那如果我改搜尋別的東西，而它已經……好，篩選條件會在這時重設。這樣還可以，但我很好奇 C 長什麼樣子。我真的不喜歡頂端那個「Search diagrams」的字樣，看起來不太美觀，不過先看看這個選項吧。

**選項 C**：搜尋 model，哇，現在所有結果都直接列在同一處，沒有篩選器。我其實非常喜歡這個，不過有幾個地方我不喜歡。例如那些「目前」（current）標記，看起來像是很技術性、很奇怪的東西，而且「目前」這個標記還與圖表快照一起顯示。於是我有了一些回饋要提供給原型。

### 壓縮上下文並提供回饋

這一輪原型製作大約花了 10 萬個 token。所以我打算先壓縮（compact）上下文，並告訴它「我們要針對這個再做一些 QA」。我認為此時壓縮是合理的：我們需要保留原型的所有資訊，以及當中所有的設計決策，只需要給它一些回饋，並在程式碼庫中的同一個位置繼續對話即可。

我真的應該另外做一支影片，講講我用來判斷「該壓縮、該清除（clear），還是該交接（handoff）」的決策樹，不過那是以後的事了。

好，現在來給回饋。我很喜歡 A 的搜尋框，也喜歡 C 的版面配置。我已經用語音輸入了更多回饋，現在送出。

### 反覆調整，產出豐富的資產

這個階段的重點，在於反覆調整這個原型。我不是單純地說「好，這個最好」，而是要真正做出一些設計決策，產出一份內容極為豐富的資產。所有這些設計決策都會被編碼進原型中，而我通常會把原型儲存在一個拋棄式分支（throwaway branch）上。這意味著，當實際要動手實作時，除了規格之外，還有真正的前端程式碼可以參考，通常可以直接複製貼上使用。

當然，製作這些原型確實需要時間：擬真度越高，token 成本就越高。如果我們試著只用討論來解決，擬真度會比較低，得到的答案也就比較沒有用，但花費的 token 也比較少。

可以看到，它現在開始產出我一路朝向的 D 版本了。

有一點要特別提醒：**這個原型是直接整合在線上運作中的頁面裡的**，並不是做在一個拋棄式的路由上。你想的話當然也可以那樣做，但我很喜歡看它真正接進線上路由，因為這樣能給你更多彈性，也更真實地呈現程式碼實際運作的樣子。

### 檢視最終的 D 版本

好，看起來 D 已經產生好了，來看看它長什麼樣子。沒錯，我們有 A 的搜尋框；在裡面搜尋 model，就能看到我要求的東西全都完成了。之前有一個項目重複出現，現在只剩一個。理論上，如果我點擊這個，我不確定它是否真的能運作，也不知道這是不是原型的一部分。可以，它能運作！太棒了，很多功能看起來現在都已經完成了。

### 下一步是什麼？

你可能會問：之後的下一步是什麼？現在我認為這個原型已經完成了。這次算是很快的一次，通常我會在這個階段做得更多。我會把它交給一個 AFK 代理程式（人不必在場、自行運作的代理程式），讓它把所有東西接起來、刪除舊的原型程式碼，並確保它符合原本的規格。

你可以想像，這樣得到的成果相當驚人。因為我們進行的是高擬真度的討論，我們能看到一個正在執行的線上版本，並據此給出回饋。這些回饋極具價值，而且已經內建在拋棄式分支裡，供實作者直接參考。

我常常看到有人說：「它做出來的東西不是我要的。我寫了一份又大又漂亮的規格，結果它做出來的東西卻莫名其妙。」你很可能只是沒有以夠高的擬真度進行討論，而你其實應該去做原型。

## 原型不只適用於 UI 或前端

最後，我不希望你帶走的印象是「這只適用於 UI 或前端」。

前端當然從原型中獲益良多，因為「它該長什麼樣子」是一個非常關鍵、卻很難在討論階段回答的問題。然而，當你在處理更複雜的事情，尤其是後端工作時，也會遇到這樣的問題：這個邏輯、這個狀態模型，感覺對嗎？只要你建構的東西有一定程度的複雜性，或需要在真實世界中運作，你就會一再遇到這類問題。而要解決這些問題、做出真正滿足使用者需求的東西，特別是面對複雜的系統時，最好的方法往往就是做一個原型。

原型不一定要是 UI 原型。我在技能裡寫的是：**建構一個小型的互動式終端機應用程式，讓狀態機（state machine）跑過那些光靠紙上推演很難想清楚的案例。** 換句話說，就是純邏輯原型。我收到許多人的回饋，說這是個很棒的小功能。

這兩個分支各有自己的參考文件，會明確告訴代理程式該如何進行：如果要建構的是邏輯原型，它就看這一份；如果要建構的是 UI 原型，就看另一份。

所以，我懇請你：**以更高的擬真度來進行討論。**

隨著代理程式越來越擅長使用畫布（canvas）與設計工具，我相信線框圖（wireframe）也一定會捲土重來。而關鍵在於：從討論與規格跳到可上線的程式碼，這一步的跨度非常大；但如果你手上有一個可運作的原型，要把它轉化為正式環境的程式碼就簡單得多。
