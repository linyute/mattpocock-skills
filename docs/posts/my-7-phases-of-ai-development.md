# 我的 AI 開發七階段

我歸納出與 AI 協作開發的七個階段，這些階段能持續帶來高品質的成果。無論你使用的是 [Ralph loops](https://www.aihero.dev/getting-started-with-ralph)、[GSD](https://github.com/gsd-build/get-shit-done)、[Spec Kit](https://github.com/github/spec-kit)，還是任何其他 AI 程式設計方法，這些階段都適用。

具體如何實作由你決定，但這七個階段代表了成功的 AI 輔助開發工作流程中的共通模式。

本指南寫給相信基本功在 AI 時代依然重要的工程師。它不適合 vibe coder，而是為那些認真看待 AI 工程、致力於建構可長久維護之應用程式的人而寫。

## 階段 1：構想

每個專案都始於一個構想，也就是你啟動這個流程的原因。它可能是：

- 你想建構的完整應用程式
- 特定的功能或錯誤修正
- 程式碼庫重構

構想的規模可大可小。這套流程可從大型專案延展到範圍狹窄、目標明確的任務。

### 精煉你的構想

在進入研究或原型設計之前，先反覆精煉你的構想。我使用 [`/grill-me` 技能](https://github.com/mattpocock/skills)，它會透過一連串提問，協助充實概念並使其更加具體。

這個早期的精煉工作有助於釐清需求並找出隱含的假設，避免在研究或原型上投入時間之後才發現問題。

## 階段 2：研究（選用）

如果你的構想涉及外部相依性，或需要經歷困難的探索階段，請加入研究階段。

例如，當你要整合 Stripe 或不常見的 API 時，可以建立一個 `RESEARCH.md` 資產，將所有相關資訊快取在你的儲存庫中，讓代理程式可以存取。

### 為什麼研究很重要

代理程式通常在全新的上下文視窗中運作。如果探索過程十分困難（例如外部 API、不易取得的文件），將這些資訊快取在 `research.md` 檔案中，可以省去重複探索的工夫，並提升代理程式的表現。

**重要：** 研究資產通常只在本次衝刺或功能開發期間有效。研究內容若保留過久，可能會過時，或讓代理程式走錯方向。

## 階段 3：原型設計

當你需要將自己的品味落實到成果上時，原型設計是不可或缺的。在這個階段，你仍在探索要建構什麼，以及它應該如何運作。

在拋棄式路由上建立多種變化版本，讓 LLM 向你展示不同的做法。透過幾輪工作階段反覆調整，找出最佳選項。

這適用於：

- UI 設計與行為
- 軟體架構決策
- 測試外部服務整合

及早進行原型設計，讓你能將勝出的設計提交到程式碼庫中，供代理程式在實作期間使用。等到撰寫 PRD 時，具體的範例會比抽象的描述更有價值。

## 階段 4：產品需求文件（PRD）

完成研究與原型設計後，就該好好描述目的地了。此時你應該已經清楚掌握最終狀態。

請專注於使用者會看到什麼，以及它的行為方式，而非實作細節。PRD（產品需求文件）描述的是最終狀態，而非過程。

在撰寫 PRD 時，請提示代理程式針對每個決策點對你進行追問，以敲定設計。走過你完整的決策樹，找出邊界情況與需求。我使用專為這個流程打造的 [`/write-a-prd` 技能](https://github.com/mattpocock/skills)。

## 階段 5：實作規劃（看板）

將 PRD 拆解為實作計畫。看板是一份帶有阻擋關係的工單清單，描述了所有需要完成的工作。

雖然你可以建立單一的循序計畫，但看板能讓平行處理更有效率。找出所有未被阻擋的工單，並為每一張啟動一個代理程式。我使用 [`/prd-to-issues` 技能](https://github.com/mattpocock/skills)來自動化這個拆解過程。

GitHub issues 同時適用於 PRD 與看板，不過它沒有內建的阻擋關係功能。如果你需要這項功能，[Linear](https://linear.app) 是更好的選擇。

## 階段 6：執行

執行程式設計代理程式，完成看板上的所有工單。這就是實際撰寫程式碼的階段。

多數時候，由單一代理程式依序處理每張工單就已足夠。不過，若看板結構良好，你可以同時讓多個代理程式處理未被阻擋的工單，以平行方式進行。

我使用 [Ralph loops](https://www.aihero.dev/getting-started-with-ralph)，它與這樣的配置搭配得相當有效。Ralph loops 讓代理程式能自主運作，同時透過自動化測試與驗證維持程式碼品質。

### 離開鍵盤執行（AFK）

只要有妥善的準備（研究、原型、看板與 PRD），你就能在離開鍵盤的情況下執行這個執行迴圈，並獲得出色的成果。

關鍵在於確保代理程式擁有所需的全部上下文：

- 針對外部相依性的研究資產
- 提供設計模式的原型程式碼
- 說明需求的清晰 PRD
- 附有驗收條件、定義明確的工單

當這些要素都到位時，代理程式就能在無需人類不斷介入的情況下做出明智的決策。

## 階段 7：品質保證

執行完成後，請代理程式建立一份供人工審查的 QA 計畫。這份計畫應列出要驗證的具體測試情境、邊界情況與驗收條件。

QA 通常會發現問題或改進機會，進而產生更多看板工單，並開始另一輪執行迴圈。這是預期中的正常現象，也是健康的做法：你會反覆經歷階段 5 到 7 多次，直到產出精緻的產品。

每一次迭代都應讓你更接近正式環境的品質：

1. 代理程式建立 QA 計畫
2. 人類審查並測試實作成果
3. 人類找出錯誤、UX 問題或改進之處
4. 建立新的工單
5. 回到執行階段

### 程式碼審查與人為參與

QA 包含由人類閱讀所產生的程式碼，以確保品質、可維護性與正確性。這未必永遠有必要（尤其是在灰箱架構下），但對於正式環境的系統而言，這是一道重要的品質關卡。

請檢查：

- 邏輯錯誤或邊界情況
- 安全性漏洞
- 效能問題
- 程式碼的可維護性與可讀性
- 是否遵循專案的模式

這七個階段構成了與 AI 代理程式有效協作的核心框架。

## 摘要

| 階段                | 目的                 | 主要交付成果     |
| ------------------- | -------------------- | ---------------- |
| 1. 構想             | 定義你想建構的內容   | 問題陳述         |
| 2. 研究（選用）     | 探索外部相依性       | `research.md` 資產 |
| 3. 原型（選用）     | 測試設計與 UX 構想   | 可運作的原型     |
| 4. PRD              | 記錄最終狀態         | 產品需求         |
| 5. 看板             | 將工作拆解為工單     | 含相依關係的任務清單 |
| 6. 執行             | 建構實際的實作       | 可運作的程式碼   |
| 7. QA               | 驗證已完成的工作     | `QA` 計畫與回饋  |

這個框架可能會隨著新模式的出現而演進。程式碼審查值得特別關注，它可以整合進執行流程，或在 QA 階段中進一步擴充。
