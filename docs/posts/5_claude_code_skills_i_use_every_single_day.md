# 我每天都在用的 5 個 Claude Code 技能（Skills）

我當工程師將近十年了，而我認為，在此時此刻，「流程」從未如此重要。現在你唾手可得一整支「中等到不錯」的工程師大軍，隨時都能調度。但這些工程師有個怪異之處：他們沒有記憶，不記得自己以前做過什麼。因此，你需要極其嚴格、定義明確的流程，才能讓這些代理（agent）真正做出有用的事。

這意味著，身為開發者的你，必須不斷尋找各種方法來引導代理，讓它們不偏離正軌。對我來說，這催生了大量的技能（skill）建構工作。

我目前使用的所有技能都放在這個儲存庫中，每一個都是我親自逐一檢視並設計的。有些我比較少用，但有些我每天都會用。這些技能幫助我把自己的流程編碼化，讓 AI 每一次都能沿著一條非常嚴格的路徑前進。使用這些技能之後，AI 產出的程式碼品質大幅提升。

## 技能一：Grill Me（拷問我）

這可能是我最喜歡的技能。它只有短短三句話，我們直接完整唸出來看看它在做什麼：

1. 不斷地針對這份計畫的每個面向訪談我，直到我們達成共識。
2. 沿著設計樹（design tree）的每一個分支往下走，逐一解決各項決策之間的相依關係。
3. 如果某個問題可以透過探索程式碼庫來回答，就去探索程式碼庫，而不是問我。

### 什麼是設計樹？

「設計樹」的概念出自 Frederick P. Brooks 的《The Design of Design》。嚴格來說，我不確定它是否真的源自這本書，但這是我第一次看到它的地方。

設計樹的概念是：當你逐步朝著某個設計前進時，必須走遍設計樹上所有的分支。舉例來說，假設你要設計一個搜尋頁面，必須先決定要做「進階搜尋」還是單純的「文字方塊」。如果選擇進階搜尋，就得進一步釐清需要哪些篩選條件、哪些排序方式。你就這樣一路沿著樹往下走，直到在實際動手寫程式碼之前，把設計盡可能完整地想清楚。

### 為什麼需要它

我會在想與 LLM 達成共識時呼叫這個技能。我最近發現，Claude Code 在計畫模式（plan mode）下，往往會太早丟出一份計畫，在我覺得與 LLM 還沒達成共識之前，就先建立好一份文件。而 Grill Me 技能會強制展開這場對話，迫使 LLM 針對每一個環節訪談我。

### 實際範例

這是我最近與 Claude 的一段對話，主題是為我的課程影片編輯器程式碼庫新增一項功能。我給了它一份我自己做的研究（存成 Markdown 檔案），然後說：「拷問我。我想想看要不要把這個加到正確的頁面上。」

它載入了這個技能，而我想讓你看的是它到底問了我多少問題。首先，它先探索了程式碼庫中相關的部分，這很好。接著往下看，可以看到：

- 問題 1：文件存放在哪裡？
- 問題 2：UI 版面配置為何？
- 問題 3：哪些模式要有文件面板？
- 問題 4：文件的生命週期。
- 問題 5：寫入文件的工具長什麼樣子？
- 問題 6：編輯工具的形式。
- ……一路到問題 9、10、11、12，甚至到第 16 個問題。

以我的標準來看，這還算是相當短的拷問環節。我遇過坐在那裡與 AI 一問一答將近半小時、45 分鐘的狀況，針對的是非常複雜的功能，問題可能多達 30、40、50 個，而這一切都來自這個小得不能再小的技能。

這是我希望你帶走的一個重點：**技能不需要很長才有影響力。** 你只需要在對的時間，為 LLM 選對文字。而「設計樹加上逐一解決相依關係」這個做法，對我來說實在太好用了。

順帶一提，如果你想要這些技能，連結會放在下方。

## 技能二：Write a PRD（撰寫 PRD）

當我已經與 LLM 達成共識、把想法拷問過一輪並理解其所有影響之後，如果決定要實作，就會呼叫下一個技能：撰寫 PRD（產品需求文件）的技能。

在剛才那段對話中，我就是這麼做的：它問我「有什麼遺漏或錯誤的地方嗎？」我回答：「Write a PRD。」我會在後面加上 `user` 的後綴，因為我有一些放在專案內的同名技能，所以才這樣區分。

### 技能內容

這個技能會在使用者想建立 PRD 時被呼叫。你可以略過不必要的步驟。例如在先前的對話中，它說：「我們已經做過深入的訪談了，直接進入步驟四。」

各步驟如下：

1. 請使用者提供一份冗長而詳細的描述。
2. 探索儲存庫，驗證使用者的說法。
3. 不斷地訪談使用者，基本上就是把 Grill Me 技能再複製一次。
4. 勾勒出為了完成實作，需要建構或修改的主要模組。（這部分稍後會再談，因為它連結到我之後會介紹的技能。）
5. 一旦對問題與解法都有完整的理解，就使用下方的範本撰寫 PRD。PRD 應以 GitHub issue 的形式提交。

### 我的開發流程

我的開發流程是：把這些 PRD 放在 GitHub 上，將它們轉成更多引用父層 PRD 的 GitHub issue，然後由一個 Ralph loop 逐一迴圈處理每個 issue，直到全部完成。

### PRD 範例

回到剛才那段對話，可以看到它建立了這份 PRD，是四天前的事。裡面有問題陳述：文章撰寫頁面目前在每次 AI 互動時，都會重新產生整份文件。而解決方案是在文章撰寫器中加入分割窗格的文件編輯體驗：聊天維持在左側，新的文件面板在右側，等等。

這是個大型功能：我們要在一個類似 AI 聊天的功能中加入文件編輯。這裡最重要的是**使用者故事（user stories）**，這份 PRD 裡有非常多的使用者故事。這源自敏捷方法論，基本上我們是試圖用語言來描述系統期望的行為，這並不是件容易的事。我自己還沒有真正找到最理想的格式，目前這種寫法只是我個人比較喜歡的，但你完全可以改用 Cucumber 語法，或任何你習慣的方式。

接著捲到最下方，我們會看到一些實作決策。這些實作決策不要寫得過度細節，因為我們希望它們經得起時間考驗；如果程式碼與 PRD 逐漸脫節，等到真正要實作時就會出問題。不過你可以看出其中的道理：它是對我們要前往的「目的地」非常好的描述。

但 PRD 裡沒有的，是實際的「旅程」，也就是我們要如何抵達這個目的地。

## 技能三：PRD to Issues（PRD 轉 Issue）

回到那段對話，這就是我使用下一個技能的時機：PRD to Issues。它會取得一份 PRD，也就是目的地，並將它轉換成一塊由各個 issue 組成的看板（Kanban board），每個 issue 都可以獨立被領取。

### 運作步驟

第一步是找出 PRD。如果 PRD 還不在你的上下文視窗（context window）中，就用指定的指令把它抓取進來。必要時探索程式碼庫，然後——等等等等等——草擬「垂直切片」（vertical slices）。

### 垂直切片與曳光彈

要如何把一份 PRD 拆解成個別任務，往往不是那麼明確。開發者幾百年來（yonks）一直都在做這件事，也培養出了一種直覺。依我之見，最好的方式是把它拆成能**盡快揪出「未知的未知」**的任務。舉例來說，如果你要整合一種新的服務，或是要整合兩個你從沒整合過的東西，那就應該先做這部分，因為它能讓你儘早得到回饋，知道你的做法究竟是否可行。

這裡最貼切的類比是「曳光彈（tracer bullet）」。我不細講它的意思，但基本上，每個 issue 都是一片穿過所有整合層的薄薄「垂直切片」，而不是只涵蓋單一層的「水平切片」。

### 實際成果

在那段對話中，它把那份相當複雜的 PRD 拆成了僅僅四個切片。它首先建立了一個帶有測試的「引擎」。這其實是個很好的垂直切片，因為這個引擎之後會驅動其餘的整體架構。如果這個引擎因故無法運作，或根本不可行，我們就需要儘快找出來，而這個拆解方式正是做到了這點。

### 阻擋關係與平行處理

PRD to Issues 也會在任務之間建立「阻擋關係」（blocking relationships）。例如這裡的第 2 項沒有被任何項目阻擋，所以它可以獨立於第 1 項被領取。如果你有平行代理的設定，可以同時派出兩個代理處理，例如以背景任務執行，這就非常實用。這也代表未來你可以在其中加入其他 issue，例如你發現的 QA 問題或需要改善的地方，然後在它們與其他所有項目之間建立阻擋關係。

我們可以看到：第 3 項被第 1 項（編輯引擎）阻擋，而第 4 項（Monaco 編輯器切換）被第 2 項阻擋。我對這些全部回答了「是」，於是它就建立了所有這些 GitHub issue。這些 issue 會引用父層 PRD，讓本機的代理可以抓取並檢視。它基本上說明了要建構什麼，而且關鍵在於，它會引用 PRD 中先前的使用者故事。

### 實作結果

接著我們可以看到一則來自 Claude Code 的留言，是實際完成這項實作的代理所留下的。它寫道：「一個純函式的文件編輯引擎，附有 28 個測試，涵蓋所有驗收條件。」我們也可以查看引用這個 issue 的 commit。基本上，是我的 Ralph loop 過來根據這個 issue 完成實作、留下註解、關閉它，接著下一個 issue 就解除了阻擋。

### 小結

到目前為止：

- **Grill Me** 技能幫助你充實一個想法；
- **Write a PRD** 技能幫助你把那個想法轉成一份文件；
- **PRD to Issues** 技能則幫助你把那份「目的地」文件，轉成一段實際的「旅程」。

但接下來，你要怎麼真正執行這些任務？要如何讓實作穩如磐石，並提升產出程式碼的品質？

## 技能四：TDD（測試驅動開發）

我們有一個 TDD 技能。TDD 即「測試驅動開發」（test-driven development）。當你呼叫這個技能時，它基本上會強制（更精確地說，是鼓勵）代理遵循「紅燈—綠燈—重構」（red-green-refactor）的循環。

和我其他的技能不同，這個技能裡面的內容相當多。它不只是技能本身，還包含了關於重構、模擬（mocking），以及什麼是深層模組（deep modules）的想法。做好 TDD，一直是我持續提升代理產出的最穩定方法。讓我們看看裡面到底有什麼。

我會略過哲學的部分，留給大家自己閱讀。我們直接看這個工作流程。

### 步驟一：與使用者確認需要的介面變更

第一點非常重要：**與使用者確認需要哪些介面（interface）變更。**

我最近做過一支關於介面與實作的影片，這裡簡單摘要一下。當 AI 面對一個糟糕的程式碼庫時，它看到的是像這樣的東西：有大量細小而沒有區隔的模組，並沒有真正分組在一起，它不太理解這些東西之間的關係。因此它得花費許多功夫去釐清：誰負責什麼？相依關係是什麼？這個程式碼庫到底是怎麼運作的？

反過來說，如果你把它重組成幾個較大的模組，上面只覆蓋一層薄薄的介面（介面指的是這些模組實際匯出的函式，也就是呼叫端真正會呼叫的東西），那麼 AI 要在這個程式碼庫中導覽就容易得多，也更容易判斷該如何測試這些模組，因為你只需要在它們的介面、也就是邊界上進行測試。完整影片可以在下方查看。

因此，這個 TDD 技能想做的，就是讓這些介面變更成為 AI 最優先考慮的事，讓它明白：更動介面是一個重要的決策，需要花時間仔細處理。

### 其餘步驟

- 與使用者確認要測試哪些行為。
- 為可測試性而設計介面（連結到一份文件）。
- 接著還有一些關於規劃的內容。

### 紅燈—綠燈—重構循環

之後它會進入一個很棒的迴圈：一次只寫一個測試，而且先寫測試。我之前談過紅燈—綠燈—重構，如果你有興趣，我會把影片連結放在下方。但我發現，紅燈—綠燈—重構搭配代理，效果令人驚豔。它基本上會重複這個迴圈直到完成：先寫一個會失敗的測試，再寫程式碼讓測試通過，最後逐一檢視並尋找可重構的候選項目。

說實話，重構這一步我並不覺得特別出色，表現也不算絕佳，因為 LLM 往往相當不願意重構自己寫的程式碼。如果你清空 LLM 的上下文，它等於抹去了自己的記憶，對剛寫出來的程式碼就不會那麼執著。但當它自己的程式碼還躺在它自己的上下文視窗裡時，它就很不願意去改動。

這個 TDD 技能，就是我用來提示我的 Ralph loop，讓它們執行紅燈—綠燈—重構的技能。

## 技能五：Improve Codebase Architecture（改善程式碼庫架構）

TDD 對你的要求很高，更精確地說，是對你的**程式碼庫**要求很高。在結構不良的程式碼庫中做 TDD 非常困難，因為測試邊界很不清楚：該單獨測試這些模組嗎？還是單獨測試那些模組？邊界到底在哪裡？

相反地，當你的程式碼庫長得更像是模組邊界清楚的樣子時，測試就容易得多。所以，如果有個東西能讓你的程式碼庫變成那個樣子，不是很棒嗎？好消息是：我們有「改善程式碼庫架構」技能。

### 流程

**1. 探索程式碼庫。** 就像代理自然會做的那樣去探索。我們的目標是找出令人困惑之處，也就是自然地浮現出 AI 覺得困惑的地方，以便之後幫助它。例如：

- 理解一個概念時，需要在許多小檔案之間跳來跳去的地方在哪裡？
- 哪裡只是為了可測試性而抽出純函式，但真正的臭蟲卻藏在這些函式被呼叫的方式中？
- 哪裡有緊密耦合的模組，在它們之間的接縫處造成了整合風險？

這些都是資深工程師會對你的程式碼庫提出的問題。

**2. 提出候選項目。** 呈現一份編號清單，列出「深化機會」（deepening opportunities），也就是把程式碼庫中淺層模組深化為深層模組的機會。

**3. 使用者挑選一個候選項目。**

**4. 設計多種介面。** 技能會指示同時啟動三個子代理（subagent），每一個都必須為這個要深化的模組產出一套截然不同的介面。換句話說，我們把那段程式碼抽取出來，設計它未來可能呈現的各種樣貌。用多種不同方式去設計，是決定正確方向的絕佳方法。我看過這個代理為了一次大型重構，啟動了多達五個不同的子代理。

最棒的是，你不需要對介面設計懂得很多，也能讓它運作。比較之後，它會提出建議，說明它認為哪個設計最強、為什麼；如果不同設計的某些元素組合起來會很好，就提出混合方案。

請注意，我讓這個技能與語言無關，甚至可以說與一切無關。你可以在任何程式碼庫中執行它，就能得到一個像樣的答案，知道如何改善。也許會有四、五個候選項目真的需要處理，但我認為一次只應該做其中一個，因為它們真的很難完全消化，需要有人類坐下來參與，一起改善程式碼庫，因為這些決策需要品味。

**5. 建立 GitHub issue。** 最後，它會用 `gh issue create` 建立一份重構 RFC，作為 GitHub issue。

通常完成後，我會接著使用我的 PRD to Issues 技能，引用剛建立的那個 GitHub issue。這份 RFC 描述的是目的地，我們還需要一段旅程才能抵達，這就交給 PRD to Issues。

### 使用時機

在一個程式碼庫中偶爾執行這個技能，例如每週一次，找出改善的機會；或者在你突然大量開發、新增了一整塊額外功能之後，這個技能就非常、非常有用，能確保新程式碼符合程式碼庫的其餘部分，不會太草率。

隨著你不斷執行、不斷精煉你的程式碼庫，你會注意到代理的產出品質提升了，因為那句老話確實適用：如果你的程式碼庫是垃圾，AI 就會在其中產出垃圾。

## 結語：把代理當成人來對待

老實說，如果你把這些技能全部拿來，當作一本給人類看的小型 Markdown 流程手冊，它看起來也不會格格不入。我發現，要提升代理產出的程式碼品質，最成功的方法就是把它們當成人來對待。當然，是帶有奇怪限制的人：沒有記憶、像是複製出來的，一從育嬰艙出來就直接去上班。

如果你和我一樣，認為這些真正的工程能力非常重要，那麼這門課絕對適合你。
