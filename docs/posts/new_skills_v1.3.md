大家好，我的 Skills 套件 1.3 版正式推出了，這次帶來三項已經成為我工作流程核心的重要技能。今天我要介紹 implement spec、PR，還有 retro。其中 retro 是我在社群媒體上看到討論度最高、迴響最熱烈的一項技能，對我來說它也確實強大得驚人。

## Implement Spec：讓規格自動拆解成票券並逐一實作

我用來一次完成大型工作的主要做法，本質上是靠兩個不同的實體：一個是「規格（spec）」，另一個是實作該規格的「票券（tickets）」。規格就像是你要抵達的目的地，而票券則是把這個目的地拆解成一連串的工作階段（session），讓你可以分別交給單一的程式碼代理人（coding agent）去執行。

如果你試圖讓單一個程式碼代理人一次把整份規格做完，就會讓它陷入「腦袋變鈍」的狀態，甚至可能觸發自動壓縮（auto compact）。雖然這種做法有時候行得通，而且情況也在逐漸改善，但我仍然認為把工作拆成一張張獨立的票券，做法乾淨俐落得多。

問題在於，該怎麼編排（orchestrate）這些票券、怎麼把每張票券分派給一個程式碼代理人，一直讓使用者感到有點困惑，我自己對於該怎麼建議大家也反覆思考過好幾次。最麻煩、最需要手動操作的方式，就是由你自己管理整個流程：你告訴代理人「我們先實作第一張票券」，等它完成後，清空情境（context），再說「現在實作第二張」，等待、清空情境、再說「實作第三張」。你等於是在扮演一個 for 迴圈，這其實不太可行。這種方式我稱之為「手動迴圈」，一點也不好玩。

你可以改用「確定性迴圈（deterministic loop）」來取代它：寫一支腳本，讓它讀取每一張票券，然後自行呼叫實作流程。我會建議大多數人採用這種方式，因為一旦你把確定性迴圈設定好，它每次執行的方式都會完全相同，非常可靠，而且成本低廉——畢竟你不需要動用代理人或人力來跑這個迴圈，單純交給一支腳本去做就好。然而，建置這套機制相當複雜，需要耐心不斷打磨、調校，才能讓迴圈愈跑愈順，所以我認為這對初學者來說門檻太高。

因此，我想找一個方法，讓初學者不必自己手動跑迴圈。於是我決定嘗試一個折衷方案：讓子代理人（sub agent）去跑這個迴圈。換句話說，改由代理人來「帶小孩」，而不是人類。這代表所有的票券都會由子代理人來實作。這件事最近才變得可行，因為子代理人本身現在也能夠再衍生出子代理人——過去子代理人的能力多少被閹割過，但現在它們已經和編排用的主代理人（orchestrator agent）一樣強大了。

這正是 implement spec 技能在做的事：由代理人坐鎮，檢視所有票券、進行編排，再透過子代理人逐一實作。整體而言，這種方式還是比確定性迴圈差一些，畢竟確定性迴圈的優勢就在於「確定」——它每次執行的方式都一樣。但 implement spec 是一個很好的起點，可以讓你開始體驗「離開鍵盤（AFK，away from keyboard）」的工作流程：你暫時離開，它就會把整份規格實作完成。

在使用任何技能之前，你都應該把整份技能說明讀過一遍，而這份說明其實不會太長。它的流程總共有九個步驟，開頭還附上了一小段參考資料。其中一個關鍵重點是：它會盡可能地進行平行化處理。說明裡提到，這些票券並不是一份單純的步驟清單，而是一張帶有阻擋關係（blocking relationships）的工作圖（task graph）。也就是說，永遠會有一批「前緣（frontier）」票券處於可以被認領、立即執行的狀態。

來看看實際的步驟：它會先讀取規格與票券，接著在自己的子代理人中做一些初步探索，建立一條整合分支（integration branch），然後呼叫實作用的子代理人，以測試驅動開發（TDD）並搭配工作樹（work trees）的方式逐一實作每張票券。完成後，它會透過子代理人把成果合併回整合分支，再繼續派出更多實作子代理人，直到所有工作都完成為止。等全部工作完成後，它會對整合分支呼叫程式碼審查（code review），接著清理所有過程中產生的工作內容，把 PR 整理到可供審核的狀態。最後，你就能從這一份龐大的規格，得到一個單一的 PR。

老實說，我用這項技能的頻率，遠比我原本預期的還要高，尤其是在那些你還沒有建立好確定性腳本、還沒把「軟體工廠」流程調校到位的系統上，implement spec 真的非常好用。這項技能其實已經醞釀一段時間了，但我覺得現在正是推出的好時機，讓大家可以開始使用、實際動手調整，甚至打造出屬於自己的版本。這只是「如何實作自己的規格」的一個基本版本，你完全可以做出截然不同的變化版，例如使用疊加式 PR（stacked PRs），或是各種其他玩法。

## PR 技能：讓人類審查變得輕鬆

說到 PR，就不得不提我最近最常用的技能之一：PR 技能（PR skill.md）。我一直都是 Dex Hies 的忠實粉絲，最近也有機會跟他本人見面。他有一項很漂亮的技能叫做 Show Me，其作用是透過簡潔的圖表，幫助使用者以視覺化的方式理解目前討論的主題，並搭配相當精緻的虛擬碼呈現。單獨看這些虛擬碼可能覺得有點粗糙，但放進 PR 的脈絡裡一起看時，真的能讓 PR 變得容易閱讀、容易審查許多。

PR 始終是工作成果能否順利進入主線（main）的主要瓶頸。我設計這項 PR 技能的目標，某種程度上是受到 Show Me 的啟發，就是要讓人類的審查盡可能輕鬆。這項技能做的事情，本質上就是提供一套撰寫 PR 內文的範本，僅此而已。

我們首先會根據 Show Me 風格的範本撰寫一段摘要（這個範本也包含在技能之中），接著要求提供「證據」，也就是變更前與變更後的對照。這份證據是建立「信任代理人」、「信任代理人輸出結果」的重要環節。實際要求代理人提供證據，往往也會促使它多跑一個測試、多截一張畫面（如果它有這個能力的話），進而提供你關於實際變更是否真的如預期運作的執行期資訊。如果不要求確鑿的證據，代理人很容易只是說「嗯，這應該可以吧，因為我讀過程式碼了」。但沒有經過驗證，是我最近開始非常在意的一件事，尤其是在我和 Lauren 的那場訪談之後。

第三個標題是「合併風險（merge danger）」：這個 PR 合併之後會有多危險？我很喜歡的一個比喻是——這是一扇「雙向門」還是「單向門」？雙向門指的是你走過去之後還能再走回來的門，也就是說，我們可以輕鬆地將這個 PR 回復（revert）。而單向門則是那種一旦執行，就會對外部世界產生實際影響的 PR——它可能會刪除某些資料，或者回復起來的代價相當高昂。

最後一項則是「影響範圍（blast radius）」，也就是這次變更可能帶來的實際後果。舉例來說，如果一個 PR 屬於「雙向門」，而且影響範圍很小，那麼你其實不需要花太多力氣去仔細審查它。正因如此，把這項資訊放在內文最下方——很可能是審查者第一眼或第二眼就會看到的內容——就顯得格外重要。

舉個例子，這是我自己 repo 裡，由 PR 技能所產生的一份 PR 內文。這份 PR 本質上是把兩個幾乎一模一樣的演算法合併在一起。我們可以在適當的脈絡下看到哪些檔案被刪除、哪些檔案被新增，也能理解其中的函式與呼叫堆疊（call stack）是如何建構的。但最關鍵的，是這裡附上了實際證據——在一個真實的實體上，呈現了變更前與變更後的對照。在這個案例中，變更前沒有 intro 區塊，變更後則新增了 intro，這正是我們期望看到的行為。

最後，我們還能看到這個 PR 的合併風險被標示為「雙向門」——單純是一次重構，外加一項刻意的行為變更，而且影響範圍很小。

這項 PR 技能，已經徹底融入我的工作流程，成為不可或缺的一部分。它同時也是我見過「模型自行叫用」最穩定的技能之一——身為使用者的你，幾乎完全不需要操心。至少在 Opus 5.5 上，它似乎每一次都會自動被叫用。所以你應該只需要下載它，就能親眼看到自己的 PR 內文品質跟著變好。當然，如果你本來就已經有一套 PR 內文技能，那也不妨直接從這份技能裡挑你需要的部分來用。

## Domain Modeling 更名：從 context.md 變成 glossary.mmd

在談 retro 技能之前，先提一個重要變動：尤其是我 grill with docs 相關的功能，出現了一次重大調整。先來看一下 domain modeling（領域塑模）技能——現在它不再寫入 context.md，而是改寫入 glossary.mmd。

這項技能的靈感來自 DDD（領域驅動設計，Domain-Driven Design），源自 Eric Evans 那本《Domain-Driven Design》。當初我會用 context.md 這個檔名，本質上是取自 DDD 裡「限界上下文（bounded context）」這個概念。不過現在，我已經逐漸脫離原本那套偏向 DDD 風格的流程——雖然骨子裡其實還是在用 DDD 的精神，只是不再冠上那個名稱——因為我想要一個負擔沒那麼重的詞。context.md 這個名字實在太模糊了，既沒辦法在對的時機觸發代理人把它載入，對使用者來說也相當令人困惑。

另外，我也把 glossary（也就是原本的 context.md）裡的內容大幅精簡，精簡到最後，它本質上就只剩下一份詞彙表（glossary）而已，所以留著舊名稱也沒有意義了。現在統一改名為 glossary.mmd，而且這個變更已經套用到所有地方——我有大量的技能都仰賴偵測到 glossary.mmd 的存在，才能正確運作、才能在所有環節都正確使用這套領域語言，因此你一定得更新這個檔名。除此之外，這項技能本身的行為並沒有其他變化，純粹就是改個檔名而已，而我認為這是許多人期待已久的調整，很高興終於能推出。

## Retro 技能：回顧代理人的實際表現

接下來，讓我們實際執行一次 retro 技能看看。我注意到自己整套技能，其實對使用者提出了不少要求。過去我要求你負責長期維護並改善整個 repo——也就是說，我要求你管理你的 agents.mmd、管理你的技能、確保 repo 的 token 使用有效率、確保環境對代理人撰寫程式碼來說是安全無虞的，還要有良好的 lint 規則、良好的導覽結構。

後來我發現，其實我自己也在對自己的 repo、自己的代理人做大量類似的事情，為的就是讓它們更容易配合我工作、效能更好。於是我想，何不乾脆把這些事情打包成一項技能？這就是 retro 的由來——retro 是 retrospective（回顧、檢討）的縮寫。你可以針對某一次程式碼代理人的工作階段執行它，無論是目前這一次、或是像我目前手邊累積的十次之中的某一次，甚至是上一次的工作階段，它都會針對下一次的改善提出建議。

真正閱讀實際工作階段紀錄最棒的地方在於，它能夠看出當時到底發生了什麼事，能夠察覺到那些代理人可能自己都會迴避不提的低效環節。我很喜歡 Andre 寫的那篇關於 retro 的貼文，標題大致是「改變規則的一項利器」——我的代理人一路撞上各種問題，卻完全沒被發現，但靠著不屈不撓的堅持，功能最終還是以某種方式做出來了。換句話說，代理人抱怨的程度，其實遠遠不如它應該要抱怨的程度，也不會主動嘗試修正自己的錯誤。你某種程度上需要另一個代理人，回頭檢視那些工作階段，看看哪裡出了問題、該怎麼協助改善。

這正是我們這次執行時，代理人所發現的內容。它發現：代理人在你選定修正方案之前，就執行了一項「不可逆的公開動作」。它找出了 1.3.0 版為什麼會「消失不見」——原來是代理人在沒有真正徵詢的情況下，就直接執行了發布動作。這也是為什麼你實際去看發布紀錄時，會發現根本沒有 1.3.0 這個版本，只有 1.3.1。說實話，Claude 這次確實搞砸了，不過我個人並不是太在意，所以也不介意把這件事留在我的情境裡。

我們還能看到，這個 repo 目前完全沒有真正的防護機制——雖然有一支 PNPM 檢查腳本，但實際上根本沒有任何東西會去執行它，所以它建議我加上一套 CI 流程。再往下看，它也發現長時間的工作階段中，每次壓縮（compaction）之間會出現情境流失的情形。我現在會用 animatics 來製作影片或早期草稿，而它指出壓縮過程中確實會流失一些資訊，因此建議把部分重複出現的指示，搬進一個專屬的 animatic 技能裡——這一點我覺得真的很不錯，我一定會把它實作出來。

還有一項更有趣的發現：我為自己的課程影片管理工具打造的一支自訂 CLI，居然在浪費 token。可見 retro 同樣也會檢視 token 使用上的低效問題。另外還有一支叫 Wiki 的自訂 CLI，在本機環境裡根本不在 PATH 裡；而 Wiki AI 的「英雄」機制也被發現有缺口。總之，retro 毫不留情——它會確確實實檢視你實際的工作階段紀錄，找出問題所在，而且幾乎每次都能找到可以改善的地方。

不過，使用 retro 時，我要提醒大家務必動用自己的人類判斷力來看待這些建議。舉例來說，這次它認為最嚴重的那個問題，其實沒有那麼糟——頂多就是一次版本發布而已，我隨時都能重新切一個新版本出來。retro 的設計初衷，就是要保留「人在迴圈中（human in the loop）」的機制，而不是讓它自己不斷隨機產生修正方案。幾乎每次我展示這項技能給別人看，大家的第一反應都是：「哇，真想把這個完全自動化！」——不，你真的不會想這麼做。一旦自動化，代理人很容易陷入一個迴圈：不斷找出假性問題（false positives），不斷嘗試修正，最後你的 repo 跟代理人就會被帶往一個根本不該去的詭異方向。

所以我建議的做法，是針對你的代理人工作階段，抽樣執行 retro 就好。每當你有空檔、突然意識到「啊，我好一陣子沒跑 retro 了」，就找最近的幾次工作階段跑一次看看；也可以挑一次你覺得出了問題、或是代理人表現得有點怪的工作階段來檢視，retro 通常都能找出修正的方向。

在 retro 技能的內部步驟中，它會依照幾個類別去檢查可以改善的地方：你的程式碼庫導覽起來容不容易？有沒有可以加入的自動化檢查？能不能幫自動化審查者制定一套程式碼標準來落實？全域的 agents.mmd 健康狀況如何？工具的使用效率好不好？steering 檔案裡的指示有沒有空包彈（noop）？代理人是否能取得它所需要的全部資訊？

整體而言，自從我開始定期執行 retro 之後，我的 token 使用效率，以及能產出的工作品質，都有大幅度的提升。如果你也想讓自己的工作品質跟著提升，我會建議你去上我在 aihero.dev 上的 AI 程式設計速成課程。我今天也剛好在更新這門課程，新增了一堂聚焦在 implement spec 的課。如果你想真正掌控你的程式碼代理人、更好地運用我這些技能，這會是很適合的地方。
