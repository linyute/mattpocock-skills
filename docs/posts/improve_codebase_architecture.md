# 如何拯救被 AI 搞砸的程式碼庫（只需一個技能）

你大概已經看過無數 LinkedIn 上 CEO 們的貼文，說程式碼現在變得很廉價，大家可以比以往任何時候都更快推進。但實際發生的情況是：AI 只是加速了軟體熵增。換句話說，程式碼庫崩壞的速度比以往任何時候都快，因為每次你做出一項沒有考量整個程式碼庫的變更，就很可能引入一些細小、古怪的東西，讓程式碼庫變得更難修改。隨著時間推移，這些問題會像滾雪球般越滾越大，最後變成一大坨泥巴球（ball of mud）。這種髒亂不堪的爛泥，如果不知道方法，幾乎無法挽回。

我之前做過一支影片，向大家介紹「深模組（deep modules）」的概念。那支影片偏重於預防，也就是如何避免你的專案走到那個地步。這次我們來談談解方：如何把一個感覺已經無可救藥的程式碼庫救回來。你可以靠著一些老派的軟體基本功，加上我改良後的「改善程式碼庫架構」（improve codebase architecture）技能來做到。

我們會先逐步了解這個技能做了什麼，並回顧另一支影片中談過的一些術語，接著把它們應用到一個真實的程式碼庫上。順帶一提，這個技能是我 GitHub Skills 儲存庫的一部分，目前已有 4.1 萬 5 千顆星，簡直不可思議。

## 與 AI 建立共通詞彙

我最近為這個技能新增了一份術語表。與 AI 擁有共通的詞彙非常重要，因為這代表你們可以使用同一種語言交談、理解彼此的用詞，並且能更精確地表達你的需求。這些術語非常實用，我會用影片的一部分時間逐一說明它們的意義。老實說，只要深入理解這些概念，就能讓你成為更好的軟體開發者。

### 模組（Module）

我們先從模組談起。模組是應用程式中的一個單元。它可以是一組組合起來構成一個頁面的 React 元件；可以是應用程式中全權負責身分驗證的一群函式；也可以單純是你選用的記錄器（logger），例如把記錄輸出到主控台、寫入檔案，或傳送到第三方服務。

### 介面（Interface）與實作（Implementation）

在良好的程式碼庫中，模組之間會彼此溝通，而且是透過各自的介面來溝通。介面是呼叫者為了正確使用該模組而必須知道的一切。舉例來說，如果是身分驗證模組，它可能有登入方法與登出方法，這些方法就是該模組的介面。

不過，方法並不是唯一重要的東西。介面還包含一些比較難以界定的資訊，說明該如何呼叫這個模組，所以也可能包括文件。

而實作，則是模組內部的內容，也就是當你呼叫登入或登出時，它實際上做了什麼。

因此，我們談論的核心基本單元，就是散布在你應用程式各處、具有介面與實作的模組。

### 深模組與淺模組

這些模組可能是深模組，也可能是淺模組。深模組在相對簡單的介面背後，隱藏了大量的實作；淺模組則擁有複雜的介面，背後卻沒有多少實作。這些觀念來自 John Ousterhout 的著作《A Philosophy of Software Design》，我很推薦你買一本來讀。

深模組被認為比淺模組更好，因為它能向呼叫者隱藏更多資訊。換句話說，呼叫它的人（或呼叫它的函式）只需要了解那個小小的介面，就能使用背後全部的實作，非常棒。

我們把這稱為「深度（depth）」：呼叫者每學習一單位的介面，所能運用的行為量。非常優秀的開源函式庫（例如 TanStack Query）就擁有很好的深模組，也就是在極簡單的介面背後隱藏了大量的複雜度。

### 接縫（Seam）

這些模組會彼此互動，並相互依賴。例如，這個模組可能與那個模組互動，而那個模組又與上方的另一個模組互動，它們之間存在著這些依賴關係。（註：原逐字稿此處缺漏部分內容。）模組介面在應用程式中所在的位置，稱為接縫。接縫通常就是你進行單元測試或整合測試的地方。例如，如果我們想單獨測試下方的某個模組，就會在這個接縫處加上一個 mock 之類的替身。因此，找出接縫在應用程式中的位置，對於打造良好的架構至關重要。

### 轉接器（Adapter）

當你找出應用程式中的接縫後，就需要一個具體的東西（一個模組）來滿足該介面。我把它稱為轉接器，這個概念借自六角形架構（hexagonal architecture）。

舉例來說，假設你的應用程式依賴時鐘的運作。你可以在正式環境中使用真正的時鐘，而在某些測試中，則使用一個假時鐘作為轉接器。兩者都滿足該接縫處的介面，這代表你可以在測試中使用假時鐘，就不必真的等上兩週才能讓測試跑完。這就是接縫與轉接器相互配合的方式。

## 深模組的兩大好處

這一切帶來的好處是，深模組有兩項主要特性（或說兩大益處）：

- **區域性（Locality）**：對於維護者，也就是維護該模組的人而言，針對該模組的變更、錯誤及相關修正，都會集中在同一個地方，也就是那個深模組之內。如果它們分散在多個不同的模組中，區域性就很低。你想要的是高區域性：把重要且經常一起變動的東西歸納並放置在一起。
- **槓桿效益（Leverage）**：對於使用這個模組的人而言，模組越深，獲得的槓桿效益越大。換句話說，每學習一單位的介面，就能得到更多能力。

因此，當我們談論改善程式碼庫時，這正是我們要追求的兩項屬性。

## 實戰：改善一個真實的程式碼庫

好，知識夠了，基本的交戰規則我們都清楚了。現在來實際改善一個程式碼庫。

我們要看的是我的 course video manager 程式碼庫，也就是我錄製這支影片時實際使用的軟體儲存庫。這個程式碼庫大約有 1,500 次提交。我不會說它是一坨泥巴球，但也不能說它完美。它是一個 React Router 應用程式，底層使用 effect.ts。

### 啟動技能

我會在這裡開啟一個新的 Claude 工作階段，並執行我的改善程式碼庫架構技能。我們先把自動模式（auto mode）關掉，因為自動模式在這類需要人類參與的流程中會有些奇怪的行為，所以我不想在這裡開啟它。

可以看到它開始探索並瀏覽程式碼，這是它被指示最先要做的事。接著出現「探索架構以找出可深化的機會」。一個糟糕的程式碼庫，通常是有大量淺模組的程式碼庫，或是這些模組的槓桿效益很差，又或是區域性很差，也就是許多東西散落在許多不同的地方。

### 找出候選項目

好的，它回傳了一些候選項目。我們來把畫面放大，希望 Claude Code 不會當場崩潰。嗯，看來沒辦法放大畫面，謝啦 Claude Code。

我們可以看到它找出了六個可深化的機會。這些候選項目很難解釋，因為它們需要具備我這個儲存庫的領域知識。不過可以看到，它指出有一個概念並沒有單一的接縫。換句話說，這個插入點有兩套實作，它們各自存在，而兩者之間的接縫必然未經測試。這基本上意味著前端可能做了一些變更，但後端因為有另一套平行的實作，可能與前端不同步。

所以我認為這其實是個很好的候選項目，適合重構成單一模組。我們會獲得區域性，如它所說：交錯的片段（clip）與片段區段（clip section）的排序規則將集中在同一個地方。

### 挑選一個並進入拷問階段

我們來看看這個。我就說：「好，我想選這一個，看起來是個不錯的候選項目。」送出之後看它怎麼說。

好吧，Claude 在捉弄我，它回說「我想選一個」。我的意思是我選那「一個」。好。

接著它回來了，兩邊都有具體的程式碼作為依據，並進入一個「拷問（grilling）」階段。在這個拷問階段中，我們可以拿出裡面的想法，開始討論更好的解決方案會是什麼。這裡有句不錯的話：「後端沒有盡頭（The back end has no end）。」不要太字面地去理解它。

使用這個技能的過程，就是討論可能提出的解決方案，然後它會提出一個架構形態。一切完成之後，你可以把它當作 GitHub issue 放進你的議題追蹤系統，再由 AFK（不需人員在場）的代理程式接手處理。如果你對這部分有興趣，可以看看我關於 Sandcastle 的影片。

### 加速流程並檢視設計

在一般的開發過程中，我會逐一仔細地回答這些問題。但由於我正在錄影，情境稍微有些刻意，所以我會說：「你能不能直接為這些問題選擇你推薦的答案？」這應該能讓我們快速進入實際進行變更，或是把它整理成 issue 的階段。

於是它回來了，提出一個模組的形態，同時也要求驗證實作中某個 end 被折疊（collapsed）的部分，並草擬實際的 TypeScript 介面。我說：「好，兩個都做，聽起來很棒。」送出看看它怎麼說。

好，它已經釐清了所需的實作細節，並回傳了一份設計提案，也就是哪些函式基本上會成為這個模組的介面。我們可以和 AI 討論並把它確定下來。它又提出了兩個設計決策，希望我給予意見。

到這裡，我想你已經大致了解這個技能的運作方式，以及你會和 AI 進行哪種對話。如果我想把它轉成讓 AFK 代理程式接手的 issue，可以選擇轉成 PRD 或 issue。

順帶一提，如果你對我談到的這些技能有興趣，可以看看下方連結的這個網站。我打算為這些技能建立一個正式的文件網站，目前則有一份電子報可供訂閱，內容包括最新消息，以及讓你充分發揮代理程式效益的訣竅、技巧與資源。

## 心得：這個技能需要你做判斷

這裡需要注意的重點是，這個技能對你這位使用者要求很高。它不是那種可以放著跑、全靠它持續改善程式碼庫的 AFK 技能。它需要你這位坐在大型語言模型（LLM）之上的程式設計師做出判斷。

我把代理程式視為非常出色的「戰術型」程式設計師。它們能深入第一線、快速完成變更，但它們需要上一層的「戰略型」程式設計師來帶領。這個技能正是如此：它讓士官長（sergeant）在程式碼庫中四處巡視，尋找潛在的改善機會；但接下來，必須由你這位將軍（general）親自決定要做哪些變更，並判斷什麼對程式碼庫的長期健康最有利。

### 建議的使用頻率

我建議大約每隔幾天就執行一次這個技能，特別是在變動快速的程式碼庫中，你會找到大量可以深化程式碼庫的機會。模組越深，你從中獲得的槓桿效益就越高。而槓桿效益同時也意味著可測試性：如果你的程式碼庫擁有一組清楚明確的接縫，你就能圍繞這些漂亮的深模組寫出非常好的測試。測試越好，代理程式的產出品質也就越好。

## 在舊有程式碼庫中導入 AI

最後還有一點想法。很多人問我，要如何在舊有（legacy）程式碼庫中開始使用 AI。舊有程式碼庫很可能有許多淺模組。我的意思是，我們說的舊有程式碼庫，其實指的就是糟糕的程式碼庫，也就是難以修改的程式碼庫。

在開始修改舊有程式碼庫之前，你真正需要的是在程式碼庫外圍建立一套防護（harness），確保你的變更不會把任何東西搞壞。為此，你需要測試，而且是針對那些具有高槓桿效益與高區域性的優質深模組進行測試。因此，執行「改善程式碼庫架構」是個很好的起點。
