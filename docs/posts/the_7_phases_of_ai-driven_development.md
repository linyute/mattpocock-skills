# AI 驅動開發的 7 個階段

大家好！我會盡量簡短扼要地說明。我歸納出了與 AI 協作開發的七個階段。換句話說，當你和 AI 程式碼助理（我通常使用的是 Claude Code）一起寫程式時，想要交付出色的成果，就應該思考這七個階段。

至於如何達成這些階段，則由你自行決定。實作方式有很多種，但這七個階段是我認為在各種不同做法中相當普遍的共通點。無論你像我一樣主要採用 Ralph loop、使用 GSD，還是使用 Spec Kit，你很可能都會經歷這七個階段。

如果你認同這些內容，也相信在 AI 時代工程基本功依然非常重要，那就對了，我也這麼認為。這正是我在電子報中所探討與闡述的主題。這不是寫給 vibe coding 的人看的，我們是認真看待 AI 工程、認真打造可長可久之應用程式的人。如果這聽起來就是你，而且你想精進自己的技能，那麼這裡就是你要找的地方。

話不多說，我們直接進入清單。

## 階段一：構想（Idea）

一切從構想開始。你有某個想法，有某個理由啟動這個流程，有某件事想請 AI 為你完成。它可能是一個完整的應用程式構想，也可能只是要在現有程式碼庫中完成的一件小事，例如修正錯誤或新增功能。我也把重構算在這個範圍內，所以如果你有一個程式碼庫需要重構，這套流程同樣適用。

這個構想可大可小。這套流程可以把非常龐大的構想化為現實，也可以處理極小、極為聚焦的任務，兩者皆可。

先讓你預覽一下後續的安排：這個構想會被轉換為一組工單（ticket），由 AI 來完成。這組工單可能會交給許多 AI 同時處理，也可能只是一長串任務清單，由 AI 依序逐一完成。

## 階段二：研究（Research）

如果這個構想涉及任何研究，或在建構程式碼的過程中有任何困難的探索工作，那麼你可能需要加入研究階段。

舉例來說，如果你要整合 Stripe，或是串接一個不太常見的 API，你可能會希望建立一份資產，把與該主題相關的所有研究（依據你的構想）整理後快取起來，放在儲存庫中，或是任何你的代理程式（agent）可以存取的地方。

原因在於，代理程式每次進行工作時，可能都必須在全新的上下文視窗中探索儲存庫。如果這種探索並不容易，例如牽涉到外部 API，或是難以存取的地方，那麼你就會希望把結果快取到一份 research.md 資產中，並且在這個時間點務必執行研究階段。

## 階段三：原型（Prototype）

研究之後的下一步是製作原型。在原型階段，我們仍然不太確定究竟要建構什麼，甚至可能不確定為什麼要建構它。

如果你需要把自己的品味融入成果中，原型就非常重要。例如，你需要某個 UI 呈現出特定的外觀或行為，但還不確定該採用哪一種。我通常的做法是在一個用完即丟的路由上，放上一大堆不同的構想，也就是讓 LLM 把它能想到的所有原型做法都展示給我看。接著我會在幾個工作階段中反覆調整原型，然後說：「好，這個看起來最棒。」

我發現及早這麼做絕對是必要的，因為你可以把原型提交（commit）到程式碼庫中，讓代理程式在真正開始實作時能夠參考它。

## 階段四：撰寫 PRD

第四個階段是建立 PRD。經過研究階段，我們對所使用的外部 API 有了更多的了解；經過原型階段，我們對原型也有了更多認識，並且實際看過一些程式碼。現在是時候好好描述目的地了。

此時我們應該有信心能夠理解最終狀態，也就是我們最後想要建立的成果。我們還不會知道所有的實作決策，只會知道最基本的部分：使用者會看到什麼，以及它會如何運作。

順帶一提，我們不一定要稱它為 PRD。PRD 是產品需求文件（product requirements document）的縮寫，但說穿了，它只是一份描述我們要前往之最終狀態的文件。

在建立這個最終狀態的過程中，我們必須徹底敲定設計。這意味著我們需要提示代理程式，讓它徹底地盤問我們，沿著決策樹的每個分支逐一走過。我有一個專為此目的設計的「撰寫 PRD」技能（skill），如果你有興趣，我會把連結放在下方。

## 階段五：看板（Kanban board）

建立好 PRD 之後，就該把它拆解為某種實作計畫。

如果你不是開發人員，或是從未使用過看板（Kanban board）、Jira 看板之類的工具，這裡簡單說明：看板就是一份工單清單，工單之間具有阻擋（blocking）關係。我們本質上只是在描述需要完成的工作。

因此，我另外有一個技能，用來把 PRD 轉換為一個個獨立的議題（issue）。我們也可以建立單一的循序計畫，把 PRD 轉成實際的程式碼，但使用看板能讓我們非常有效地平行處理。我可以直接到看板上，找出所有沒有被阻擋的工單，為每一張工單啟動一個代理程式去解決它。

## 階段六：執行（Execution）

說到這裡，我已經開始談到執行了。在某種迴圈中，執行一個程式碼代理程式，去完成看板上所有的工單。

多數情況下，你並不需要平行處理，由一個代理程式依序處理每張工單通常就足夠了。對我來說，這就是 Ralph loop，在這套設定下運作得非常有效。我會在下方附上我撰寫的 Ralph 相關文章連結。

## 階段七：品質保證（QA）

最後，當執行完成，你得到一份可供檢視的成果後，接著請代理程式建立一份 QA 計畫，供人類對完成的工作進行 QA。

這通常會在看板上產生更多任務，然後再次進入執行迴圈。因此，你往往會把最後這三個步驟（看板、執行、QA）重複迴圈許多次，逐步迭代到完美的產品。

這裡的 QA 也包括由人類實際閱讀執行迴圈中產出的程式碼。這不一定每次都需要，尤其是當你採用我在先前影片中談過的灰箱（gray box）架構時。

## 總結

整體而言，這七個階段就是我與 AI 代理程式協作時所思考的事項：

1. **構想**：從某個應用程式、功能或重構開始。
2. **研究**：如果知道有外部相依項目，以及難以執行的探索工作，就在研究階段把它們快取下來。順帶一提，這些研究資料通常只在這個衝刺（sprint）的期間內有效，也就是只在我們為應用程式提出的這個構想的生命週期內有效。原因是研究資料可能會過時，或是逐漸腐朽，進而導致代理程式在不必要的地方轉錯方向。
3. **原型**：如果需要融入我的品味，就會在這裡使用原型。我會實際與代理程式坐在一起，由人類參與其中（human in the loop），敲定一些想法。這不僅限於設計，也可以用於軟體架構，或是測試某個外部服務。這是必要的一步，因為等到 PRD 階段時，內容會有點太過抽象，你必須先取得具體的回饋。
4. **PRD**：接著我撰寫 PRD，也就是文件，描述我們要前往何處的規格。
5. **看板**：接下來，我把 PRD 轉換為看板，藉此理解通往 PRD 的路徑。順帶一提，我通常使用 GitHub issues 來處理 PRD 和看板，這是我發現的簡單做法。不過 GitHub 目前還沒有內建方式來表示工單之間的阻擋關係，所以你可能更適合改用 Linear 之類具備此功能的工具。
6. **執行**：看板準備就緒後，我以某種迴圈來執行它，對我而言就是 Ralph loop。我想你也可以採用人類參與的方式，自己坐下來逐張執行工單。但我通常發現，有了這一整套準備（研究、原型、看板，以及 PRD 的輔助），你完全可以讓這個執行迴圈在無人看管（AFK）的情況下執行，而且結果會非常好。
7. **QA**：為了確保結果真的很好，我們接著進入 QA 階段，請代理程式產出 QA 計畫。然後由人類（沒錯，就是人類，我們在這裡）實際逐步檢查完成的工作，並為看板產出更多工單，再去執行、再做 QA，你應該懂了。

## 結語

你覺得這套流程如何？我有哪些地方說錯了，又遺漏了什麼？我想隨著我有更多想法，這些階段會增加到八個、九個階段。

這裡並沒有明確提到程式碼審查（code review）。我想我可以把它納入執行流程的一部分，或許也可以歸在 QA 之下，但無論如何，它絕對是產出良好程式碼的必要步驟。
