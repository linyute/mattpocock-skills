我想我找到了一種方法，可以與 AI 代理（agent）一起規劃任何規模的工作。我先前使用、把玩過的規劃工具，甚至是我自己做的那些，都顯得太受限，也太侷限於單一工作階段（session）。我覺得自己無法放手追求更大的野心，結果反而是在遷就 AI，把正在建構的東西縮小到剛好塞得進去，這感覺不對。這個新方法沒有這種限制。你可以規劃極為龐大的工作，它會跨越多種不同類型的工作階段來統籌規劃。它明白你無法一路順暢地走到終點，必須先一步步撥開戰爭迷霧；它理解彼此相依的決策，甚至讓你能夠平行規劃。而最棒的是，這一切都建立在軟體基本功之上，也就是我在 AI 出現之前，還是個「真正的開發者」時所學到的工作規劃基本原則。我已經把這些全部打包成一個技能（skill），現在就能在我的 skills 儲存庫中取得，名字叫做 Wayfinder。

## 為什麼需要 Wayfinder

過去我規劃工作的方式，完全綁在單一工作階段裡，也就是我 skills 儲存庫中的 grill me（或 grill with docs）技能。它至今仍是非常重要的基本元件，但終究只侷限在單一工作階段。

有些工作比上下文視窗（context window）還大，尤其是比代理的「智慧區」（smart zone，上下文視窗中表現最佳的範圍）還大。你一開始就知道這點，所以通常會在開啟 AI 代理的工作階段之前，先花時間把工作拆成較小的區塊，心想：「好，我先處理這一小塊，再處理那一小塊。」但接著你會發現，自己正朝著規劃的目標，在這一輪拷問（grilling）中前進，然後碰到一個無法回答的問題，或者乾脆發現自己迷失在迷霧中。同時你還得一直管理智慧區，盡量不要耗費太多 token。

這個技能已經推出一段時間了，大家都非常喜愛。有人說它一次就做出了原型（prototype），讓他連續好幾個月不斷重新開始的專案終於有了進展。（我很討厭「one-shotting」這個說法，但我想他的意思就是它真的幫上了大忙。）還有一位 John 甚至因為太喜歡 Wayfinder 的做法，自己打造了一套工具（harness），上面有一張漂亮的小星圖，讓你可以邊走邊領取任務。它已經問世一小段時間，而我終於做出了大家一直希望我做的影片：Wayfinder 是什麼？該怎麼用才最好？

## 什麼是 Wayfinder

我們先來看看大型工作通常是怎麼規劃的。你有一個起點，也就是你必須出發的地方，手上只有一個模糊的想法，並不真的知道該怎麼前進；你想抵達某個目的地，大致知道自己想去哪裡，但兩者之間的步驟一片迷茫，完全不知道怎麼走。這不只是工程上的情況，在生活中許多規劃宏大計畫的場合也是如此。

因此，你首先該做的，大概就是針對它進行一次拷問（grilling）：讓 AI 訪談你，釐清你要前進方向的基本前提。對某些工作來說，這樣就夠了，你可以直接抵達目的地。但對許多工作而言，這仍然會讓你身處大片迷霧之中。根據最初那次拷問的結果，你可能還需要進行更多工作階段：也許是一次原型製作，也許是另一次拷問，也可能需要先去做一些研究。

概念上，我們看到的是一張地圖。我們正在繪製一張「如何抵達目的地」的地圖，這就是它叫做 wayfinder（尋路者）的原因：我們正在找出通往目的地的路。地圖上的每一個項目都是一張票券（ticket），每張票券都需要與代理進行各自獨立的工作階段。所以你可能會有一個原型製作階段、一個拷問階段、一個研究階段，而這些全都由 Wayfinder 建立與管理。順帶一提，這全都只是單一一個技能，而且適用於任何寫程式的代理。

在它的地圖上，Wayfinder 會呈現出一條「前線」（frontier）的票券，也就是目前已知的決策。同時，它也會追蹤所有仍在迷霧中的事項：那些因為還沒做研究、沒有原型可看、或對話與拷問不夠充分，而暫時還無法決定的事情。到了某個時刻，所有的迷霧都會被撥開，你也終於做出了足夠的決策，得以抵達目的地。

Wayfinder 不僅能管理研究，也能處理任務。例如你需要設定某些組態，或需要出門找人談談、實際跑一趟腿，Wayfinder 也能替你安排。換句話說，規劃大事時你可能需要做的所有繁雜事務，Wayfinder 都會替你統籌。它記錄所有已完成的事項、替你衡量戰爭迷霧的範圍，並持續追蹤你當下可以決定的整條前線。

## 在 Issue 追蹤器中運作

它是怎麼追蹤的呢？答案是在你的 issue 追蹤器裡。在我公開的 course video manager 儲存庫中，可以看到我最近做的所有 Wayfinder 地圖。以其中一張為例，這是一張很大的總地圖，底下有 12 個子任務（子 issue），這些就是決策票券。我們可以往下檢視，了解已經做出的所有決策。

隨著決策被做出，它們自然會在票券內被解決。比方這張子 issue「在發佈競態中關閉片段（close the clips during publish race）」，我們在幾週前透過一次討論解決了它。這個解決結果也會回寫到上層的地圖，所以往上看，可以看到它的精簡版本也被寫進了地圖。Wayfinder 持續追蹤所有已做出的決策、所有已建立的原型、所有已完成的任務。

另外，雖然我在這裡用的是 GitHub，但我的技能與 issue 追蹤器無關，所以你可以搭配任何喜歡的 issue 追蹤器使用，只需要透過 setup 技能做一點設定即可。無論是 Linear、Jira，或任何你喜歡的工具都行。

## 實際操作流程

啟動新的 Wayfinder 工作階段時，你首先要決定的是目的地。以這次為例，我當時要在我的應用程式中加入一個具備許多新動作的命令面板（command palette），而我最後想要的是一份可建構的規格（buildable spec），也就是針對 CVM 圖表視窗中 Cmd+K 命令面板的規格。

我是這樣開始的：呼叫 Wayfinder 技能，然後描述我想要什麼。我希望在 CVM 中能加入圖示選擇器（icon picker）；不僅如此，我還希望能搜尋其他圖表，也希望能從圖表中複製內容並儲存下來，是一大塊工作。它先探索了儲存庫，接著呼叫拷問技能來拷問我想要什麼。它首先問我「完成」長什麼樣子、我是否想要一份規格，並建議我採用規格，這很好。然後它先問了幾個初步問題，接著才開始建立票券與第一張地圖，並把其他票券建立為子 issue。

我們一開始就有七張票券，但其中只有三張當下可以領取：釐清圖示名稱的來源、元件儲存結構（component storage schema），以及面板的資訊架構與網格鍵盤操作（palette information architecture and grid keyboard）。最後那張我記不太清楚了。

接著，我在新的工作階段中逐一處理這些票券。做法是直接以票券名稱呼叫 Wayfinder。我用的方式稍微花俏一點：我有一個交接（handoff）技能，會自動替我寫好提示詞，並啟動一個 Claude 子代理（sub-agent）。但它本質上做的，就是針對這張地圖與特定票券呼叫 Wayfinder 技能，不論票券在哪裡。你看，這就是其中一張票券，「Translucent SVG geometry to path builder」，它只需要帶入完整的票券名稱。

所以，這就是走完一張 Wayfinder 地圖的方式：先下達一次初始的 Wayfinder 提示，繪製地圖並找出接下來的票券；之後針對每一張票券，帶著票券網址呼叫 Wayfinder。也就是說，Wayfinder 既用於最初繪製地圖，也用於逐一走過每張票券。

## 四種票券類型

從圖表中你大概已經看得出來，票券有不同的類型，共有四種，而這些票券類型會直接被帶入 issue 追蹤器中。

- **研究（Research）**：Wayfinder 研究票券是代理需要出去找一些資訊再帶回來的情況。它通常會立即開始執行，所以你其實不需要盯著它；它會在子代理中完成，然後回報結果。
- **原型（Prototype）**：原型票券會建立一個原型。在規劃過程中，它對於讓想法真正「活起來」有著難以言喻的價值。我另外做過一支完整的影片談原型有多重要，而它重用了該影片中的原型技能。有些人看到 Wayfinder 會想：「天啊，這麼多規劃，這不就是瀑布式開發（waterfall）嗎？」而原型正是避免它變成瀑布式的方法，因為瀑布式意味著大量低擬真度的前期規劃，原型則是以高擬真度的方式，針對你實際要建構的東西取得回饋。Wayfinder 鼓勵你製作大量原型，這也讓最終的成果好得難以置信。
- **拷問（Grilling）**：當然也有拷問類型的票券，用於需要針對某個實作細節、或計畫的某個特定面向展開討論的時候。
- **任務（Task）**：最後一種是任務，指的是需要在現實世界中完成的事情，也就是代理自己無法完成的事；或者有時代理其實做得到，但被排在其他工作之後。

## 阻擋關係與前線推進

Wayfinder 還有一點很棒，就是它會在票券之間建立阻擋（blocking）關係，因為有些決策必須等其他決策做出之後才能決定。以這張地圖為例，17 張票券中已完成 14 張，完成了很多工作；但我們還沒建構這整張地圖所圍繞的那個技能。等技能建構完成後，我們還需要根據它的運作方式，以及它實際帶來的改進，回頭重新檢視其他一些事項。

當你走過一張 Wayfinder 地圖時，很多時候你做的事情是：「好，我解決了這張票券，來看看它開啟了哪些新票券。前線推進到哪裡了？」

## 地圖完成之後：轉為規格

地圖完成之後，接下來該怎麼處理？以這張地圖來說，因為它的目的地是一份規格，而 Wayfinder 地圖本身對於直接當作規格來說可能太過密集，所以我喜歡從地圖建立規格。這是我據此建立的規格，可以看到它的設定基本上與我之前的做法相同。我只是直接對這張 Wayfinder 地圖呼叫 to-spec，它就把地圖中幾乎所有的決策匯整成一份龐大的文件，放進這個 GitHub issue 中。事實上，最初的草稿大到超過了 GitHub 的字元上限（［笑］），由此就能看出它有多龐大。

之後，我用我慣用的做法把它轉換成票券：先轉規格，再轉票券。換句話說，Wayfinder 恰好取代了我原本流程中 Grill with Docs 的位置。你不再是先做 Grill with Docs，再做 to-spec 與轉票券，而是花更多時間在 Wayfinder 中建立這張龐大的地圖，接著將地圖轉為規格、再轉為票券，然後逐一實作每張票券，最後執行程式碼審查（code review）。

Wayfinder 這套做法真正厲害的地方在於，它產生的規格非常密集，而且全都連結回最初的決策票券。因此，當代理對任何內容感到困惑時，可以回頭查看第一手來源。這一直是 Grill with Docs 的弱點：你必須仰賴規格作為單一事實來源（source of truth），但規格永遠只是會議中實際討論內容的摘要。現在有了 Wayfinder，你就能取得那份第一手來源，這真的太棒了。

## 小結

以上就是 Wayfinder：透過事先非常詳細地規劃，來繪製大型工作的地圖。它能處理原型製作、研究、各種任意的任務，也能處理討論。

## 常見問題（FAQ）

接下來進入常見問題，也就是大家問我 Wayfinder 時最常被問到的幾個問題。

### 「這流程太多了，對我做的工作來說太重了。我到底什麼時候該用它？」

答案是：如果你認為手上的工作可以在單一工作階段中完成並規劃好，那就在單一工作階段中規劃。如果你本來就大致知道通往目的地的路，就不需要使用 Wayfinder，直接在單一工作階段中一路走過去、把它搞定就好。Wayfinder 適用於「有戰爭迷霧」的情況：你不太確定該往哪裡去，只能先出發，再看看會走到哪裡。

順帶一提，我也把 Wayfinder 用在非程式設計的任務上。我一直想在花園裡蓋一間花園辦公室，就是用 Wayfinder 來規劃：委託場地勘查、釐清各種細節、找出該聯絡的對象、做完所有研究、找到可以承建的各家廠商。這真的很棒。

### 「這就是 SDD 吧？」

另一種常見的反應是：「這就是 SDD（spec-driven development，規格驅動開發）吧？我不想做規格驅動開發，不想花這麼多時間去寫規格，這太誇張了。」

我對規格的看法，其實只是把它當作多工作階段工作的「目的地」。也就是說，我們有一個很大的任務，假設是第四號任務，需要分散到多個代理工作階段中完成，因為它實在太大；我們需要一份規格，這樣走到最後才能知道當初是往哪裡去。在這個脈絡下，規格就只是這樣：一份為了處理多工作階段工作而存在的「目的地文件」。接著每個工作階段，都在一張實作票券中完成。

另外，人們剛開始使用 Wayfinder 時常會感到困惑：「等等，它正在建立一些票券，不是應該晚點才做票券嗎？」這其實是實作票券與決策票券的差別。在 Wayfinder 中，你有的是決策票券；這些則是實作票券。

我的做法與多數其他做法的差異在於：大多數人走到最後，會把規格留存在某個地方；我則是關閉含有規格的 issue，規格就消失了，它不會留在我的儲存庫裡，我也很少，甚至幾乎不會再回頭參考它。一旦規格的內容已經體現在程式碼中，你就可以直接刪除規格。相對地，採用規格驅動開發的人則會回頭編輯、修改規格。規格驅動開發有許多不同流派，我這樣說大概會惹惱某些人，但我想表達的重點是：這些規格是「非持久性」的。

## 結語

最後，我建議大家動手去繪製屬於自己的、充滿迷霧的絕佳構想。我發現 Wayfinder 讓人感到無比自由，因為它讓我能夠直接開始，並替我處理那些艱難的決策。我用它來規劃課程、進行工程工作，也用它來建造花園辦公室，真的非常棒。

它很酷的一點是，目的地完全由你決定。你可以讓它產出一份規格，再交給離線（AFK）代理去執行，這也是我的做法；或者，你也可以直接讓它以任務的形式替你完成實作，它完全做得到。沒有什麼比開啟一個新的 Wayfinder 工作階段更有趣了：你知道自己將會看到很棒的成果，卻又不確定該如何抵達那裡。
