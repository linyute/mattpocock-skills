## 功能說明

`improve-codebase-architecture` 審查程式碼庫以尋找**加深機會（deepening opportunities）**：即淺模組（介面幾乎與其所隱藏的事物一樣複雜）可以轉化為深模組之處。它將這些機會整理為獨立的 HTML 報告，然後針對你選擇的項目對你進行[盤問（grills）](https://www.aihero.dev/ai-coding-dictionary/grilling)。

它絕不修改程式碼。整個執行過程僅在作業系統的暫存目錄中產生一個 HTML 檔案並進行一場對話；重構本身則在稍後於獨立的 [session](https://www.aihero.dev/ai-coding-dictionary/session) 中透過正常的建構流程進行。這正是它屬於調查審查而非重構工具的原因，也是為何此技能值得在尚未準備動手修改的程式碼庫上執行的原因。

兩道過濾器可防止報告淪為通用的清理建議。每個候選對象都必須通過**刪除測試**：移除該模組是否會將複雜度集中於較小的介面背後，還是只會將複雜度散落給呼叫端？只有符合「集中」的情況才能贏得一張卡片。且除非你將其指向特定區域，否則它會優先讀取最近的 commit 歷史記錄，並將掃描偏向頻繁變動的路徑，理由是深化無人觸碰的程式碼是一場你永遠無法兌現收益的重構。

## 何時使用

你可以透過輸入 `/improve-codebase-architecture` 來呼叫它；[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不會主動使用它。

它位於建構循環之外：它不是主循環中的步驟，而是定期執行以排入更多改善程式碼庫工作的工具。它適用的四種情境：

| 情境 | 使用方式 |
| --- | --- |
| 例行維護 | 每隔幾天執行一次，或在有空檔時執行，以防止結構在功能開發之間腐化。 |
| 大型建構之前 | 將其指向 [spec](https://www.aihero.dev/ai-coding-dictionary/spec)：「我們該如何讓這項變更變得簡單？」這是最有效的提示詞。 |
| 既有專案稽核 | 在龐大、缺乏結構或[憑感覺撰寫程式碼（vibe-coded）](https://www.aihero.dev/ai-coding-dictionary/vibe-coding)的儲存庫上執行，以了解其真實形態。 |
| 遺留程式碼測試工作 | 在針對難以測試的程式碼撰寫測試之前，先用它找出缺失的接縫。 |

與相近技能容易混淆之處：

- 若要設計已選定的單一模組，請使用 [codebase-design](https://aihero.dev/skills-codebase-design)：那是工作台，而本技能是用來尋找放上工作台之對象的審查工具。
- 若整個工作量過於龐大而無法在單一 session 內處理，請使用 [wayfinder](https://aihero.dev/skills-wayfinder)。
- 若針對「特定事物發生故障」，請使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)。當真正的發現是缺乏能鎖定該錯誤的良好接縫時，它會交接回此處。

## 先決條件

執行時無需先決條件。若存在 `GLOSSARY.md` 及 `docs/adr/` 中的 ADRs，它會讀取它們，並使用你領域特有的名詞來表達：候選項目會描述為「深化 Order 接收模組」，而非「重構 FooBarHandler」。

它會寫入兩個位置。報告會存至儲存庫之外的 `<tmpdir>/architecture-review-<timestamp>.html`。在盤問循環中，它會在 `GLOSSARY.md` 中新增或提煉術語（若該檔案不存在則會建立），並提議將否決的候選項目記錄為 ADR，使未來的執行不會重複建議該項目。

## 深度與搜尋深度的報告

該技能圍繞著一個核心概念：**深度（depth）**。深模組將大量行為置於小型且穩定的介面背後。淺模組則透過幾乎與其底層程式碼一樣龐雜的介面洩漏其內部實作。報告從三種形式尋找淺薄性：純粹為了可測試性而提取但真正錯誤卻隱藏在呼叫方式中的純函式（缺乏**局部性**）、跨**接縫**洩漏的模組、以及不開啟五個檔案就無法理解的概念。最後它會提出修復該問題的深化提議。

每個候選項目都是一張卡片：涉及的檔案、摩擦點、純文字解決方案、以**局部性**與**槓桿效應**陳述的效益、修改前後對照圖、以及強度徽章。

| 徽章 | 對你而言的意義 |
| --- | --- |
| `Strong` | 刪除測試明確通過且摩擦點屬實。請認真對待這些項目。 |
| `Worth exploring` | 合理的深化方向，但成效取決於程式碼未來的演進方向。 |
| `Speculative` | 為求完整性而呈現。多數項目皆可安全忽略。 |

報告以**首要推薦**（建議優先處理的項目）作結，隨後技能停止並詢問你想探索哪一個候選項目。在該時間點尚未做出任何決定，程式碼亦完全未被變動。

## 選定項目後的後續流程

選取候選項目會針對它啟動一場 [grilling](https://aihero.dev/skills-grilling) session：限制條件、接縫背後封裝的內容、哪些測試得以保留、深化後的介面應長成什麼樣。該 session 的產出是一項決策，而非 diff。從該處開始適用常規流程：將決策帶入 [to-spec](https://aihero.dev/skills-to-spec)，接著是 [to-tickets](https://aihero.dev/skills-to-tickets)，最後是 [implement](https://aihero.dev/skills-implement)。

## 常見問題

**它就單一點子盤問了我一個小時，而沒有給我選項。我可以關閉此功能嗎？**

可以：在呼叫時說明即可（「不要盤問我，直接顯示報告」）。這是該技能遭遇最強烈的抱怨。一位使用者直言：他們喜歡它作為「獲取全面改進分析的便利途徑」，而在加入盤問循環後卻發現它「幾乎無法使用」，並回報 session 中它提出單一解決方案後接著拋出「數十甚至上百個問題」。設計的初衷是報告先行，且僅針對你挑選的候選項目啟動盤問，但能力較弱的[模型](https://www.aihero.dev/ai-coding-dictionary/model)會直接跳至針對其產生的第一個想法對你進行訪談。該討論串中的回報因模型不同而有極大差異，且這是一個尚未解決的 issue：該技能目前尚無記載的免盤問模式。

**報告開啟時呈現為無樣式的原始 HTML 且沒有圖表。發生了什麼事？**

該報告透過 CDN 載入 Tailwind 與 Mermaid，因此開啟時需要網路連線，且當有軟體阻擋這些指令碼時會靜默出錯。記錄的案例是一個要求 SRI 雜湊的安全 hook：agent 新增了雜湊值，但 CDN 傳送給瀏覽器的位元組與用來計算雜湊值的 `curl` 不同，導致瀏覽器封鎖了該指令碼。離線與受嚴格控管的環境也會遇到相同的瓶頸。Agent 無法察覺這一點，因為它從未渲染該頁面。因應方式是要求產生行內 CSS 與手繪 SVG 圖表，而非依賴 CDN 鷹架。這是一個尚未解決的 issue，也是真實存在的瑕疵。

**它給了我十二個候選項目。我應該在同一個 session 中逐一處理，還是開啟新的 session？**

每個 session 處理一個候選項目。在單次對話中處理多個項目會使 [context window](https://www.aihero.dev/ai-coding-dictionary/context-window) 同時被報告、盤問、領域模型編輯以及程式碼變更所塞滿。報告僅存在於暫存檔中，因此請轉移候選項目本身而非轉移該檔案：挑選一個、進行盤問、將決策帶入 `/to-spec`，並將其餘項目轉化為稍後可獨立處理的 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)。請將選定的改進事項納入規格中，而非直接跳入實作。這是一個反覆出現的問題，且技能本身並未記載對應的工作流程。

**我該如何撰寫提示詞？**

著眼於你接下來要建構的事物。若即將進行大型建構，請將其指向規格並詢問「我們該如何讓這項變更變得簡單？」未給予特定提示的執行會自行掃描熱點，這對例行維護很適合，但指明方向才能讓報告具備可操作性。

**它在大型既有遺留程式碼庫上有效嗎？**

部分有效。在缺乏一致結構的大型既有程式碼庫上表現良好，且是任何單次結構化設定後推薦的維護機制。坦白的反面情況是：擁有真正失控專案的使用者回報它「有一點幫助但似乎仍不夠力」，而一位維護八年遺留程式碼庫的開發者回報模型在原地打轉，反觀同一技能在整潔的儲存庫上能產出乾淨的關聯圖。針對此情況目前尚未有專屬的 `/refactor` 技能。若程式碼庫完全沒有共用的詞彙，先使用 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 建立詞彙，往往能讓本技能的產出更加優秀。

**這與 `/codebase-design` 有何不同？**

`/codebase-design` 是一份參考指南，而非 session 引導工具。它提供詞彙（模組、介面、深度、接縫、配接器、槓桿效應、局部性），而本技能借用這些詞彙。將全新 agent 指向 `/codebase-design` 作為要「執行」的任務是已知的失敗模式：由於缺乏自身可遵循的流程，agent 會自行拼湊流程、重新探索程式碼並執行極長一段時間後才向你提問。請使用本技能進行引導驅動；並引用該技能的詞彙。

**它是否曾告訴我程式碼庫狀況良好？**

極少，且你在使用前就該知道這一點。該技能的設計旨在輸出發現，因此其架構設定會促使它產出候選項目，而非得出「沒有任何問題」的結論。強度徽章是其防禦機制：一份所有項目皆為 `Speculative` 的報告，正是該技能以其唯一所知的方式告訴你它沒有發現任何問題。

**它能在 Codex 或其他 harness 中運作嗎？**

部分可行。探索步驟直接指名了 Claude Code 帶有 `subagent_type=Explore` 的 `Agent` 工具，因此沒有該工具的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 可能會直接略過平行探索，而非以自身的工具替代。該技能仍可執行；只是掃描不夠徹底。曾有人提議編寫相容於各 harness 的重寫版本，但尚未被合併。

**我究竟該如何在 TypeScript 中實作深模組？**

隨附的技能中沒有提供良好的解答。反覆出現的請求是希望有一份 `TYPESCRIPT.md` 提供符合這些原則的具體檔案與模組配置，但這份文件並不存在。該技能會告訴你加深適用的位置以及接縫背後應封裝的內容；將其轉化為套件或目錄結構目前仍由你自行決定。

## 運作正常的指標

- 候選項目使用的是你領域的概念，而非虛構的類別名稱：「Order intake module」而非「FooBarHandler」。
- 候選項目集中在你最近編輯過的檔案中，而非儲存庫中未活躍的角落。
- 執行期間沒有任何程式碼變更。唯一的全新檔案是暫存目錄中的 HTML 報告。
- 它在產出報告後停止，並詢問你需要哪一個候選項目，而非自行繼續執行。
- 每張卡片將效益解釋為局部性或槓桿效應，並指出哪些測試變得更簡單，而不僅僅是「這更簡潔」。
- 基於長遠理由拒絕候選項目會促使它提議記錄 ADR，使下次執行不會再次建議該項目。

## 適用位置

`improve-codebase-architecture` 屬於**定期維護**：每隔幾天在任何鏈條之外執行一次，用以排入工作而非立即執行工作。其相鄰技能為 [codebase-design](https://aihero.dev/skills-codebase-design)（擁有撰寫每個候選項目時所使用的深度與接縫詞彙）、[grilling](https://aihero.dev/skills-grilling)（一旦你選定候選項目便走過決策樹），以及 [domain-modeling](https://aihero.dev/skills-domain-modeling)（在決策敲定時保持 `GLOSSARY.md` 與 ADR 最新狀態）。它產出的是一個點子，並在 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec) 處重新進入主要建構流程。它在主要流程結尾的對應技能是 [retro](https://aihero.dev/skills-retro)：本技能改善 agent 工作所在的程式碼，`retro` 則在建構完成後改善其周遭環境（檢查、標準、導引檔案）。至於哪項技能適合某個情境，[ask-matt](https://aihero.dev/skills-ask-matt) 是涵蓋整個集合的路由器。
