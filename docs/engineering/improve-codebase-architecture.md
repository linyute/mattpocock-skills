## 功能說明

`improve-codebase-architecture` 調查程式碼庫以尋找**深化機會** — 淺模組（介面幾乎與其隱藏事物一樣複雜）可以變成深模組的地方 — 將它們撰寫為自包含的 HTML 報告，然後透過 [grills](https://www.aihero.dev/ai-coding-dictionary/grilling)（審問）就你挑選的任何一個項目進行訪談。

它絕不會變更程式碼。整個執行過程在你的作業系統全域或暫存目錄中產生一個 HTML 檔案以及一段對話；重構本身稍後在獨立的[工作階段](https://www.aihero.dev/ai-coding-dictionary/session)中透過正常的建構流程進行。這正是使其成為調查而非重構工具的原因，且這也是為什麼該技能值得在尚未準備動手的程式碼庫上執行的原因。

兩個篩選條件可防止報告變成通用的清理建議。每個候選項目都必須通過**刪除測試** — 移除此模組會將複雜性集中在較小的介面背後，還是僅將其分散至呼叫者中？只有「集中」的情況才能獲得一張卡片。除非你將其指向特定領域，否則它會先閱讀最近的提交歷史紀錄，並偏向掃描正在積極變更的路徑，理由是在無人碰觸的程式碼中進行深化是你永遠無法變現的重構。

## 何時使用

你透過輸入 `/improve-codebase-architecture` 來呼叫此技能 — [agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不會自行主動使用它。

它位於建構迴圈之外 — 它不是主要迴圈中的一個步驟，而是你定期執行的操作，以排隊更多改進程式碼庫的工作。它被使用的四種狀況：

| 狀況 | 使用方式 |
| --- | --- |
| 例行維護 | 每隔幾天執行一次，或在有空閒時間時執行，以防止功能開發之間結構腐爛。 |
| 在大型建構之前 | 將其指向 [spec](https://www.aihero.dev/ai-coding-dictionary/spec)（規格）：「我們該如何讓這項變更變得容易？」這是針對它最有效的 prompt。 |
| 既存專案（Brownfield）稽核 | 在大型、未結構化或 [vibe-coded](https://www.aihero.dev/ai-coding-dictionary/vibe-coding) 的儲存庫上執行它，以了解其真實狀況。 |
| 遺留測試工作 | 在針對無法測試的程式碼撰寫測試之前，先使用它尋找缺失的接縫。 |

容易與兄弟技能混淆之處：

- 對於設計你已經挑選好的單一模組，使用 [codebase-design](https://aihero.dev/skills-codebase-design) — 那是工作台，本技能則是尋找要放在上面的調查。
- 對於過大而無法在單一工作階段中容納的完整工作，使用 [wayfinder](https://aihero.dev/skills-wayfinder)。
- 對於「這個特定的東西損壞了」，使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)。當真實發現為沒有良好的接縫來鎖定錯誤時，它會將工作交還至此。

## 先決條件

執行無需先決條件。如果存在 `CONTEXT.md` 以及 `docs/adr/` 中的任何 ADR，它會讀取它們，並在存在時使用你領域自己的名詞來陳述 — 候選項目會陳述為「深化訂單接收模組」，而不是「重構 FooBarHandler」。

它寫入兩個地方。報告進入儲存庫之外的 `<tmpdir>/architecture-review-<timestamp>.html`。在審問迴圈期間，它會新增或精煉 `CONTEXT.md` 中的術語（如果該檔案不存在則建立它），並提議將被拒絕的候選項目記錄為 ADR，以便未來的執行不會重新建議它。

## 深度與尋找深度的報告

本技能立足於一個概念：**深度**。深模組在小型、穩定的介面背後放置了大量的行為。淺模組則透過與底層程式碼幾乎一樣寬的介面洩漏其實作。報告是對淺層的尋找 — 純函式僅為了可測試性而提煉，而真實的錯誤活在它們如何被呼叫中（無**區域性**）、跨**接縫**洩漏的模組、不開啟五個檔案就無法理解的概念 — 以及修復該問題的深化提議。

每個候選項目都是一張卡片：涉及的檔案、摩擦點、純英文解答、以**區域性**與**槓桿**說明的效益、前後對比圖，以及強度標章。

| 標章 | 對你意味著什麼 |
| --- | --- |
| `Strong`（強烈） | 刪除測試明確通過且摩擦點是真實的。請認真看待這些項目。 |
| `Worth exploring`（值得探索） | 似合理的深化，但回報取決於程式碼接下來的方向。 |
| `Speculative`（推測性） | 為了完整性而呈現。其中大多數可以安全忽略。 |

報告以**頂級建議（Top recommendation）**結尾 — 即它最先處理的建議 — 然後技能停止並詢問你想探索哪一個候選項目。在該時間點尚未做出任何決定，且沒有程式碼移動。

## 挑選一個之後發生的事

挑選候選項目會啟動關於它的 [grilling](https://aihero.dev/skills-grilling)（審問）工作階段：約束條件、接縫背後有什麼、哪些測試能存活、深化後的介面應該是什麼樣子。該工作階段的輸出是一個決策，而不是 diff。從那裡適用正常的流程 — 將決策帶入 [to-spec](https://aihero.dev/skills-to-spec)，然後 [to-tickets](https://aihero.dev/skills-to-tickets)，接著 [implement](https://aihero.dev/skills-implement)。

## 常見問題

**它就一個想法對我審問了一個小時，而不是展示選項給我看。我可以關閉它嗎？**

可以 — 在呼叫它時說明（「不要審問我，直接展示報告」）。這是對該技能最烈的抱怨。一位使用者直言不諱地指出：他們喜歡它作為「獲取改進徹底分析的便利方式」，但在新增審問迴圈後發現它「接近無法使用」，回報工作階段中它提出單一解答，然後詢問「幾十或上百個問題」。設計意圖是報告最先出現，且審問僅在你選擇的候選項目上開始，但較弱的 [models](https://www.aihero.dev/ai-coding-dictionary/model)（模型）會直接跳至就它們的第一個想法對你進行訪談。該討論串中的報告因模型而異，且這是一個開放議題 — 該技能尚未具備記錄在案的無審問模式。

**報告以沒有樣式的原始 HTML 打開，且沒有圖表。發生了什麼事？**

報告從 CDN 載入 Tailwind 與 Mermaid，因此在你打開它時需要網路存取，且在某些內容封鎖這些指令碼時會在靜默中損壞。記錄的案例是一個要求 SRI 雜湊的安全性掛鉤：agent 新增了它們，CDN 向瀏覽器提供的位元組與用於計算雜湊的 `curl` 不同，瀏覽器封鎖了該指令碼。離線與封閉環境會遇到相同的障礙。Agent 無法看到這一點，因為它從不安裝繪製頁面。替代方案是要求內聯 CSS 與手建 SVG 圖表，而不是 CDN 腳手架。這是一個開放議題，也是真實的粗糙邊角。

**它給了我 12 個候選項目。我是要在同一個工作階段中處理完它們，還是開始一個新的工作階段？**

每個工作階段處理一個候選項目。在單一對話中處理多個項目會一次性用報告、審問、領域模型編輯與程式碼變更填滿 [context window](https://www.aihero.dev/ai-coding-dictionary/context-window)（context 視窗）。報告僅存在於暫存檔中，因此攜帶候選項目本身而不是檔案：挑選一個、審問它、將決策帶入 `/to-spec`，並將其餘部分轉換為你稍後可以獨立處理的 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)。將選定的改進放入規格中，而不是直接進行實作。這是一個重複發生的問題，且技能本身沒有記錄工作流程。

**我該如何給予 Prompt 提示？**

將你接下來要建構的事物銘記於心。在即將進行大型建構的地方，將其指向規格並詢問「我們該如何讓這項變更變得容易？」未提示的執行會自行掃描熱點，這對於例行維護來說很好，但指定方向才是使報告付諸實行的關鍵。

**它在大型遺留程式碼庫上能運作嗎？**

部分可以。它在缺乏一致結構的大型現有程式碼庫上表現強勁，且是在任何一次性結構設定後推薦的維護機制。坦白的制衡因素：擁有真正失控專案的使用者回報它「有一點幫助但似乎仍不夠」，且一位擁有八年遺留程式碼庫的開發者回報模型在同一個技能於整潔儲存庫上產生乾淨圖表的地方打轉。目前還沒有針對該情況的專用 `/refactor` 技能。如果程式碼庫完全沒有共享詞彙，先透過 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 建立詞彙往往會使本技能的輸出好得多。

**這與 `/codebase-design` 有何不同？**

`/codebase-design` 是一份參考文件，而不是工作階段驅動者。它提供詞彙 — module、interface、depth、seam、adapter、leverage、locality — 而本技能借用它。將新的 agent 指向 `/codebase-design` 作為要「做」的事情是一個已知的失敗：由於沒有自身的流程可供遵循，agent 會捏造一個流程，重新探索程式碼，並在詢問你任何事情之前執行很長時間。使用本技能來驅動；使用該技能來消耗資訊。

**它會告訴我程式碼庫很好嗎？**

很少，且你在進入時就應該知道這一點。該技能被建構用於輸出發現，因此架構會推動它產生候選項目，而不是得出沒有問題的結論。強度標章是防禦手段 — 一份所有項目都是 `Speculative`（推測性）的報告是該技能以它所知道的唯一方式告訴你它沒有發現任何問題。

**它在 Codex 或其他 harness 中能運作嗎？**

部分可以。探索步驟直接指定了 Claude Code 帶有 `subagent_type=Explore` 的 `Agent` 工具，因此沒有該工具的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 可能會跳過平行探索而不是替換為其自身的工具。該技能仍會執行；只是掃描不那麼徹底。已提出 harness 中立的重新撰寫，但尚未合併。

**我該如何在 TypeScript 中實際實作深模組？**

本技能發布時沒有提供良好的解答。重複提出的要求是提供給出原則之具體檔案與模組版面配置的 `TYPESCRIPT.md`，但該檔案並不存在。本技能會告訴你深化的歸屬位置以及接縫背後應該有什麼；將其翻譯為套件或目錄結構目前由你負責。

## 運作正常的指標

- 候選項目指定了你領域的概念，而不是捏造的類別名稱 —「訂單接收模組」，而非「FooBarHandler」。
- 候選項目集中在你最近編輯過的檔案中，而不是在儲存庫休眠的角落。
- 在執行期間沒有變更任何程式碼。唯一的全新檔案是你暫存目錄中的 HTML 報告。
- 它在報告後停止並詢問你想選擇哪一個候選項目，而不是自己繼續進行。
- 每張卡片都將回報解釋為區域性或槓桿，並說明哪些測試變得更簡單 — 而不僅僅是「這更乾淨」。
- 出於持久的原因拒絕候選項目會為你提供記錄 ADR 的建議，以便下一次執行不會重新建議它。

## 適用位置

`improve-codebase-architecture` 是**定期維護** — 每隔幾天在任何鏈結之外執行它，以排隊工作而非直接執行工作。它的鄰居是 [codebase-design](https://aihero.dev/skills-codebase-design)（擁有撰寫每個候選項目時使用的深度與接縫詞彙）、[grilling](https://aihero.dev/skills-grilling)（在你選擇候選項目後引導決策樹），以及 [domain-modeling](https://aihero.dev/skills-domain-modeling)（在決策確定時維持 `CONTEXT.md` 與 ADR 為最新狀態）。它所產生的是一個想法，該想法在 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec) 處重新進入主要建構流程。對於適合某個狀況的技能，[ask-matt](https://aihero.dev/skills-ask-matt) 是涵蓋整個集合的路由器。
