## 功能說明

`diagnosing-bugs` 針對棘手的錯誤或效能退化執行六階段診斷：建立重現、將其最小化、排列假說、加入插樁（instrumentation）、使用迴歸測試進行修復、清理。

在**緊湊（tight）**的回饋循環建立之前，它不會允許 agent 提出理論：這需要一個具名指令，且已經執行過一次，在*此*錯誤上會亮紅燈，修復完成後會轉為綠燈。當 coding agent 收到錯誤報告時，預設行為是閱讀程式碼並進行猜測；本技能阻止了這種行為。如果沒有能呈現紅燈的指令，就不會有階段 2。這道單一門檻正是本技能存在的目的。一旦信號存在，其後的所有事情（二分搜尋、假說測試、插樁）都是機械式的操作。

## 何時使用

輸入 `/diagnosing-bugs`，或者當任務適合時 agent 會自行調用它：它由模型呼叫，並在出現「診斷」、「除錯」或回報某處損壞、拋出例外、失敗或緩慢時觸發。

遇到棘手問題時請使用它：乍看之下難以解決的錯誤、間歇性的不穩定問題（flake）、在兩個已知良好狀態之間悄悄引入的退化問題。它在設計上偏重量級，對於希望單一訊息就能獲得解答的問題來說，它是錯誤的工具。

| 你的情境 | 建議前往的技能 |
| --- | --- |
| 你能描述為特定徵狀的具體缺陷 | 本技能 |
| 緩慢的端點或已知前後狀態的時間退化 | 本技能：它具備效能分支（測量基準線，然後進行二分搜尋） |
| 「此程式碼庫的瓶頸在哪裡？」，無具體徵狀 | 非本技能。它診斷的是單一已知失敗，不負責全面稽核 |
| 來自其他人的原始錯誤報告，尚未被確認或整理 | 先使用 [triage](https://aihero.dev/skills-triage) |
| 用於回答設計問題而非追蹤缺陷的一次性程式碼 | [prototype](https://aihero.dev/skills-prototype) |
| 透過測試先行建構規劃中的行為 | [tdd](https://aihero.dev/skills-tdd) |
| 不存在適合鎖定該錯誤的良好接縫 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)：本技能會自行交接至該處 |

## 緊湊循環即技能核心

階段 1 獲得了不成比例的精力投入，因為它是唯一困難的階段。該技能提供了一套建構循環的階梯式方法，大致依偏好順序排列：

1. 在能觸及該錯誤的任何接縫處撰寫失敗的測試。
2. 針對執行中開發伺服器的 curl 或 HTTP 指令碼。
3. 帶有固件（fixture）輸入的 CLI 呼叫，並與已知良好的快照比對 diff。
4. 對 DOM、console 或網路進行斷言的無頭瀏覽器指令碼。
5. 重播擷取資料：儲存的請求、payload 或事件日誌，在隔離環境中走過該程式碼路徑。
6. 一次性 harness：系統的最小子集、單一函式呼叫。
7. 基於性質（property）或模糊測試（fuzz）的循環，適用於「偶爾輸出錯誤」。
8. 可交由 `git bisect run` 執行的二分搜尋 harness。
9. 差異比對循環：相同輸入，新舊版本相互比對。
10. [人機協同（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 指令碼，作為最後手段。該技能為此隨附了 `scripts/hitl-loop.template.sh`：agent 執行該指令碼，你依照終端機中的提示操作，你的回答將作為可解析的輸出回傳。

單純*一個*循環並不是目標。**緊湊**才是：快速（數秒內）、具確定性（每次執行結論相同）、敏銳（斷言你確切的徵狀，而非「沒有當機」），且能讓 agent 在無人看管下執行。一個耗時 30 秒且不穩定的循環幾乎不比沒有循環好。對於偶爾才出現的錯誤，目標不是乾淨的重現，而是**更高的重現率**：循環觸發、平行化、增加負載、注入休眠，直到不穩定發生的頻率高到足以進行除錯為止。

當它確實無法建立循環時，會依照指示停止並說明情況、列出已嘗試的項目，並向你索取[環境](https://www.aihero.dev/ai-coding-dictionary/environment)存取權限、擷取的產物、或新增臨時插樁的許可。它不應在缺乏循環的情況下逕自提出假說。

## 各階段之間的門檻

這些階段是門檻，而非檢查清單。每一道門檻在特定條件滿足之前都拒絕開啟。

| 門檻 | 必須滿足的條件 |
| --- | --- |
| 進入階段 2 | 一個具名指令，已執行並貼上其輸出，且能在此錯誤上亮紅燈 |
| 進入階段 3 | 重現案例已重現*且*已最小化：所有保留下來的元素都具關鍵支撐作用 |
| 進入階段 4 | 存在 3–5 個排序過且具可證偽性的假說，各自陳述其預測，且在測試任何假說前已展示給你 |
| 進入階段 5 | 探針精確對應特定預測，一次只變動一個變數，每條除錯日誌都帶有 `[DEBUG-a4f2]` 風格的標籤，以便透過一次 grep 即可完成清理 |
| 完成 | 原始重現案例不再重現、插樁程式碼已清除，且被證實正確的假說已寫入 commit 訊息中 |

階段 5 有一個值得注意的退場機制。迴歸測試在修復前撰寫，但前提是必須存在**正確的接縫**：該接縫能讓測試演練呼叫端發生錯誤時的真實模式。如果唯一可用的接縫過於膚淺，技能會直接說明這一點，而非撰寫一個給予虛假信心的測試。接縫的缺失本身就是一項發現，這會將事後檢討引導至 `improve-codebase-architecture`。

## 常見問題

**它在我想獲得直接答案的簡短問題上觸發。**
這是該技能回報最多的問題，且確實存在。特別是在 GPT-5.6-Sol 上，使用者回報它會在對問題的單純描述中觸發：「模型反而觸發了相當正式的 diagnosing-bugs 技能。接著它在給出回覆或建議之前，著手建構重現場景（通常是建立價值有限的模擬場景）。這導致了相當長的回覆延遲。」有四個人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 回報了相同情況。公認的修復方式是先從輕量級方法著手，僅在問題需要時才升級為重量級方法，但該變更尚未釋出。該技能是針對 Claude Code 的呼叫行為進行校準；啟動門檻較低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)會過度觸發它。在分級機制實施之前，實際的解決方法是直接說明你的需求（「直接回答即可，不要進行診斷」）或在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 中停用其模型呼叫。

**我可以將它指向程式碼庫並詢問效能問題在哪裡嗎？**
不行。它診斷的是你已經能明確指出的單一失敗。它的效能分支是用於帶有徵狀的退化問題（建立基準線測量，然後進行二分搜尋，先測量後修復），而非用於主動清查。主動清查版本的技能曾被[提議並已關閉](https://github.com/mattpocock/skills/issues/431)；目前沒有專門針對該用途的技能。

**它在撰寫修復程式碼之前會停下來問我嗎？**
不會。只有階段 3 設有人工檢查點：在測試任何假說之前會向你展示排序後的假說清單，且如果你不在場，它會依據自己的排序繼續進行。在插樁與修復之間沒有門檻，因此 agent 可能在你同意其根本原因之前就開始撰寫程式碼。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求設立該門檻，目前仍處於開啟狀態。如果你需要該門檻，請在呼叫技能時明確說明。

**我已經對此錯誤報告執行過 `/triage`。這是在重複相同工作嗎？**
部分重複，且兩項技能都未明言這一點。正如一位讀者所說：「Triage 的步驟 3 本質上是 diagnosing-bugs 階段 1–2 的淺層受限實例，但兩個檔案都沒有提到彼此。」Triage 執行的是有界限的「這到底是不是錯誤，以及其波及面為何」檢視；而本技能執行的是徹底版本。先執行 triage 並非浪費（其驗證通常能為你提供階段 1 大部分的原始素材），但預期在這邊需要嚴謹地重做一次，而且別期望會有交叉參照告訴你這一點。

**它貼出的重現輸出是否會洩漏機密？**
有可能。該技能要求 agent 貼上呼叫與其輸出，並索取如 HAR 檔案、日誌 dump 及 core dump 等產物。這些內容在指令中都沒有被過濾淨化。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正好提出了這一點（憑證、tokens、cookies 和個人資料隨之流入對話、issue 或 PR 中）並提議加入遮蔽防護欄。該 issue 仍處於開啟且未實作狀態。目前請將遮蔽處理視為你自己的工作，特別是在輸出發布到任何公開場合之前。

**我的安全性掃描器將此技能標記為高風險。**
Snyk 會標記它，但這項標記是偽陽性（false positive）。它是該集合中唯一隨附可執行 shell 指令碼（`hitl-loop.template.sh`）以及執行它與 curl 開發伺服器之指示的技能。隨附 `.sh` 加上執行指示再加上對外 HTTP 請求，足以觸發靜態掃描器。指令碼本身只有約 30 行暫停等待人工輸入的 `read -r -p` 提示。掃描器評估的是能力接觸面，而非已證實的漏洞利用。

**`/diagnose` 怎麼了？**
在 v1.0.0 中已重新命名為 `/diagnosing-bugs`。舊名稱已不復存在。任何串聯 `/diagnose` 的自訂項目（包裝技能、儲存的提示詞）都需要更新。

## 運作正常的指標

- 在提出任何理論之前，它會向你展示一個指令及其紅燈輸出。如果理論先出現，表示該技能未正常執行。
- 它所重現的失敗正是你所回報的，而不是在過程中順便發現的鄰近問題。
- 在開始猜測之前，它會先縮減重現案例，並能告訴你為何每個保留下來的部分都至關重要。
- 在測試任何假說之前，會向你展示包含 3–5 個假說的排序清單，且每個假說都帶有可證偽的預測。
- 它加入的每條除錯日誌都帶有類似 `[DEBUG-a4f2]` 的標籤，且當它宣告完成時，對該標籤進行 grep 的結果為空。
- commit 或 PR 訊息中指明了哪個假說是正確的。
- 當它無法用測試鎖定錯誤時，會坦白說明，而不是寫出一個膚淺的測試。

## 適用位置

`diagnosing-bugs` 是一個隨時可調用的獨立技能。當某個部分損壞時你可以進入它，而在修復與迴歸測試完成後即可離開；它不保留狀態，也無需事前設定。[ask-matt](https://aihero.dev/skills-ask-matt) 會將「某處發生故障」路由至此。

兩個相鄰技能至關重要。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的發現是「程式碼缺乏能鎖定該錯誤的接縫」時接手[交接（handoff）](https://www.aihero.dev/ai-coding-dictionary/handoff)；該建議是在修復完成、掌握更多資訊後提出。[triage](https://aihero.dev/skills-triage) 則位於其上游，針對其他人提出的原始報告錯誤，執行前兩個階段的淺層版本。
