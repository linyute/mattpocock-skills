## 功能說明

`diagnosing-bugs` 針對棘手的錯誤（bug）或效能退化執行六階段的診斷：建立重現（repro）、最小化重現、對假設進行排名、裝設儀表（instrumentation）、使用迴歸測試進行修復、清理。

它不會讓 agent 建立理論，直到存在一個**緊密（tight）**的回饋迴圈 — 一個已執行過一次具名指令，對*這個*錯誤顯示紅燈（失敗），並在修復後顯示綠燈（成功）。當程式碼編寫 agent 收到錯誤報告時的預設行為是閱讀程式碼並進行猜測；本技能會封鎖這種做法。如果不存在能顯示紅燈的指令，就不存在階段 2。這單一閘門正是本技能的目的所在。在信號存在之後，其後的一切 — 對分法（bisection）、假設測試、裝設儀表 — 都是機械式的。

## 何時使用

輸入 `/diagnosing-bugs`，或者當任務適合時，agent 會自行主動使用它 — 它是由模型呼叫的，並會在出現「診斷（diagnose）」/「偵錯（debug this）」或關於某些內容損壞、拋出異常、失敗或變慢的回報時觸發。

在應對棘手問題時使用它：初看時難以解決的錯誤、間歇性的不穩定問題（flake）、在兩個已知良好狀態之間悄悄引入的退化。它在設計上是沉重的，對於希望在單一訊息中獲得解答的問題來說，它是錯誤的工具。

| 你的狀況 | 前往之處 |
| --- | --- |
| 你可以描述為症狀的特定缺陷 | 本技能 |
| 具有已知前後對比的慢速端點或時序退化 | 本技能 — 它有一個效能分支（測量基準線，然後對分） |
| 「這個程式碼庫的瓶頸在哪裡？」— 無特定症狀 | 非本技能。它診斷單一已知失敗，不進行稽核 |
| 來自其他人的原始錯誤報告，尚未確認或記錄 | 先使用 [triage](https://aihero.dev/skills-triage) |
| 用於回答設計問題而非追蹤缺陷的一次性程式碼 | [prototype](https://aihero.dev/skills-prototype) |
| 以測試先行方式建構預期行為 | [tdd](https://aihero.dev/skills-tdd) |
| 不存在良好的接縫來鎖定錯誤 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) — 本技能會自行轉移至該處 |

## 緊密迴圈即是技能

階段 1 獲得不成比例的投入，因為它是唯一困難的階段。本技能提供了一系列建構迴圈的方法，大致按偏好順序排列：

1. 在觸及錯誤的任何接縫處撰寫失敗的測試。
2. 針對正在執行的開發伺服器發送 curl 或 HTTP 指令碼。
3. 帶有測試資料（fixture input）的 CLI 呼叫，並與已知良好的快照進行 diff。
4. 針對 DOM、主機板控制台（console）或網路進行斷言的無頭瀏覽器指令碼。
5. 重放擷取 — 儲存的請求、負載（payload）或事件記錄，獨立通過程式碼路徑執行。
6. 一次性 harness：系統的最小子集、單一函式呼叫。
7. 屬性測試或模糊測試（fuzz loop），用於「偶爾出現錯誤輸出」的情況。
8. 你可以交給 `git bisect run` 的對分 harness。
9. 差異迴圈（differential loop）— 相同的輸入，舊版本比對新版本。
10. [human-in-the-loop](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)（人在迴圈中）bash 指令碼，這是最後手段。本技能附帶了用於此目的的 `scripts/hitl-loop.template.sh`：agent 執行指令碼，你在終端機中遵循提示，而你的答案會作為可解析的輸出返回。

*一個*迴圈不是目標。**緊密（Tight）**才是目標：快速（幾秒內）、確定性（每次執行結論相同）、銳利（斷言你的精確症狀，而非「沒有當機」），且 agent 可無人值守執行。一個 30 秒且不穩定的迴圈僅比完全沒有好一點點。對於只偶爾出現的錯誤，目標不是乾淨的重現，而是**更高的重現率** — 循環觸發器、平行化、增加壓力、注入 sleep，直到不穩定率（flake rate）高到足以進行偵錯。

當它確實無法建構迴圈時，它被指示停止並說明這一點，列出它嘗試過的內容，並向你要求 [environment](https://www.aihero.dev/ai-coding-dictionary/environment) 存取權限、擷取的產物，或新增臨時裝設儀表的許可。它不應該無論如何都繼續進行假設。

## 階段之間的閘門

這些階段是閘門，而不是檢核表。在特定條件成立之前，每一個階段都會拒絕開啟。

| 閘門 | 必須成立的條件 |
| --- | --- |
| 進入階段 2 | 一個已執行過並貼出其輸出的具名指令，且能對此錯誤顯示紅燈 |
| 進入階段 3 | 重現已被重現*且*最小化 — 剩餘的每個元素都是關鍵承重的 |
| 進入階段 4 | 存在 3–5 個經過排名且可證偽的假設，每個假設都陳述了其預測，且在進行任何測試之前展示給你 |
| 進入階段 5 | 探針映射至特定預測，一次處理一個變數，每個偵錯記錄都帶有 `[DEBUG-a4f2]` 風格的標籤，因此清理只需一次 grep |
| 完成 | 原始重現不再重現、裝設的儀表已移除，且證實正確的假設已被寫入提交訊息中 |

階段 5 有一個值得了解的安全逃生口。迴歸測試是在修復之前撰寫的，但前提是必須存在**正確的接縫** — 在該處測試可以執行在呼叫處發生的真實錯誤模式。在唯一可用的接縫過淺的情況下，技能被告知說明這一點，而不是撰寫給予虛假信心的測試。該缺口本身就是發現，且正是它將檢討報告（post-mortem）路由至 `improve-codebase-architecture` 的原因。

## 常見問題

**對於我只想獲得直接答案的快速問題，它也會觸發。**
這是該技能回報最多的問題，且是真實存在的。特別是在 GPT-5.6-Sol 上，使用者回報它會在問題的純文字描述上觸發：「模型反而觸發了相當正式的 diagnosing-bugs 技能。然後它繼續構建重現情境 — 通常是建立價值有限的模擬情境 — 然後才給我回應或建議。這導致了相當大的回覆延遲。」四個不同的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上回報了相同的狀況。公認的修復方法是先從較輕量的方式開始，僅在問題需要時才升級為較沉重的方式，但該變更尚未實施。該技能是針對 Claude Code 的呼叫行為進行校準的；啟動門檻較低的 [model](https://www.aihero.dev/ai-coding-dictionary/model)（模型）會過度觸發它。在分級實施之前，實際的修復方法是說明你的需求（「直接回答這個，不要診斷」）或在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 中為其停用模型呼叫。

**我可以將它指向程式碼庫並詢問效能問題在哪裡嗎？**
不行。它診斷你可以指出的單一失敗。它的效能分支適用於帶有症狀的退化 — 建立基準線測量，然後對分，先測量再修復 — 而不是用於主動掃描。針對主動掃描版本的技能曾被[提出並關閉](https://github.com/mattpocock/skills/issues/431)；目前沒有對應的技能。

**它會在撰寫修復前停下來詢問我嗎？**
不會。只有階段 3 擁有人類檢查點 — 經過排名的假設清單會在進行任何測試之前展示給你，如果你不在場，它會按照自己的排名繼續進行。在裝設儀表與修復之間沒有閘門，因此 agent 可以在你同意其根本原因之前就開始撰寫程式碼。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求增加該閘門且目前仍處於開放狀態。如果你希望有該閘門，請在呼叫技能時予以說明。

**我已經針對這份錯誤報告執行了 `/triage`。這又是相同的重複工作嗎？**
部分是，且兩個技能都沒有承認這一點。正如一位讀者所言：「Triage 的步驟 3 本質上是 diagnosing-bugs 階段 1–2 的淺層、有界實例，但這兩個檔案都沒有提及對方。」Triage 執行有界的「這實際上是一個錯誤嗎？表面範圍是什麼？」審查；而本技能則執行徹底的版本。先執行 triage 並沒有浪費 — 其驗證通常能為你提供階段 1 的大部分原始材料 — 但預期需要在這裡妥善地重做，且預期沒有相互引用來告知你這一點。

**它貼出的重現輸出會洩露秘密嗎？**
可能會。本技能要求 agent 貼上呼叫與其輸出，並要求 HAR 檔案、記錄傾印（log dumps）與核心傾印（core dumps）等產物。這些內容都沒有依照指示進行淨化。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正好提出了這一點 — 憑證、token、cookie 與個人資料隨同進入對話、議題或 PR — 並提議增加修飾（redaction）防禦欄杆。該議題目前處於開放且未實作狀態。目前請將數據淨化視為你的工作，特別是在將輸出公開發表之前。

**我的安全性掃描器將此技能標記為高風險。**
Snyk 標記了它，而該標記是誤報（false positive）。它是集合中唯一附帶可執行 shell 指令碼（`hitl-loop.template.sh`）以及執行它與 curl 開發伺服器指示的技能。發布 `.sh` 加上執行指示加上出站 HTTP 足以觸發靜態掃描器。指令碼本身大約有 30 行 `read -r -p` 提示，用於暫停以等待人類輸入。掃描器評估的是功能表面範圍，而不是已證實的漏洞。

**`/diagnose` 發生了什麼事？**
在 v1.0.0 中已重新命名為 `/diagnosing-bugs`。舊名稱不再存在。你所有鏈結 `/diagnose` 的內容 — 封裝技能、儲存的 prompt — 都需要更新。

## 運作正常的指標

- 在提出任何理論之前，它會向你展示指令與其紅燈輸出。如果理論先到達，說明技能並未在執行。
- 它重現的失敗是你回報的那一個，而不是它在途中發現的附近失敗。
- 它在開始猜測之前縮小重現範圍，並能告訴你為什麼剩餘的每個部分都是關鍵承重的。
- 在對其中任何一個進行測試之前，會向你展示 3–5 個排名的假設清單，每個假設都帶有你可以證偽的預測。
- 它新增的每個偵錯記錄都帶有像 `[DEBUG-a4f2]` 這樣的標籤，且當它宣告完成時，對該標籤進行 grep 會返回空白。
- 提交或 PR 訊息會指出哪一個假設是正確的。
- 當它無法透過測試鎖定錯誤時，它會平實地說明這一點，而不是撰寫一個淺層的測試。

## 適用位置

`diagnosing-bugs` 是一個隨時可用的獨立技能。當某些東西損壞時，你進入它；當修復與其迴歸測試完成時，你離開它；它不保留狀態且不需要事先設定。[ask-matt](https://aihero.dev/skills-ask-matt) 會將「某些東西損壞了」路由至此。

有兩個重要的鄰居。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真實發現為程式碼沒有鎖定錯誤的接縫時接管 [handoff](https://www.aihero.dev/ai-coding-dictionary/handoff) — 該建議是在完成修復且獲得更多資訊後提出的。[triage](https://aihero.dev/skills-triage) 位於其上游，處理作為來自其他人的原始報告而到達的錯誤，並執行相同前兩個階段的較淺版本。
