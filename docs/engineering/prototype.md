## 功能說明

`prototype` 撰寫**回答問題的一次性程式碼** — 這個狀態模型感覺對嗎，或者這個畫面應該是什麼樣子。問題擺在第一位，決定了其後一切的形狀；無論看起來多麼美好，回答了錯誤問題的原型（prototype）都是純粹的浪費。

「一次性」是對程式碼如何*撰寫*的約束，而不是摧毀它的承諾。沒有測試、除了讓其執行之外沒有額外的錯誤處理、沒有抽象、沒有持久化 — 因為這些對於幫助你學習你試圖學習的單一事物毫無幫助。存活下來的是解答（融合至真實程式碼中），以及原型本身（停放在獨立於 main 的分支上，作為解答來源的證據）。

## 何時使用

輸入 `/prototype`，或者當任務適合時，[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 會自動使用它。

當你遇到無法透過對話解決的問題時使用它 — 邊界條件無法在腦海中掌握的狀態機、在並排看到三個版本之前無法想像的畫面。[Grilling](https://www.aihero.dev/ai-coding-dictionary/grilling)（審問）工作階段恰恰會因這些問題而膨脹：agent 重新措辭，你進行猜測，而範疇擴大以填補不確定性。停止審問，建構一次性版本，看看它，然後在一行中回答。相反地，如果已經建構的內容行為異常且你想知道原因，請使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) — 原型探索建構什麼，而不是已建構的事物為什麼損壞。

你也會在未刻意選擇的情況下到達這裡。[wayfinder](https://aihero.dev/skills-wayfinder) 在其地圖上記錄 `prototype` 決策 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)，而處理其中一個正是本技能。

## 兩個分支

問題決定分支，且分支會產生截然不同的產物：

- **「這個邏輯/狀態模型感覺對嗎？」** — **單一可分享的 HTML 檔案**。一個自包含的頁面，無需建構（build）也無需伺服器，任何人雙擊即可打開。它包含一個標記的狀態面板，每次點擊後都會重新繪製；帶有用於以任何順序測試模型的自由操作按鈕；以及標籤頁式的**引導式流程體驗（guided walkthroughs）** — 每個標籤頁一個情境，每個情境下方帶有要按下的有序按鈕。一切都以領域語言進行標記，因此你可以將其交給設計師、PM 或領域專家，讓他們親身感受模型。頁面背後的邏輯是一個小型純模組 — reducer、狀態機、一組函式 — 保持與 DOM 無關，以便驗證後的版本可以直接移入真實程式碼中。
- **「這個應該是什麼樣子？」** — 單一路徑上的幾個**截然不同**的 UI 變體，可從浮動底欄與 `?variant=` URL 參數進行切換。變體必須在結構上而非顏色上有所不同；三個微調的卡片網格是桌布，而不是原型。它們儘可能在真實頁面內部、針對真實資料與真實密度進行繪製，因為在真空環境中審視變體看起來總是很好。

兩者都將狀態保留在記憶體中，開始時無需思考，並在每一步後向你展示完整的狀態。當你發現自己在強化其中一個變體時 — 新增測試、連接真實資料庫、為以後可能想要的狀況進行通用化 — 你就已經停止了原型開發。

## 原型是第一手來源（Primary source）

完成的原型留下兩樣東西，且它們去往不同的地方。

**解答** — 裁決加上其解決的問題 — 會被持久擷取：提交訊息、ADR、實作議題。這正是 main 分支所保留的，融合至真實程式碼中。

**原型**是解答來源的可執行證據，且它不會被刪除。它也不屬於 main — 那裡沒有任何東西需要維護且它很快會過期 — 因此它被提交至獨立於 main 的一次性 `prototype/<name>` 分支，從不合併，並在實作議題上留下指向該分支的 [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。Main 保持乾淨；探索保持可被找到，且可由接管後續工作的任何人重新執行。

## 常見問題

**等等 — 原型難道不應該被刪除嗎？**
現在不再如此了。過去是：建構它、保留解答、丟棄程式碼。對此最犀利的反對意見從來不是關於速度 — 而是*誰在下一個[工作階段](https://www.aihero.dev/ai-coding-dictionary/session)接管工作，且他們有什麼基礎可供工作？* 原型的散文摘要會遺漏使其具有說服力的要素。因此，原型現在被視為 [primary source](https://www.aihero.dev/ai-coding-dictionary/primary-source)（第一手來源）：它落腳於獨立於 main 的 `prototype/<name>` 分支，且實作議題指向它。改變的是程式碼存放的位置，而不是規範 — 它仍然絕不合併至 main。

**它過去會建構終端機應用程式。那個去了哪裡？**
邏輯分支現在改為輸出單一可分享的 HTML 檔案。終端機應用程式只能由複製了儲存庫並安裝了執行階段（runtime）的人驅動，這恰好排除了需要其意見的人 — 設計師、PM、知道狀態模型應該意味著什麼的領域專家。一個雙擊即可打開且在郵件發送後仍可使用的自包含檔案可以由任何人驅動。底下純粹的邏輯模組保持不變，且仍然是可以移入真實程式碼中的部分。

**Agent 告訴我在應該進行實作時執行 `/prototype`。**
這是已知問題，且是一個命名問題。`prototype` 是一個通用的、吸引人的詞彙，對於不知道流程的 agent 而言，一旦 tickets 存在，它會被解讀為「顯而易見的下一步」，因此即使設計已經在對話中完全確定，它也會被按名稱推薦。如果你已經知道要建構什麼，下一步是按 ticket 執行 `/implement`。僅在特定的設計問題確實未解決且對話無法解決時，才使用原型。

**我是否應該在建構任何正式環境功能之前原型化整個應用程式 — 例如，向潛在客戶進行展示？**
那是冠以本技能名稱的另一種產物。這裡的原型範圍僅限於一個問題，而「整個應用程式是什麼？」並不是一個問題。完整應用程式的原型沒有自然的停止點，因此它會在慣性下變成正式環境應用程式：清理檢查從未發生，且在原型規則下撰寫的程式碼（無測試、無錯誤處理）最終會呈現在使用者面前。如果你需要銷售展示，請刻意將其建構為展示，並明確說明其中沒有任何正式環境內容。如果你需要解決設計問題，請將其縮減為該問題。

**我該如何在它自己的工作階段中執行它？**
原型存在於自己的目錄中，並產生大量你不想在提出問題的對話討論串中出現的 [context](https://www.aihero.dev/ai-coding-dictionary/context)，因此請在其他地方執行它，並僅帶回解答。[handoff](https://aihero.dev/skills-handoff) 是雙向的橋樑。

**這難道不是合成（消耗）token 最快的方式嗎？**
如果你對原本可以透過對話回答的問題進行原型開發，或者讓一個原型蔓延至整個功能，那確實有可能。重要的比較不是 token 對比零；而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 對比建構錯誤的狀態模型並在擁有正式環境呼叫者後才發現。保持問題狹窄且執行簡短，支出就會保持相稱。

## 運作正常的指標

- 你可以用一句話說明原型存在旨在回答什麼問題 — 且它寫在展示的頂部，而不僅僅在你的腦海中。
- 不讀程式碼的人也能驅動邏輯展示。他們打開檔案、按下引導標籤頁中的按鈕，並用他們自己的話描述所看到的內容。
- 有人說「等等，那應該是不可能的」或「蛤，我以為是 X」。那是*想法*中的錯誤（bug），而這正是整個重點所在。
- UI 變體在版面配置與資訊層級上有所不同，而不僅僅是顏色與文案 — 且你獲得的回饋是「B 的頁首搭配 C 的側邊欄」。
- 它在一次過程中獲得解答。如果你在一天後仍在建構它，說明問題太大了；請將其拆分。
- 當它結束時，main 包含決策且不包含任何原型，且實作議題指向仍然保留原型的分支。

## 適用位置

`prototype` 是一個**隨時可用的獨立技能** — 你進入它以解決一個設計問題，然後離開它 — 且它也是另一個技能執行的機制。

它最大的消耗者是 [wayfinder](https://aihero.dev/skills-wayfinder)。Wayfinder 地圖由**決策 tickets** 組成，而 `prototype` 是 ticket 可以是的四種類型之一：當阻礙性問題是「這應該是什麼樣子」或「這應該如何運作」（再多討論也無法解決）時使用的類型。Wayfinder 透過製造具體的事物來供反應，從而提高了模糊討論的忠實度，而本技能正是建構該具體事物的方式。原型 ticket 由解答確定解決，且原型作為資產從地圖連結。

其他鄰居位於其上游與下游。[grill-me](https://aihero.dev/skills-grill-me) 與 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可審問的問題；不可審問的問題改為來到這裡，且單行解答會返回訪談中。在下游，驗證後的狀態模型或 UI 方向成為 [to-spec](https://aihero.dev/skills-to-spec) 的確定輸入，後者可以內聯原型產生的富含決策的程式碼片段，而不是在散文中描述它。對於其他任何事物，[ask-matt](https://aihero.dev/skills-ask-matt) 會在整個集合中為你進行路由。
