# 詢問 Matt (Ask Matt)

您記不住每項技能，所以開口問。

**流程 (flow)** 是穿越各技能的路徑。大多數路徑沿著一條**主流程**前進，並有兩條**入口引道**匯入其中。其餘一切皆為獨立項目，或在底層運作的詞彙層。

## 主流程：點子 → 發布 (idea → ship)

大多數工作所遵循的路徑。您有一個想法並希望將其實作出來。

1. **`/grill-with-docs`** 透過訪談精煉想法。每當您**在工作目錄中工作**時皆由此開始：它是具備狀態的，會將所學保留在 `GLOSSARY.md` 與 ADR 中。（沒有工作目錄？改用 `/grill-me`，詳見「獨立項目」章節。兩者皆執行相同的 `/grilling` 原語；`grill-with-docs` 是會留下書面紀錄的版本，這使得每當有儲存庫可供留存時，它都是兩者中較佳的選擇。）
2. **分支：您能在對話中解決每個問題嗎？** 若問題需要可執行的解答（狀態、商業邏輯、必須看到的 UI），請繞經原型，透過雙向的 **`/handoff`** 銜接（原型存在於自己的目錄中，這正是 `/handoff` 的用途；請參閱階段邊界）：
   - 以 **`/handoff`** 導出，然後針對該檔案開啟全新工作階段，
   - 使用 **`/prototype`** 以一次性程式碼回答問題，
   - 將所學以 **`/handoff`** 帶回，並從原始想法討論串中引用它。
3. **分支：這是跨多個工作階段的建構嗎？**
   - **是** → **`/to-spec`**（將討論串轉換為規格），接著使用 **`/to-tickets`** 將其拆解為曳光彈工單，各自宣告其**阻礙邊緣**。然後以兩種方式之一處理工單：
     - 每張工單分別進行 **`/implement`**，**在各工單之間 `/clear` 上下文**。在本地追蹤器上，這是 `.scratch/<feature>/issues/` 下每張工單一個檔案，手動依阻礙優先順序處理；在真實追蹤器上，邊緣會變成原生阻礙連結，因此任何阻礙已完成的工單都可以被拾取。每張工單都是自包含的，因此前一張工單的上下文是可以丟棄的。
     - 一次執行針對整個規格的 **`/implement-spec`**。它將工單讀取為**任務圖**，在就緒**前沿**平行執行實作者子代理，並將所有內容整合至單一**整合分支**。當您寧願編排建構流程而非親自驅動每張工單時，請使用此工具。
   - **否** → 直接在相同的上下文視窗中於此處 **`/implement`**。

   無論哪種方式，程式碼都透過驅動 **`/tdd`**（一次一個紅－綠切片）建構，並以 **`/code-review`**（對 diff 進行「標準 + 規格」的雙軸審查）收尾。`/implement` 針對每張工單執行這兩者；`/implement-spec` 的實作者各自驅動 `/tdd`，並在整合分支上執行一次 `/code-review`。當您只想以測試優先方式建構具體行為而無需完整規格時，請單獨使用 **`/tdd`**；每當您想比對固定時間點審查分支或 PR 時，請單獨使用 **`/code-review`**。

   當工作作為 Pull Request 提出時，**`/pr`** 會塑造其內文結構：展示變更的最小視覺化呈現、運作正常的變更前／變更後佐證，以及單向門或雙向門判定。它是模型呼叫的，因此代理在撰寫 PR 時隨時會取用它。

4. **`/retro`** 完成迴圈閉環。在建構完成後，特別是走偏的建構，它會回顧整個工作階段，並對代理的**環境**（而非程式碼本身）提出變更建議：導覽指標、自動化檢查、`/code-review` 強制的編碼標準、引導檔案、工具鏈。機械性錯誤變成確定性檢查；主觀判斷變成編碼標準。下一次建構便從更好的環境開始。

### 上下文衛生

將步驟 1–3 保持在**單一不中斷的上下文視窗**中（在 `/to-tickets` 之前不要壓縮或清除），讓盤問、規格與工單都能立足於相同的思維基礎上。接著每次 `/implement` 皆從工單全新開始。在 `/retro` 所回顧的工作階段內執行它（在您清除之前）；清除之後，改為將它指向該工作階段的記錄檔。

對此的限制是**[聰明區 (smart zone)](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏銳推論的視窗（在最先進模型上約為 15 萬 tokens）。若工作階段在 `/to-tickets` 之前接近此上限，切勿在能力退化下硬推；在最近的階段邊界處進行 `/compact` 並繼續（請參閱階段邊界）。

## 入口引道 (On-ramps)

產生工作並隨後匯入主流程的起始情況。

- **錯誤與請求不斷堆積** → **`/triage`**。它透過分流角色推進 issue 並產生代理就緒的 issue，隨後由 **`/implement`** 拾取。

  分流僅適用於**非您建立**的 issue：錯誤回報、傳入的功能請求、任何以原始狀態到達的事項。`/to-tickets` 所產生的工單已經是代理就緒的，因此**請勿對它們進行分流**。

- **某處壞掉了** → **`/diagnosing-bugs`**。針對棘手問題：初看難以理解的錯誤、間歇性的不穩定測試、在兩個已知良好狀態之間悄悄引入的退化。它拒絕在擁有**緊密意見回饋迴圈**（一個在此錯誤上已經變紅的指令）之前進行理論推測，然後使用迴歸測試進行修復。當真正的發現是沒有良好的接縫可鎖定該錯誤時，其驗屍分析會轉交給 **`/improve-codebase-architecture`**。

- **龐大且模糊的努力：全新專案或龐大的功能建構，大到單一工作階段無法容納** → **`/wayfinder`**，此處最具認知要求的流程。當從這裡到目的地的道路尚不明確時，它會在 issue 追蹤器上繪製**決策工單**的**共享地圖**，並逐一解決，產出**決策而非交付成果**，直到迷霧散去、道路清晰。**`/grill-with-docs`** 是用來精煉您在單一工作階段內能掌握的想法，而 wayfinder 則適用於您無法掌握的想法，且它更慢、更密集，因此請專門用於該情況，絕不用於範疇明確的功能。

  當地圖釐清後，**它會進行交接，而不直接建構**：在 **`/to-spec`** 處匯入主流程，將地圖的關聯決策收縮為可建構的計劃，然後照常進行 `/to-tickets` 與 `/implement`。將地圖直接循環輸入 `/implement` 會跳過該收縮過程並拋棄關聯細節，因此僅當這項努力確實很小時才直接進入 `/implement`。

## 程式碼庫健康

非功能開發工作，僅作維護。

- 每當您有閒暇時間保持程式碼庫利於代理運作時，即可執行 **`/improve-codebase-architecture`**。它會找出**深化機會**；挑選其中一項即可_產生想法_，供您帶入 `/grill-with-docs` 的主流程中。它是尋找候選對象的調查工具；**`/codebase-design`**（見下方）則是您用來設計所選項目的工作台。

## 底層詞彙

在其他技能*底層*運作的兩個模型呼叫參考資料，各自為其詞彙的單一真實來源。當**用詞**而非流程才是問題癥結時，可直接取用它們；或讓上述技能將其帶入。

- **`/domain-modeling`**：精煉專案的*領域*語言：質疑模糊術語、解決多載詞彙（「帳戶」承擔三種職責）、將難以反轉的決策記錄為 ADR。這是 `/grill-with-docs` 驅動以保持 `GLOSSARY.md` 成為乾淨詞彙表的積極紀律。
- **`/codebase-design`** 是深層模組詞彙（模組、介面、深度、接縫、配接器、槓桿、局部性），用於設計模組的*形狀*：在乾淨接縫處以小介面封裝大量行為。`/tdd` 與 `/improve-codebase-architecture` 都使用這套詞彙。

## 階段邊界 (Phase boundaries)

**階段 (phase)** 是工作階段內的一大塊工作：盤問、實作、QA。在兩者之間的**邊界**處，您有五個選項，而在它們之間做選擇是整個地圖中最模糊的決策：

- **Continue**：留在原地。零成本，零損失。
- **`/clear`**：清空視窗，當此處的一切與接下來的事項無關時。
- **`/handoff`** 撰寫可攜式 Markdown 檔案。適用範圍狹窄：僅用於**新框架**、**新目錄**、**同事**，或在**階段中**分叉出旁支任務。它換取的是可攜性。
- **Subagent**：將範疇狹窄的任務傳送至其專屬視窗並取得報告回傳。
- **`/compact`** 壓縮此上下文並以此播種全新工作階段。這是決策樹底部的**預設值**，而非第一首選。

閱讀 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以瞭解有序決策樹：五個問題、每個分支背後的推論，以及為何原始來源成本使 **Continue** 成為最先應排除的項目。請**在**邊界處做決策；在階段進行中，請繼續或將剩餘部分拆分為子代理。

## 獨立項目 (Standalone)

完全獨立於主流程之外。

- **`/grill-me`**：與 `/grill-with-docs` 相同的緊湊盤問訪談，但**無狀態**：它不在本地儲存任何內容，也不建構 `GLOSSARY.md`。當您**不在工作目錄中工作**時請使用它（精煉計劃、設計、一篇文章、任何底層沒有儲存庫的事物）。若您位於工作目錄中，請改用 `/grill-with-docs`：它執行相同的訪談並留下書面紀錄，因此絕對是更好的選擇。
- **`/grilling`** 是訪談原語本身：輪次、前沿、事實是代理的職責而決策是您的。`/grill-me` 與 `/grill-with-docs` 是兩種具名的切入方式，而 `/triage`、`/wayfinder` 與 `/improve-codebase-architecture` 都在內部執行它。僅當您希望進行不帶任何包裝的訪談時，才直接取用它。
- **`/prototype`** 是一個小型一次性程式，用以回答一個設計問題：這個狀態模型感覺合適嗎，或者這個 UI 應該長什麼樣子。一次性是對程式碼撰寫方式的約束，而非銷毀它的承諾：答案會融入真實程式碼中，而原型本身則作為**原始來源**保留在從 main 分支出來的 `prototype/<name>` 分支上，並由實作 issue 指向它。它是主流程步驟 2 中的迂迴路徑，但任何時候設計問題難以在紙上定案時，都可使用它。
- **`/research`**：將閱讀的繁重外勤工作委派給**背景代理**：它針對**原始來源**調查問題，然後在儲存庫中留下具備引用來源的 Markdown 檔案。在它閱讀時繼續工作。它產生的檔案可以帶*入* `/grill-with-docs` 的主流程中，因為研究是為思考提供素材而非取代思考。
- **`/to-questionnaire`** 當阻礙您的事物不在您的腦袋中或程式碼庫中，而是在**別人的腦袋中**時登場，並為他們撰寫一份問卷以供填寫。它是 `/grill-me` 的反向操作：它不是就主題訪談您，而是就**傳送對象**（要寄給誰、您需要收回什麼）訪談您，並將問題對準缺口。收回的內容是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 專用於僅有**人類**能執行的步驟：佈建基礎架構、設定憑證或 CI 密鑰、點擊陌生的第三方儀表板、執行一次性遷移或移轉。它會產生互動式 bash 指令稿，開啟每個 URL、擷取每個數值，並將其寫入 `.env` 和 GitHub 密鑰中，因此該程序不再是您每次都要向代理重新解釋的事項。模型呼叫，因此代理在碰到只有您能越過的牆壁時會立即取用它。如果代理能自己完成，它就應該自己做；這是專為人類真正參與其中的情境所準備的。
- **`/wait-what`** 是對未能傳達清楚之訊息的矯正措施。在任何其他技能的對話進行中使用它，代理會使用您遺漏的上下文，以純文字並使用 `GLOSSARY.md` 詞彙重新闡述剛才所說的內容。它在事後起作用；`/grill-with-docs` 則是事前預防，因為及早約定共享語言才能從一開始就阻止術語混淆的發生。
- **`/teach`**：跨多個工作階段學習概念，使用目前目錄作為具備狀態的工作區。
- **`/writing-for-agents`** 是撰寫供代理閱讀之文件的參考指引：技能、AGENTS.md、被指向的文件。

## 前置條件 (Precondition)

**`/setup-matt-pocock-skills`**：在您的第一個工程流程前執行，以設定其他技能所預期的 issue 追蹤器、分流標籤和文件配置。自訂 issue 追蹤器也能運作。
