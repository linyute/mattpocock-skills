# 詢問 Matt

您不必記得每項技能，隨時詢問。

**流程（flow）**是穿越各個技能的路徑。大多數路徑沿著一個**主流程**進行，並有兩個**匯入道（on-ramps）**匯入其中。其他一切都是獨立的，或者是在底下運作的詞彙層。

## 主流程：構想 → 發佈

大多數工作遵循的路線。您有一個構想並希望建構它。

1. **`/grill-with-docs`** — 透過訪談精煉構想。每當您在**工作目錄中工作**時從這裡開始：它是有狀態的，會將學到的內容保留在 `CONTEXT.md` 和 ADR 中。（沒有工作目錄？使用 `/grill-me` — 參見獨立技能。兩者皆執行相同的 `/grilling` 原語；`grill-with-docs` 是會留下紀錄追蹤的一個，只要有儲存庫可供留下紀錄，它就是兩者中較佳的選擇。）
2. **分支 — 您可以在對話中解決每個問題嗎？** 如果某個問題需要可執行的解答（狀態、商業邏輯、您必須看到的 UI），請繞道原型（prototype），並在兩個方向上透過 **`/handoff`** 橋接（原型存在於自己的目錄中，這正是 `/handoff` 的用途 — 參見階段邊界）：
   - **`/handoff`** 匯出，然後針對該檔案開啟全新會話，
   - **`/prototype`** 使用一次性程式碼回答問題，
   - **`/handoff`** 將您學到的內容匯回，並從原始構想討論串中引用它。
3. **分支 — 這是多會話建構嗎？**
   - **是** → **`/to-spec`**（將討論串轉換為規格），然後 **`/to-tickets`** 將其拆分為追光彈票券（tracer-bullet tickets），每張票券宣告其**阻塞邊界**。在本地追蹤器上，那是 `.scratch/<feature>/issues/` 底下每張票券一個檔案，手動先處理阻塞項；在真實追蹤器上，邊界會變成原生阻塞連結，因此任何阻塞項已完成的票券都可以被領取 — 為每張票券啟動 **`/implement`**，在每張票券之間 **`/clear` 上下文**。每張票券都是獨立自洽的，因此上一張票券的上下文是可以拋棄的。
   - **否** → 就在這裡相同的上下文視窗中執行 **`/implement`**。

   無論哪種方式，**`/implement`** 都會在內部透過驅動 **`/tdd`** 來建構每個議題 — 一次一個紅綠切片 — 然後在提交前執行 **`/code-review`**（對差異進行標準 + 規格的雙軸審查）來結束。當您只想在沒有完整規格的情況下以測試優先建構具體行為時，請單獨使用 **`/tdd`**；每當您想針對固定點審查分支或 PR 時，請單獨使用 **`/code-review`**。

### 上下文衛生

將步驟 1–3 保持在**單一未中斷的上下文視窗**中 — 在 `/to-tickets` 之後才進行壓縮或清空 — 這樣審問、規格和票券就能建構在相同的思考之上。接著每個 `/implement` 都可以全新開始，從票券展開工作。

此過程的限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏銳推理的視窗範圍（最先進的模型約 ~150k tokens）。如果會話在 `/to-tickets` 之前接近此限制，切勿在效能退化的情況下硬推 — 在最接近的階段邊界處進行 `/compact` 然後繼續（參見階段邊界）。

## 匯入道

產生工作並匯入主流程的起始情境。

- **Bug 與請求堆積** → **`/triage`**。它透過分揀角色推動議題，並產生 Agent 隨時可處理的議題，稍後由 **`/implement`** 接手。

  分揀僅適用於**非您建立**的議題 — Bug 報告、傳入的功能請求、任何原始到達的內容。`/to-tickets` 產生的票券已經是 Agent 隨時可處理的狀態，因此**請勿對它們進行分揀**。

- **有些東西損壞了** → **`/diagnosing-bugs`**。針對棘手問題：乍看之下難以診斷的 Bug、間歇性閃爍、在兩個已知良好狀態之間潛入的退化。在獲得**緊密的回饋迴圈**（一個針對*此* Bug 變紅的命令）之前，它拒絕進行理論推測，然後使用退化測試進行修復。當真正的發現是沒有良好的接縫來鎖定 Bug 時，其事後檢討會交接給 **`/improve-codebase-architecture`**。

- **龐大且模糊的工作 — 全新專案或龐大的功能建構，對單一會話而言太過龐大** → **`/wayfinder`**，這裡認知需求最高的流程。當從此處通往目的地的道路尚未清晰時，它會在議題追蹤器上繪製**決策票券**的**共享地圖**，並一次解決一張 — 產生**決策而非交付物** — 直到迷霧退去、道路清晰。`/grill-with-docs` 是精煉能在單一會話中掌握的構想，而 wayfinder 則適用於無法掌握的構想 — 它更慢且更為密集，因此請留給該種情境使用，絕不要用於範疇明確的功能。

  當地圖變得清晰時，**它會進行交接而非建構**：在 **`/to-spec`** 處匯入主流程，將地圖的連結決策折疊為可建構的計劃，然後照常執行 `/to-tickets` 與 `/implement`。將地圖直接循環至 `/implement` 會跳過該折疊過程並丟棄連結細節 — 只有當工作量證實極小時才直接前往 `/implement`。

## 程式碼庫健康

非功能開發工作 — 而是維護。

- **`/improve-codebase-architecture`** — 每當您有空閒時間時執行，以保持程式碼庫適合 Agent 操作。它會浮現出**深化機會**；選擇一項會 _產生構想_，您可以將其帶入 `/grill-with-docs` 的主流程中。這是尋找候選項目的調查；而 **`/codebase-design`**（如下）則是用於設計所選項目的工作台。

## 底層詞彙

在其他技能*底下*運作的兩個模型呼叫參考資料 — 各自為其詞彙的單一事實來源。當問題在於**用字**而非流程時，可直接存取它們；或者讓上述技能引入它們。

- **`/domain-modeling`** — 精煉專案的*領域*語言：質疑模糊術語、解決重載詞彙（例如「帳號」承擔三項工作）、將難以逆轉的決策記錄為 ADR。這是 `/grill-with-docs` 所驅動的主動紀律，以維持 `CONTEXT.md` 為乾淨的術語表。
- **`/codebase-design`** — 用於設計模組*形狀*的深度模組詞彙（模組、介面、深度、接縫、轉接器、槓桿、局部性）：在乾淨接縫的小型介面背後具備大量行為。`/tdd` 與 `/improve-codebase-architecture` 皆使用此詞彙。

## 階段邊界

一個**階段（phase）**是會話內部的一塊工作 — 審問、實作、QA。在兩者之間的**邊界**處，您有五個選項，而在它們之間做選擇是整張地圖中最模糊的決策：

- **Continue** — 保持原狀。零成本、無損失。
- **`/clear`** — 當這裡沒有任何內容對接下來的工作重要時，清空視窗。
- **`/handoff`** — 撰寫可攜式的 Markdown 檔案。適用情境窄：僅用於**新的 Harness**、**新的目錄**、**同事**，或在**階段中途**分支旁支任務。它帶來的是可攜性。
- **Subagent** — 將範疇緊湊的任務發送至其專屬視窗並接收回覆報告。
- **`/compact`** — 壓縮此上下文，並用它播種全新的會話。這是**預設值**，位於決策樹底部而非首選。

閱讀 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以瞭解有序的決策樹 — 五個問題、每個分支背後的推理，以及為什麼主要來源成本使得 **Continue** 成為最先考慮評估的選項。請**在**邊界處做出決策；在階段中途，請繼續或將其餘部分拆分給子 Agent。

## 獨立技能

完全脫離主流程。

- **`/grill-me`** — 與 `/grill-with-docs` 相同的嚴格訪談，但是為**無狀態**：它不會在本地儲存任何內容，也不會建構 `CONTEXT.md`。當您**不在工作目錄中工作**時請使用它 — 精煉計劃、設計、一篇寫作、任何底下沒有儲存庫的內容。如果您在工作目錄中，請改用 `/grill-with-docs`：它執行相同的訪談並留下紀錄追蹤，因此絕對是更好的選擇。
- **`/grilling`** — 訪談原語本身：輪次、邊界，事實是 Agent 的工作，決策是您的工作。`/grill-me` 與 `/grill-with-docs` 是兩種命名的進入方式，而 `/triage`、`/wayfinder` 與 `/improve-codebase-architecture` 皆在內部執行它。只有當您希望在沒有包裝的情況下直接進行訪談時才直接調用它。
- **`/resolving-merge-conflicts`** — 逐塊處理進行中的 merge 或 rebase 衝突，透過追溯至各方主要來源的**意圖**進行解決，而非隨機選擇行數，然後完成操作。它絕不執行 `--abort`。獨立於所有流程之外：當您已經處於衝突中途時請使用它。
- **`/prototype`** — 小型、一次性的程式，用於回答一個設計問題：此狀態模型感覺是否正確，或此 UI 看起來應該如何。一次性是對程式碼撰寫方式的限制，而非銷毀它的承諾：解答會併入真實程式碼中，而原型本身會作為**主要來源**保留在從 main 分出的 `prototype/<name>` 分支上，並從實作議題中被引用。這是主流程步驟 2 中的繞道，但每當設計問題難以在紙上定奪時，皆可隨時調用它。
- **`/research`** — 將閱讀的繁重工作委派給**背景 Agent**：它會針對**主要來源**調查問題，然後在儲存庫中留下引用來源的 Markdown 檔案。在它閱讀時繼續工作。它產生的檔案是可以帶*入* `/grill-with-docs` 主流程的內容 — 研究為思考提供養分，而非取代思考。
- **`/to-questionnaire`** — 當阻礙您的事物不在您的腦海或程式碼庫中，而在**他人的腦海**中時，這會為他們撰寫一份問卷以供填寫。這是 `/grill-me` 的逆向操作：它不是方針對主題訪談您，而是針對**發送**進行訪談 — 發送給誰、您需要回收什麼 — 並將問題對準空缺。回收的內容是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** — 用於只有**人類**才能執行的步驟：佈署基礎架構、設定憑證或 CI 密鑰、點擊不熟悉的第三方儀表板、執行一次性遷移或切換。它會產生互動式 bash 腳本，開啟每個 URL，擷取每個值，並將其寫入 `.env` 與 GitHub 密鑰 — 這樣該程序就不必每次都重新向 Agent 解說。由模型呼叫，因此當 Agent 碰到只有您能通過的牆壁時就會立刻調用它。如果 Agent 能自己完成，它就應該自己做；這是專門用於人類確實需要參與的情境。
- **`/wait-what`** — 針對未能理解的訊息的修正方法。在對話中途、任何其他技能內部使用它，Agent 會使用您缺少的上下文、通俗易懂的語言以及 `CONTEXT.md` 詞彙，重新阐述剛才說過的內容。它是事後修正；而 `/grill-with-docs` 是事前預防，因為早期約定的共享語言才是阻止專有名詞困擾的根本方法。
- **`/teach`** — 透過多個會話學習概念，使用當前目錄作為有狀態的工作區。
- **`/writing-for-agents`** — 撰寫 Agent 所讀取文件的參考資料：技能、AGENTS.md、被指引的文件。

## 前置條件
