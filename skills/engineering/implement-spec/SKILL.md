您已收到一份規格。此規格應有關聯的工單，描述如何實作該規格。

issue 追蹤器應該已提供給您。若尚未提供，請告知使用者執行 `/setup-matt-pocock-skills`。

其目標是在單一**整合分支**上實作整個規格，並依 issue 追蹤器結案工作的方式解決每張工單。

工單不是步驟清單。它們是彼此之間具有阻礙關係的**任務圖**。這意味著隨時都有一個可供拾取的就緒工單**前沿**。

與子代理之間的通訊應保持精簡。主要透過**上下文指標**進行溝通：指向規格、工單、研究筆記以及先前的 commit。請勿重複已可透過指標取得的資訊。

**實作者子代理**應盡可能在背景執行，以獲得最大的並行度。

## 步驟

1. 閱讀規格與工單以理解任務圖。

2.（選用）使用**探索子代理**進行工單所需的任何探索 — 相關的程式碼庫檔案或外部文件。確保探索子代理能夠儲存檔案 — 它應將其 Markdown 筆記儲存在儲存庫之外的目錄中，供所有未來的子代理存取。這讓**實作者子代理**能專注於實作而非探索。

3. 建立整合分支。若 issue 追蹤器透過 PR 結案工作，或使用者要求建立 PR，請在步驟 5 的第一次合併後開啟草稿 PR（沒有超前 main 之 commit 的分支無法開啟 PR），標記為關閉該規格與工單。

4. 使用**實作者子代理**實作每張工單，各自在專屬分支上的專屬工作樹 (worktree) 中進行。每個實作者子代理：
   - 在開始前確認其工作樹基於整合分支，若否則重設至該分支；
   - 呼叫帶有 `tdd` 的 Skill 工具以建構該工單；
   - 在回報完成前將整合分支頂端合併至其自身分支

5. 一旦**實作者子代理**完成，使用**合併者子代理**將其工作合併至整合分支。

6. 若此舉變更了可用工單的**前沿**，啟動更多**實作者子代理**處理新工單。這能實現最大程度的並行。

7. 當所有工單皆完成後，在整合分支上呼叫帶有 `code-review` 的 Skill 工具。在單一**實作者子代理**中修復程式碼審查提出的所有問題。

8. 若存在草稿 PR，將其標記為準備審查。否則，依 issue 追蹤器結案工作的方式解決每張工單，並回報整合分支。

9. 清理所有**實作者子代理**工作樹。
