# 領域模型建構 (Domain Modeling)

在設計過程中積極建構並精煉專案的領域模型。這是一門*積極主動*的紀律：質疑術語、設想邊角案例情境，並在詞彙與決策成形的當下記錄下來。（單純為了詞彙而*閱讀* `GLOSSARY.md` 並不屬於此技能：那是任何技能都能做到的單行習慣。此技能適用於您在變更模型而不只是取用模型之時。）

## 檔案結構 (File structure)

大多數儲存庫具有單一上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目錄存在 `GLOSSARY-MAP.md`，則該儲存庫具有多個上下文。地圖指向每個上下文所在之處：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 全系統決策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文特定決策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

延遲建立檔案：僅在您有內容要寫入時才建立。若不存在 `GLOSSARY.md`，在解決第一個術語時建立一個。若不存在 `docs/adr/`，在需要第一個 ADR 時建立它。

## 在工作階段進行期間

### 對照詞彙表進行質疑

當使用者使用的術語與 `GLOSSARY.md` 中的既有語言衝突時，立即提出指正。「您的詞彙表將『取消』定義為 X，但您似乎是指 Y。究竟是哪一個？」

### 精煉模糊語言

當使用者使用模糊或多載的術語時，提出精確的標準術語。「您提到『帳戶』：您是指客戶還是使用者？這兩者是不同的概念。」

### 討論具體情境

當討論領域關聯時，使用特定情境對其進行壓力測試。設想探測邊界案例的情境，強迫使用者精確定義概念之間的邊界。

### 與程式碼交叉對照

當使用者陳述某事物如何運作時，檢查程式碼是否相符。若發現矛盾，請予以揭露：「您的程式碼會取消整筆訂單，但您剛才說部分取消是可行的。哪一個才正確？」

### 內嵌更新 GLOSSARY.md

當一個術語得到解決時，立即於該處更新 `GLOSSARY.md`。不要批次處理：在發生時即刻擷取。請使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 應完全不含實作細節。切勿將 `GLOSSARY.md` 視為規格、草稿筆記本或實作決策的儲存庫。它僅僅是詞彙表，沒有別的。

### 謹慎提供 ADR

僅在下列三項條件全部符合時才提議建立 ADR：

1. **難以反轉**：日後改變主意的成本相當重大
2. **缺乏背景資訊時令人意外**：未來的讀者會納悶「他們為什麼要這樣做？」
3. **真實權衡取捨的結果**：存在真正的替代方案，而您出於特定原因選擇了其中之一

若三者缺少任何一項，請略過 ADR。請使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
