# 領域模型建構

在設計時主動建構與精煉專案的領域模型。這是*主動*的紀律 — 質疑術語、構思邊界情況情境，並在術語表和決策具體化的那一刻將其記錄下來。（僅僅為了解詞彙而*閱讀* `CONTEXT.md` 並非此技能 — 那是任何技能都能做到的單行習慣。此技能適用於您正在變更模型，而非僅僅使用模型時。）

## 檔案結構

大多數儲存庫具有單一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目錄存在 `CONTEXT-MAP.md`，則該儲存庫具有多個上下文。地圖會指向每個上下文所在位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系統層面的決策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 特定上下文的決策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性建立檔案 — 僅在有內容要撰寫時才建立。如果不存在 `CONTEXT.md`，在解決第一個術語時建立一個。如果不存在 `docs/adr/`，在需要第一個 ADR 時建立。

## 在會話期間

### 對照術語表進行質疑

當使用者使用的術語與 `CONTEXT.md` 中現有的語言衝突時，請立即指出。「您的術語表將『取消』定義為 X，但您似乎是指 Y — 究竟是哪一個？」

### 精煉模糊的語言

當使用者使用模糊或重載的術語時，請提出精準的規範術語。「您說『帳號』— 您是指客戶（Customer）還是使用者（User）？這兩者是不同的概念。」

### 討論具體情境

在討論領域關係時，使用具體情境對其進行壓力測試。構思能試探邊界情況的情境，並迫使使用者對概念之間的邊界保持精準。

### 與程式碼交叉比對

當使用者說明某事物如何運作時，檢查程式碼是否相符。如果發現矛盾，請浮現出來：「您的程式碼取消了整個訂單，但您剛才說部分取消是可能的 — 哪一個才是正確的？」

### 內聯更新 CONTEXT.md

當解決一個術語時，立即在該處更新 `CONTEXT.md`。不要批量處理 — 在發生時實時記錄。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 應該完全沒有實作細節。請勿將 `CONTEXT.md` 視為規格、草稿本或實作決策的儲存庫。它是一個術語表，僅此而已。

### 謹慎提供 ADR

僅在以下三者同時成立時才建議建立 ADR：

1. **難以逆轉** — 事後改變主意的成本相當高
2. **缺乏上下文時令人驚訝** — 未來的讀者會好奇「他們為什麼要這樣做？」
3. **真實權衡的結果** — 存在真實的替代方案，且您出於特定原因選擇了其中之一

如果三者中缺少任何一個，請跳過 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
