# ADR 格式 (ADR Format)

ADR 存放在 `docs/adr/` 中並使用循序編號：`0001-slug.md`、`0002-slug.md` 等。

延遲建立 `docs/adr/` 目錄：僅在需要第一個 ADR 時才建立。

## 範本 (Template)

```md
# {決策的簡短標題}

{1-3 句話：背景是什麼、我們做出了什麼決策，以及原因。}
```

就這樣。一個 ADR 可以只有一個段落。其價值在於記錄*已做出*決策以及*為何*做出該決策，而非填滿各個區塊。

## 選用區塊 (Optional sections)

僅在能帶來實質價值時納入這些區塊。大多數 ADR 不需要它們。

- **狀態 (Status)** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在重新檢討決策時很有用
- **考量過的選項 (Considered Options)**：僅在被否決的替代方案值得銘記時納入
- **後果 (Consequences)**：僅在需要特別指出不明顯的下游影響時納入

## 編號 (Numbering)

掃描 `docs/adr/` 找出目前現有的最大編號，並遞增一。

## 何時提出 ADR (When to offer an ADR)

下列三項條件必須全部成立：

1. **難以反轉**：日後改變主意的成本相當重大
2. **缺乏背景資訊時令人意外**：未來的讀者檢視程式碼時會納悶「他們到底為什麼要這樣做？」
3. **真實權衡取捨的結果**：存在真正的替代方案，而您出於特定原因選擇了其中之一

若決策容易反轉，請略過：直接反轉即可。若不令人意外，沒人會納悶原因。若沒有真正的替代方案，除了「我們做了顯而易見的事」之外沒什麼好記錄的。

### 哪些情況符合資格

- **架構形狀。**「我們使用單一儲存庫 (monorepo)。」「寫入模型採用事件溯源，讀取模型投影至 Postgres。」
- **上下文之間的整合模式。**「訂單與計費透過領域事件進行通訊，而非同步 HTTP。」
- **帶有綁定風險的技術選擇。** 資料庫、訊息匯流排、驗證提供者、部署目標。並非每個函式庫：僅限更換需耗費一季時間的那些。
- **邊界與範疇決策。**「客戶資料歸客戶上下文所有；其他上下文僅透過 ID 參照它。」明確的否定與肯定一樣有價值。
- **深思熟慮後偏離顯而易見的路徑。**「我們使用手動 SQL 而非 ORM，因為 X。」任何合理讀者會做出相反假設的情況。這能阻止下一位工程師去「修復」刻意為之的設計。
- **程式碼中看不見的限制條件。**「由於合規需求，我們無法使用 AWS。」「由於合作夥伴 API 合約，回應時間必須在 200 毫秒以內。」
- **否決理由不明顯時被否決的替代方案。** 若您考慮過 GraphQL 但因微妙原因選擇了 REST，請予以記錄；否則六個月後又會有人提議使用 GraphQL。
