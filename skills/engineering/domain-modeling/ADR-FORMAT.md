# ADR 格式

ADR 存在於 `docs/adr/` 中，並使用順序編號：`0001-slug.md`、`0002-slug.md` 等。

惰性建立 `docs/adr/` 目錄 — 僅在需要第一個 ADR 時才建立。

## 範本

```md
# {決策的簡短標題}

{1-3 句話：上下文是什麼，我們決定了什麼，以及原因。}
```

就這樣。ADR 可以只有單一段落。價值在於記錄做出了*該*決策以及*原因* — 而不是填寫各個章節。

## 可選章節

僅在它們能帶來真實價值時才包含這些內容。大多數 ADR 不需要它們。

- **Status** frontmatter (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 在重新檢視決策時非常有用
- **Considered Options** — 僅在被拒絕的替代方案值得記住時使用
- **Consequences** — 僅在需要特別提請注意不明顯的下游影響時使用

## 編號

掃描 `docs/adr/` 尋找現有的最高編號並加一。

## 何時提供 ADR

以下三者必須同時成立：

1. **難以逆轉** — 事後改變主意的成本相當高
2. **缺乏上下文時令人驚訝** — 未來的讀者看著程式碼會想「他們究竟為什麼要這樣做？」
3. **真實權衡的結果** — 存在真實的替代方案，且您出於特定原因選擇了其中之一

如果決策容易逆轉，請跳過它 — 您直接逆轉即可。如果不令人驚訝，沒有人會好奇原因。如果沒有真實的替代方案，除了「我們做了顯而易見的事」之外，沒有什麼可記錄的。

### 符合條件的情況

- **架構形狀。**「我們正在使用 monorepo。」「寫入模型是事件溯源（event-sourced），讀取模型投射至 Postgres。」
- **上下文之間的整合模式。**「訂單與帳務透過領域事件通訊，而非同步 HTTP。」
- **帶有鎖定效應的技術選擇。** 資料庫、訊息總線、驗證提供者、佈署目標。不是每個函式庫 — 只是那些需要花一整季才能替換掉的函式庫。
- **邊界與範疇決策。**「客戶資料由客戶上下文擁有；其他上下文僅透過 ID 引用它。」明確的拒絕與贊同一樣有價值。
- **偏離顯而易見路徑的深思熟慮。**「我們使用手動 SQL 而非 ORM，因為 X。」任何合理讀者都會做相反假設的情況。這些可以防止下一位工程師去「修復」深思熟慮後的設計。
- **程式碼中不可見的約束。**「由於合規性要求，我們不能使用 AWS。」「由於合作夥伴 API 合約，回應時間必須在 200ms 以下。」
- **當拒絕原因不明顯時被拒絕的替代方案。** 如果您考慮過 GraphQL 但出於微妙的原因選擇了 REST，請將其記錄下來 — 否則六個月後有人會再次提出 GraphQL。
