# 測試驅動開發

TDD 即為 紅 → 綠 的迴圈。本技能是使該迴圈產生值得保留的測試的參考資料：什麼是良好的測試、測試放置在何處、反模式，以及迴圈的規則。每個章節皆適用於每個週期 — 在迴圈之前與過程中進行諮詢，而不是事後。

探索程式碼庫時，請閱讀 `CONTEXT.md`（如果存在），以便測試名稱與介面詞彙符合專案的領域語言，並遵守您所接觸區域的 ADR。

## 什麼是良好的測試

測試透過公開介面而非實作細節來驗證行為。程式碼可以完全重寫；但測試不應該改變。一個良好的測試讀起來像規格說明 —「使用者可以使用有效的購物車結帳」會精準告訴您存在什麼功能 — 並且能在重構中存活，因為它關心的是公開介面而非內部結構。

範例參見 [tests.md](tests.md)，mock 指引參見 [mocking.md](mocking.md)。

## 接縫 — 測試放置在何處

**接縫（seam）**是您進行測試的公開邊界：您在該介面處觀察行為而無需深入內部。測試部位於接縫處，絕不針對內部。

**僅在預先約定的接縫處進行測試。** 在撰寫任何測試之前，寫下受測試的接縫並向使用者確認。絕不在未確認的接縫處撰寫測試。您無法測試所有內容 — 預先約定接縫是將測試精力投入於關鍵路徑與複雜邏輯而非每個邊界情況的方法。

詢問：「公開介面是什麼，我們應該測試哪些接縫？」

當該介面的形狀本身受到質疑時 — 例如模組應有多深、接縫應位於何處，以及介面應公開哪些內容 — 請以「codebase-design」呼叫 Skill 工具，以取得相關詞彙。它是模組、介面、深度、接縫、介面卡、槓桿與區域性等術語的共用來源，是供查閱的參考資料，而非需要執行的工作階段。

## 反模式

- **與實作耦合** — mock 內部協作者、測試私有方法，或透過旁路管道進行驗證（查詢資料庫而非使用介面）。特徵：當您重構時測試損壞，但行為並未改變。
- **同義反覆（Tautological）** — 斷言以程式碼的方式重新計算預期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手動推導的快照、與自身斷言相等的常數），因此它憑藉結構通過，絕不會與程式碼產生異議。預期值必須來自獨立的事實來源 — 已知良好的實字、完整的範例、規格。
- **水平切片** — 先撰寫所有測試，然後撰寫所有實作。批量測試驗證的是_想像中_的行為：您測試的是事物的_形狀_而非面向使用者的行為，測試對真實變更失去敏感度，且您在理解實作之前就投入到了測試結構中。改為在**垂直切片**中工作 — 一個測試 → 一個實作 → 重複，每個測試都是一個**追光彈（tracer bullet）**，對上一個週期教給您的內容做出回應。

## 迴圈的規則

- **先紅後綠。** 先撰寫失敗的測試，然後僅撰寫足以通過它的程式碼。不要預期未來的測試或新增投機性的功能。
- **一次一個切片。** 每個週期一個接縫、一個測試、一個最小實作。
- **重構不是迴圈的一部分。** 它屬於審查階段（參見 `code-review` 技能），而不屬於 紅 → 綠 實作週期。
