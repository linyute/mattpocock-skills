# 測試驅動開發

TDD 即是「紅燈 → 綠燈」循環。此技能是使該循環產出值得保留之測試的參考指引：何謂好的測試、測試應置於何處、反模式以及此循環的規則。每個章節適用於每個週期：請在循環之前與期間參閱，而非事後。

在探索程式碼庫時，請閱讀 `GLOSSARY.md`（若存在），以便測試名稱和介面詞彙符合專案的領域語言，並遵守你所接觸領域中的 ADR。

## 何謂好的測試

測試透過公開介面驗證行為，而非實作細節。程式碼可以完全重寫；測試則不應隨之更動。好的測試讀起來就像規格說明：「使用者可以使用有效購物車結帳」精確地告訴你具備何種功能，而且在重構時依然有效，因為它不在乎內部結構。

請參閱 [tests.md](tests.md) 取得範例，並參閱 [mocking.md](mocking.md) 取得模擬指引。

## 接縫：測試該放哪裡

**接縫（seam）** 是你進行測試的公開邊界：也就是在不深入內部的情況下觀察行為的介面。測試存在於接縫處，絕不針對內部細節。

**僅在預先約定的接縫處進行測試。** 在編寫任何測試之前，請記下受測的接縫並向使用者確認。不得在未確認的接縫處編寫測試。你無法測試所有東西，因此預先約定接縫是將測試精力集中在關鍵路徑和複雜邏輯上，而非每個邊緣案例的方法。

詢問：「公開介面是什麼，我們應該測試哪些接縫？」

當該介面的輪廓本身有疑問時（模組有多深、接縫屬於何處、介面應該公開什麼），呼叫帶有 "codebase-design" 的 Skill 工具以取得詞彙。它是 module、interface、depth、seam、adapter、leverage 與 locality 術語的共用來源，也是供查閱的參考資料，而非要執行的工作階段。

## 反模式

- **耦合實作（Implementation-coupled）**：模擬內部協作者、測試私有方法，或透過旁門左道進行驗證（查詢資料庫而非使用介面）。徵兆：重構時測試損毀，但行為並未改變。
- **套套邏輯（Tautological）**：斷言以程式碼相同的方式重新計算預期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手動衍生快照、斷言常數等於其自身），因此它依結構即通過，絕不可能與程式碼產生分歧。預期值必須來自獨立的事實來源：已知的正確常值、演算範例、規格。
- **水平切片（Horizontal slicing）**：先撰寫所有測試，再進行所有實作。批量測試驗證的是*想像中*的行為：你測試的是事物的*形狀*而非面向使用者的行為，測試對真正的變更失去敏感度，而且你在理解實作之前就承諾了測試結構。改為在**垂直切片**中工作：一次測試 → 一次實作 → 重複進行，每個測試都是一個**曳光彈（tracer bullet）**，用以回應上個週期帶給你的回饋。

## 循環規則

- **先紅後綠。** 先撰寫失敗的測試，然後只撰寫足以使其通過的程式碼。不要預期未來的測試或加入投機性功能。
- **一次一個切片。** 每個週期一個接縫、一個測試、一個最小實作。
- **重構不屬於此循環的一部分。** 它屬於審查階段（參見 `code-review` 技能），而非紅燈 → 綠燈的實作循環。
