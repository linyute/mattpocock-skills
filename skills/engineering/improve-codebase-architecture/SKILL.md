# 改善程式碼庫架構

找出架構摩擦並提出**深化機會**：將淺模組轉換為深模組的重構。目標在於可測試性與 AI 可導航性。

此指令受專案領域模型所_啟發_，並建立在共用的設計詞彙之上：

- 使用 "codebase-design" 呼叫 Skill 工具以取得架構詞彙（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原則（刪除測試、「介面即測試表面」、「一個介面卡 = 假設接合點，兩個 = 真實」）。在每個建議中精確使用這些術語，切勿偏離為 "component"、"service"、"API" 或 "boundary"。
- `GLOSSARY.md` 中的領域語言為良好接合點命名；`docs/adr/` 中的 ADR 記錄了此指令不應重新爭辯的決策。

## 流程

### 1. 探索

**掃描前先劃定範圍：YAGNI。** 深化模組的好處在於使未來的變更更容易，因此應特別重視程式碼庫中最近變動的部分。在檢視之前先決定*該往何處*檢視：

- 若使用者指定了方向（模組、子系統、痛點），請直接採用，並略過下方的推論。
- 否則，回溯一段提交歷史紀錄（`git log --oneline`）以找出程式碼庫的熱點、持續出現的檔案與區域，並讓這些路徑優先吸引您的注意力。若變更分散且無明確熱點，請擴大範圍。

優先閱讀專案的領域術語表（`GLOSSARY.md`）以及您所觸及區域中的任何 ADR。

接著產生子代理來走訪程式碼庫。不要遵循死板的啟發式規則；有機地探索並記錄您遇到摩擦的地方：

- 在哪裡理解一個概念需要穿梭於許多小模組之間？
- 在哪裡的模組是**淺的**，其介面複雜度幾乎與實作相當？
- 在哪裡純函式純粹是為了可測試性而被萃取出來，但真正的錯誤卻隱藏在其呼叫方式中（缺乏**局部性**）？
- 在哪裡緊密耦合的模組穿過其接合點洩漏？
- 程式碼庫的哪些部分未經測試，或是難以透過其目前的介面進行測試？

對您懷疑為淺薄的任何事物套用**刪除測試**：刪除它會將複雜性集中，還是僅僅將其轉移？「是的，集中」正是您想要的訊號。

### 2. 以 HTML 報告呈現候選項

將自包含的 HTML 檔案寫入作業系統的暫存目錄，以確保不會有任何內容落入儲存庫中。從 `$TMPDIR` 解析暫存目錄，退回至 `/tmp`（或 Windows 上的 `%TEMP%`），並寫入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次執行都能獲得全新檔案。為使用者開啟它（Linux 上使用 `xdg-open <path>`，macOS 上使用 `open <path>`，Windows 上使用 `start <path>`）並告知其絕對路徑。

該報告使用 **CDN 的 Tailwind** 進行排版與樣式設定，並使用 **CDN 的 Mermaid** 繪製可藉由圖表／流程／循序可靠傳達結構的圖表。將 Mermaid 與手刻 CSS/SVG 視覺效果混合使用：當關係為圖形狀時（呼叫圖、相依性、循序）使用 Mermaid，當您想要更有編輯風格的視覺效果時（質量圖、橫截面、摺疊動畫）使用手刻 div/SVG。每個候選項都會獲得**修改前／修改後視覺化**。務必具視覺效果。

為每個候選項呈現包含以下內容的卡片：

- **檔案**：涉及哪些檔案／模組
- **問題**：目前的架構為何造成摩擦
- **解決方案**：以平實文字描述將會做什麼變更
- **效益**：以局部性（locality）與槓桿作用（leverage）進行說明，以及測試將如何改善
- **修改前／修改後圖表**：並排、自訂繪製，說明其淺薄與深化之處
- **建議強度**：`Strong`、`Worth exploring`、`Speculative` 其中之一，呈現為徽章

報告結尾附上**最首要建議**區段：您會先處理哪個候選項以及原因。

**針對領域使用 GLOSSARY.md 詞彙，針對架構使用 `/codebase-design` 詞彙。** 若 `GLOSSARY.md` 定義了「Order」，請討論「Order intake 模組」，而非「FooBarHandler」，亦非「Order 服務」。

**ADR 衝突**：若候選項與既有 ADR 相牴觸，僅在摩擦已強烈到足以重新檢視該 ADR 時才提出。在卡片中清楚標示（例如警告標註：_「與 ADR-0007 衝突，但值得重新討論，因為……」_）。不要列出 ADR 所禁止的每項理論性重構。

完整 HTML 鷹架、圖表模式與樣式指引請參閱 [HTML-REPORT.md](HTML-REPORT.md)。

尚**不要**提出介面。檔案寫入後，詢問使用者：「您想探索其中的哪一個？」

### 3. 深入探討迴圈（Grilling loop）

一旦使用者挑選了候選項，使用 "grilling" 呼叫 Skill 工具與其一起走訪決策樹：條件約束、相依性、深化模組的外觀、接合點背後是什麼、哪些測試能保留。

隨著決策逐漸成形，副作用會即時發生；在進行過程中，使用 "domain-modeling" 呼叫 Skill 工具以維持領域模型為最新狀態：

- **要以不在 `GLOSSARY.md` 中的概念來命名深化模組嗎？** 將該術語新增至 `GLOSSARY.md`。若檔案不存在則延遲建立。
- **在對話過程中讓模糊術語更加明確？** 當場更新 `GLOSSARY.md`。
- **使用者因關鍵支撐理由而拒絕該候選項？** 提供 ADR，表達方式如：_「需要我將此記錄為 ADR，以便未來的架構審查不再重複建議嗎？」_ 僅在未來的探索者確實需要該理由以避免重複建議相同內容時才提供；略過短暫的理由（「目前不值得做」）與顯而易見的理由。
- **想要為深化模組探索替代介面嗎？** 使用 "codebase-design" 呼叫 Skill 工具，並使用其雙重設計（design-it-twice）平行子代理模式。
