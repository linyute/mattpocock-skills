# 改進程式碼庫架構

浮現架構摩擦並提出**深化機會** — 將淺層模組轉變為深度模組的重構。目標是可測試性與 AI 可巡覽性。

此命令由專案的領域模型*提供資訊*，並建構於共享設計詞彙之上：

- 執行 `/codebase-design` 技能以獲取架構詞彙（**模組**、**介面**、**深度**、**接縫**、**轉接器**、**槓桿作用**、**局部性**）及其原則（刪除測試、「介面即測試表面」、「一個轉接器 = 假設性接縫，兩個 = 真實接縫」）。在每個建議中精準使用這些術語 — 切勿偏離為「元件」、「服務」、「API」或「邊界」。
- `CONTEXT.md` 中的領域語言為良好接縫命名；`docs/adr/` 中的 ADR 記錄了此命令不應重新爭論的決策。

## 流程

### 1. 探索

**在掃描前劃定範疇 — YAGNI。** 深化模組的效益在於使未來對其進行的變更更容易，因此請在最近變更過的程式碼庫部分上投入更多權重。在查看之前決定要查看*何處*：

- 如果使用者指定了方向 — 模組、子系統、痛點 — 請採納並跳過下方的推斷。
- 否則，向上追溯一段相當長的提交歷史（`git log --oneline`）以尋找程式碼庫的熱點 — 不斷出現的檔案與區域 — 並讓這些路徑首先吸引您的注意力。如果變更很分散且沒有明確的熱點，請擴大範圍。

首先閱讀專案的領域術語表（`CONTEXT.md`）以及您接觸區域的任何 ADR。

然後衍生一個子 Agent 來巡覽程式碼庫。不要遵循死板的啟發式方法 — 有機地探索並記錄您體驗到摩擦的地方：

- 在何處理解一個概念需要在一堆小模組之間跳來跳去？
- 在何處模組是**淺層的** — 介面幾乎與實作一樣複雜？
- 在何處僅僅為了可測試性而擷取了純函式，但真實 Bug 卻隱藏在它們被呼叫的方式中（缺乏**局部性**）？
- 在何處緊密耦合的模組跨越其接縫洩漏？
- 程式碼庫的哪些部分尚未測試，或很難透過目前的介面進行測試？

對您懷疑是淺層的任何內容套用**刪除測試**：刪除它會集中複雜性，還是只是轉移複雜性？「是，會集中」是您想要的訊號。

### 2. 將候選項呈現為 HTML 報告

撰寫獨立的 HTML 檔案至 OS 暫存目錄，這樣就不會有任何內容落在儲存庫中。從 `$TMPDIR` 解析暫存目錄（備用方案為 `/tmp`，Windows 上為 `%TEMP%`），並寫入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次執行都獲得全新的檔案。為使用者開啟它 — Linux 上為 `xdg-open <path>`，macOS 上為 `open <path>`，Windows 上為 `start <path>` — 並告知他們絕對路徑。

報告使用 **Tailwind via CDN** 進行佈局與樣式設定，並使用 **Mermaid via CDN** 繪製圖形/流程/時序能可靠傳達結構的圖表。將 Mermaid 與手作 CSS/SVG 視覺效果混合使用 — 在關係為圖形狀時（呼叫圖、依賴項、時序）使用 Mermaid，在想要更具編輯感的效果時（質量圖、橫截面、折疊動畫）使用手動建立的 div/SVG。每個候選項都會獲得 **before/after 視覺化**。要視覺化。

為每個候選項渲染一張帶有以下內容的卡片：

- **檔案** — 涉及哪些檔案/模組
- **問題** — 為何目前的架構會造成摩擦
- **解決方案** — 用通俗語言描述將改變什麼
- **好處** — 從局部性和槓桿作用，以及測試將如何改進的角度進行解釋
- **Before / After 圖表** — 並排自訂繪製，說明淺層化與深化
- **建議強度** — `Strong`、`Worth exploring``Speculative` 之一，渲染為標籤

以**首要建議**章節結束報告：您會最先處理哪個候選項以及原因。

**使用 CONTEXT.md 詞彙處理領域，並使用 `/codebase-design` 詞彙處理架構。** 如果 `CONTEXT.md` 定義了「Order」，請稱其為「Order intake 模組」— 而不是「FooBarHandler」，也不是「Order 服務」。

**ADR 衝突**：如果候選項與現有 ADR 矛盾，僅在摩擦足夠真實、值得重新檢視 ADR 時才浮現出來。在卡片中清晰標記（例如警告標註：_「與 ADR-0007 矛盾 — 但值得重新探討，因為…」_）。不要列出 ADR 所禁止的每種理論上的重構。

參見 [HTML-REPORT.md](HTML-REPORT.md) 以了解完整的 HTML 骨架、圖表模式與樣式指引。

尚切勿提出介面方案。檔案寫入後，詢問使用者：「您想探索其中的哪一個？」

### 3. 審問迴圈

一旦使用者選擇了一個候選項，執行 `/grilling` 技能與他們一起走過決策樹 — 約束、依賴項、深化模組的形狀、部位於接縫背後的內容、有哪些測試能存活。

隨著決策具體化，副作用會在內部產生 — 執行 `/domain-modeling` 技能，以便在過程中保持領域模型為最新狀態：

- **以 `CONTEXT.md` 中不存在的概念命名深化模組？** 將該術語新增至 `CONTEXT.md`。如果檔案不存在則惰性建立。
- **在對話過程中精煉模糊的術語？** 立即在該處更新 `CONTEXT.md`。
- **使用者以具承重作用的原因拒絕了該候選項？** 建議建立 ADR，構架為：_「要我將此記錄為 ADR 嗎？這樣未來的架構審查就不會再次建議它。」_ 僅在未來探索者確實需要該原因以避免再次建議相同事物時才提供 — 跳過短暫的原因（「現在不值得」）與顯而易見的原因。
- **想要為深化的模組探索替代介面？** 執行 `/codebase-design` 技能並使用其 design-it-twice 平行子 Agent 模式。
