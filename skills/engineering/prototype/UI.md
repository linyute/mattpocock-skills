# UI 原型

在單一路由上產生**數種截然不同的 UI 變體**，可從浮動底列進行切換。使用者可以在瀏覽器中切換各變體、挑選其中一個（或從每個變體中擷取部分優點），然後將其餘部分丟棄。

若問題涉及邏輯／狀態而非外觀長相，那這就選錯分支了。請使用 [LOGIC.md](LOGIC.md)。

## 適合此形式的時機

- 「這個頁面應該長什麼樣？」
- 「我想在確認之前先看看這個儀表板的幾個選項。」
- 「為設定畫面嘗試不同的版面配置。」
- 任何使用者本來會在腦海中花上一整天在三個模糊模型之間抉擇的時候。

## 兩種子形式：強烈建議使用子形式 A

當 UI 原型**緊鄰應用程式的其他部分**時更容易進行評估：真實的頁首、真實的側邊欄、真實的資料、真實的密度。單獨的拋棄式路由就像真空環境：每個變體在孤立狀態下看起來都很不錯。只要有合理的既有頁面可容納變體，請預設使用子形式 A。只有在原型確實沒有鄰近歸宿時，才求助於子形式 B。

### 子形式 A：對既有頁面的調整（首選）

路由已經存在。變體會在**同一個路由上**算圖，透過 `?variant=` URL search param 進行控制。既有的資料擷取、參數與身分驗證皆予以保留。僅有算圖部分被替換。這是預設做法；除非有特定原因，否則請選擇此方式。

若原型是針對尚無頁面但*自然會存在於某個頁面內部*的事物（儀表板的新區段、設定畫面上的新卡片、既有流程中的新步驟），仍然屬於子形式 A。將變體掛載於宿主頁面中。

### 子形式 B：新頁面（最後手段）

僅在正在製作原型的項目確實沒有可置於其中的既有頁面時才使用（例如全新的頂層介面，或是無法合理嵌入任何地方的流程）。

遵循專案已使用的任何路由慣例，建立一個**拋棄式路由**。不要發明新的頂層結構。為其命名以便明顯看出是原型（例如在路徑或檔名中包含 `prototype` 字樣）。採用相同的 `?variant=` 模式。

在確認採用子形式 B 之前，請先進行健全性檢查：真的沒有可以嵌入的既有頁面嗎？空白路由會掩蓋被填滿的路由原本能暴露出來的設計問題。

在這兩種子形式中，浮動底列是完全相同的。

## 流程

### 1. 陳述問題並挑選 N

預設為 **3 個變體**。超過 5 個就不再具備截然不同的差異，且會變成雜訊，因此以此為上限。

在原型的位置或檔案頂端的註解中用一行寫下計畫：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

無論使用者是否在場給予反饋，這種方式都適用。

### 2. 產生截然不同的變體

起草每個變體。每個變體都必須符合：

- 頁面的目的及其可存取的資料。
- 專案的元件函式庫／樣式系統（TailwindCSS、shadcn、MUI、純 CSS 等）。
- 明確匯出的元件名稱，例如 `VariantA`、`VariantB`、`VariantC`。

變體必須在**結構上有所不同**：不同的版面配置、不同的資訊階層、不同的主要能供性（affordance），而不僅僅是顏色不同。三個稍微調整的卡片網格不是 UI 原型，那是壁紙。如果兩個草案看起來太相似，請在明確「不要使用卡片網格」的指引下重做其中一個。

### 3. 將它們連接在一起

在路由上建立單一切換器元件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

針對子形式 A（既有頁面）：將所有既有的資料擷取保留在切換器之上；每個變體僅變更所算圖的子樹。

針對子形式 B（新頁面）：在 `/prototype/<name>` 下的拋棄式路由掛載相同的切換器。

### 4. 建構浮動切換器

位於螢幕底部中央的小型固定位置列，包含三個部分：

- **向左箭號**：循環切換至上一個變體（循環繞回）。
- **變體標籤**：顯示目前的變體鍵值，若變體有匯出名稱，亦顯示該名稱。例如 `B (Sidebar layout)`。
- **向右箭號**：向前循環切換（循環繞回）。

行為：

- 點擊箭號會更新 URL search param（使用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），使變體具備可分享性且重新載入後保持穩定。
- 鍵盤：`←` 與 `→` 箭頭鍵也可進行循環切換。當焦點位於 `<input>`、`<textarea>` 或 `[contenteditable]` 時，請勿攔截方向鍵。
- 視覺上與頁面有所區別（例如高對比藥丸狀外觀、微微陰影），使其顯然不是正在評估的設計的一部分。
- 在正式建構中隱藏：以 `process.env.NODE_ENV !== 'production'` 或同等檢查進行把關，避免走失的原型合併將此列發布給使用者。

將切換器放在單一共用元件中，以便兩種子形式都能重複使用它。將其放置在專案中存放共用 UI 的位置。

### 5. 交付

呈現 URL（以及 `?variant=` 鍵值）。使用者會在有空時瀏覽。有趣的意見回饋通常是**「我想要 B 的頁首搭配 C 的側邊欄」**，這才是他們真正想要的設計。

### 6. 擷取答案並清理

一旦選出勝出的變體，擷取答案（哪個變體及其原因），然後按照 [SKILL](SKILL.md) 描述的方式擷取原型。將勝出者整合至真實程式碼中，並將其餘部分移至拋棄式分支，而非 main：

- **子形式 A**：將勝出者整合進既有頁面；從 main 中捨棄落選的變體與切換器。
- **子形式 B**：將勝出變體晉升為真實路由；從 main 中捨棄拋棄式路由與切換器。

完整的變體集合是一手資料來源，因此它會存放在拋棄式分支中，而不是回收桶裡，因為留在 main 分支中的變體元件與切換器很快就會腐爛並讓下一位閱讀者感到困惑。

## 反模式

- **僅在顏色或文案上有所不同的變體。** 那是微調，不是原型。真正的變體在結構上是有分歧的。
- **在變體之間共用過多程式碼。** 共用 `<Header>` 沒問題；共用 `<Layout>` 則失去了意義。每個變體都應該能自由推翻版面配置。
- **將變體連接至真實的變異（mutations）。** 唯讀的原型就足夠了。若變體需要進行變異，請將其指向存根（stub）：問題是「這應該長成什麼樣」，而不是「後端是否能運作」。
- **將原型直接晉升至正式環境。** 變體程式碼是在原型約束下撰寫的（無測試、最精簡的錯誤處理）。將其整合進去時請妥善重寫。
