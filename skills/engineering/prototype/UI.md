# UI 原型

在單一路線上產生**多個截然不同的 UI 變體**，可從浮動底部列進行切換。使用者在瀏覽器中於各變體之間切換，選擇其中一個（或從各個變體中取材），然後丟棄其餘部分。

如果問題涉及邏輯/狀態而非某些事物看起來如何 — 走錯分支了。請使用 [LOGIC.md](LOGIC.md)。

## 何時這是正確的形狀

- 「這個頁面看起來應該像什麼？」
- 「在提交前我想看看這個儀表板的幾個選項。」
- 「為設定畫面嘗試不同的佈局。」
- 任何使用者若非如此就會花上一整天在腦海中的三個模糊 Mockup 之間做選擇的情況。

## 兩種子形狀 — 強烈偏好子形狀 A

當 UI 原型**與應用程式的其他部分相鄰**時（真實的標頭、真實的側邊欄、真實的資料、真實的密度），評判起來會容易得多。獨自存在的一次性路線就像一個真空：隔離看來每個變體都不錯。只要存在合理承載變體的現有頁面，就預設使用子形狀 A。僅當原型確實沒有附近的宿主時才調用子形狀 B。

### 子形狀 A — 對現有頁面的調整（首選）

路線已經存在。變體渲染**在相同的路線上**，由 `?variant=` URL 搜尋參數控制。現有的資料擷取、參數與驗證皆保持不變 — 僅交換渲染內容。這是預設選項；除非有不這樣做的特定原因，否則請選擇它。

如果原型針對的是尚未擁有頁面但*自然會存在於其中*的事物（儀表板的新區塊、設定畫面的新卡片、現有流程中的新步驟）— 這仍是子形狀 A。將變體掛載於宿主頁面內部。

### 子形狀 B — 新頁面（最後手段）

僅當被原型設計的事物確實沒有現有頁面可供存在時才使用 — 例如全新的頂層介面，或無法內嵌至任何合理位置的流程。

遵循專案已採用的任何路由慣例建立**一次性路線** — 不要發明新的頂層結構。對其命名使其顯然是原型（例如在路徑或檔名中包含 `prototype` 一詞）。採用相同的 `?variant=` 模式。

在確定採用子形狀 B 之前，進行健全性檢查：真的沒有可以內嵌此內容的現有頁面嗎？空白路線會掩蓋填充內容的路線所能暴露的設計問題。

在兩種子形狀中，浮動底部列都是相同的。

## 流程

### 1. 陳述問題並選擇 N

預設為 **3 個變體**。超過 5 個就不再具備截然不同性，並開始變成雜訊 — 以此為限。

在原型的位置或檔案頂部註解中，用一行文字寫下計劃：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

無論使用者是否在此反駁，這都能發揮作用。

### 2. 產生截然不同的變體

起草每個變體。讓每個變體遵循：

- 頁面的目的以及它有權存取的資料。
- 專案的元件函式庫 / 樣式系統（TailwindCSS、shadcn、MUI、純 CSS 等等）。
- 清晰的導出元件名稱，例如 `VariantA`、`VariantB`、`VariantC`。

變體必須在**結構上不同** — 不同的佈局、不同的資訊階層、不同的主要可負擔性（affordance），而不僅僅是不同的顏色。三個微調的卡片網格不是 UI 原型，而是桌布。如果兩個草稿太相似，請在「不要使用卡片網格」的明確指示下重新製作其中一個。

### 3. 將它們連接在一起

在路線上建立單一切換器元件：

```tsx
// 虛擬程式碼 — 調整以適應專案的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

對於子形狀 A（現有頁面）：將所有現有的資料擷取保持在切換器之上；每個變體僅變更渲染的子樹。

對於子形狀 B（新頁面）：在 `/prototype/<name>` 下的一次性路線會掛載相同的切換器。

### 4. 建構浮動切換器

螢幕底部中央小型固定位置的邊列，包含三個部分：

- **向左箭頭** — 循環切換至上一個變體（迴繞）。
- **變體標籤** — 顯示當前變體金鍵，如果變體導出了名稱，也顯示該名稱。例如 `B — Sidebar layout`。
- **向右箭頭** — 向前循環切換（迴繞）。

行為：

- 點擊箭頭會更新 URL 搜尋參數（使用框架的路由器 — Next 上為 `router.replace`，React Router 上為 `navigate` 等），使變體可共享且重新載入後穩定。
- 鍵盤：`←` 與 `→` 方向鍵也會進行循環。當焦點位於 `<input>`、`<textarea>` 或 `[contenteditable]` 時，請勿攔截方向鍵。
- 在視覺上與頁面有所區隔（例如高對比膠囊、微妙陰影），因此它顯然不屬於正在評估的設計的一部分。
- 在正式環境建構中隱藏 — 以 `process.env.NODE_ENV !== 'production'` 或同等檢查進行限制，因此意外的原型合併不會將此邊列發佈給使用者。

將切換器放在單一共享元件中，以便兩種子形狀都可以重用它。將其放置在專案中共享 UI 所在的任何位置。

### 5. 進行交付

浮現 URL（與 `?variant=` 金鍵）。使用者會在方便時進行翻閱。有趣的相應回饋通常是**「我想要 B 的標頭配上 C 的側邊欄」**— 這才是他們想要的實際設計。

### 6. 擷取答案並清理

一旦某個變體勝出，擷取答案 — 哪個變體以及原因 — 然後按照 [SKILL](SKILL.md) 描述的方式擷取原型。將勝出者併入真實程式碼中，並將其餘部分移動至一次性分支，而不是 main：

- **子形狀 A** — 將勝出者併入現有頁面；從 main 中捨棄落選的變體與切換器。
- **子形狀 B** — 將勝出的變體提升為真實路線；從 main 中捨棄一次性路線與切換器。

完整的變體集合是主要來源，因此它會落在一次性分支上而非垃圾桶中 — 留在 main 分支中的變體元件與切換器會快速腐爛並困惑下一位讀者。

## 反模式

- **僅在顏色或文案上有差異的變體。** 那是微調而非原型。真實的變體在結構上存在異議。
- **在變體之間共享太多程式碼。** 共享 `<Header>` 是可以的；共享 `<Layout>` 則違背了初衷。每個變體都應該可以自由捨棄佈局。
- **將變體連接至真實的變更操作（mutation）。** 唯讀原型即可。如果變體需要進行變更，請將其指向存根（stub）— 問題是「這個看起來應該像什麼」，而不是「後端是否運作」。
- **將原型直接提升至正式環境。** 變體程式碼是在原型約束下撰寫的（沒有測試，極少的錯誤處理）。當您將其併入時，請適當地重寫它。
