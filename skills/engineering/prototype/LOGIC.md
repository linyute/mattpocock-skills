# 邏輯原型

單一且獨立的 HTML 檔案 — **可共享的 Demo** — 讓任何人都能透過點擊按鈕來驅動狀態模型。當問題涉及**商業邏輯、狀態轉移或資料形狀**時使用此檔案 — 這類事物在紙面上看似合理，但只有在您將其推向真實案例時才會感覺不對勁。

因為它是一個無需安裝任何內容的檔案，您可以將其交給非開發人員 — 設計師、PM、領域專家 — 讓他們親身感受模型。因此它使用的是他們的語言，而不是程式碼的語言。

## 何時這是正確的形狀

- 「我不確定這個狀態機是否能處理 X 然後 Y 的邊界情況。」
- 「這個資料模型是否真的能讓我表示…的情況」
- 「我想在撰寫 API 之前先感受一下 API 應該是什麼樣子。」
- 任何希望有人能夠**按按鈕並觀察狀態變化**的情境。

如果問題是「這個看起來應該像什麼」— 走錯分支了。請使用 [UI.md](UI.md)。

## 流程

### 1. 陳述問題

在撰寫程式碼之前，寫下您正在建構原型的狀態模型與問題。單一段落，位於 Demo 頂部（在可見的介紹中，而不僅僅是註解）。回答錯誤問題的邏輯原型純粹是浪費 — 請將問題明確化，以便日後檢查，無論使用者現在正在觀看還是離線後回頭檢視。

### 2. 在可攜式模組中隔離邏輯

將實際邏輯 — 回答問題的那部分 — 放在寫成小型純模組的單一 `<script>` 區塊中，該模組日後可以被拔出並放進真實的程式碼庫中。圍繞它的頁面是一次性的；但這個模組不是。

正確的形狀取決於問題：

- **純 Reducer** — `(state, action) => state`。當動作是離散事件且狀態為單一值時效果很好。
- **狀態機** — 明確的狀態與轉移。當「目前哪些動作甚至是合法的」是問題的一部分時效果很好。
- 一套針對純資料型別的**小型純函式集**。當沒有隱式的當前狀態 — 只有轉換時效果很好。
- 當邏輯確實擁有持續的內部狀態時，使用具有清晰方法表面的**類別或模組**。

選擇最適合作出提問解答的形狀，*而不是*最容易連接至頁面的形狀。保持純淨：沒有 DOM、沒有 `document`、沒有按鈕處理常式觸及內部。頁面呼叫它；沒有內容朝反方向流動。這使得原型在其自身生命週期之外依然有用：一旦問題得到解答，驗證過的 reducer / 狀態機 / 函式集就能獨立提升至真實模組中。

### 3. 建構可共享的 HTML 檔案

單一檔案，純 HTML/CSS/JS — 沒有框架、沒有打包工具、沒有伺服器，所有內容皆內聯，因此雙擊即可開啟，即使透過電子郵件轉發也能存活。任何人開啟它都應該能夠執行。

為非開發人員而撰寫。每個標籤都使用**領域語言**而非程式碼 — 按鈕與狀態讀起來像業務邏輯，而非 reducer。用平實的語言解釋正在發生的事情。

由上至下佈局清晰的階層結構：

1. **標題與單行說明**，說明此 Demo 讓您探索什麼（步驟 1 中的問題）。
2. **當前狀態** — 完整的相關狀態，渲染為可讀面板（帶標籤的欄位，而不是原始 JSON 傾印），每次點擊後重新渲染，以便變更是可見的。在有助於非開發人員跟進的地方，特別註明剛才改變了什麼。
3. **自由操作按鈕** — 每個動作一個按鈕，始終可用，以便任何人都可以按任何順序試探模型。每次點擊會發出其動作並重新渲染狀態。
4. **引導式流程** — 一組**情境**，每個分頁一個。每個分頁包含對該情境的簡短通俗語言描述 — 它設定的情境以及需要注意的事項 — 在其下方是針對該情境按順序排列的**要按下的按鈕**。每個步驟都是真實的按鈕：點擊它會執行該動作並進入下一個步驟。啟動引導式流程會重置為已知的初始狀態，因此每次情境都會以相同的方式執行。

選擇展示棘手情況的情境 — 理想路徑、棘手的邊界情況、嘗試做某些應該是非法的事 — 那些難以在紙面上推理的情況。

保持美觀但克制：乾淨的字體排印、寬鬆的間距、一種強調色。沒有動畫、沒有噱頭 — 沒有任何會與狀態和按鈕競爭特寫的內容。

### 4. 進行交付

將檔案發送給他們，或為他們開啟。他們會在方便時點擊引導式流程與自由操作；有趣的時間點是當他們說「等等，那應該是不可能的」或「疑，我以為 X 會有所不同」— 那些就是_構想_中的 Bug，而這正是整個重點。如果他們想要新的動作或新的情境，請添加它們。原型是會演進的。

### 5. 擷取答案與原型

一旦原型回答了它的問題，擷取答案，然後按照 [SKILL](SKILL.md) 描述的方式擷取原型。特定於邏輯的映射：驗證過的 reducer / 狀態機 / 函式集提升至真實模組中（決策，被吸收）；HTML 外殼則一併前往保留原型作為主要來源的一次性分支 — 由於它是一個獨立的檔案，它在該處保持簡便可重新執行。

## 反模式

- **不要新增測試。** 需要測試的原型不再是原型。
- **不要將其連接至真實資料庫。** 使用記憶體內狀態，除非問題專門針對持久性。
- **不要過度通用化。** 不要出現「如果我們稍後想支援 X 該怎麼辦」。原型僅回答一個問題。
- **不要將邏輯與頁面混為一談。** 如果純模組引用了 DOM、`document` 或按鈕處理常式，它就不再可提升。保持頁面作為純模組之上的薄外殼。
- **不要調用框架、打包工具或伺服器。** 接收者雙擊開啟的單一檔案；React 應用程式或開發伺服器會破壞「可共享性」。
- **不要將 HTML 外殼發佈至正式環境。** 頁面是針對手動點擊進行最佳化的。其背後的邏輯模組才是值得保留的部分。
