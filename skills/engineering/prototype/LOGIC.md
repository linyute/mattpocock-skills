# 邏輯原型

單一自包含的 HTML 檔案（**可分享的展示品**），讓任何人都能透過按鈕點擊來驅動狀態模型。當問題涉及**業務邏輯、狀態轉換或資料形狀**時使用：這類事情在紙面上看起來合理，但唯有帶入真實案例時才會感覺出問題。

因為它只是一個無需安裝任何東西的單一檔案，你可以將它交給非開發人員（設計師、PM、領域專家），讓他們親自感受這個模型。因此它使用的是他們的語言，而不是程式碼的語言。

## 適合此形式的時機

- 「我不確定這個狀態機是否能處理先 X 後 Y 的邊界情況。」
- 「這個資料模型真的能讓我表達……的情況嗎？」
- 「我想在編寫 API 之前先感受一下它的外觀應該長什麼樣。」
- 任何有人想要**按下按鈕並觀察狀態變化**的情況。

如果問題是「這應該長成什麼外觀」，那這就選錯分支了。請使用 [UI.md](UI.md)。

## 流程

### 1. 陳述問題

在撰寫程式碼之前，寫下你正在製作原型的狀態模型與問題。在展示品頂部寫一個段落（在可見的介紹中，而不僅僅是註解）。回答錯誤問題的邏輯原型純粹是浪費，因此請明確陳述問題以便稍後查驗，無論使用者現在正在觀看還是稍後非同步回來查看。

### 2. 在可攜式模組中隔離邏輯

將實際邏輯（回答問題的那部分）放在單一 `<script>` 區塊中，寫成一個小巧純粹的模組，以便稍後提取並放入真正的程式碼庫中。其周圍的頁面是用過即丟的；但這個模組不是。

適當的形式取決於問題：

- **純粹的 reducer**：`(state, action) => state`。當動作是離散事件且狀態為單一值時非常適合。
- **狀態機**：明確的狀態與轉換。當「目前哪些動作合法」本身就是問題的一部分時非常適合。
- 針對純資料型別的**一組小型純函式**。當沒有隱含的目前狀態、只有轉換時非常適合。
- 當邏輯確實擁有持續的內部狀態時，具有**清楚方法表面積的類別或模組**。

挑選最適合所提問題的形式，*而不是*最容易連結到頁面的形式。保持其純粹性：沒有 DOM、沒有 `document`、沒有按鈕處理常式觸及內部。頁面呼叫進入它；反方向則毫無流通。這就是讓原型超越其自身生命週期的關鍵：一旦問題得到解答，經驗證的 reducer／狀態機／函式集合便能單獨提取至真實模組中。

### 3. 建構可分享的 HTML 檔案

單一檔案，純 HTML/CSS/JS：無框架、無打包工具、無伺服器，所有內容皆行內化，以便點兩下即可開啟並能在電子郵件中傳遞。任何人開啟它都應該能直接執行。

為非開發人員而寫。每個標籤都使用**領域語言**，而非程式碼：按鈕與狀態讀起來像業務術語，而非 reducer。用平實的字詞解釋正在發生的事情。

由上而下採用清晰的階層進行版面配置：

1. **標題與單行解釋**，說明此展示品可探索的內容（步驟 1 中的問題）。
2. **目前狀態**：完整的相關狀態，呈現為易讀的面板（帶有標籤的欄位，而非原始 JSON 傾印），每次點擊後重新算圖，以便看清變化。在有助於非開發人員理解的地方，標註剛剛變更的內容。
3. **自由操作按鈕**：每個動作一個按鈕，隨時可用，讓任何人都能以任何順序測試模型。每次點擊都會分派其動作並重新算圖狀態。
4. **引導式逐步操作**：一組**情境**，每個分頁一個。每個分頁包含該情境的簡短白話描述（設定的情況以及應注意的事項），其下方則是該情境應**按下的循序按鈕**。每個步驟都是真正的按鈕：點擊它會執行該動作並進入下一步。開始逐步操作會重設為已知的初始狀態，使情境每次都以相同方式執行。

選擇能展示棘手情況的情境，即那些在紙面上難以推論的情境：順暢路徑（happy path）、棘手的邊界情況、嘗試進行應該非法的操作。

保持美觀但克制：乾淨的字型排印、寬敞的間距、單一強調色。無動畫、無噱頭：沒有任何會與狀態及按鈕互相競爭的事物。

### 4. 交付

將檔案傳送給他們，或為他們開啟。他們會在有空時點擊逐步操作與自由操作；有趣的時刻是當他們說「等等，那應該是不可能的」或「咦，我以為 X 應該不同」；那些就是_想法_上的缺陷，而這正是整件事的重點。如果他們想要新的動作或新的情境，請予以新增。原型會不斷演進。

### 5. 擷取答案與原型

一旦原型回答了問題，請擷取答案，然後按照 [SKILL](SKILL.md) 描述的方式擷取原型。邏輯專屬的對應：經驗證的 reducer／狀態機／函式集合提取至真實模組中（吸收該決策）；HTML 外殼則隨之進入用過即丟的分支，該分支將原型保留為一手資料來源，並且由於它是單一自包含檔案，在該處仍可輕易重新執行。

## 反模式

- **不要新增測試。** 需要測試的原型就不再是原型。
- **不要將其連接到真實資料庫。** 除非問題專門針對持續性（persistence），否則請使用記憶體內狀態。
- **不要過度泛化。** 不要考慮「如果我們以後想支援 X 該怎麼辦」。原型只回答一個問題。
- **不要將邏輯與頁面混雜在一起。** 如果純模組引用了 DOM、`document` 或按鈕處理常式，它就不再具備可提取性。讓頁面維持作為純模組之上的薄外殼。
- **不要求助於框架、打包工具或伺服器。** 收件者點兩下即可開啟單一檔案；React 應用程式或開發伺服器會違背「可分享」的初衷。
- **不要將 HTML 外殼發布至正式環境。** 該頁面已針對手動點擊進行最佳化。其背後的邏輯模組才是值得保留的部分。
