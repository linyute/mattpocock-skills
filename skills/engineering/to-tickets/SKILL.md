# 轉為 Tickets

將計畫、規格或對話拆解為一組 **ticket**：曳光彈垂直切片，每個切片均宣告**阻礙**它的 ticket。

issue tracker 和分流標籤字彙應該已經提供給你。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集情境

根據對話情境中已有的任何內容展開工作。如果使用者傳入參考（規格路徑、issue 編號或 URL）作為引數，請擷取它並讀取其完整內文與留言。

### 2. 探索程式碼庫（選用）

如果你尚未探索程式碼庫，請探索以了解程式碼的當前狀態。Ticket 標題與說明應使用專案的領域詞彙表，並遵守你所接觸領域中的 ADR。

尋找預先重構（prefactor）程式碼的機會，使實作更容易。「先讓變更變容易，然後再做出容易的變更。」

### 3. 起草垂直切片

將工作拆解為**曳光彈（tracer bullet）** ticket。

<vertical-slice-rules>

- 每個切片在每一層（結構描述、API、UI、測試）開闢一條狹窄但「完整」的路徑：垂直切片，而「非」單一層的水平切片
- 完成的切片可單獨展示或驗證
- 每個切片的大小均適合成單一全新情境視窗
- 任何預先重構都應優先完成

</vertical-slice-rules>

為每個 ticket 賦予其**阻礙邊（blocking edges）**：在該 ticket 開始之前必須完成的其他 ticket。沒有阻礙者的 ticket 可以立即開始。

**大規模重構是垂直切片的例外。** **大規模重構（wide refactor）** 是單一機械式變更（重命名欄位、重新為共用符號定義型別），其**影響範圍（blast radius）** 擴散至整個程式碼庫，以致單一編輯就會同時破壞數千個呼叫點，且沒有任何垂直切片能以綠燈收尾。不要強將其塞入曳光彈中；將其排程為**擴展-收縮（expand–contract）**。首先擴展：在舊形式旁新增新形式，以確保沒有任何東西損壞。接著按影響範圍大小（每個套件、每個目錄）分批將呼叫點遷移過去，每批都是自身受擴展阻礙的 ticket，藉由舊形式仍然存在使各批次之間的 CI 保持綠燈。最後收縮：一旦不再有呼叫者殘留，即在受所有遷移批次阻礙的 ticket 中刪除舊形式。當連各批次都無法單獨保持綠燈時，請維持此順序，但讓它們共用一個整合分支，所有批次都阻礙最終的整合與驗證 ticket；僅在那裡保證綠燈。

### 4. 詢問使用者

以編號清單呈現提議的拆解方案。對於每個 ticket，顯示：

- **標題**：簡短具描述性的名稱
- **阻礙者**：必須先完成的其他 ticket（如果有的話）
- **交付內容**：此 ticket 實現的端對端行為

詢問使用者：

- 粒度是否感覺合適？（太粗 / 太細）
- 阻礙邊是否正確：每個 ticket 是否僅取決於真正對其設限的 ticket？
- 是否應合併或進一步拆分任何 ticket？

反覆迭代直到使用者核准此拆解方案。

### 5. 將 ticket 發布至已設定的 tracker

發布核准的 ticket。**如何發布**取決於 `/setup-matt-pocock-skills` 所設定的 tracker；無論哪種方式 ticket 都相同，只有阻礙邊的呈現形式有所改變：

- **本地檔案** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下為每個 ticket 寫入一個檔案，按相依性順序（阻礙者優先）從 `01` 開始編號。每個檔案的 "Blocked by" 會列出其相依的編號/標題。使用下方的單一 ticket 檔案範本：每個檔案一個 ticket，絕不使用單一合併檔案。
- **真實 issue tracker（GitHub、Linear、…）** → 依相依性順序（阻礙者優先）為每個 ticket 發布一個 issue，讓每個 ticket 的阻礙邊都能引用真實識別碼。若平台具備原生阻礙 / 子 issue 關聯，請使用該功能；否則將每個 ticket 的 "Blocked by" 設定為阻礙的 issue。套用 `ready-for-agent` 分流標籤，除非另有指示；ticket 本身在結構上就是可供 Agent 領取的。

推進**前沿（frontier）**：其阻礙者已全部完成的任何 ticket。對於純線性鏈，這意味著由上至下進行。

請「不要」關閉或修改任何父層 issue。
