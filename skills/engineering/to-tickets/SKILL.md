# 轉為票券

將計劃、規格或對話分解為一組**票券（tickets）** — 追光彈垂直切片，每張票券宣告**阻塞**它的票券。

議題追蹤器與分揀標籤詞彙應該已經提供給您 — 如果沒有，請執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

從對話上下文中已有任何內容展開工作。如果使用者傳遞了一個引用（規格路徑、議題號碼或 URL）作為引數，請擷取它並閱讀其完整的內文與留言。

### 2. 探索程式碼庫（可選）

如果您尚未探索程式碼庫，請進行探索以理解程式碼的當前狀態。票券標題與描述應精準使用專案的領域術語表詞彙，並遵守您所接觸區域的 ADR。

尋求預重構程式碼的機會，使實作更容易。「使變更變得容易，然後進行容易的變更。」

### 3. 起草垂直切片

將工作分解為**追光彈（tracer bullet）**票券。

<vertical-slice-rules>

- 每個切片穿過每個層級（schema、API、UI、測試）切出一條狹窄但完整的路徑 — 是垂直的，而不是單一層級的水平切片
- 完成的切片本身是可 Demo 或可驗證的
- 每個切片的大小調整為適應單一全新的上下文視窗
- 任何預重構應該最先完成

</vertical-slice-rules>

為每張票券給予其**阻塞邊界** — 在其可以開始前必須完成的其他票券。沒有阻塞項的票券可以立即開始。

**廣泛重構是垂直切片的例外。****廣泛重構**是一種機械性變更 — 重命名欄位、重新定義共享符號的型別 — 其**爆炸半徑（blast radius）**擴散至整個程式碼庫，因此單次編輯會一次破壞數千個呼叫位置，且沒有垂直切片能保持綠燈。不要將其強行擠入追光彈；請將其排序為**擴展–收縮（expand–contract）**。首先擴展：在舊形式旁邊新增新形式，使任何內容都不會損壞。然後按爆炸半徑劃分批次大小（按套件、按目錄）將呼叫位置遷移過去，每個批次本身是一張受擴展阻塞的票券，由於舊形式仍然存在，批次與批次之間保持 CI 為綠燈。最後收縮：一旦沒有呼叫者殘留，在受所有遷移批次阻塞的票券中刪除舊形式。當連批次都無法單獨保持綠燈時，保持該順序，但讓它們共享一個整合分支，該分支會阻塞最終的整合與驗證票券 — 綠燈僅在該處承諾。

### 4. 詢問使用者

將提出的拆分呈現場為帶有編號的清單。對於每張票券，顯示：

- **標題**：簡短描述性名稱
- **受阻塞於**：哪些其他票券（如果有）必須最先完成
- **其交付內容**：此票券所使其運作的端對端行為

詢問使用者：

- 粒度感覺是否正確？（太粗 / 太細）
- 阻塞邊界是否正確 — 每張票券是否僅依賴於確實限制它的票券？
- 是否應合併或進一步拆分任何票券？

迭代直到使用者批准拆分方案。

### 5. 將票券發布至設定的追蹤器

發布批准的票券。**如何發布**取決於 `/setup-matt-pocock-skills` 所設定的追蹤器 — 無論哪種方式票券本身都是相同的，只有阻塞邊界的形狀會改變：

- **本地檔案** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每張票券寫入一個檔案，按依賴順序（阻塞項優先）從 `01` 開始編號。每個檔案的「Blocked by」列出其依賴的編號/標題。使用下方的單張票券檔案範本 — 每張票券一個檔案，絕非單一合併的檔案。
- **真實議題追蹤器（GitHub、Linear 等）** → 按依賴順序（阻塞項優先）為每張票券發布一個議題，以便每張票券的阻塞邊界可以引用真實的標示符。在使用平台原生阻塞 / 子議題關係的地方使用該關係；否則將每張票券的「Blocked by」設定為阻塞議題。除非另有指示，否則套用 `ready-for-agent` 分揀標籤 — 票券憑藉結構即為 Agent 可領取的狀態。

處理**邊界（frontier）**：任何阻塞項已全部完成的票券。對於純線性鏈，那意味著從上到下。

切勿關閉或修改任何父議題。
