`HEAD` 和使用者提供固定點之間差異的雙軸審查：

- **標準** — 程式碼是否符合此儲存庫記載的程式碼撰寫標準？
- **規格** — 程式碼是否忠實實作了源頭議題 / 規格？

兩個軸線皆作為**平行子 Agent**執行，因此不會互相污染上下文，然後此技能會彙整它們的發現。

應已提供議題追蹤器給你。如果缺少 `docs/agents/issue-tracker.md`，請告知使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 釘住固定點

無論使用者說什麼都是固定點 — 提交 SHA、分支名稱、標籤、`main`、`HEAD~5` 等。如果他們沒有指定，請詢問。

擷取一次差異命令：`git diff <fixed-point>...HEAD`（三點，因此比較對象是 merge-base）。同時透過 `git log <fixed-point>..HEAD --oneline` 記錄提交清單。

在進一步處理之前，確認固定點可解析（`git rev-parse <fixed-point>`）且差異非空。無效的引用或空的差異應該在這裡失敗 — 而不是在兩個平行子 Agent 內部。

### 2. 識別規格來源

按以下順序尋找源頭規格：

1. 提交訊息中的議題引用（`#123`、`Closes #45`、GitLab `!67` 等）— 透過 `docs/agents/issue-tracker.md` 中的工作流程擷取。
2. 使用者作為引數傳遞的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 底下與分支名稱或功能符合的規格檔案。
4. 如果未找到任何內容，請詢問使用者規格在哪裡。如果他們表示沒有規格，**規格**子 Agent 將跳過並回報「無可用規格」。

### 3. 識別標準來源

儲存庫中記載如何撰寫程式碼的任何內容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了儲存庫記載的任何內容之外，標準軸線始終帶有下面的**壞氣味基準線** — 即使儲存庫未記載任何內容也適用的固定 Fowler 程式碼壞氣味（_Refactoring_，第 3 章）集合。兩條規則約束著它：

- **儲存庫優先。** 記載的儲存庫標準始終勝出；當它背書基準線會標示的內容時，請抑制該壞氣味。
- **始終是裁量判斷。** 每個壞氣味都是有標籤的啟發式方法（「可能的 Feature Envy」），絕非硬性違規 — 而且，就像這裡的任何標準一樣，跳過工具自動強化的任何內容。

每個壞氣味的閱讀方式為 *它是什麼* → *如何修復*；將其與差異進行比對：

- **Mysterious Name（神秘名稱）** — 函式、變數或型別的名稱未能揭示其作用或儲存的內容。 → 重命名它；如果找不到誠實的名稱，說明設計很模糊。
- **Duplicated Code（重複程式碼）** — 相同的邏輯形狀出現在變更中的多個區塊或檔案中。 → 擷取共享形狀，並從兩處呼叫。
- **Feature Envy（依戀情結）** — 存取另一個物件資料頻率高於自身資料的方法。 → 將該方法移動至其所依戀的資料上。
- **Data Clumps（資料泥團）** — 相同的幾個欄位或參數總是結伴同行（渴望誕生為型別）。 → 將它們打包成一個型別並傳遞。
- **Primitive Obsession（基本型別偏執）** — 代表值得擁有自身型別的領域概念的基本型別或字串。 → 給予該概念自身的小型型別。
- **Repeated Switches（重複的 Switch）** — 在整個變更中針對相同型別重複出現相同的 `switch`/`if` 級聯。 → 替換為多型，或兩處共享的一個映射。
- **Shotgun Surgery（發散式修改 / 霰彈槍手術）** — 一個邏輯變更迫使在差異的多個檔案中進行散亂的編輯。 → 將一起變更的內容聚集到單一模組中。
- **Divergent Change（發散式變化）** — 一個檔案或模組出於多個不相關的原因而被編輯。 → 拆分以便每個模組出於單一原因進行變更。
- **Speculative Generality（誇誇其談 / 投機性通用）** — 為規格未具備的需求添加抽象、參數或鉤子。 → 刪除它；內聯回去直到出現真實需求。
- **Message Chains（訊息鏈）** — 呼叫者不應依賴的漫長 `a.b().c().d()` 導覽。 → 將巡覽隱藏在第一個物件的單一方法背後。
- **Middle Man（中間人）** — 主要只是向外委派的類別或函式。 → 裁撤它，直接呼叫真實目標。
- **Refused Bequest（被拒絕的遺產）** — 忽略或覆寫其繼承的大部分內容的子類別或實作者。 → 放棄繼承，改用組合。

### 4. 平行啟動兩個子 Agent

**標準子 Agent 提示詞** — 包含：

- 完整的差異命令與提交清單。
- 您在步驟 3 中找到的標準來源檔案清單，**加上步驟 3 中壞氣味基準線**的完整貼上 — 子 Agent 無法透過其他管道存取它。
- 簡報："回報 — 在相關處按檔案/區塊 — (a) 差異違反記載標準的每個地方：引用標準（檔案 + 規則）；以及 (b) 您發現的任何基準線壞氣味：命名並引用該區塊。區分硬性違規與裁量判斷 — 記載的標準違規可以是硬性的，但基準線壞氣味始終是裁量判斷，且記載的儲存庫標準優先於基準線。跳過工具強化的任何內容。400 字以內。"

**規格子 Agent 提示詞** — 包含：

- 差異命令與提交清單。
- 規格的路徑或擷取的內容。
- 簡報："回報：(a) 規格要求但缺失或部分的缺口；(b) 差異中未被要求的行為（範疇膨脹）；(c) 看似已實作但實作看似錯誤的要求。引用每個發現的規格行號。400 字以內。"

如果缺失規格，請跳過規格子 Agent，並在最終報告中註明此點。

### 5. 彙整

在 `## 標準` 與 `## 規格` 標題下呈現這兩份報告，逐字或稍作整理。**切勿**合併或重新排序發現 — 這兩個軸線是故意分開的（參見 *為什麼需要兩個軸線*）。

以單行摘要結尾：每個軸線的總發現數，以及*每個軸線內部*最嚴重的議題（如果有）。切勿跨軸線選出單一勝出者 — 那正是分開機制要防止的重新排序。

## 為什麼需要兩個軸線

變更可能通過一個軸線而未通過另一個軸線：

- 遵循每項標準但實作錯誤內容的程式碼 → **標準通過，規格未通過。**
- 完全符合議題要求但破壞專案慣例的程式碼 → **規格通過，標準未通過。**

分別回報可以防止一個軸線掩蓋另一個軸線。
