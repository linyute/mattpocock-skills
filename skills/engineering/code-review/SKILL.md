針對 `HEAD` 與使用者提供的固定點之間的 diff 進行雙軸審查：

- **標準 (Standards)**：程式碼是否符合此儲存庫記錄的編碼標準？
- **規格 (Spec)**：程式碼是否忠實實作原始 issue／規格？

兩個軸向皆作為**平行子代理**執行，以免互相污染彼此的上下文，隨後此技能會彙整它們的發現。

issue 追蹤器應該已提供給您。若缺少 `docs/agents/issue-tracker.md`，請告知使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 錨定固定點

無論使用者指定何者為固定點（commit SHA、分支名稱、標籤、`main`、`HEAD~5` 等）。若未指定，請向其詢問。

擷取一次 diff 指令：`git diff <fixed-point>...HEAD`（三點語法，以便與 merge-base 進行比較）。同時透過 `git log <fixed-point>..HEAD --oneline` 記錄 commit 清單。

在進一步處理之前，確認固定點能正確解析（`git rev-parse <fixed-point>`）且 diff 非空。無效的參照或空的 diff 應在此處失敗，而非在兩個平行子代理內部失敗。

### 2. 識別規格來源

依下列順序尋找原始規格：

1. commit 訊息中的 issue 參照（`#123`、`Closes #45`、GitLab `!67` 等），透過 `docs/agents/issue-tracker.md` 中的工作流程擷取。
2. 使用者作為引數傳入的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 下符合分支名稱或功能的規格檔案。
4. 若未找到任何內容，請詢問使用者規格位於何處。若他們表示沒有規格，**規格**子代理將跳過並回報「無可用規格」。

### 3. 識別標準來源

儲存庫中記錄程式碼應如何撰寫的任何內容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了儲存庫記錄的任何內容之外，「標準」軸向始終帶有下方的**異味基準線**：一組固定的 Fowler 程式碼異味（《重構》第 3 章），即使儲存庫未記錄任何內容時亦適用。兩條規則約束著它：

- **儲存庫優先。** 儲存庫記錄的標準始終優先；若其認可了基準線會標記的某些內容，請壓制該異味。
- **始終是主觀判斷。** 每個異味都是一個帶有標籤的啟發式判斷（「可能的依戀情結」），絕非強制違規。如同此處的任何標準，略過工具鏈已強制執行的任何內容。

每個異味皆依*它是什麼* → *如何修復*說明；將其與 diff 比對：

- **神祕名稱 (Mysterious Name)**：名稱無法揭示其作用或容納內容的函式、變數或型別。→ 將其重新命名；若想不出如實的名稱，表示設計不夠清晰。
- **重複程式碼 (Duplicated Code)**：變更中的多個區塊或檔案出現相同的邏輯形狀。→ 擷取共享形狀，並從兩處呼叫。
- **依戀情結 (Feature Envy)**：涉入另一個物件的資料多於自身資料的方法。→ 將該方法移動至其所依戀的資料上。
- **資料泥團 (Data Clumps)**：相同的幾個欄位或參數總是結伴傳遞（渴望成為一個型別）。→ 將其綁定為單一型別並進行傳遞。
- **基本型別偏執 (Primitive Obsession)**：以基本型別或字串代替值得擁有專屬型別的領域概念。→ 為該概念賦予專屬的小型別。
- **重複的 switch (Repeated Switches)**：在整個變更中反覆出現針對相同型別的相同 `switch`/`if` 串接。→ 以多型取代，或使用兩處共享的單一對應表。
- **散彈式修改 (Shotgun Surgery)**：單一邏輯變更迫使 diff 中的許多檔案散落著各處編輯。→ 將一同變更的內容聚集到單一模組中。
- **發散式變化 (Divergent Change)**：單一檔案或模組因數個無關的原因而受到編輯。→ 進行拆分，使每個模組僅因單一原因而變更。
- **誇誇其談未來性 (Speculative Generality)**：為規格中不存在的需求添加抽象層、參數或掛鉤。→ 將其刪除；內嵌還原直到展現真實需求為止。
- **訊息鏈 (Message Chains)**：呼叫端不應依賴的過長 `a.b().c().d()` 導覽。→ 將該走訪隱藏在第一個物件的單一方法之後。
- **中間人 (Middle Man)**：大部分僅是轉發委派的類別或函式。→ 刪除它，直接呼叫真實目標。
- **被拒絕的遺贈 (Refused Bequest)**：忽略或覆寫其大部分繼承內容的子類別或實作者。→ 放棄繼承，改用組合。

### 4. 平行衍生兩個子代理

**標準子代理提示詞**應包含：

- 完整的 diff 指令與 commit 清單。
- 您在步驟 3 中找到的標準來源檔案清單，**加上步驟 3 中的異味基準線**全文貼上（子代理沒有其他存取途徑）。
- 摘要任務：「依檔案／區塊回報（若相關）：(a) diff 違反記錄標準的每個地方：引用標準（檔案 + 規則）；以及 (b) 您發現的任何基準線異味：指出名稱並引用該區塊。區分強制違規與主觀判斷：記錄標準的違規可能是強制性的，但基準線異味始終是主觀判斷，且儲存庫記錄的標準優先於基準線。略過工具鏈強制執行的任何內容。400 字以內。」

**規格子代理提示詞**應包含：

- diff 指令與 commit 清單。
- 規格的路徑或擷取的內容。
- 摘要任務：「回報：(a) 規格要求但缺失或僅部分實作的需求；(b) diff 中未被要求的行為（範疇蔓延）；(c) 看似已實作但實作看似錯誤的需求。為每項發現引用規格行。400 字以內。」

若缺少規格，請略過規格子代理並在最終報告中註明。

### 5. 彙整

在 `## Standards` 與 `## Spec` 標題下呈現兩份報告，逐字或經微調清理呈現。**請勿**合併或重新排序發現，因為這兩個軸向是刻意分開的（請參閱*為何需要雙軸*）。

以單行摘要結尾：每個軸向的總發現數，以及*各軸向內部*最嚴重的問題（若有）。切勿跨軸向評選單一贏家：分開的用意正是為了防止此類重新排序。

## 為何需要雙軸

一項變更可能通過一個軸向卻在另一個軸向失敗：

- 遵循每項標準但實作了錯誤內容的程式碼 → **標準通過，規格失敗。**
- 完全符合 issue 要求但破壞專案慣例的程式碼 → **規格通過，標準失敗。**

分開回報可防止一個軸向遮蔽另一個軸向。
