# 診斷錯誤 (Diagnosing Bugs)

針對棘手錯誤的紀律。僅在有明確正當理由時方可跳過特定階段。

探索程式碼庫時，請閱讀 `GLOSSARY.md`（若存在）以獲取相關模組的清晰心智模型，並檢查您所接觸區域的 ADR。

## 遮蔽機密 (Redact)

此技能需要您展示指令、輸出以及擷取的構件。**請先遮蔽所有機密**：在其位置寫入 `<REDACTED>`。圍繞環境變數建構迴圈，使憑證保留在環境中而非出現在您展示的內容中。擷取的構件帶有授權標頭：僅引用帶有信號的行。

若遮蔽後的輸出不足以診斷錯誤，請明確指出並詢問使用者。

## 階段 1：建構意見回饋迴圈

**這就是此項技能的核心。** 其餘一切皆為機械化操作。若您對該錯誤擁有**緊密**的通過／失敗信號（一個在此錯誤上會變紅的信號），您就能找到原因；二分搜尋、假設測試以及程式碼檢測都只是使用此信號。若您沒有此信號，盯著程式碼看再久也無濟於事。

在此處投入不成比例的努力。**積極主動。發揮創意。拒絕放棄。**

### 建構信號的方式，大致依此順序

1. 在能觸及錯誤的任何接縫處建立**失敗測試**：單元測試、整合測試、端對端測試。
2. 針對執行中的開發伺服器撰寫 **Curl／HTTP 指令稿**。
3. 使用固定裝置輸入進行 **CLI 呼叫**，將 stdout 與已知良好的快照進行 diff。
4. 驅動 UI 並在 DOM／主控台／網路上進行斷言的**無頭瀏覽器指令稿** (Playwright / Puppeteer)。
5. **重播擷取的追蹤記錄。** 將真實的網路請求／負載／事件記錄儲存至磁碟；在隔離環境中透過程式碼路徑重播它。
6. **一次性測試控架。** 啟動系統的最小子集（單一服務、模擬依賴項），透過單一函式呼叫調用錯誤程式碼路徑。
7. **屬性測試／模糊測試迴圈。** 若錯誤為「有時輸出錯誤」，請執行 1000 次隨機輸入並尋找失敗模式。
8. **二分搜尋控架。** 若錯誤出現在兩個已知狀態（commit、資料集、版本）之間，自動化「以狀態 X 開機、檢查、重複」，以便您能進行 `git bisect run`。
9. **差異比對迴圈。** 透過舊版本與新版本（或兩種組態）執行相同的輸入並比對輸出。
10. **人機協同 (HITL) bash 指令稿。** 最後手段。若必須由人類點擊，使用 `scripts/hitl-loop.template.sh` 引導*他們*，以使迴圈仍保持結構化。擷取的輸出會回饋給您。

建構正確的意見回饋迴圈，錯誤就已經解決了 90%。

### 緊縮迴圈

將迴圈視為一項產品。一旦您擁有*一個*迴圈，**緊縮**它：

- 我能否讓它更快？（快取設定、略過無關的初始化、縮小測試範疇。）
- 我能否讓信號更銳利？（針對具體症狀進行斷言，而非「沒有當機」。）
- 我能否讓它更具確定性？（固定時間、設定隨機種子、隔離檔案系統、凍結網路。）

一個 30 秒且不穩定的迴圈幾乎不比沒有迴圈好；一個 2 秒且確定性的迴圈則是緊密的除錯超能力。

### 非確定性錯誤

目標不是乾淨的重現，而是**更高的重現率**。將觸發條件循環執行 100 次、平行化、增加壓力、縮小時間視窗、插入休眠。50% 失敗率的不穩定錯誤是可除錯的；1% 則不可，因此請不斷提高重現率直到其可除錯為止。

### 當您確實無法建構迴圈時

停下來並明確說明。列出您嘗試過的方法。向使用者要求：(a) 存取重現該問題的任何環境，(b) 經遮蔽的擷取構件（HAR 檔案、記錄傾印、核心傾印、帶有時間戳記的螢幕錄影），或 (c) 新增臨時生產環境檢測的權限。在沒有迴圈的情況下，**切勿**繼續進行假設。

### 完成準則：會變紅的緊密迴圈

當迴圈具備**緊密**且**能變紅**時，階段 1 即告完成：您能指出**一個指令**（指令稿路徑、測試呼叫、curl），且您**已經至少執行過一次**（展示該呼叫及其遮蔽後的輸出），並且符合：

- [ ] **能變紅**：它驅動實際的錯誤程式碼路徑並對**使用者的確切症狀**進行斷言，因此它能在此錯誤上變紅，且修復後變綠。不是「執行且沒有錯誤」；它必須能夠*捕捉到此特定錯誤*。
- [ ] **確定性**：每次執行皆獲得相同結論（針對不穩定錯誤：依上述方式維持固定且高重現率）。
- [ ] **快速**：數秒，而非數分鐘。
- [ ] **代理可執行**：您可以無人值守地執行它；僅透過 `scripts/hitl-loop.template.sh` 納入人機協同。

若您發現自己在該指令存在之前就透過閱讀程式碼來建構理論，**請停下來：直接跳到假設正是此技能所防止的失敗狀況。** 沒有能變紅的指令，就沒有階段 2。

## 階段 2：重現 + 最小化

執行迴圈。觀察它隨著錯誤出現而變紅。

確認：

- [ ] 該迴圈產生**使用者**所描述的失敗模式，而非剛好在附近的另一種失敗。錯誤的錯誤 = 錯誤的修復。
- [ ] 該失敗在多次執行中皆可重現（或者，對於非確定性錯誤，其重現率高到足以進行除錯）。
- [ ] 您已擷取確切的症狀（錯誤訊息、錯誤輸出、緩慢的時間），以便後續階段能驗證修復是否真正解決了該問題。

### 最小化

一旦它變紅，請將重現情境縮減為**仍會變紅的最小情境**。**一次剪除一項**輸入、呼叫端、組態、資料以及步驟，並在每次剪除後重新執行迴圈，僅保留對失敗起承重作用的部分。

為何需要這樣做：最小化重現縮減了階段 3 中的假設空間（剩下的可疑活動部件較少），並成為階段 5 中乾淨的迴歸測試。

當**所有剩餘元素皆具備承重作用**時即告完成：移除其中任何一個都會使迴圈變綠。

在完成重現**並且**最小化之前，請勿繼續進行。

## 階段 3：提出假設

在測試任何假設之前，先產生 **3–5 個排序過的假設**。單一假設的產生會錨定在第一個看似合理的想法上。

每個假設必須**具備可證偽性**：陳述其做出的預測。

> 格式：「若 <X> 是原因，則 <變更 Y> 會使錯誤消失／<變更 Z> 會使其惡化。」

若您無法陳述預測，該假設只是一種感覺：請捨棄或精煉它。

**在測試前向使用者展示排序後的清單。** 他們通常擁有能立即重新排序的領域知識（「我們剛部署了對第 3 項的變更」），或知道他們已經排除的假設。廉價的檢查點，巨大的時間節省。不要為此阻塞；若使用者離開鍵盤，請依您的排序繼續進行。

## 階段 4：程式碼檢測

每個探針必須對應到階段 3 的特定預測。**一次只變更一個變數。**

工具偏好順序：

1. **偵錯工具／REPL 檢視**（若環境支援）。一個中斷點勝過十行記錄。
2. 位於區分假設之邊界處的**針對性記錄**。
3. 絕不「記錄所有內容並使用 grep」。

為每個除錯記錄**加上唯一前綴標籤**，例如 `[DEBUG-a4f2]`。最後的清理工作將簡化為單次 grep。未標記的記錄會殘留；標記的記錄會被刪除。

**效能分支。** 對於效能退化，記錄通常是錯誤的做法。相反地：建立基準線測量（計時控架、`performance.now()`、分析器、查詢計劃），然後進行二分搜尋。先測量，後修復。

## 階段 5：修復 + 迴歸測試

在**修復之前**撰寫迴歸測試，但前提是存在適用於它的**正確接縫**。

正確的接縫是指測試在呼叫端呼叫時能調用**真實錯誤模式**的接縫。若唯一可用的接縫過於淺層（當錯誤需要多個呼叫端時卻採用單一呼叫端測試、無法複製觸發錯誤之鏈結的單元測試），在該處進行迴歸測試會帶來虛假的安全感。

**若不存在正確接縫，此發現本身即為結論。** 請記錄下來。程式碼庫架構阻礙了錯誤被鎖定。將此標記給下一個階段。

若存在正確接縫：

1. 將最小化重現情境轉變為該接縫處的失敗測試。
2. 觀察其失敗。
3. 套用修復。
4. 觀察其通過。
5. 針對原始（未最小化）情境重新執行階段 1 的意見回饋迴圈。

## 階段 6：清理

在宣告完成前必須達成：

- [ ] 原始重現情境不再重現（重新執行階段 1 的迴圈）
- [ ] 迴歸測試通過（或已記錄缺乏接縫的事實）
- [ ] 移除所有 `[DEBUG-...]` 檢測程式碼（`grep` 該前綴）
- [ ] 刪除一次性原型（或移至標記清楚的除錯位置）
- [ ] 在 commit／PR 訊息中陳述被證實正確的假設，以便下一位除錯人員學習
