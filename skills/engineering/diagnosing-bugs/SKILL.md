# 診斷 Bug

針對棘手 Bug 的紀律。僅在有明確正當理由時才跳過階段。

探索程式碼庫時，請閱讀 `CONTEXT.md`（如果存在）以獲取相關模組的清晰心智模型，並檢查您正在接觸領域的 ADR。

## 遮蔽敏感資訊（Redact）

此技能會讓您展示命令、輸出和擷取的產物。**首先遮蔽每個機密** — 在其位置寫入 `<REDACTED>`。針對環境變數建構迴圈，使憑證保持在環境中，而不是呈現在您展示的內容中。擷取的產物帶有驗證標頭：僅引用帶有訊號的行。

如果遮蔽後的輸出不足以診斷 Bug，請說明並詢問使用者。

## 階段 1 — 建立回饋迴圈

**這就是技能的核心。** 其他一切都是機械性的。如果您對此 Bug 具備**緊密**的通過/失敗訊號 — 在*此* Bug 上變紅的訊號 — 您就會找到原因；二分法、假設測試和植入檢測都不過是在使用它。如果您沒有這個訊號，再怎麼凝視程式碼也救不了您。

在此處投入非同尋常的精力。**要積極。要有創意。拒絕放棄。**

### 建構回饋迴圈的方法 — 大致按此順序嘗試

1. 在觸及 Bug 的任何接縫處的**失敗測試** — 單元、整合、e2e。
2. 針對正在執行的開發伺服器的 **Curl / HTTP 腳本**。
3. 使用固定裝置（fixture）輸入的 **CLI 呼叫**，將 stdout 與已知良好的快照進行比較。
4. **無頭瀏覽器腳本**（Playwright / Puppeteer）— 驅動 UI，在 DOM/主控台/網路上進行斷言。
5. **重播擷取的追蹤。** 將真實的網路請求 / 負載 / 事件紀錄儲存至磁碟；在隔離狀態下透過程式碼路徑重播它。
6. **一次性 Harness。** 啟動系統的最小子集（一個服務，mock 的依賴項），透過單一函式呼叫執行 Bug 程式碼路徑。
7. **屬性 / Fuzz 迴圈。** 如果 Bug 是「有時輸出錯誤」，請執行 1000 個隨機輸入並尋找失敗模式。
8. **二分法 Harness。** 如果 Bug 出現在兩個已知狀態（提交、資料集、版本）之間，請自動化「在狀態 X 啟動、檢查、重複」，以便您可以 `git bisect run` 它。
9. **差異迴圈。** 透過舊版本與新版本（或兩種設定）執行相同的輸入，並比較輸出差異。
10. **HITL bash 腳本。** 最後手段。如果人類必須點擊，請使用 `scripts/hitl-loop.template.sh` 驅動*他們*，使迴圈仍具備結構。擷取的輸出會回饋給您。

建立正確的回饋迴圈，Bug 就修復了 90%。

### 緊密化迴圈

將迴圈視為一個產品。一旦您具備了*一個*迴圈，請**緊密化**它：

- 我能否讓它更快？（快取設定、跳過不相關的初始化、縮小測試範疇。）
- 我能否讓訊號更敏銳？（針對具體症狀進行斷言，而非「沒有當機」。）
- 我能否讓它更具確定性？（固定時間、設定 RNG 種子、隔離檔案系統、凍結網路。）

30 秒的不穩定迴圈幾乎不比沒有迴圈好；2 秒的確定性迴圈則非常緊密 — 這是除錯的超能力。

### 非確定性 Bug

目標不是乾淨的重現，而是**更高的重現率**。將觸發條件迴圈執行 100 次、平行化、增加壓力、縮短時間視窗、注入 sleep。50% 閃爍的 Bug 是可除錯的；1% 則不可除錯 — 持續提高機率，直到其變得可除錯。

### 當您確實無法建立迴圈時

停止並明確說明。列出您嘗試過的內容。向使用者索取：(a) 存取重現該問題的任何環境、(b) 遮蔽後的擷取產物（HAR 檔案、紀錄傾印、核心傾印、帶有時間戳記的螢幕錄影），或 (c) 新增臨時正式環境檢測的權限。在沒有迴圈的情況下，**切勿**進一步提出假設。

### 完成標準 — 變紅的緊密迴圈

當迴圈為**緊密**且**具備變紅能力**時，階段 1 即告完成：您可以說出**一個命令** — 腳本路徑、測試呼叫、curl — 且您**已經至少執行過一次**（展示其呼叫及輸出，已遮蔽），並且該命令為：

- [ ] **具備變紅能力** — 它驅動實際的 Bug 程式碼路徑並斷言**使用者的確切症狀**，因此它可以在此 Bug 上變紅，修復後變綠。不是「執行且無錯誤」— 它必須能夠*擷取此特定 Bug*。
- [ ] **確定性** — 每次執行判定相同（不穩定的 Bug：固定的高重現率，如上所述）。
- [ ] **快速** — 數秒，而非數分鐘。
- [ ] **Agent 可執行** — 您可以無人值守地執行它；僅透過 `scripts/hitl-loop.template.sh` 讓人類參與。

如果您發現自己在建立此命令之前就在閱讀程式碼以建立理論，請**停止 — 直接跳到假設正是此技能所要防止的失敗。** 沒有具備變紅能力的命令，就沒有階段 2。

## 階段 2 — 重現 + 最小化

執行迴圈。看著它變紅 — Bug 出現。

確認：

- [ ] 迴圈產生了**使用者**描述的失敗模式 — 而不是剛好在附近的差異失敗。錯誤的 Bug = 錯誤的修復。
- [ ] 失敗可在多次執行中重現（或者對於非確定性 Bug，重現率足夠高以供除錯）。
- [ ] 您已擷取確切的症狀（錯誤訊息、錯誤輸出、緩慢的時間控制），以便後續階段可以驗證修復是否確實解決了該問題。

### 最小化

一旦變紅，請將重現縮減至**仍會變紅的最簡情境**。一次剪裁**一個**輸入、呼叫者、設定、資料和步驟，在每次剪裁後重新執行迴圈 — 僅保留對失敗具備承重作用的內容。

為何要這樣做：最小化重現縮小了階段 3 中的假設空間（剩下的可疑動態元件更少），並成為階段 5 中乾淨的退化測試。

當**剩餘的每個元素都具備承重作用**時完成 — 移除其中任何一個都會使迴圈變綠。

在重現**且**最小化之前，請勿進一步處理。

## 階段 3 — 提出假設

在測試任何假設之前，產生 **3–5 個排序後的假設**。單一假設產生會沉錨於第一個貌似合理的構想上。

每個假設都必須是**可證偽的**：說明其做出的預測。

> 格式："如果 <X> 是原因，那麼 <改變 Y> 將使 Bug 消失 / <改變 Z> 將使其變得更糟。"

如果您無法說明預測，該假設只是一種直覺 — 丟棄或精煉它。

**在測試之前將排序清單展示給使用者。** 他們通常具備能立即重新排序的領域知識（「我們剛佈署了對 #3 的變更」），或者知道他們已經排除的假設。低成本的檢查點，大幅節省時間。不要為此阻塞 — 如果使用者離線（AFK），請依照您的排序繼續處理。

## 階段 4 — 植入檢測

每個探針必須對映至階段 3 的特定預測。**一次僅變更一個變數。**

工具偏好：

1. **除錯器 / REPL 檢查**（如果環境支援）。一個中斷點勝過十條紀錄。
2. 區分假設邊界處的**針對性紀錄**。
3. 絕不「記錄所有內容並使用 grep」。

為每條除錯紀錄**加上標籤**前綴，例如 `[DEBUG-a4f2]`。最後的清理會變成一次單獨的 grep。未加標籤的紀錄會殘留；加標籤的紀錄會清除。

**效能分支。** 對於效能退化，紀錄通常是錯誤的。相反地：建立基準線測量（時間控制 harness、`performance.now()`、剖析器、查詢計劃），然後進行二分法。先測量，後修復。

## 階段 5 — 修復 + 退化測試

在修復**之前**撰寫退化測試 — 但僅限於存在對應的**正確接縫**時。

正確的接縫是指測試可以在呼叫位置執行發生時的**真實 Bug 模式**。如果唯一可用的接縫太淺（當 Bug 需要多個呼叫者時的單一呼叫者測試，無法複製觸發 Bug 鏈條的單元測試），在該處進行退化測試會給予虛假的信心。

**如果不存在正確的接縫，這本身就是一項發現。** 請註明這一點。程式碼庫架構阻礙了 Bug 被鎖定。為下一個階段標記此點。

如果存在正確的接縫：

1. 將最小化的重現轉化為該接縫處的失敗測試。
2. 觀察其失敗。
3. 套用修復。
4. 觀察其通過。
5. 針對原始（未最小化）的情境重新執行階段 1 的回饋迴圈。

## 階段 6 — 清理

宣告完成前必須：

- [ ] 原始重現不再重現（重新執行階段 1 迴圈）
- [ ] 退化測試通過（或記載了缺少接縫）
- [ ] 所有 `[DEBUG-...]` 檢測已被移除（`grep` 該前綴）
- [ ] 一次性原型已被刪除（或移動至標記清晰的除錯位置）
- [ ] 證實正確的假設已在提交 / PR 訊息中說明 — 以便下一位除錯者學習
