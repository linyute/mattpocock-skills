# 程式碼庫設計 (Codebase Design)

設計**深層模組 (deep modules)**：在乾淨的接縫處，於小型介面背後封裝大量行為，並可透過該介面進行測試。每當設計或重構程式碼時，請使用此語言與這些原則。其目標是為呼叫端提供槓桿、為維護者提供局部性，並為所有人提供可測試性。

## 詞彙表 (Glossary)

請精確使用這些術語：切勿以「元件 (component)」、「服務 (service)」、「API」或「邊界 (boundary)」替代。保持語言一致是其核心目的。

**模組 (Module)**：任何擁有介面與實作的事物。特意與規模無關：函式、類別、套件或跨層切片。*避免使用*：單元 (unit)、元件 (component)、服務 (service)。

**介面 (Interface)**：呼叫端為了正確使用該模組所必須知道的一切：型別簽名，同時也包含不變量、順序限制、錯誤模式、必要組態以及效能特徵。*避免使用*：API、簽名（過於狹隘，它們僅指型別層級的表面）。

**實作 (Implementation)**：模組內部的程式碼主體。與**配接器 (Adapter)** 不同：某個事物可以是一個包含大型實作的小型配接器（Postgres 儲存庫），也可以是一個包含小型實作的大型配接器（記憶體內偽造物件）。當主題圍繞於接縫時使用「配接器」；其餘情況使用「實作」。

**深度 (Depth)**：介面處的槓桿。呼叫端（或測試）每學習一個單位的介面所能調用的行為量。當大量行為位於小型介面背後時，模組即為**深層**；當介面與實作幾乎一樣複雜時，模組即為**淺層**。

**接縫 (Seam)** _(Michael Feathers)_：無須在此處編輯即可變更行為的地方；模組介面所在的*位置*。接縫放置於何處本身就是一項設計決策，與其背後容納的內容有別。*避免使用*：邊界（與 DDD 的限界上下文詞彙重疊）。

**配接器 (Adapter)**：在接縫處滿足介面的具體事物。描述*角色*（填補什麼插槽），而非實質內容（內部包含什麼）。

**槓桿 (Leverage)**：呼叫端從深度中獲得的好處。每學習一個單位的介面獲得更多功能。一次實作在 N 個呼叫端位置與 M 個測試中得到回報。

**局部性 (Locality)**：維護者從深度中獲得的好處。變更、錯誤、知識與驗證集中在單一位置，而非散布於各個呼叫端。修復一次，處處修復。

## 深層 vs 淺層 (Deep vs shallow)

**深層模組** = 小型介面 + 大量實作：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**淺層模組** = 大型介面 + 少許實作（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

設計介面時，請自問：

- 我能否減少方法的數量？
- 我能否簡化參數？
- 我能否在內部隱藏更多複雜性？

## 原則 (Principles)

- **深度是介面的屬性，而非實作的屬性。** 深層模組內部可由小型、可模擬、可替換的部件組成；它們只是不屬於介面的一部分。模組可擁有**內部接縫**（對其實作私有，供其自身測試使用）以及位於其介面處的**外部接縫**。
- **刪除測試法 (The deletion test)。** 想像刪除該模組。若複雜性隨之消失，則它僅是一個透傳傳遞者。若複雜性在 N 個呼叫端中重新浮現，則它確實物有所值。
- **介面即測試表面。** 呼叫端與測試跨越相同的接縫。若您希望*穿透*介面進行測試，該模組的形式可能不正確。
- **一個配接器意味著假設性的接縫。兩個配接器才意味著真實的接縫。** 除非有事物確實跨接縫發生變化，否則切勿引入接縫。

## 為可測試性而設計 (Designing for testability)

良好的介面使測試變得自然：

1. **接收依賴項，而非建立依賴項。**

   ```typescript
   // 可測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **回傳結果，而非產生副作用。**

   ```typescript
   // 可測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小型接觸表面。** 越少的方法 = 所需測試越少。越少的參數 = 越簡單的測試設定。

## 關聯性 (Relationships)

- 一個**模組**恰好擁有一個**介面**（它向呼叫端與測試所呈現的表面）。
- **深度**是**模組**的一項屬性，針對其**介面**進行衡量。
- **接縫**是**模組**的**介面**所在之處。
- **配接器**位於**接縫**處並滿足**介面**。
- **深度**為呼叫端帶來**槓桿**，為維護者帶來**局部性**。

## 被否決的架構觀點 (Rejected framings)

- **將深度定義為實作行數與介面行數的比例** (Ousterhout)：獎勵在實作中灌水。我們改用「深度即槓桿」。
- **將「介面」視為 TypeScript 的 `interface` 關鍵字或類別的公開方法**：過於狹隘：此處的介面包含呼叫端必須知曉的每項事實。
- **「邊界 (Boundary)」**：與 DDD 的限界上下文多載混淆。請使用**接縫**或**介面**。
