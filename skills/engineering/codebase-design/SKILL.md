# 程式碼庫設計

設計**深度模組**：在乾淨接縫處的小型介面背後具備大量行為，且可透過該介面進行測試。無論在何處設計或重構程式碼，皆請使用此語言與這些原則。目標是為呼叫者提供槓桿作用、為維護者提供局部性，並為每個人提供可測試性。

## 術語表

請精準使用這些術語 — 不要替換為「元件（component）」、「服務（service）」、「API」或「邊界（boundary）」。語言一致性是整個重點。

**模組（Module）** — 具備介面與實作的任何事物。故意與規模無關：函式、類別、套件或跨層切片。_避免使用_：單元、元件、服務。

**介面（Interface）** — 呼叫者要正確使用模組所必須了解的一切：型別簽名，還有不變性、順序約束、錯誤模式、所需設定和效能特性。_避免使用_：API、簽名（太狹隘 — 它們僅指型別層面的表面）。

**實作（Implementation）** — 模組內部的內容，即其程式碼主體。與**轉接器（Adapter）**不同：事物可以是具有大型實作的小型轉接器（Postgres 儲存庫），也可以是具有小型實作的大型轉接器（記憶體內偽造物）。當主題是接縫時使用「轉接器」；否則使用「實作」。

**深度（Depth）** — 介面處的槓桿作用：呼叫者（或測試）每學習一個單位的介面所能執行的行為量。當大量行為位於小型介面背後時，模組就是**深的**；當介面與實作幾乎一樣複雜時，模組就是**淺的**。

**接縫（Seam）** _(Michael Feathers)_ — 一個您可以改變行為而無需在該處進行編輯的地方；模組介面所在的*位置*。將接縫放置在哪裡是其自身的設計決策，與位於其背後的內容不同。_避免使用_：邊界（與 DDD 的限界上下文重載）。

**轉接器（Adapter）** — 在接縫處滿足介面的具體事物。描述*角色*（填補什麼插槽），而不是實質內容（內部有什麼）。

**槓桿作用（Leverage）** — 呼叫者從深度中獲得的好處：每學習一個單位的介面就能獲得更多功能。一個實作在 N 個呼叫位置和 M 個測試中獲得回報。

**局部性（Locality）** — 維護者從深度中獲得的好處：變更、Bug、知識和驗證集中在一個地方，而不是分散在各個呼叫者中。一次修復，到處修復。

## 深 vs 淺

**深度模組** = 小型介面 + 大量實作：

```
┌─────────────────────┐
│       小型介面      │  ← 方法少，參數簡單
├─────────────────────┤
│                     │
│       深度實作      │  ← 隱藏複雜邏輯
│                     │
└─────────────────────┘
```

**淺層模組** = 大型介面 + 少量實作（避免）：

```
┌─────────────────────────────────┐
│           大型介面              │  ← 方法多，參數複雜
├─────────────────────────────────┤
│           薄實作                │  ← 僅透傳
└─────────────────────────────────┘
```

設計介面時，請詢問：

- 我能否減少方法的數量？
- 我能否簡化參數？
- 我能否在內部隱藏更多複雜性？

## 原則

- **深度是介面的屬性，而非實作的屬性。** 深度模組可以在內部由小型、可 mock、可替換的零件組成 — 它們只是不屬於介面的一部分。模組可以具有**內部接縫**（為其實作私有，由其自身的測試使用）以及在其介面處的**外部接縫**。
- **刪除測試。** 想像刪除該模組。如果複雜性消失了，說明它只是一個透傳。如果複雜性在 N 個呼叫者中重新出現，說明它在發揮價值。
- **介面即測試表面。** 呼叫者和測試跨越相同的接縫。如果您想超越介面進行測試，該模組的形狀可能是不正確的。
- **一個轉接器代表假設性的接縫。兩個轉接器代表真實的接縫。** 除非跨越該處確實存在變化，否則不要引入接縫。

## 為可測試性而設計

良好的介面讓測試變得自然：

1. **接受依賴項，而不是建立它們。**

   ```typescript
   // 可測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **傳回結果，而不是產生副作用。**

   ```typescript
   // 可測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小型表面積。** 更少的方法 = 需要更少的測試。更少的參數 = 更簡單的測試設定。

## 關係

- 一個**模組**恰好擁有一個**介面**（它呈現給呼叫者和測試的表面）。
- **深度**是**模組**的屬性，對照其**介面**進行衡量。
- **接縫**是**模組**的**介面**所在的位置。
- **轉接器**部位於**接縫**處並滿足**介面**。
- **深度**為呼叫者產生**槓桿作用**，為維護者產生**局部性**。

## 拒絕的構想架構

- **將深度定義為實作行數與介面行數的比率** (Ousterhout)：這獎勵了填補實作。我們改用「深度即槓桿作用」。
- **將「介面」定義為 TypeScript `interface` 關鍵字或類別的公開方法**：太狹隘 — 這裡的介面包含呼叫者必須了解的每個事實。
- **「邊界」**：與 DDD 的限界上下文重載。請說**接縫**或**介面**。
