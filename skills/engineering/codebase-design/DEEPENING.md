# 深化

考慮其依賴項，如何安全地深化一組淺層模組。假定已了解 [SKILL.md](SKILL.md) 中的詞彙 — **模組（module）**、**介面（interface）**、**接縫（seam）**、**轉接器（adapter）**。

## 依賴項類別

評估深化的候選項時，請分類其依賴項。類別決定了如何跨越其接縫測試深化後的模組。

### 1. 進程內（In-process）

純計算、記憶體內狀態、無 I/O。始終可深化 — 合併模組並直接透過新介面進行測試。不需要轉接器。

### 2. 本地可替換（Local-substitutable）

具備本地測試替身（Postgres 的 PGLite、記憶體內檔案系統）的依賴項。如果替身存在，則可深化。深化後的模組在測試套件中使用執行的替身進行測試。接縫是內部的；模組的外部介面上沒有埠（port）。

### 3. 遠端但自有（埠與轉接器，Ports & Adapters）

跨越網路邊界的自有服務（微服務、內部 API）。在接縫處定義一個**埠（port）**（介面）。深度模組擁有邏輯；傳輸作為**轉接器**注入。測試使用記憶體內轉接器。正式環境使用 HTTP/gRPC/佇列轉接器。

建議形式：*「在接縫處定義一個埠，為正式環境實作一個 HTTP 轉接器，並為測試實作一個記憶體內轉接器，這樣即使邏輯佈署在網路上，也能存在於單一深度模組中。」*

### 4. 完全外部（Mock）

您無法控制的第三方服務（Stripe、Twilio 等）。深化後的模組將外部依賴項作為注入的埠；測試提供 mock 轉接器。

## 接縫紀律

- **一個轉接器代表假設性的接縫。兩個轉接器代表真實的接縫。** 除非至少兩個轉接器（通常是正式環境 + 測試）合理，否則不要引入埠。單一轉接器的接縫只是間接層。
- **內部接縫 vs 外部接縫。** 深度模組可以具備內部接縫（為其實作所私有，由自身的測試使用）以及在其介面處的外部接縫。不要僅僅因為測試使用它們就在介面中暴露內部接縫。

## 測試策略：替換，而非分層

- 一旦存在深度模組介面上的測試，淺層模組上的舊單元測試就會變成浪費 — 刪除它們。
- 在深化模組的介面上撰寫新測試。**介面即測試表面**。
- 測試透過介面斷言可觀察的結果，而不是內部狀態。
- 測試應該在內部重構中存活 — 它們描述行為而非實作。如果當實作變更時測試必須隨之變更，說明它超越介面進行了測試。
