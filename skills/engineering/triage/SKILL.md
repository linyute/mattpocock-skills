# 分揀

透過分揀角色的小型狀態機引導專案議題追蹤器上的議題。

如果此儲存庫將外部 Pull Request 視為請求表面（參見 issue-tracker 設定），分揀也會涵蓋它們：**PR 是附加了程式碼的議題** — 相同的角色、相同的狀態、相同的機器，下方標記「對於 PR」之處有一些差異。根據追蹤器設定將單純的 `#42` 解析為議題或 PR。

在分揀期間發布至議題追蹤器的每條留言或議題都**必須**以此免責聲明開頭：

```
> *這是由 AI 在分揀期間產生的。*
```

## 參考文件

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰寫耐用的 Agent 簡報
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知識庫如何運作

## 角色

兩個**類別**角色：

- `bug` — 某事物損壞了
- `enhancement` — 新功能或改進

五個**狀態**角色：

- `needs-triage` — 維護者需要評估
- `needs-info` — 等待回報者提供更多資訊
- `ready-for-agent` — 規範完整，準備好供離線 Agent 使用
- `ready-for-human` — 需要人類實作
- `wontfix` — 將不予採取行動

對於 PR，相同的狀態對照附加的程式碼讀取：`ready-for-agent` 意味著附加了簡報，且 Agent 應該對該差異採取下一步；`ready-for-human` 意味著準備好供人類合併。

每個經過分揀的議題都應該恰好帶有一個類別角色與一個狀態角色。如果狀態角色衝突，請標記它並在進行任何其他操作之前詢問維護者。

這些是規範的角色名稱 — 議題追蹤器中實際使用的標籤字串可能有所不同。應該會提供標籤對應表給你。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

狀態轉移：未標記標籤的議題通常會先轉至 `needs-triage`；從那裡移動至 `needs-info``ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦回報者回覆，`needs-info` 就會返回 `needs-triage`。維護者可以隨時覆寫 — 標記看起來異常的轉移並在繼續前詢問。

## 呼叫

維護者呼叫 `/triage` 並用自然語言描述他們想要的內容。解釋該請求並採取行動。範例：

- 「向我展示任何需要我注意的事物」
- 「我們來看看 #42」（議題或 PR）
- 「將 #42 移動至 ready-for-agent」
- 「有哪些準備好供 Agent 領取了？」

## 展示需要注意的事項

查詢議題追蹤器並呈現三個貯列，最舊的優先：

1. **未標記** — 從未進行分揀。
2. **`needs-triage`** — 評估進行中。
3. **自上次分揀筆記以來回報者有活動的 `needs-info`** — 需要重新評估。

當 PR 處於範疇之內時，在這些貯列中包含外部 PR 並在每行標記 `[PR]` 或 `[issue]`。探索僅會浮現*外部* PR（追蹤器設定會定義誰被視為外部）— 協作者進行中的 PR 不是分揀工作。此過濾器僅用於探索；無論作者是誰，明確具名的 PR 總是會被分揀。

顯示每個項目的計數與單行摘要。讓維護者挑選。

## 分揀特定議題或 PR

1. **收集上下文。** 閱讀完整的議題或 PR（主體、留言、標籤、作者、日期；對於 PR 還有差異）。解析先前的分揀筆記，以便您不會重新詢問已解決的問題。使用專案的領域術語表探索程式碼庫，並遵守該區域的 ADR。對程式碼庫執行兩項檢查：(a) **冗餘** — 依據領域概念（而不僅僅是請求的措辭）搜尋請求行為的現有實作，並回報您查看的位置。如果找到，它就是一個已經實作的 `wontfix`（步驟 5）。(b) **先前的拒絕** — 閱讀 `.out-of-scope/*.md` 並浮現任何與此請求類似的內容。

2. **建議。** 向維護者說明您的類別與狀態建議及其推理，再加上與請求相關的簡短程式碼庫摘要 — 包含它是否已經實作。等待指示。

3. **驗證主張。** 在進行任何盤問之前，檢查該主張是否站得住腳。對於 Bug，從回報者的步驟重現它。對於 PR，確認差異實現了其所聲稱的內容 — 切換檢出它，執行相關測試或命令。回報發生的情況：已確認（帶有程式碼路徑）、失敗或細節不足（強烈 `needs-info` 訊號）。確認無誤的驗證能製作出強大得多的 Agent 簡報。

4. **盤問（如有需要）。** 如果請求需要補充細節，請呼叫 Skill 工具兩次，分別用於「盤問」和「領域建模」——一次提出一輪問題，逐步完善請求、精確化領域術語，並在決策確定時即時更新 `CONTEXT.md`／ADR。

5. **套用結果：**
   - `ready-for-agent` — 發布 Agent 簡報留言（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 結構與 Agent 簡報相同，但註明為何無法委派（判斷呼叫、外部存取、設計決策、手動測試）。
   - `needs-info` — 發布分揀筆記（範本如下）。
   - `wontfix` — 關閉，留言取決於*原因*：
     - **已經實作** — 變更已經存在於程式碼庫中。指向它存在的位置；**切勿**寫入 `.out-of-scope/`（該知識庫是用於*被拒絕的*請求，而非已建構的請求）。
     - **被拒絕（Bug）** — 禮貌說明，然後關閉。
     - **被拒絕（增強功能）** — 寫入 `.out-of-scope/`，從留言連結至它，然後關閉（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 套用該角色。如果有部分進度可選加上留言。

## 快速狀態覆寫

如果維護者說「將 #42 移動至 ready-for-agent」，信任他們並直接套用該角色。確認您即將要做的事（角色變更、留言、關閉），然後採取行動。跳過盤問。如果在沒有盤問會話的情況下移動至 `ready-for-agent`，詢問他們是否想要撰寫 Agent 簡報。

## Needs-info 範本

```markdown
## Triage Notes

**What we've established so far:**

- 要點 1
- 要點 2

**What we still need from you (@reporter):**

- 問題 1
- 問題 2
```

將盤問期間解決的所有內容記錄在「established so far」之下，使工作不會遺失。問題必須具體且具可操作性，而非「請提供更多資訊」。

## 恢復先前的會話

如果議題或 PR 上存在先前的分揀筆記，請閱讀它們，檢查回報者是否已回答任何未解決的問題，並在繼續前呈現場更新後的全貌。不要重新詢問已解決的問題。
