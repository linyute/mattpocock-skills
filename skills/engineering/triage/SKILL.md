# 分流

讓專案 issue tracker 上的 issue 經由分流角色的微型狀態機進行流轉。

若本儲存庫將外部 Pull Request 視為請求介面（請參閱 issue-tracker 設定），分流亦涵蓋它們：**PR 是附帶程式碼的 issue**，使用相同的角色、相同的狀態和相同的狀態機，僅有少數差異在下方標記為「針對 PR」。依據 tracker 設定將單純的 `#42` 解析為 issue 或 PR。

分流期間發布至 issue tracker 的每則留言或 issue **必須**以此免責聲明開頭：

```
> *This was generated by AI during triage.*
```

## 參考文件

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰寫耐久的 Agent 簡報
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知識庫如何運作

## 角色

兩種**類別**角色：

- `bug`：某功能損壞
- `enhancement`：新功能或改進

五種**狀態**角色：

- `needs-triage`：維護者需要評估
- `needs-info`：等待回報者提供更多資訊
- `ready-for-agent`：規格完整，已準備好供離線 Agent 處理
- `ready-for-human`：需要人工實作
- `wontfix`：不會進行處理

對於 PR，相同的狀態對應於所附加的程式碼：`ready-for-agent` 表示已附加簡報，且 Agent 應針對該差異採取下一步；`ready-for-human` 表示已準備好供人工合併。

每個完成分流的 issue 應帶有恰好一個類別角色和一個狀態角色。如果狀態角色發生衝突，請在執行其他任何動作之前先標記並詢問維護者。

這些是標準角色名稱。issue tracker 中實際使用的標籤字串可能會有所不同。該對應關係應該已經提供給你。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

狀態轉移：未標記的 issue 通常首先進入 `needs-triage`；從那裡它會轉移至 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦回報者回覆，`needs-info` 就會返回 `needs-triage`。維護者可以隨時覆寫；標記看起來不尋常的轉移並在繼續之前進行詢問。

## 呼叫

維護者呼叫 `/triage` 並以自然語言描述其所需。解讀請求並採取行動。範例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 顯示需要注意的項目

查詢 issue tracker 並呈現三個貯列，最舊的優先：

1. **未標記**：從未分流。
2. **`needs-triage`**：評估進行中。
3. **在上次分流筆記後有回報者活動的 `needs-info`**：需要重新評估。

當 PR 在範圍內時，在這些貯列中納入外部 PR，並為每行標記 `[PR]` 或 `[issue]`。探索時僅顯示*外部* PR（tracker 設定定義了誰算作外部），因此協作者進行中的 PR 不屬於分流工作。此篩選僅適用於探索；明確指定的 PR 無論作者為何均會進行分流。

顯示計數以及每個項目的單行摘要。讓維護者挑選。

## 分流特定 issue 或 PR

1. **收集情境。** 閱讀完整的 issue 或 PR（內文、留言、標籤、作者、日期；對於 PR，也包含差異）。解析任何先前的分流筆記，這樣你就不會重複詢問已解決的問題。使用專案的領域詞彙表探索程式碼庫，並遵守該領域中的 ADR。針對程式碼庫執行兩項檢查：(a) **備援（redundancy）**：依領域概念（而非僅依請求的措辭）搜尋請求行為的現有實作，並報告你查看的位置。如果找到，這是一個已實作的 `wontfix`（步驟 5）。(b) **先前拒絕**：讀取 `.out-of-scope/*.md` 並提出與此請求類似的任何項目。

2. **建議。** 告訴維護者你的類別與狀態建議及推論，加上與請求相關的簡短程式碼庫摘要（包含是否已實作）。等待指示。

3. **驗證主張。** 在進行任何盤問之前，請檢查該主張是否站得住腳。對於錯誤，請根據回報者的步驟重現它。對於 PR，確認差異是否達到其聲稱的目的：檢出該差異，執行相關測試或指令。回報所發生的情況：已確認（附帶程式碼路徑）、失敗，或細節不足（強烈的 `needs-info` 信號）。經確認的驗證能產生更強大的 Agent 簡報。

4. **盤問（若需要）。** 如果請求需要充實，請呼叫 Skill 工具兩次，分別針對 "grilling" 和 "domain-modeling"，並一次一輪問題將其盤問成形，隨著決策確立同時釐清領域術語並就地更新 `GLOSSARY.md`/ADR。

5. **套用結果：**
   - `ready-for-agent`：發布 Agent 簡報留言（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：結構與 Agent 簡報相同，但註明為什麼不能委派（價值判斷、外部存取、設計決策、手動測試）。
   - `needs-info`：發布分流筆記（下方範本）。
   - 對於 `wontfix`，關閉 issue，留言取決於*原因*：
     - **已實作**：該變更已存在於程式碼庫中。指出其所在位置；**不要**寫入 `.out-of-scope/`（該知識庫是針對*被拒絕*的請求，而非已建構的請求）。
     - **被拒絕 (bug)**：給予禮貌的解釋，然後關閉。
     - **被拒絕 (enhancement)**：寫入 `.out-of-scope/`，在留言中連結至該檔案，然後關閉（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：套用該角色。若有部分進展，可選擇性留言。

## 快速狀態覆寫

如果維護者說「將 #42 移至 ready-for-agent」，請信任他們並直接套用該角色。確認你即將執行的動作（角色變更、留言、關閉），然後執行。跳過盤問。如果在沒有盤問工作階段的情況下移至 `ready-for-agent`，請詢問他們是否要撰寫 Agent 簡報。

## Needs-info 範本

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

將盤問期間解決的所有內容記錄在「established so far」下，以免工作成果遺失。問題必須具體且具可操作性，而非「請提供更多資訊」。

## 恢復先前的工作階段

如果 issue 或 PR 上存在先前的分流筆記，請閱讀它們，檢查回報者是否已回答任何待決問題，並在繼續之前呈現更新的概況。不要重新詢問已解決的問題。
