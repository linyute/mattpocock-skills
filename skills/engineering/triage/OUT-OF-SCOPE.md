# 範圍之外知識庫

儲存庫中的 `.out-of-scope/` 目錄儲存被拒絕功能請求的持久記錄。它具備兩個目的：

1. **組織記憶**：功能被拒絕的原因，使該推論不會在 issue 關閉時遺失
2. **重複資料刪除**：當傳入符合先前拒絕的新 issue 時，該技能可以顯示先前的決策，而無需重新爭辯

## 目錄結構

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每個**概念**一個檔案，而非每個 issue 一個。請求相同事物的多個 issue 會分組在一個檔案下。

## 檔案格式

此檔案應以輕鬆、易讀的風格撰寫，更像是一篇簡短的設計文件，而非資料庫條目。使用段落、程式碼範例和範例，使推論清晰並對初次接觸的人有所助益。

```markdown
# Dark Mode

此專案不支援深色模式或面向使用者的佈景主題。

## 為什麼這超出範圍

渲染管線假定在 `ThemeConfig` 中定義了單一調色盤。
支援多個佈景主題將需要：

- 包裝整個元件樹的佈景主題情境提供者 (Context Provider)
- 每個元件具備佈景主題感知能力的樣式解析
- 使用者佈景主題偏好設定的持久層

這是一項重大的架構變更，與專案對內容創作的關注點不符。
佈景主題設定是嵌入或重新散布輸出的
下游取用者應關注的事項。

```ts
// 目前的 ThemeConfig 介面並非針對執行階段切換所設計：
interface ThemeConfig {
  colors: ColorPalette; // 單一調色盤，在建置時期解析
  fonts: FontStack;
}
```

## 先前請求

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 為檔案命名

為概念使用簡短、具描述性的 kebab-case 名稱：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名稱應具備足夠的辨識度，讓瀏覽目錄的人無須開啟檔案就能了解拒絕了什麼。

### 撰寫原因

原因應具實質性：不是「我們不想要這個」，而是為什麼。良好的原因參照：

- 專案範圍或哲學（「此專案專注於 X；佈景主題是下游關注點」）
- 技術限制（「支援此功能需要 Y，這與我們的 Z 架構衝突」）
- 策略決策（「我們選擇使用 A 而非 B，因為……」）

原因應具備耐久性。避免參照暫時性情況（「我們現在太忙了」）；那些不是真正的拒絕，而是延期。

## 何時檢查 `.out-of-scope/`

在分流期間（步驟 1：收集情境），讀取 `.out-of-scope/` 中的所有檔案。評估新 issue 時：

- 檢查該請求是否符合現有的超出範圍概念
- 比對是依概念相似性進行，而非關鍵字：「night theme」符合 `dark-mode.md`
- 如果有相符項目，將其呈現給維護者：「這與 `.out-of-scope/dark-mode.md` 類似。我們之前拒絕過此項目，原因為 [reason]。你現在的想法是否仍然相同？」

維護者可以：

- **確認**：新 issue 被新增至現有檔案的「Prior requests」清單，然後關閉
- **重新考慮**：刪除或更新該 out-of-scope 檔案，且該 issue 按照正常分流進行
- **不同意**：這些 issue 相關但不同，按照正常分流進行

## 何時寫入 `.out-of-scope/`

僅在**增強功能**（而非錯誤）被*拒絕*為 `wontfix` 時。這完全適用於增強功能 PR，正如適用於 issue 一樣：被拒絕的 PR 記錄於此，因此相同的請求不會作為全新程式碼再次出現。

當某項目因為**已經實作**而被關閉為 `wontfix` 時，請**勿**寫入此處。那是已建構的功能，而非被拒絕的功能；記錄它會以錯誤的拒絕污染重複資料刪除檢查。取而代之的是，關閉留言應指出該功能已經存在的位置。

流程：

1. 維護者決定某功能請求超出範圍
2. 檢查是否已存在相符的 `.out-of-scope/` 檔案
3. 若是：將新 issue 附加至「Prior requests」清單
4. 若否：建立包含概念名稱、決策、原因和第一個先前請求的新檔案
5. 在 issue 上發布留言說明該決策並提及 `.out-of-scope/` 檔案
6. 使用 `wontfix` 標籤關閉 issue

## 更新或移除超出範圍檔案

如果維護者對先前拒絕的概念改變了想法：

- 刪除該 `.out-of-scope/` 檔案
- 該技能不需要重新開啟舊 issue；它們是歷史記錄
- 觸發重新考慮的新 issue 按照正常分流進行
