# 撰寫文件頁面

`engineering/` 與 `productivity/` 中的每項技能都在 `docs/<bucket>/<skill-name>.md` 有一個面向人員的**文件頁面**。文件目錄樹鏡射了 `skills/` 底下的這兩個分桶資料夾。它發布在 `https://aihero.dev/skills-<skill-name>`；無論哪個分桶，URL 始終為 `skills-<skill-name>`，因此文件路徑僅用於儲存庫組織。該頁面不是技能本身，也不是 `SKILL.md` 的副本。僅這兩個分桶被推廣；其餘的（`misc/`、`in-progress/`、`deprecated/`）不發布文件頁面。

這些技能大多數是**使用者呼叫**：代理永遠不會替您觸發它們，因此*您*就是必須記住它們存在以及何時取用它們的索引。這種記憶是一種**認知負擔**。文件頁面的工作就是減輕這種負擔：讓一位讀者快速掌握一項技能，使其能記在腦海中、知道何時取用，並了解它在系統中的位置。這些頁面共同構成一個分散式路由器；每一頁都是一個節點。

每當新增、重新命名已推廣的技能或變更其行為時請採取行動：建立或重新同步其文件頁面。重新命名也會移動檔案（`docs/<bucket>/<old>.md` → `docs/<bucket>/<new>.md`），因為發布的 URL 與名稱連動；在 `engineering/` 與 `productivity/` 之間移動的技能會將其文件檔案移至對應的資料夾。`misc/`、`in-progress/` 與 `deprecated/` 中的技能沒有頁面，因為這些分桶都未推廣。從其中一個分桶*移出*至 `engineering/` 或 `productivity/` 的技能會獲得一個頁面；反向移動的技能則會失去該頁面。被完全移除的已推廣技能會將其頁面保留為**封存**頁面：保留內文原樣，並以區塊引言通知開頭（`> **封存。** ...`），說明移除它的版本及任何替代項目，以確保發布的 URL 仍可解析。

因為這些頁面發布在 `aihero.dev` 上，**每個連結都是絕對連結**：絕不是儲存庫相對路徑。指向另一項技能的連結指向 `https://aihero.dev/skills-<name>`；指向儲存庫內部的連結指向其完整的 `https://github.com/mattpocock/skills/...` URL。在儲存庫中有效的相對連結一旦發布就會損壞。

沒有 H1 標題。發布的頁面從 slug 取得標題。

## 頁面結構

填寫以下範本，保持其順序。**固定框架**（`## 它的作用`、`## 何時取用它`、`## 它在系統中的位置`）會出現在每個頁面上。`## 先決條件` 與自由形式的實質內容章節僅包含該特定技能需要的內容；其餘部分請刪除。

四個章節使頁面值得一讀：`它的作用`、`何時取用它`、`常見問題`、`運作良好的徵兆`。前兩個章節幫助讀者建立方向；後兩個章節則是頁面不再只是總結技能，而是開始回應讀者自身情境的地方。後兩個章節各自有下方說明的標準，若兩者皆未達標，應將頁面視為未完成，而非完成且簡短。

**頁面不包含安裝指令。** ai-hero 頁面範本會在內文上方自行呈現安裝小工具（複製按鈕、單一技能指令、完整集合指令以及更新行）。若頁面同時寫出這些內容，會向讀者顯示相同的指令兩次，且兩份副本會脫節：每個頁面上手寫的一對指令與旁邊的小工具相比變得過時。安裝措辭是網站的屬性，而非頁面的屬性。若需要修改，請在 ai-hero 中修改；標準措辭位於[安裝區塊](./install-block.md)。

## 它的作用

一到兩個淺顯易懂的段落。以技能的單句核心任務開頭，然後陳述**定義性限制**：使該技能與明顯預設行為有所不同的單一事實（對於 `to-spec`：它不會再次訪談使用者，而是綜合已知資訊）。將其寫成普通的陳述句，絕不要使用如「定義性限制：」或「關鍵之處：」等標籤化的旁白；該公式讀起來像是湊字數。這一行是頁面上最有價值的內容；絕不可省略。

## 何時取用它

您如何以及何時取用該技能，透過實際上始終存在的兩個節奏來陳述：

- **呼叫模式。** 陳述是由您輸入還是由代理觸發。使用者呼叫的技能：「您可以透過輸入 `/<name>` 來呼叫此技能，代理不會自行取用它。」模型呼叫的技能：「輸入 `/<name>`，或者當任務適合時代理會自動取用它。」
- **觸發邊界。** 索引條目：「當…時取用此技能」。當該技能容易與相鄰技能混淆時，加上另一半說明：「若要改為<X>，請使用 [<sibling>](https://aihero.dev/skills-<sibling>)。」

## 先決條件

選用：僅在該技能需要就定位的事物才能發揮功能時包含；否則請完全省略該標題。涵蓋範圍：它**寫入的工作區**（像 `grill-with-docs` 這種有狀態的技能會寫入 `GLOSSARY.md` 與 ADR；`teach` 會建構一整個目錄，因此請說明它寫入了什麼以及寫入何處）、**事先設定**（`triage`/`to-spec`/`to-tickets` 需要 `setup-matt-pocock-skills` 已設定好問題追蹤器），或**儲存庫專屬工具**。在任何地方都能執行的無狀態技能沒有先決條件，因此請去掉該章節。

## <自由形式的中間章節>

一到三個簡短章節，採用該技能*自身的詞彙*，使其易於理解。選擇適合該技能的任何標題：它執行的迴圈、它產生的成品、它產生的分支、它消滅的單一反模式。沒有規定的標題；這些技能太過多樣化，無法統一。

唯一不可協商的原則：**突顯該技能的引導詞 / 定義性理念**（緊湊的（`tight`）回饋迴圈、深層模組（`deep module`）、拋棄式程式碼回答問題、紅燈-綠燈）。這能帶來雙重回報：讀者了解技能*是什麼*，並學會他們日後用來*取用*該技能時心中所想的關鍵詞。

## 常見問題

讀者真正會針對此技能提出的問題，每個問題以粗體標示，答案在下方各行呈現。不使用子標題。

觀察到的真實問題永遠優於捏造的問題，因此在撰寫之前請先搜尋：

- **Wiki。** 若此機器上存在 `~/repos/matt/personal-wiki`，它是現有最豐富的來源。其 `wiki/audience/` 區域是圍繞著受眾想要什麼、討論什麼以及**對什麼感到困惑**來組織的：先閱讀 `wiki/index.md` 取得頁面登錄表，然後閱讀與該技能相關的頁面。每個頁面都帶有連回原始 X、Discord、GitHub 與電子郵件討論串的 `sources:` 連結；wiki 是二手資料來源，因此請引用提問者自己的問題，而不是 wiki 對它的摘要。若該目錄不存在，請略過此點。
- **此儲存庫的 Issues。** `gh issue list --repo mattpocock/skills --search "<skill-name>" --state all`。被提出過兩次的問題就是頁面必須解答的問題。
- **`CHANGELOG.md`。** 任何被重新命名、移動或行為有所變更的項目都會產生「它移去哪裡了？」的問題，頁面必須予以回答。

若搜尋結果有限，該章節也可以包含讀者顯然會問的問題，但**問題數量必須如實反映證據**。討論充分的技能可以有六個；冷門的技能可以有一到兩個，或者完全沒有。為了讓內容稀少的技能與豐富的技能篇幅相符而注水，只會讓該章節充斥著沒人會問的問題，而捏造的問題無法教會讀者任何事。

依照每個問題出現的頻率排序，最犀利的排在前面，若屬實請直言不諱：過長的盤問（grilling）會話通常意味著範疇太大；被要求撰寫自己技能的模型產生的內容會很冗長。若沒有值得回答的問題，請省略該標題。

## 運作良好的徵兆

列出讀者在該技能正常發揮作用時會看到的幾個要點。每一項的標準是讀者無需打開 `SKILL.md` 就能檢查：在他們自己的工作中或眼前的追蹤日誌中的訊號。「文件越改越好、篇幅越變越短」符合標準；「函式庫章節與 `template.sh` 位元組完全一致」則是掛著此章節名稱對技能內部進行的合規性檢查。只要跡象清晰明確就包含此章節；若依然模糊不清則省略該標題。

## 它在系統中的位置

永遠存在。用一到兩句話說明技能在系統中的位置：

- **角色。** 指出其定位：**鏈條步驟**（`grill-with-docs → to-spec → to-tickets → implement → code-review`）、**單次執行設定**（`setup-matt-pocock-skills`）、**週期性維護**（`improve-codebase-architecture`，「每隔幾天」），或**隨時取用的獨立項**（`diagnosing-bugs`、`prototype`、`handoff`）。獨立項的位置圖是一句真實的陳述，這遠比省略該章節好得多。
- **鄰近項目。** 關鍵的一到兩個相鄰技能，各自附上理由子句，並使用絕對連結。
- **全景圖。** 指向涵蓋整個集合的路由器 [ask-matt](https://aihero.dev/skills-ask-matt)，使此頁面保持為一個節點，永遠不必重新繪製整張圖。

## 慣例

- 解釋**原因**（why），而非流程。頁面定位並確立技能的情境；它絕不重現 `SKILL.md` 的步驟或範本輸出：選擇工具的人員不需要操作手冊。
- **絕不提及作者姓名。** 該頁面是一份技術文件，不是記錄誰說了什麼的紀錄。「Matt 說」、「Matt 自己的回答」、「他的立場是」、引用的回覆：所有這些都要刪除。問題搜尋中的發現值得保留；其出處歸屬則不應保留。將實質內容表述為對技能的客觀陳述（「修復方式是一條直接指示：…」、「劃分歸結為會話次數」）並去掉人名框架。讀者是在決定是否使用工具；無論哪種方式意見都具有相同的份量，且一旦立場改變，標註出處的言論就會過時。引用*使用者*則沒問題：「一位使用者回報…」是該技能在實際應用中的證據，並保持匿名。
- 使用技能的**引導詞**（_seam_、_deep module_、_tracer bullet_），使頁面與技能使用統一的語言。
- **若存在 [AI Coding Dictionary](https://www.aihero.dev/ai-coding-dictionary) 的術語，請使用該術語，並在頁面首次使用時建立連結。** 該字典是 AI 寫程式的內部詞彙表：_context window_、_subagent_、_harness_、_primary source_、_agent mode_。優先使用它的詞彙，而非您自行發明的同義詞。將每個術語的首次出現連結至 `https://www.aihero.dev/ai-coding-dictionary/<slug>`（slug 是將術語轉為小寫並將非英數字元替換為連字號：_context window_ → `context-window`），後續出現則不加連結。僅在單詞具有該字典定義的含義時才建立連結：領域 *model*、背景 *context* 或身分驗證 *token* 是剛好相同但涵義不同的詞。絕不要在標題、程式碼區塊或現有連結內部建立連結，也絕不要為代表此儲存庫中的技能名稱而非該概念的單詞建立連結。如需完整的術語清單，若此機器上存在 `~/repos/ai/ai-coding-dictionary/dictionary/` 請閱讀該目錄（每個術語一個檔案，檔名*即是*該術語），否則請閱讀 [mattpocock/dictionary-of-ai-coding](https://github.com/mattpocock/dictionary-of-ai-coding)，無論哪種方式它都是單一真相來源。
- **分支請使用表格或清單，絕不要放在段落中。** 當頁面提供選擇時（該技能可產生的兩種成品、觸發它的四種情境、邊界處的五個選項），讀者是在掃描符合其情境的單一資料行。段落會迫使他們讀完整個內容才能找到答案。簡短的 Markdown 表格（左欄為條件，右欄為該採取的行動）或項目符號清單能讓人一目了然。這適用於分支出現的任何地方，最常出現在 `## 何時取用它` 與自由形式的中間章節。
- 保持頁面本身低負擔。這是有關低認知負擔技能的文件；多餘的修飾（多餘的標題、重複陳述的連結）正是它所反對的事物。

## 完成標準

- 頁面存在於 `docs/<bucket>/<name>.md`，且重新命名或分桶移動後沒有殘留過時頁面。
- 頁面不帶有來源連結，也不自行撰寫安裝指令。
- `## 它的作用` 陳述定義性限制，作為純文字敘述而非標籤化旁白。
- 頁面不提及任何作者姓名也不引用任何作者：每個主張皆能獨立成立。
- `## 何時取用它` 陳述呼叫模式與觸發邊界。
- `## 它在系統中的位置` 指出其角色並連結至 `ask-matt`。
- 若存在先決條件（工作區、事先設定、工具），則陳述先決條件；若不存在則省略該章節。
- 中間章節突顯引導詞。
- 頁面使用的每個 AI Coding Dictionary 術語皆按照字典的方式拼寫，且其首次使用（且僅限首次使用）連結至字典條目。
- 每個多向分支皆為表格或清單，而非讀者必須完整閱讀的段落。
- 執行了尋找真實問題的步驟（wiki、issues、changelog），且 `## 常見問題` 的規模符合搜尋所得，而不是為了與更豐富技能的頁面相符而注水。
- 每個 `## 運作良好的徵兆` 項目符號皆可在不開啟 `SKILL.md` 的情況下進行檢查。
- 章節按照範本的順序呈現。
- 每個連結都是絕對連結，且每個連結都能解析。
