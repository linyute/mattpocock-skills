# 撰寫文件頁面

`engineering/` 和 `productivity/` 中的每一個技能在 `docs/<bucket>/<skill-name>.md` 都具有一個面向人類的**文件頁面** — 文件樹會鏡像呈現 `skills/` 下的那兩個 Bucket 資料夾。它發布於 `https://aihero.dev/skills-<skill-name>`；無論 Bucket 為何，URL 始終為 `skills-<skill-name>`，因此文件路徑僅用於儲存庫組織。頁面本身並非技能，也不是 `SKILL.md` 的副本。只有這兩個 Bucket 會被推廣；其餘的（`misc/`、`in-progress/`、`deprecated/`）都不會發布文件頁面。

這些技能大多是**使用者呼叫**的：Agent 絕不會為您觸發它們，因此*您*就是必須記住它們存在以及何時使用它們的索引。這份記憶是**認知負擔**。文件頁面的工作就是減輕這份負擔 — 為讀者指引單一技能的方向，使他們能在腦海中掌握它、知道何時使用它，並瞭解它在系統中的位置。這些頁面共同構成了一個分散式路由器；每一頁都是一個節點。

當推廣的技能被新增、重命名或其行為發生變更時進行操作：建立或重新同步其文件頁面。重命名也會移動檔案（`docs/<bucket>/<old>.md` → `docs/<bucket>/<new>.md`），因為發布的 URL 會追蹤名稱；在 `engineering/` 與 `productivity/` 之間移動的技能會將其文件檔案移動至匹配的資料夾中。在 `misc/`、`in-progress/` 和 `deprecated/` 中的技能不會取得頁面 — 這些 Bucket 都未被推廣。移出其中之一並進入 `engineering/` 或 `productivity/` 的技能會獲得一個頁面；反向移動的技能則會失去頁面。

因為這些頁面發布在 `aihero.dev` 上，**每個連結都是絕對連結** — 絕不使用相對儲存庫的路徑。指向另一個技能的連結指向 `https://aihero.dev/skills-<name>`；指向儲存庫內部的連結指向其完整的 `https://github.com/mattpocock/skills/...` URL。在儲存庫中可用的相對連結一旦發布就會失效。

沒有 H1 標題 — 發布的頁面會從 Slug 取用其標題。

## 頁面結構

填寫下方範本，並保持其順序。**固定框架**（`## What it does`、`## When to reach for it`、`## Where it fits`）會出現在每一個頁面上。`## Prerequisites` 以及自由形式的內容章節僅包含該特定技能需要的內容；其餘部分請刪除。

四個章節使頁面值得閱讀：`What it does`、`When to reach for it`、`Common questions`、`It's working if`。前兩個為讀者指引方向；後兩個則是頁面停止摘要技能並開始回答讀者自身處境的地方。後兩個中的每一個都有一個需要符合的標準（如下所述）— 但請將這兩者均未符合的頁面視為未完成，而非已完成且簡短。

**頁面不包含任何安裝命令。** ai-hero 頁面範本會在內文上方自行呈現安裝元件 — 包含複製按鈕、單一技能命令、全套命令以及更新行。若頁面也寫出這些內容，將會向讀者顯示兩次相同的命令，且這兩個副本會產生偏差：每個頁面上手寫的一對命令會相對於其旁邊的元件過時。安裝說明文字是網站的屬性，而非頁面的屬性。若需要修改，請在 ai-hero 中修改；規範字句部位於 [安裝區塊](./install-block.md)。

## 它的功能

一或兩個平實語言的段落。先說明該技能的一句話工作，然後陳述**定義約束條件** — 使該技能表現得不同於明顯預設行為的單一事實（對於 `to-spec`：它不會再次採訪使用者，而是綜合已知資訊）。將其寫成平實的敘述句 — 絕不要使用帶有標籤的旁白，如 "The defining constraint:" 或 "The key thing:"；這種公式化的寫法會顯得贅述。這一行是頁面上最有價值的一行；切勿省略。

## 何時使用它

您如何以及何時使用該技能 — 兩個節奏，兩者實際上總是存在：

- **呼叫模式。** 說明是您輸入它還是 Agent 觸發它。使用者呼叫的技能："You invoke this by typing `/<name>` — the agent won't reach for it on its own." 模型呼叫的技能："Type `/<name>`, or the agent reaches for it automatically when a task fits."
- **觸發邊界。** 索引條目："reach for this when …"。當該技能容易與兄弟技能混淆時，請加上另一半 — "for <X> instead, use [<sibling>](https://aihero.dev/skills-<sibling>)."

## 前置條件

選填 — 僅在技能需要適當的配置才能正常運作時包含；否則請完全省略此標題。涵蓋：它**寫入的工作區**（像 `grill-with-docs` 這樣的具狀態技能會寫入 `CONTEXT.md` 和 ADR；`teach` 會建構整個目錄 — 請說明它寫入什麼以及寫入何處）、**先前設定**（`triage`/`to-spec`/`to-tickets` 需要 `setup-matt-pocock-skills` 已設定好議題追蹤器），或**儲存庫專屬工具**。在任何地方都能執行的無狀態技能沒有前置條件 — 請刪除此章節。

## <自由形式中間段落>

一至三個短章節，使用技能*自身的詞彙*，使其易於理解 — 選擇任何適合該技能的標題：它執行的迴圈、它產生的產物、它產生的分支，或是它消除的一種反模式。沒有規定的標題；技能差異極大，無法統一。

唯一不可妥協的原則：**突出技能的核心關鍵字 / 定義概念** — `tight` 反饋迴圈、`deep module`、拋棄式程式碼回答問題、紅燈-綠燈。這會帶來雙重回報：讀者學會技能*是什麼*，並學會他們日後思考並*使用*它時所採用的詞彙。

## 常見問題

讀者針對此技能真正提出的問題，每一個都以粗體表示，答案位於下方各行中 — 不使用副標題。

觀察到的問題總是勝過編造的問題，因此在撰寫前請去尋找它們：

- **Wiki。** 如果這台機器上存在 `~/repos/matt/personal-wiki`，它是最豐富的來源。其 `wiki/audience/` 區域圍繞著受眾想要什麼、討論什麼以及**對什麼感到困惑**來組織 — 請先閱讀 `wiki/index.md` 以獲取頁面登錄表，然後閱讀與此技能相關的頁面。每個頁面都帶有連回原始 X、Discord、GitHub 和 Email 討論串的 `sources:` 連結；Wiki 是次要來源，因此請引用提問者自己的問題，而非 Wiki 對其進行的摘要。在該目錄不存在的情況下跳過此項。
- **此儲存庫的 Issue。** `gh issue list --repo mattpocock/skills --search "<skill-name>" --state all`。提交過兩次的問題是該頁面有責任解答的問題。
- **`CHANGELOG.md`。** 任何重命名、移動或行為變更的內容都會產生「它去哪裡了？」的問題，頁面必須予以解答。

在搜尋結果貧乏的情況下，該章節也可以包含讀者顯然會問的問題 — 但**數量必須誠實反映證據**。一個經過充分討論的技能可以獲得六個問題；一個冷門的技能獲得一兩個問題，或者完全沒有。為了與豐富的技能相匹配而對貧乏的技能進行填補，會使該章節充斥著無人提出的問題，而編造的問題無法傳授讀者任何東西。

按照每個問題出現的頻率進行排序，最犀利的排在最前面，並在屬實的情況下說出不加修飾的事實 — 非常長的審查工作階段通常意味著範圍太大；被要求撰寫自身技能的模型會產出冗長的東西。如果沒有值得解答的內容，請省略此標題。

## 適合適用情境 / 系統位置

## 慣例

- 解釋**原因**，而非過程。頁面指引並定位該技能；它絕不重現 `SKILL.md` 的步驟或範本輸出 — 人類在選擇工具時不需要操作手冊。
- **絕不提及作者姓名。** 頁面是技術文件，而非誰說了什麼的記錄。"Matt says"、"Matt's own answer"、"his position is"、引用的回覆 — 所有這些都要去除。從問題搜尋中獲得的發現值得保留；但其歸因則不需要。將內容陳述為對技能的平實主張（"the fix is a direct instruction: …"、"the split comes down to session count"）並去框架化。讀者是在決定是否使用工具；無論如何，觀點都具有相同的份量，且附帶歸因的觀點會在立場轉移時過時。引用*使用者*的話依然是可以的 — "one user reported …" 是關於野外技能的證據，並保持匿名。
- 使用技能的**核心關鍵字**（_seam_、_deep module_、_tracer bullet_），使頁面和技能使用同一種語言。
- **在使用 AI Coding Dictionary 術語的地方使用該術語，並在頁面上的首次使用處附上連結。** 字典是 AI 程式編寫的官方詞彙表 — _context window_、_subagent_、_harness_、_primary source_、_agent mode_。優先使用其詞彙而非您發明的同義詞。將每個術語的第一次出現連結至 `https://www.aihero.dev/ai-coding-dictionary/<slug>`（Slug 是小寫並以連字號替換非字母數字字元的術語：_context window_ → `context-window`），並使後續所有出現保持不連結。僅在詞彙符合字典語義的地方進行連結 — 領域 *model*、背景 *context* 或驗證 *token* 是恰好匹配的不同詞彙。切勿在標題、程式碼區段或現有連結內部進行連結，且切勿連結代表此儲存庫中技能名稱而非概念的詞彙。有關完整的術語清單，如果這台機器上存在 `~/repos/ai/ai-coding-dictionary/dictionary/`，請閱讀該目錄 — 每個術語一個檔案，檔名*即為*術語 — 否則參閱 [mattpocock/dictionary-of-ai-coding](https://github.com/mattpocock/dictionary-of-ai-coding)，無論如何它都是單一事實來源。
- **分支必須放在表格或列表中，絕不能放在段落中。** 當頁面呈現選擇時 — 該技能可以產生的兩種產物、觸發它的四種情況、邊界處的五個選項 — 讀者正在掃描與其情況匹配的那一行。段落迫使他們閱讀所有內容才能找出答案。簡短的 Markdown 表格（左欄為條件，右欄為做法）或列表項目可以一眼看出。這適用於分支出現的任何地方，最常出現在 `## 何時使用它 (When to reach for it)` 和自由形式的中間部分。
- 保持頁面本身的低負擔。它是*關於*低認知負擔技能的文件；無用擺設（多餘的標題、重複陳述的連結）正是它所反對的事物。

## 完成標準

- 頁面存在於 `docs/<bucket>/<name>.md`，且重命名或 Bucket 移動後沒有過時的頁面殘留。
- 頁面不包含任何來源連結，也不自行撰寫安裝命令。
- `## 它的功能 (What it does)` 以平實散文而非帶標籤的旁白陈述定義約束條件。
- 頁面未提及作者姓名，也未引用作者 — 每個主張獨立成立。
- `## 何時使用它 (When to reach for it)` 陳述呼叫模式和觸發邊界。
- `## 適合適用情境 / 系統位置 (Where it fits)` 命名角色並連結至 `ask-matt`。
- 前置條件（工作區、先前設定、工具）在存在時予以陳述，不存在時則省略該章節。
- 中間部分突出核心關鍵字。
- 頁面使用的每個 AI Coding Dictionary 術語都符合字典的拼寫方式，且其首次使用 — 且僅限首次使用 — 連結至字典條目。
- 每個多路分支都是表格或列表，而非需要讀者完整閱讀的段落。
- 執行了真實問題的搜尋 — Wiki、Issue、Changelog — 且 `## 常見問題 (Common questions)` 的規模符合搜尋結果，未進行填補以匹配更豐富技能的頁面。
- 每個 `## 正常運作的指標 (It's working if)` 列表項目都可以在不安裝/開啟 `SKILL.md` 的情況下進行檢查。
- 章節按照範本的順序出現。
- 每個連結都是絕對連結，且每一個都能解析。
